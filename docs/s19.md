# s19 - Security Hardening

> **Tag:** `s19`
> Goal: close the security gaps left open for convenience in earlier stages. External Secrets replaces plaintext Secrets in Git. Pod Security Standards restrict container privileges. Kyverno policies enforce organizational rules. Egress NetworkPolicies lock down outbound traffic.

Every stage so far has cut security corners: `adminPassword: "admin"` in Grafana values, database passwords in plaintext Secrets committed to Git, containers running as root, no egress restrictions. This stage fixes them systematically.

---

## What this stage covers

| Gap | Where introduced | Fix |
| --- | --- | --- |
| Plaintext Secrets in Git | s2 (Secret YAML), s5 (Postgres password), s12 (Grafana admin) | **External Secrets Operator** (ESO): Secrets are stored in a secret manager and synced to the cluster at runtime |
| Containers running as root | Every Deployment | **Pod Security Standards** (PSS): namespace-level enforcement of `restricted` profile |
| No policy guardrails | All stages | **Kyverno**: admission policies (require labels, deny privileged, require resource limits) |
| Unrestricted egress | s7 added ingress NetworkPolicy, but egress is wide open | **Egress NetworkPolicy**: default-deny egress + explicit allowlist |
| Unscanned images | All stages | **Trivy**: scan images for CVEs before/after deployment |

## External Secrets Operator (ESO)

### The problem

```yaml
# This is committed to Git right now:
apiVersion: v1
kind: Secret
metadata:
  name: users-api
stringData:
  DATABASE_URL: "postgresql://app:postgres123@postgres-rw:5432/usersdb"
```

Anyone with read access to the repo has the database password. `git log` keeps it forever even after deletion. This is the #1 Kubernetes security anti-pattern.

### How ESO fixes it

ESO syncs secrets from an external secret manager into Kubernetes Secrets at runtime. The Git repo contains an `ExternalSecret` CR that references the secret by name — the actual value never touches Git.

```text
┌──────────────┐     ┌─────────────────────────┐     ┌──────────────┐
│  Git repo     │     │  External Secrets        │     │  Secret       │
│               │     │  Operator                │     │  Manager      │
│  ExternalSecret ──▶ │  reads CR, fetches from  │◀──▶ │  (kind: fake  │
│  CR (no values)│     │  secret manager, writes   │     │   or Vault    │
│               │     │  Kubernetes Secret         │     │   or AWS SM)  │
└──────────────┘     └─────────────────────────┘     └──────────────┘
                              │
                              ▼
                     ┌──────────────┐
                     │  Kubernetes   │
                     │  Secret       │
                     │  (real values)│
                     └──────────────┘
```

### SecretStore vs ClusterSecretStore

| CRD | Scope | Use case |
| --- | --- | --- |
| `SecretStore` | Namespaced | Team-scoped: each namespace has its own secret store config |
| `ClusterSecretStore` | Cluster-wide | Platform-scoped: one store, all namespaces reference it |

For kind, we use the **Fake provider** (values are embedded in the SecretStore for testing). In production, this becomes the AWS Secrets Manager provider, Vault provider, or GCP Secret Manager provider.

### ExternalSecret CR

The `ExternalSecret` tells ESO what to fetch and where to put it:

- `spec.secretStoreRef`: which SecretStore to use.
- `spec.target.name`: the Kubernetes Secret name to create.
- `spec.data[]`: list of keys to fetch. Each maps a `remoteRef.key` (key in the secret manager) to a `secretKey` (key in the Kubernetes Secret).

ESO creates the Kubernetes Secret automatically and keeps it in sync. If the value changes in the secret manager, ESO updates the Secret (controlled by `refreshInterval`).

## Pod Security Standards (PSS)

### The three profiles

PSS is a built-in Kubernetes feature (no extra controller). It defines three profiles, enforced at the namespace level:

| Profile | What it allows | Use case |
| --- | --- | --- |
| `privileged` | Everything. No restrictions. | System namespaces (`kube-system`, `istio-system`) |
| `baseline` | Blocks the most dangerous capabilities: `hostNetwork`, `hostPID`, `privileged` containers. Allows `runAsNonRoot: false`. | Namespaces running infrastructure tools that need some elevated access |
| `restricted` | Baseline + requires `runAsNonRoot: true`, drops all capabilities, disallows privilege escalation, requires `seccomp: RuntimeDefault` | Application namespaces (`default`) |

### Enforcement modes

Each namespace label can set three independent modes:

| Mode | Behavior |
| --- | --- |
| `enforce` | Reject Pods that violate the profile |
| `audit` | Allow the Pod but write a warning to the audit log |
| `warn` | Allow the Pod but show a warning to the `kubectl` user |

Start with `warn` + `audit` on `restricted` to find violations without breaking anything. Once all workloads comply, flip to `enforce`.

### Making your containers PSS-restricted compliant

Most violations come from missing `securityContext` fields. Add to every container:

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault
  readOnlyRootFilesystem: true
```

`readOnlyRootFilesystem: true` is not required by PSS but is a best practice. It prevents an attacker from writing to the container filesystem (e.g. dropping a reverse shell). If the app needs to write temp files, mount an `emptyDir` at the write path.

## Kyverno (Policy Engine)

### What Kyverno does

Kyverno is a Kubernetes-native policy engine. It intercepts API requests via admission webhooks and:

- **Validates**: reject requests that violate policies (deny privileged pods, require labels).
- **Mutates**: modify requests to enforce defaults (inject resource limits, add labels).
- **Generates**: create resources in response to events (create a NetworkPolicy when a new namespace is created).

### Kyverno vs OPA Gatekeeper

| | Kyverno | OPA Gatekeeper |
| --- | --- | --- |
| Policy language | Kubernetes YAML (ClusterPolicy CRD) | Rego (a dedicated policy language) |
| Learning curve | Low for Kubernetes users | Steep (Rego is its own thing) |
| Mutation | Native | Limited (only through assign/modify) |
| Generation | Native (create resources from policies) | Not supported |
| Community | CNCF graduated | CNCF graduated |

We use Kyverno because the policies are YAML — the same language as everything else in this repo.

### Useful starter policies

| Policy | What it does |
| --- | --- |
| **Require labels** | Reject Pods/Deployments missing `app` and `team` labels |
| **Deny privileged containers** | Reject containers with `privileged: true` or `hostNetwork: true` |
| **Require resource limits** | Reject containers without `resources.limits.memory` |
| **Require non-root** | Reject containers without `runAsNonRoot: true` |
| **Restrict image registries** | Only allow images from approved registries (e.g. `ghcr.io`, your private ECR) |

## Egress NetworkPolicy

s7 introduced ingress NetworkPolicy: default-deny inbound, allowlist per service. But egress was left wide open. Any compromised Pod can phone home to any IP on the internet.

### Default-deny egress

```yaml
spec:
  podSelector: {}
  policyTypes:
    - Egress
```

This blocks all outbound traffic for every Pod in the namespace. Nothing can reach anything — not even DNS.

### Allowlist pattern

After default-deny, add explicit egress rules:

| Destination | Why | Rule |
| --- | --- | --- |
| **kube-dns** (CoreDNS) | DNS resolution | Port 53 UDP/TCP to `kube-system` namespace |
| **Postgres** | Database access | Port 5432 to Pods matching `app: postgres` |
| **notify-api** | gRPC calls | Port 50051 to Pods matching `app: notify-api` |
| **Prometheus** | Metrics scraping (reverse: Prometheus reaches in) | Not needed in egress; Prometheus initiates |
| **External APIs** | If the app calls external services | Specific CIDR blocks or use a proxy |

The DNS allowlist is the most commonly forgotten rule. Without it, even allowed Pod-to-Pod traffic fails because names can't resolve.

## Trivy (Image Scanning)

Trivy scans container images for known CVEs. Run it as:

1. **Pre-deploy** (CI pipeline): scan the image before pushing to registry. Block the pipeline on critical CVEs.
2. **In-cluster** (Trivy Operator): scan running images continuously. Report vulnerabilities as `VulnerabilityReport` CRDs.

For kind, run Trivy as a CLI tool:

```bash
trivy image users-api:local-v3
```

For production, the Trivy Operator runs as a controller and produces Kubernetes-native reports that can feed into Kyverno policies (e.g. deny images with critical CVEs).

## Falco (Runtime Threat Detection)

Trivy catches known CVEs before a container runs. Falco catches anomalous behavior while it runs. They are complementary, not alternatives.

Falco watches Linux syscalls via an eBPF probe. When a container makes a syscall that matches a rule — spawning a shell, writing to `/etc/passwd`, opening a socket to an unexpected address, reading `/etc/shadow` — Falco fires an alert. The container is not stopped (Falco is detection, not prevention), but the alert feeds into your incident response pipeline.

### How it works

```text
┌──────────────────────────────────────┐
│  Container                            │
│  (users-api, postgres, kube-proxy)    │
└──────────────────────┬───────────────┘
                       │ syscalls
                       ▼
┌──────────────────────────────────────┐
│  Falco eBPF probe (per node)         │
│  - intercepts syscalls                │
│  - evaluates against rule set         │
│  - fires alert on match               │
└──────────────────────┬───────────────┘
                       │ alert
                       ▼
┌──────────────────────────────────────┐
│  Output                               │
│  stdout → Alloy → Loki (s12)          │
│  or falcosidekick → Slack/PagerDuty   │
└──────────────────────────────────────┘
```

### Install

Falco ships with two kernel drivers. For kind (which runs in Docker, which runs in WSL2), the **modern eBPF** driver works without loading a kernel module:

```bash
helm repo add falcosecurity https://falcosecurity.github.io/charts
helm repo update
helm install falco falcosecurity/falco \
  -n falco --create-namespace \
  -f helm/values/falco.values.yaml
```

```yaml
# helm/values/falco.values.yaml
driver:
  kind: modern_ebpf

falco:
  grpc:
    enabled: true
  grpc_output:
    enabled: true

falcosidekick:
  enabled: true
  config:
    slack:
      webhookurl: ""   # add your Slack webhook for real alerts
```

### Default rules

Falco ships with hundreds of rules. The most relevant for this project:

| Rule | What triggers it |
| --- | --- |
| `Terminal shell in container` | `exec` into a running container (`kubectl exec -it ... bash`) |
| `Write below etc` | Any write to `/etc/` inside a container |
| `Read sensitive file untrusted` | Reading `/etc/shadow`, `/etc/sudoers`, SSH keys |
| `Outbound Connection to C2 Servers` | Connection to known malicious IPs |
| `Unexpected outbound connection destination` | Outbound to IPs not in an allowlist (requires config) |
| `Container run as root user` | Any container started as UID 0 |

### Custom rules

Add rules in `falco_rules.local.yaml`. Example: alert if users-api opens an unexpected outbound connection:

```yaml
- rule: users-api unexpected outbound
  desc: users-api opened a connection to an unexpected destination
  condition: >
    outbound and container.name = "users-api"
    and not (fd.sip.name in (postgres_addrs) or fd.sip.name in (notify_api_addrs))
  output: >
    Unexpected outbound from users-api
    (connection=%fd.name container=%container.name pod=%k8s.pod.name)
  priority: WARNING
```

### Trivy vs Falco

| | Trivy | Falco |
| --- | --- | --- |
| **When** | Before deployment (static scan) | At runtime (dynamic detection) |
| **What** | Known CVEs in image layers | Anomalous syscall behavior |
| **Action** | Block CI pipeline | Fire alert (detection, not prevention) |
| **Misses** | Zero-days, logic bugs, misconfiguration | Known-good processes doing expected things |

Run both: Trivy stops known-bad images from deploying; Falco catches unexpected behavior from images that passed Trivy.

```bash

kubectl get externalsecret

# Test Kyverno: try to create a Pod without labels

# Error: validation error: require-labels: ...

# Test PSS: try to create a privileged Pod

# But internal traffic still works
```

## Try to break it

### 1. ExternalSecret references a missing key

```yaml
spec:
  data:
    - secretKey: DATABASE_URL
      remoteRef:
        key: wrong-key-name
```

The ExternalSecret status shows `SecretSyncedError`. The Kubernetes Secret is not created (or stale if it existed before). The app fails to start if it `envFrom`s the missing Secret.

```bash
kubectl describe externalsecret users-api
# Status: SecretSyncedError
# Message: key "wrong-key-name" not found
```

### 2. PSS blocks a legitimate workload

Apply `enforce: restricted` and try to deploy a container that writes to the filesystem:

```bash
kubectl apply -f k8s/users-api/deployment.yaml
# Warning: would violate PodSecurity "restricted": ...
```

The Deployment is created but Pods are rejected. `kubectl get events` shows the violation. Fix: add `securityContext` fields and mount `emptyDir` for writable paths.

### 3. Egress default-deny breaks DNS

Apply the default-deny egress policy without the DNS allowlist:

```bash
kubectl exec -it deploy/users-api -- nslookup postgres-rw
# ;; connection timed out; no servers could be reached
```

Every name resolution fails. The app can't connect to Postgres (can't resolve `postgres-rw`). Fix: add the DNS egress rule allowing port 53 to `kube-system`.
