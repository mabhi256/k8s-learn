# s19a - Secrets Management (External Secrets Operator)

> **Tag:** `s19a`
> Goal: replace plaintext Secrets committed to Git with ExternalSecret CRs. The External Secrets Operator syncs values from a secret manager at runtime, so actual credentials never touch version control.

Every stage since s2 has stored secrets as plaintext YAML in the repo: database passwords, session secrets, Grafana admin credentials. `git log` preserves them forever, even after the file is deleted. This sub-stage introduces the External Secrets Operator (ESO) to fix that.

---

## The problem

```yaml
# This is committed to Git right now:
apiVersion: v1
kind: Secret
metadata:
  name: users-api
stringData:
  DATABASE_URL: "postgresql://app:postgres123@postgres-rw:5432/usersdb"
```

Anyone with read access to the repo has the database password. `git log` keeps it forever even after deletion.

## How ESO fixes it

ESO syncs secrets from an external secret manager into Kubernetes Secrets at runtime. The Git repo contains an `ExternalSecret` CR that references the secret by name: the actual value never touches Git.

```text
┌────────────────┐     ┌────────────────────────┐     ┌─────────────┐
│ Git repo       │     │ External Secrets       │     │ Secret      │
│                │     │ Operator               │     │ Manager     │
│ ExternalSecret │ ──▶ │ reads CR, fetches from │◀──▶ │ (kind: fake │
│ CR (no values) │     │ secret manager, writes │     │  or Vault   │
│                │     │ Kubernetes Secret      │     │  or AWS SM) │
└────────────────┘     └────────────────────────┘     └─────────────┘
                              │
                              ▼
                     ┌──────────────┐
                     │ Kubernetes   │
                     │ Secret       │
                     │ (real values)│
                     └──────────────┘
```

## SecretStore vs ClusterSecretStore

| CRD | Scope | Use case |
| --- | --- | --- |
| `SecretStore` | Namespaced | Team-scoped: each namespace has its own secret store config |
| `ClusterSecretStore` | Cluster-wide | Platform-scoped: one store, all namespaces reference it |

For kind, we use the **Fake provider** (values are embedded in the SecretStore for testing). In production, this becomes the AWS Secrets Manager provider, Vault provider, or GCP Secret Manager provider.

## ExternalSecret CR

The `ExternalSecret` tells ESO what to fetch and where to put it:

- `spec.secretStoreRef`: which SecretStore to use.
- `spec.target.name`: the Kubernetes Secret name to create.
- `spec.data[]`: list of keys to fetch. Each maps a `remoteRef.key` (key in the secret manager) to a `secretKey` (key in the Kubernetes Secret).

ESO creates the Kubernetes Secret automatically and keeps it in sync. If the value changes in the secret manager, ESO updates the Secret (controlled by `refreshInterval`).

## Installing it through ArgoCD, not `helm install`

Since s18b, every component in this cluster is GitOps-managed: commit the manifest, ArgoCD applies it. ESO needs **two** Applications, not one, because of a chicken-and-egg problem:

- `ExternalSecret` and `SecretStore` are CRDs that ESO's own Helm chart installs. ArgoCD can't create an `ExternalSecret` CR before the CRD exists.

The fix is the same sync-wave pattern s18b uses for cert-manager/istio-base: install the operator first, at a low wave, then sync the CRs that depend on it one wave later.

| Application | File | What it deploys | Sync wave |
| --- | --- | --- | --- |
| `external-secrets` | `k8s/argocd/infra/external-secrets.yaml` | The ESO Helm chart (operator + CRDs) | `0` |
| `security-resources` | `k8s/argocd/infra/security-resources.yaml` | Everything in `k8s/security/`: `SecretStore`, `ExternalSecret` | `1` |

`security-resources` also carries Kyverno's `ClusterPolicy` resources from s19b, since both are CRs that just need "their operator's CRDs to exist first" — same directory, same wave, one Application instead of two nearly-identical ones.

## Commands

```bash
# The manual equivalent, if you weren't GitOps-managing this
# (this is what k8s/argocd/infra/external-secrets.yaml does for you):
# helm repo add external-secrets https://charts.external-secrets.io
# helm repo update
# helm install external-secrets external-secrets/external-secrets \
#   -n external-secrets --create-namespace

# 1. Commit k8s/argocd/infra/external-secrets.yaml and
#    k8s/argocd/infra/security-resources.yaml, then push.
git add k8s/argocd/infra/external-secrets.yaml k8s/argocd/infra/security-resources.yaml
git commit -m "feat(security): install External Secrets Operator via ArgoCD"
git push

# 2. ArgoCD picks both Applications up automatically (root-app's
#    directory.recurse discovers any *.yaml under k8s/argocd/).
#    Wave 0 installs the operator; wave 1 syncs the SecretStore
#    and ExternalSecrets once the CRDs exist.
kubectl get applications -n argocd external-secrets security-resources
```

### Verify

```bash
# Check ExternalSecret sync status
kubectl get externalsecret
# NAME         STORE         REFRESH INTERVAL   STATUS
# users-api    fake-store    1h                 SecretSynced

# Check the synced Kubernetes Secret
kubectl get secret users-api-secret -o yaml
```

### Stale secret after switching to `existingSecret`

When a Helm chart creates its own Secret (e.g. `kube-prometheus-grafana` for the Grafana admin password) and you later set `grafana.admin.existingSecret` to point at an ESO-managed Secret (`grafana-admin`), the chart stops rendering the old Secret. ArgoCD sees a resource it previously managed that no longer exists in the desired state and marks it `OutOfSync` with `requiresPruning: true`.

Because our sync policy has `prune: false`, ArgoCD will not delete the orphaned Secret automatically. You have to delete it manually:

```bash
kubectl delete secret kube-prometheus-grafana -n lgtm
```

This is a one-time cleanup: it only happens when migrating an existing chart-managed Secret to an externally-managed one.

## What this looks like on AWS

| s19a (kind) | EKS / AWS |
| --- | --- |
| ESO with Fake provider | ESO with **AWS Secrets Manager** provider. IAM role via IRSA (s24). |

### AWS Secrets Manager SecretStore (production example)

This is what the SecretStore looks like on EKS. It is not applied in kind.

```yaml
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata:
  name: aws-secret-store
  namespace: default
spec:
  provider:
    aws:
      service: SecretsManager
      region: us-east-1

      # IRSA: the ESO pod assumes an IAM role via a projected
      # service account token. No long-lived AWS keys in the cluster.
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa
```

The ExternalSecret manifests stay exactly the same: only `secretStoreRef.name` changes from `fake-store` to `aws-secret-store`.

Secrets are created in AWS via CLI or Terraform (never committed to Git):

```bash
aws secretsmanager create-secret \
  --name users-api/DATABASE_URL \
  --secret-string "postgresql://app:prod-password@rds-host:5432/usersdb"

aws secretsmanager create-secret \
  --name users-api/SESSION_SECRET \
  --secret-string "$(openssl rand -hex 32)"
```

### Why the Fake provider is a stepping stone, not the real thing

With the Fake provider, secret values are hardcoded in `secret-store.yaml` and committed to Git. That's no better than a plain `Secret` YAML. The value comes when you swap to a real provider:

```text
FAKE (kind, learning)                 AWS Secrets Manager (production)
─────────────────────                 ─────────────────────────────────
Values in secret-store.yaml           Values in AWS (never in Git)
  committed to Git                      created via CLI / Terraform / console

provider:                             provider:
  fake:                                 aws:
    data:                                 service: SecretsManager
      - key: users-api/DB_URL             region: us-east-1
        value: "postgres://..."           auth:
                                            jwt:
                                              serviceAccountRef:
                                                name: external-secrets-sa
```

The ExternalSecret manifests **do not change at all**. They still reference keys like `users-api/DATABASE_URL`. Only the SecretStore changes where those keys are fetched from.

### How IRSA authentication works

On EKS, ESO authenticates to AWS using IRSA (IAM Roles for Service Accounts):

1. You create an IAM role with a policy that allows `secretsmanager:GetSecretValue` on the specific secrets.
2. You annotate a Kubernetes ServiceAccount with that role's ARN:

   ```yaml
   apiVersion: v1
   kind: ServiceAccount
   metadata:
     name: external-secrets-sa
     annotations:
       eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/eso-secrets-role
   ```

3. EKS injects a projected JWT token into the pod. The ESO pod exchanges that token with AWS STS for temporary credentials.
4. No long-lived AWS access keys are stored anywhere in the cluster.

### What changes vs. a plain Secret in Git

| | Plain `Secret` in Git | ExternalSecret + AWS SM |
| --- | --- | --- |
| **Values in repo** | Yes (base64, trivially decoded) | No. Only key names are in Git. |
| **Rotation** | Manual: change YAML, commit, redeploy | Automatic: rotate in AWS, ESO picks it up on `refreshInterval` |
| **Access control** | Anyone with repo read access | IAM policies, separate from Git permissions |
| **Audit trail** | `git log` | AWS CloudTrail (who accessed which secret, when) |
| **Blast radius of repo leak** | All secrets exposed | No secrets exposed; attacker still needs AWS IAM access |

## The alternative: Sealed Secrets

Sealed Secrets is the other popular GitOps-friendly approach. Instead of pulling values from an external store at runtime, you encrypt them on your laptop and commit the ciphertext to Git. A controller in the cluster decrypts them.

```text
┌──────────────┐     ┌───────────────┐     ┌────────────────────┐
│ You (laptop) │     │ Git repo      │     │ Cluster            │
│              │     │               │     │                    │
│ kubeseal     │────▶│ SealedSecret  │────▶│ sealed-secrets     │
│ (public key) │     │ (encrypted    │     │ controller         │
│              │     │  blob in Git) │     │ (private key)      │
└──────────────┘     └───────────────┘     │ decrypts ──▶ K8s   │
                                           │             Secret │
                                           └────────────────────┘
```

### How it works

1. The `sealed-secrets-controller` runs in the cluster and holds a private/public keypair.
2. You fetch the public key and use the `kubeseal` CLI to encrypt a regular Secret into a `SealedSecret`.
3. The SealedSecret (encrypted values) is committed to Git. ArgoCD syncs it to the cluster.
4. The controller decrypts it and creates a regular Kubernetes Secret.

### Code example

Start with a normal Secret (never commit this):

```yaml
# secret-raw.yaml (local only, do NOT commit)
apiVersion: v1
kind: Secret
metadata:
  name: users-api
  namespace: default
stringData:
  DATABASE_URL: "postgresql://app:postgres123@postgres-rw:5432/usersdb"
  SESSION_SECRET: "a-random-session-secret-change-me"
```

Encrypt it with `kubeseal`:

```bash
# Fetch the controller's public key and encrypt
kubeseal --controller-name=sealed-secrets \
         --controller-namespace=kube-system \
         --format yaml \
         < secret-raw.yaml > sealed-secret.yaml

# Delete the plaintext immediately
rm secret-raw.yaml
```

The output is a SealedSecret you commit to Git:

```yaml
# sealed-secret.yaml (safe to commit)
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: users-api
  namespace: default
spec:
  encryptedData:
    # These are encrypted with the controller's public key.
    # They look like random base64 and cannot be decrypted
    # without the controller's private key.
    DATABASE_URL: AgBx7k2J... (long encrypted blob)
    SESSION_SECRET: AgCp9mR4... (long encrypted blob)
  template:
    metadata:
      name: users-api
      namespace: default
    type: Opaque
```

The controller decrypts it in-cluster and creates a regular `Secret` named `users-api`, identical to what ESO would produce.

### ESO vs Sealed Secrets

| | External Secrets (ESO) | Sealed Secrets |
| --- | --- | --- |
| **Where values live** | External store (AWS SM, Vault) | In Git (encrypted) |
| **What's in Git** | Key names only | Encrypted blobs |
| **Rotation** | Automatic via `refreshInterval` | Re-encrypt, commit, redeploy |
| **Dependencies** | Needs an external secret store | Self-contained (just the controller) |
| **Key management** | Delegated to provider (AWS KMS, etc.) | Controller's private key. Lose it = lose all secrets. Back it up. |
| **Multi-cluster** | All clusters point at the same store | Each cluster has its own keypair; re-seal per cluster |
| **Audit** | Provider's audit trail (CloudTrail, Vault) | `git log` only |
| **Setup complexity** | Higher: auth to external provider (IRSA, AppRole) | Lower: one Helm install, one CLI tool |
| **GitOps purity** | Values are external to Git | Everything (encrypted) lives in Git |

### When to pick which

**Sealed Secrets** is a good fit when:

- You want a self-contained setup with no external dependencies.
- Single cluster, small team, secrets that rarely rotate.
- You're not on a cloud provider (or don't want to pay for Secrets Manager).

**ESO** is a good fit when:

- You already have (or plan to have) a secrets manager.
- Secrets rotate frequently (database credentials, API keys with expiry).
- Multiple clusters need the same secrets.
- You need audit trails beyond `git log`.

### Why this project uses ESO

This project is building toward EKS, where AWS Secrets Manager is the natural backend. ESO lets us learn the pattern now with the Fake provider, then swap to the real provider with a one-block change in the SecretStore. Sealed Secrets would work for kind, but we'd rip it out and replace it with ESO at the EKS stage anyway.

## Try to break it

### ExternalSecret references a missing key

```yaml
spec:
  data:
    - secretKey: DATABASE_URL
      remoteRef:
        key: wrong-key-name
```

The ExternalSecret status shows `SecretSyncedError`. The Kubernetes Secret is not created (or stale if it existed before). The app fails to start if it `envFrom`s the missing Secret.

```bash
kubectl describe externalsecret users-api
# Status: SecretSyncedError
# Message: key "wrong-key-name" not found
```
