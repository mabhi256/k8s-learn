# s16 - Operators and CRDs (CloudNativePG)

> **Tag:** `s16`
> Goal: understand Custom Resource Definitions (CRDs) and operators by replacing the manual Postgres StatefulSet from s5 with CloudNativePG. The operator manages HA failover, backups, and connection pooling through a single `Cluster` CR.

Every Helm chart from s11 onward has installed CRDs: `ServiceMonitor` (kube-prometheus-stack), `VPA` (Fairwinds), `VirtualService` (Istio). We've been using CRDs without explaining the machinery. This stage opens the box.

---

## What is a CRD

A Custom Resource Definition extends the Kubernetes API with new resource types. After applying a `ServiceMonitor` CRD, the API server accepts `kind: ServiceMonitor` objects. The CRD itself just registers the type and its schema — it doesn't do anything with the objects. That's the operator's job.

```text
┌──────────────┐   registers type   ┌─────────────────────┐
│  CRD YAML    │ ─────────────────▶ │  API server          │
│  (schema)    │                    │  now accepts         │
└──────────────┘                    │  kind: Cluster       │
                                    └──────────┬──────────┘
                                               │
                                    watches via │ informer
                                               ▼
                                    ┌─────────────────────┐
                                    │  Operator            │
                                    │  (controller-manager)│
                                    │  reconciles desired  │
                                    │  state → actual      │
                                    └─────────────────────┘
```

The CRD is the schema. The CR (Custom Resource) is an instance (like a row matching the schema). The operator is the controller that watches CRs and makes reality match.

### The operator pattern

An operator is a controller that:

1. Watches one or more CRDs via the API server's watch/informer mechanism.
2. On every change (create, update, delete), runs a **reconcile loop** that compares desired state (the CR's spec) to actual state (what exists in the cluster).
3. Takes action to converge: create Pods, update configs, trigger failover, run backups.

The reconcile loop is idempotent. Calling it twice with the same input produces the same result. This is the same pattern the built-in Deployment controller uses — operators just extend it to domain-specific logic.

### Building vs using operators

| Approach | Tool | When |
| --- | --- | --- |
| **Use** an existing operator | `helm install`, apply CRs | You need managed Postgres, Redis, Kafka, etc. This stage. |
| **Build** your own operator | kubebuilder, operator-sdk | You have domain-specific lifecycle logic that doesn't exist as an operator yet. Rare for most teams. |

We focus on using operators here. Building one is a niche skill (most teams will never need it) and kubebuilder's scaffolding deserves its own deep-dive if you ever need it.

## Why CloudNativePG

The s5 Postgres setup is a single-replica StatefulSet. No failover, no automated backups, no connection pooling. If the Pod dies, the app is down until the StatefulSet controller recreates it and the PVC reattaches.

CloudNativePG (CNPG) is a CNCF-sandbox Postgres operator. One `Cluster` CR gives you:

| Feature | StatefulSet (s5) | CloudNativePG |
| --- | --- | --- |
| **HA failover** | None. Single replica. | Primary + N replicas. Automatic promotion on primary failure (typically <10s). |
| **Backups** | Manual `pg_dump` CronJob (s17). | Built-in: base backup + continuous WAL archiving to object storage or PVC. Point-in-time recovery. |
| **Connection pooling** | None. App connects directly. | Built-in PgBouncer sidecar. |
| **Rolling updates** | Manual. Must drain, update, restart. | Operator handles: update replicas first, switchover primary, zero-downtime. |
| **Monitoring** | None built-in. | Exports Prometheus metrics. Works with s12's ServiceMonitor. |

The trade-off: you run an operator (one more Deployment). On kind that's trivial. On EKS, many teams choose **RDS** instead and skip the operator entirely — managed Postgres with zero operational overhead, at higher cost.

## Architecture

```text
┌────────────────────────────────────────────────────────────┐
│  CloudNativePG operator (Deployment, 1 replica)            │
│  watches: Cluster, Backup, ScheduledBackup CRDs            │
└────────────┬───────────────────────────────────────────────┘
             │ reconciles
             ▼
┌────────────────────────────────────────────────────────────┐
│  Cluster: postgres                                         │
│                                                            │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐     │
│  │  postgres-1   │  │  postgres-2   │  │  postgres-3   │    │
│  │  (primary)    │  │  (replica)    │  │  (replica)    │    │
│  │  read-write   │  │  read-only    │  │  read-only    │    │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘     │
│         │ PVC              │ PVC              │ PVC         │
│         │                  │                  │             │
│  Services:                                                 │
│    postgres-rw  ──▶ primary only                           │
│    postgres-ro  ──▶ replicas (round-robin)                 │
│    postgres-r   ──▶ any (primary + replicas)               │
└────────────────────────────────────────────────────────────┘
```

The operator creates:

- **Pods** (not a StatefulSet — CNPG manages Pods directly for finer control over failover).
- **PVCs** per instance.
- **Services**: `-rw` for writes (always points at primary), `-ro` for read replicas, `-r` for any instance.
- **Secrets** with credentials (auto-generated or user-supplied).

### Failover

When the primary Pod fails (or the node is drained), the operator:

1. Detects the failure (via pod informer + health checks).
2. Promotes the most up-to-date replica to primary.
3. Updates the `-rw` Service to point at the new primary.
4. Reconfigures remaining replicas to follow the new primary.

Typical failover time: 5-10 seconds. Clients connected via the `-rw` Service see a brief disconnect.

## The Cluster CR

### Key fields

**`spec.instances`**: number of Postgres instances (1 primary + N-1 replicas). Set to 3 for HA (tolerates 1 failure).

**`spec.imageName`**: the Postgres image. CNPG ships curated images (`ghcr.io/cloudnative-pg/postgresql`) but accepts any Postgres image that follows the expected entrypoint contract.

**`spec.storage`**: PVC template for each instance. `size` is the volume size, `storageClass` selects the provisioner.

**`spec.bootstrap`**: how to initialize the cluster:

- `initdb`: create a fresh cluster with specified databases and owners.
- `recovery`: restore from a backup (point-in-time recovery).
- `pg_basebackup`: clone from an existing cluster.

**`spec.postgresql.parameters`**: Postgres configuration (`shared_buffers`, `max_connections`, etc.). Applied via `ALTER SYSTEM` — no restart needed for most parameters.

**`spec.monitoring.enablePodMonitor`**: creates a PodMonitor so Prometheus (s12) scrapes the built-in metrics exporter on each instance.

## Backups

CNPG supports two backup methods:

| Method | What it stores | Recovery capability |
| --- | --- | --- |
| **Base backup** | Full data directory snapshot | Restore to the backup point |
| **WAL archiving** | Continuous stream of write-ahead log segments | Point-in-time recovery (restore to any second between backups) |

For kind, backups go to a PVC. For production, they go to S3/GCS/Azure Blob via the `barmanObjectStore` configuration.

A `ScheduledBackup` CR automates recurring base backups:

```yaml
spec:
  schedule: "0 0 3 * * *"  # 3 AM daily (6-field cron: sec min hour dom mon dow)
  cluster:
    name: postgres
```

Combined with WAL archiving, this gives you continuous protection: restore to any point in time between the oldest retained base backup and now.

## Migrating from the s5 StatefulSet

The s5 StatefulSet creates a single Postgres Pod with a PVC. CNPG creates its own Pods and PVCs. The migration path:

1. Install the CNPG operator.
2. `pg_dump` the existing database (the s15 CronJob or a one-off Job).
3. Create the `Cluster` CR with `bootstrap.initdb`.
4. `pg_restore` into the new cluster.
5. Update the users-api connection string to point at `postgres-rw` (the CNPG read-write Service).
6. Delete the old StatefulSet and PVC.

For a learning project, this is fine. In production, CNPG supports `bootstrap.pg_basebackup` to clone directly from the old instance with minimal downtime.

## Commands

```bash
# 1. Install the CNPG operator
helm repo add cnpg https://cloudnative-pg.github.io/charts
helm repo update
helm install cnpg cnpg/cloudnative-pg -n cnpg-system --create-namespace

# 2. Wait for the operator to be ready
kubectl -n cnpg-system rollout status deploy/cnpg-cloudnative-pg

# 3. Create the Postgres cluster
kubectl apply -f k8s/postgres/cluster.yaml

# 4. Watch the cluster come up
kubectl get cluster postgres -w
# STATUS should go: Creating → Healthy

kubectl get pods -l cnpg.io/cluster=postgres
# postgres-1 (primary), postgres-2 (replica)
```

### Verify

```bash
# Check cluster status
kubectl describe cluster postgres

# Connect to the primary
kubectl exec -it postgres-1 -- psql -U app -d usersdb

# Verify replication
kubectl exec -it postgres-2 -- psql -U app -d usersdb -c "SELECT pg_is_in_recovery();"
# Should return: t (true = replica)

# Check the auto-generated credentials secret
kubectl get secret postgres-app -o jsonpath='{.data.uri}' | base64 -d
```

### Update users-api to use the CNPG cluster

```bash
# Update the connection string in users-api's secret/configmap
# The CNPG read-write service is: postgres-rw.default.svc:5432
# The auto-generated secret "postgres-app" contains the connection URI

# Restart users-api
kubectl rollout restart deploy/users-api
```

### Test failover

```bash
# Delete the primary pod
kubectl delete pod postgres-1

# Watch the operator promote a replica
kubectl get pods -l cnpg.io/cluster=postgres -w
# postgres-2 becomes primary, postgres-1 is recreated as replica

# Verify the app still works
curl -k https://demo.local/api/users
```

## What this looks like on AWS

| s16 (kind) | EKS / AWS |
| --- | --- |
| CloudNativePG operator in-cluster | Same chart. Or skip the operator entirely and use **RDS for PostgreSQL** (managed, zero ops). |
| PVC-backed storage (local-path) | **EBS CSI** volumes (gp3). Or EBS io2 for high IOPS. |
| Backups to PVC | Backups to **S3** via `barmanObjectStore`. Or RDS automated backups + snapshots. |
| WAL archiving to PVC | WAL archiving to S3. Enables cross-region PITR. |
| PodMonitor for Prometheus | Same. Or **RDS Performance Insights** + **CloudWatch** for managed monitoring. |

CNPG on EKS is a legitimate production choice for teams that want Postgres control (extensions, major version upgrades on their schedule, custom configs). RDS is the choice when you want zero operational burden and are OK with the constraints.

## Try to break it

### 1. Kill the primary, watch automatic failover

```bash
kubectl delete pod postgres-1
kubectl get pods -l cnpg.io/cluster=postgres -w
# postgres-2 promoted to primary within ~10s
# postgres-1 recreated as replica

kubectl describe cluster postgres | grep "Current Primary"
# Should show postgres-2
```

The `-rw` Service endpoint switches automatically. Clients that reconnect see the new primary.

### 2. Scale to 1 instance, lose HA

```bash
kubectl patch cluster postgres --type merge -p '{"spec":{"instances":1}}'
# Replicas are terminated. Only the primary remains.
# Delete the primary now:
kubectl delete pod postgres-1
# Cluster is unavailable until the operator recreates the Pod and it finishes recovery.
```

With 1 instance, "failover" is just "restart and recover." No promotion, just WAL replay. Downtime is minutes, not seconds.

### 3. Connection string points at the old StatefulSet Service

After migrating from s5, if users-api still connects to the old `postgres` Service instead of `postgres-rw`, it hits the old (now deleted) Pod. Connection refused.

```bash
kubectl logs deploy/users-api | grep "ECONNREFUSED"
```

Fix: update `DATABASE_URL` to use `postgres-rw.default.svc:5432/usersdb`.

## Cleanup

```bash
# Delete the cluster (this deletes all Pods, PVCs, and Secrets)
kubectl delete -f k8s/postgres/cluster.yaml

# Uninstall the operator
helm uninstall cnpg -n cnpg-system
kubectl delete namespace cnpg-system

# Re-apply the old StatefulSet if you want to revert to s5's setup
kubectl apply -f k8s/postgres/
```

## Diff

### New: `k8s/postgres/cluster.yaml`

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: postgres
  namespace: default
spec:
  instances: 2

  imageName: ghcr.io/cloudnative-pg/postgresql:16

  bootstrap:
    initdb:
      database: usersdb
      owner: app
      secret:
        name: postgres-app-credentials

  storage:
    size: 2Gi

  postgresql:
    parameters:
      shared_buffers: "128MB"
      max_connections: "100"

  monitoring:
    enablePodMonitor: true

  resources:
    requests:
      cpu: 100m
      memory: 256Mi
    limits:
      memory: 512Mi
```

### New: `k8s/postgres/app-credentials.yaml`

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: postgres-app-credentials
  namespace: default
type: kubernetes.io/basic-auth
stringData:
  username: app
  password: postgres123
```

### New: `k8s/postgres/scheduled-backup.yaml`

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: ScheduledBackup
metadata:
  name: postgres-daily
  namespace: default
spec:
  schedule: "0 0 3 * * *"
  backupOwnerReference: self
  cluster:
    name: postgres
  method: volumeSnapshot
```

### Changed: `k8s/users-api/configmap.yaml` (or Secret)

Update `DATABASE_URL` to point at the CNPG read-write Service instead of the old StatefulSet Service.

```diff
  data:
-   DATABASE_URL: "postgresql://app:postgres123@postgres:5432/usersdb"
+   DATABASE_URL: "postgresql://app:postgres123@postgres-rw:5432/usersdb"
```
