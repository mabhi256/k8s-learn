# s8 - ServiceAccounts and Token Automount

> **Tag:** `s8`
> Goal: give every workload its own identity (a dedicated `ServiceAccount`) instead of inheriting the namespace's `default`, and disable the projected API-server token on the workloads that don't need one. This is the AuthN / attack-surface side of workload security. AuthZ (RBAC) is the separate story in s9.

s7 closed off pod-to-pod traffic. s8 removes the bearer token the cluster injects into every container by default. The credential a compromised container would otherwise use to reach the API server. The two stages are independent: NetworkPolicy says nothing about API-server access, and an unmounted SA token has nothing to do with east-west traffic.

---

## Why this matters

Every Pod runs as some `ServiceAccount`. If the Pod spec doesn't set `serviceAccountName`, it inherits the namespace's `default` SA. The kubelet projects an authentication token for that SA into every container at:

```text
/var/run/secrets/kubernetes.io/serviceaccount/
├── ca.crt        # the API server's CA, so the Pod can verify TLS
├── namespace     # the namespace the Pod is in
└── token         # a bearer token for the SA
```

That token is a valid credential for the Kubernetes API server. Anything inside the container - a normal process, or an attacker who got RCE (remote control execution) through your app - can read it and call the API as that SA.

The `default` SA has no RBAC bindings out of the box, so the token mostly can't *do* anything useful.

- It can read self-info: `/api/v1/namespaces/<ns>/...` for things every authenticated user can see.
- Cluster operators sometimes accidentally bind permissions to `default` (e.g., a Helm chart that grants `default` access to a CRD). Once that happens, every Pod in the namespace inherits the grant.
- Even with no permissions, the token gives an attacker reconnaissance: the API server confirms the identity, hands back error messages that leak structure, and may answer authentication-status endpoints.

The fix is two lines per workload: give each one its own SA, and disable the automounted token. The token only exists where it's wanted.

---

## The ServiceAccount object

A `ServiceAccount` is mostly just a name. The cluster uses it for two things: as an identity for RBAC (s9), and as the subject for the token the kubelet projects.

Without `automountServiceAccountToken: false`, the kubelet projects the token at `/var/run/secrets/kubernetes.io/serviceaccount/token` even though nothing in the Pod will ever use it.

The field can be set at two levels:

| Level | Effect |
| --- | --- |
| **ServiceAccount** | Applies to every Pod using this SA, unless the Pod overrides it. |
| **Pod spec** | Per-Pod override. Wins over the SA-level setting if both are present. |

Setting it on the SA is the right default. Pod-spec override is for the rare case where one Pod in a workload needs different behavior.

## Wiring the SA to the workload

```yaml
# k8s/users-api/deployment.yaml (excerpt)
spec:
  template:
    spec:
      serviceAccountName: users-api
      containers:
        - name: users-api
          ...
```

Once `serviceAccountName` is set, the SA's `automountServiceAccountToken` value propagates automatically. Restart the Pod (rolling update or `kubectl rollout restart`) and the projected volume disappears.

Repeat the same shape for `frontend`, `postgres`, and `notify-api`. None of these four services call the Kubernetes API at runtime. They talk to each other over TCP/HTTP/gRPC, not to `kubernetes.default`. So all four get `automountServiceAccountToken: false`.

---

## Apply order

ServiceAccounts before the workloads that reference them avoids a few seconds of `ServiceAccount not found` warnings during rollout:

```bash
kubectl exec statefulset/postgres -- ls /var/run/secrets/kubernetes.io/serviceaccount 2>&1 || true
# ca.crt
# namespace
# token

kubectl apply -f k8s/postgres/serviceaccount.yaml \
              -f k8s/users-api/serviceaccount.yaml \
              -f k8s/frontend/serviceaccount.yaml \
              -f k8s/notify-api/serviceaccount.yaml

kubectl apply -f k8s/frontend/deployment.yaml \
              -f k8s/notify-api/deployment.yaml \
              -f k8s/users-api/deployment.yaml

kubectl apply -f k8s/postgres/statefulset.yaml
```

Verify:

```bash
kubectl get sa
# NAME           SECRETS   AGE
# default        0         ...
# frontend       0         5s
# notify-api     0         5s
# postgres       0         5s
# users-api      0         5s

kubectl get pod -l app=users-api -o jsonpath='{.items[0].spec.serviceAccountName}'
# users-api
```

The "Secrets: 0" column is expected on modern Kubernetes. The legacy auto-created secret-per-SA went away in v1.24+; tokens are now projected directly from the kubelet, not stored as Secret objects.

## How the pieces fit

```text
┌──────────────┐                  ┌────────────────────────┐
│  frontend    │   SA: frontend   │ automountToken: false  │
└──────────────┘                  │   → no token mounted   │
                                  └────────────────────────┘
┌──────────────┐                  ┌────────────────────────┐
│  users-api   │   SA: users-api  │ automountToken: false  │
└──────────────┘                  └────────────────────────┘
┌──────────────┐                  ┌────────────────────────┐
│  postgres    │   SA: postgres   │ automountToken: false  │
└──────────────┘                  └────────────────────────┘
┌──────────────┐                  ┌────────────────────────┐
│  notify-api  │   SA: notify-api │ automountToken: false  │
└──────────────┘                  └────────────────────────┘

Compromise inside any container → no SA token in the filesystem → no
credential to reuse against the API server.
```

This is purely an attack-surface story. None of these Pods talked to the API server before, and none of them do now. The change is that an attacker with code-execution in any of them no longer gets a free bearer token.

## What this looks like on AWS

| s8 (local) | EKS / AWS |
| --- | --- |
| ServiceAccount object, one per workload | Same. SA objects are pure Kubernetes. |
| `automountServiceAccountToken: false` everywhere | Same default. |
| Workloads that need API access get a token | Workloads that need *AWS* access get an SA annotated with an IAM role ARN (**IRSA**). The token is still a projected volume, but AWS treats it as an OIDC token and exchanges it for STS credentials. |
| Token is the kubelet's default projected volume | IRSA uses the same mechanism but sets `audience: sts.amazonaws.com` and a short `expirationSeconds`. Only the IRSA-bound SA gets a token; everything else keeps `automountServiceAccountToken: false`. |

The mental model: on kind, an SA gives a Pod *cluster* identity (used by RBAC). On EKS with IRSA, an SA can also carry a *cloud* identity (used by AWS IAM). The Kubernetes-side knobs (`automountServiceAccountToken`, RBAC bindings) work the same on both; IRSA adds an AWS-aware second layer on top.

## Try to break it

### 1. Confirm no token in any of the four workloads

```bash
# The token directory should not exist
for d in users-api frontend notify-api; do
  echo "=== $d ==="
  kubectl exec deploy/$d -- ls /var/run/secrets/kubernetes.io/serviceaccount 2>&1 || true
done
kubectl exec statefulset/postgres -- ls /var/run/secrets/kubernetes.io/serviceaccount 2>&1 || true
# ls: cannot access ... No such file or directory
```

Each one should report "No such file or directory." That's the projected volume being entirely absent, not just empty.

### 2. Try to use a token that isn't mounted

```bash
kubectl exec deploy/users-api -- cat /var/run/secrets/kubernetes.io/serviceaccount/token
# cat: can't open '/var/run/secrets/...: No such file or directory
```

### 3. Override at the Pod level

The SA-level setting can be undone in a single Pod spec.

```bash
kubectl run debug --rm -it --restart=Never \
  --image=nicolaka/netshoot \
  --overrides='{"spec":{"serviceAccountName":"users-api","automountServiceAccountToken":true}}' \
  -- ls /var/run/secrets/kubernetes.io/serviceaccount
# ca.crt  namespace  token
```

Sometimes one Pod genuinely needs the token even though the rest of the workload doesn't. But it means an attacker who can *create* Pods (a separate RBAC concern, s9) can sidestep the SA-level setting. We restrict Pod-create via RBAC and PodSecurity admission in s18.

### 4. Issue an on-demand token without mounting anything

`automountServiceAccountToken: false` removes the auto-projected token, but it doesn't prevent issuing tokens on-demand. The `kubectl create token` command calls the TokenRequest API directly:

```bash
kubectl create token users-api
# eyJhbGciOiJSUzI1NiIsImt...  (a JWT, valid for 1 hour by default)

kubectl create token users-api --duration=5m
# shorter-lived token, useful for one-off debugging
```

The token is real. You could use it in a `curl` call to the API server, but it only exists in your terminal, never inside the Pod. This is the right way to get a credential for manual RBAC testing in s9 without turning automount back on. Tokens issued this way are automatically invalidated when they expire; there's no cleanup needed.

### 5. Verify the SA exists even without a Pod using it

```bash
kubectl get sa users-api
# NAME        SECRETS   AGE
# users-api   0         ...

kubectl describe sa users-api
# (no Tokens section on modern clusters; projected tokens aren't Secret objects)
```

An SA is just a name and a few labels. Deleting it doesn't break running Pods immediately (they keep using whatever was mounted at start) but new Pods referencing it will fail to schedule with `ServiceAccount "users-api" not found`.

## What's next

- **s9** picks up RBAC (Role / RoleBinding / ClusterRole / ClusterRoleBinding) and sets up human access via x509 client certs on kind. The SAs created here become potential subjects in those bindings, but none of our four workloads need any API permissions for now.
- **s21** revisits SA identity with IRSA on EKS, where the same `automountServiceAccountToken: false` default applies and only a few SAs get the IAM-role annotation.
