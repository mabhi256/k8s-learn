# s5 - StatefulSet + PVC (Postgres in-cluster)

> **Tag:** `s5`
> Goal: move Postgres from the host's docker-compose into the cluster as a StatefulSet backed by a PersistentVolumeClaim. Stop pointing the app at `host.docker.internal`. Introduce stable pod identity, per-pod storage, pod anti-affinity, and the LoadBalancer Service for external DB client access.

Through s4 the users-api ran in kind but its Postgres lived outside the cluster - [k8s/users-api/configmap.yaml](../k8s/users-api/configmap.yaml) set `DB_HOST: "host.docker.internal"` and [local/docker-compose.yml](../local/docker-compose.yml) was responsible for starting the database. That worked for the stateless app stages, but it means the cluster doesn't own the part of the system that holds the actual data.

s5 is the first **stateful** workload. A stateless pod can be replaced by any other copy - its replacement doesn't need to be "the same" pod, just a working one. A stateful pod is the opposite on two axes: it owns data on disk that has to follow it across reschedules, and other things in the cluster refer to it by name. Deployments give you neither. From here on:

- Postgres runs as a `StatefulSet` inside the cluster, with one `PersistentVolumeClaim` per pod.
- users-api connects to it via a headless `Service` using stable pod DNS.
- A separate `LoadBalancer` `Service` exposes 5432 to the host so pgAdmin / DBeaver / `psql` can connect from outside the cluster.
- The kind cluster grows to **three nodes** (1 control-plane + 2 workers) so `podAntiAffinity` has somewhere to spread pods to.
- `cloud-provider-kind` runs on the host to allocate external IPs to LoadBalancer Services.

`local/docker-compose.yml` is kept around as the s0 reference but is no longer the source of truth for Postgres.

s5 also reorganizes [k8s/](../k8s/) so it doesn't grow into a flat pile of two-dozen YAMLs. Files are now grouped by component:

```text
k8s/
├── users-api/    configmap, secret, deployment, service
├── frontend/     deployment, service
├── postgres/     (new in s5) secret, configmap, init-configmap,
│                 headless-service, statefulset, loadbalancer-service
├── tls/          cert-issuers, certificate
├── ingress.yaml
└── nodeport/     alternative exposure topology kept for s2/s3 reference
```

`kubectl apply -f <dir>` does **not** recurse by default, so `kubectl apply -f k8s/users-api/` picks up exactly the four users-api files and ignores `nodeport/` and other sibling folders.

## Postgres credentials and init

These files configure what the postgres image consumes on first boot: connection identity, database name, and the schema.

### `k8s/postgres/secret.yaml`

Holds `POSTGRES_USER` and `POSTGRES_PASSWORD` (the env vars the official `postgres` image looks at on first boot). Same `appuser` / `secret` values as [k8s/users-api/secret.yaml](../k8s/users-api/secret.yaml), which holds the users-api's `DB_USER` / `DB_PASSWORD`.

s18 (External Secrets) replaces this with a single source backed by Vault / Sealed Secrets.

### `k8s/postgres/configmap.yaml`

- `POSTGRES_DB: appdb` - the database the `postgres` image creates on first boot.
- `PGDATA: /var/lib/postgresql/data/pgdata` - tells postgres to put its data dir in a **subdirectory** of the mounted volume, not at the mount point itself. The official image refuses to initialize `PGDATA` if the directory is non-empty, and a freshly bound volume sometimes contains a `lost+found` directory (on real filesystems). The subdirectory trick is the standard workaround.

### `k8s/postgres/init-configmap.yaml`

Wraps the schema (same SQL as [apps/users-api/db/init.sql](../apps/users-api/db/init.sql)) in a ConfigMap so the StatefulSet can mount it at `/docker-entrypoint-initdb.d/init.sql`. The `postgres` image runs anything dropped in that directory on first boot **only** - subsequent restarts skip it.

You can also build it from the file each time:

```bash
kubectl create configmap postgres-init \
  --from-file=init.sql=apps/users-api/db/init.sql \
  --dry-run=client -o yaml > k8s/postgres/init-configmap.yaml
```

## Headless Service

| | `ClusterIP` (default) | Headless (`clusterIP: None`) |
| --- | --- | --- |
| VIP + kube-proxy | yes | no |
| DNS returns | the VIP | one A record per pod |
| Hides which pod you hit | yes | no |
| Per-pod DNS (`postgres-0.<svc>`) | no | yes (StatefulSet only) |

Stateless apps want the VIP - any pod will do. A stateful client needs the opposite: *this specific pod*. Headless is the opt-out.

A StatefulSet wires per-pod DNS (`postgres-0.postgres-headless`) only when its `spec.serviceName` points at a headless Service. users-api uses that name to target the primary explicitly - useful later if we add read replicas (s20) and want writes pinned to `postgres-0`.

### What breaks if the Service isn't headless

- **Client uses `postgres-0.postgres-headless`** → `NXDOMAIN`. The StatefulSet only creates per-pod records against a headless Service.
- **Client uses `postgres-headless`** → resolves to a VIP. Fine at one replica; at two, ~50% of writes hit a non-primary and Postgres rejects them (`cannot execute INSERT in a read-only transaction`).

### Manifest: `k8s/postgres/headless-service.yaml`

`clusterIP: None`, selector `app: postgres`, port 5432. Three things this Service does:

1. Provides the DNS contract the StatefulSet relies on (`serviceName: postgres-headless`).
2. Gives each pod a stable per-pod DNS entry (`postgres-0.postgres-headless`).
3. Lets cluster clients (users-api) resolve `postgres-headless` to the pod IP(s) without going through kube-proxy.

It is intentionally **not** the way external clients connect. That's for `postgres-lb`.

## PV / PVC / StorageClass chain

Persistent storage in Kubernetes is a four-object chain:

```text
Pod
  │  mounts
  ▼
PersistentVolumeClaim (pgdata-postgres-0)
  │  references (by name) once bound
  ▼
PersistentVolume (pvc-... auto-created)
  │  provisioned by
  ▼
StorageClass (standard, kind's default)
  │  uses
  ▼
Provisioner (local-path-provisioner, runs as a Pod in kube-system)
  │  writes to
  ▼
Host directory (/var/local-path-provisioner/<pv-id>/ inside the kind node container)
```

- **PVC**: the workload's *request* ("I want 1Gi"). You author this (directly, or via `volumeClaimTemplates`). Pods mount the PVC, not the PV.
- **PV**: the actual storage *resource* bound to a claim. Holds the backing details (host path, EBS volume ID, NFS server). The provisioner creates it; you don't.
- **Backing data**: bytes on disk. Here, a directory inside the kind node container; on EKS, an EBS volume.

PVC ↔ PV bind 1:1. PVC is the user-facing handle; PV is k8s's record of the storage; the data is separate from both.

What you get with kind's default `standard` StorageClass:

- `provisioner: rancher.io/local-path` - a sidecar that creates a directory on whichever node the pod lands on.
- `reclaimPolicy: Delete` - when the **PVC** is deleted, the PV and host directory go too.
- `volumeBindingMode: WaitForFirstConsumer` - the PV is not created until a pod actually schedules. It lets the scheduler honor pod-affinity / anti-affinity rules *before* picking which node owns the data. If the PV were created up-front on node A, the pod would be locked to node A regardless of anti-affinity.

The data lives inside the kind node container's filesystem. If you `docker stop` the node container, the data persists across container restarts (it's in the container's writable layer). If you `kind delete cluster`, it's gone.

### Why you delete the PVC, not the PV

The two `kubectl delete` calls aren't symmetric operations. The PVC has a normal delete lifecycle; the PV does not. Deleting the PV is meant to happen *as a consequence* of deleting the PVC, not on its own.

The PVC is the **handle on the storage's lifetime**. Release the claim, and k8s tidies up the resource according to the rules on the PV. Try to remove the resource while a claim still exists, and k8s restores it.

**What happens on `kubectl delete pvc pgdata-postgres-0`:**

1. The PVC is marked for deletion.
2. The bound PV is now unclaimed, so k8s runs its `reclaimPolicy`:
   - `Delete` (kind's default) → provisioner removes the host directory, then the PV object is removed.
   - `Retain` → PV stays in `Released` state, bytes on disk untouched, waiting for an admin to recycle it manually.
3. The PVC object is removed last.

So "deleting the PVC wipes data" is really "deleting the PVC triggers the reclaim policy, and the default policy happens to be Delete."

**What happens on `kubectl delete pv pvc-151764...` while a PVC still binds it:**

1. The PV gets a `deletionTimestamp` and flips to `Terminating`.
2. The `kubernetes.io/pv-protection` finalizer blocks the actual removal. No data is touched. The pod keeps running, reading and writing as normal.
3. Nothing further happens until the PVC is also deleted. Once the reclaim policy runs and frees the PV, the finalizer is released and the PV object finally goes.

This is also why **deleting the StatefulSet doesn't delete its PVCs**: the controller owns the pods, not the claims. Data outlives the workload until you explicitly `kubectl delete pvc`. The "try to break it" section exercises this.

### Why `kubectl get pv -l app=postgres` returns nothing

The StatefulSet's `volumeClaimTemplates` carries `labels: app: postgres`, so the generated PVC is labeled correctly:

```bash
kubectl get pvc --show-labels
# NAME                STATUS   VOLUME                                     ... LABELS
# pgdata-postgres-0   Bound    pvc-151764be-9268-43de-9722-065269670ec8   ... app=postgres

kubectl get pv --show-labels
# NAME                                       ... CLAIM                       ... LABELS
# pvc-151764be-9268-43de-9722-065269670ec8   ... default/pgdata-postgres-0   ... <none>
```

The PVC has the label; the PV does not. **PVC labels do not propagate to dynamically-provisioned PVs.** The PV is created by the provisioner (`rancher.io/local-path` here, EBS CSI on EKS), and the provisioner decides what labels to attach. Labels you set on the PVC stay on the PVC.

So a "find the PV for this workload" query has to go through the PVC, not directly:

```bash
# Follow the binding from PVC to PV
kubectl get pvc -l app=postgres -o jsonpath='{.items[*].spec.volumeName}'
# pvc-151764be-9268-43de-9722-065269670ec8

# You can label the PV yourself after it binds, 
# but its manual for every reschedule
kubectl label pv pvc-151764be-9268-43de-9722-065269670ec8 app=postgres
```

## Affinity

Affinity is the scheduler-influence API.

- **`nodeAffinity`** - "place me on nodes whose labels match X". The label-based successor to `nodeSelector`. Used to pin GPU workloads to GPU nodes, or to keep a workload inside a specific zone.
- **`podAffinity`** - "place me near pods matching X". Co-location: put the cache pod on the same node as the app pod that hits it, to keep the hop local.
- **`podAntiAffinity`** - "place me away from pods matching X". Spreading: keep replicas off the same node so a node failure doesn't take all of them down.

For Postgres we want spreading, so `podAntiAffinity`. A single node failure should not lose every replica.

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: postgres
        topologyKey: kubernetes.io/hostname
```

Two axes apply to every affinity rule, including the two we don't use here:

- **Hard vs soft.** `requiredDuringSchedulingIgnoredDuringExecution` is a hard rule: the scheduler refuses to place the pod if it can't be satisfied (you'll see `Pending`). `preferredDuringSchedulingIgnoredDuringExecution` is a soft preference - it'd try to honor the rule but place the pod anyway if no node fits. Hard is right for HA-critical workloads; soft is right when you'd rather have a slightly less-spread cluster than `Pending` pods.
- **When evaluated.** `DuringScheduling` runs the rule at scheduling time. `IgnoredDuringExecution` means once the pod is placed, the rule is not re-checked. If node labels change later, or a sibling pod moves, the running pod stays put. A `RequiredDuringExecution` variant has been proposed for years but never landed, so in practice all affinity rules are schedule-time only.

`topologyKey` controls the scope of "near" or "away" for the pod-level flavors. `kubernetes.io/hostname` means per-node; `topology.kubernetes.io/zone` means per-AZ; any node label works. Spreading by hostname survives a node failure; spreading by zone survives an AZ outage. On kind we only have hostname - the cluster is one Docker network with no zones to speak of - which is fine for the lesson; s21 swaps in the zone key on EKS.

With `replicas: 1` the rule is dormant - there's nothing to avoid. The multi-node cluster added earlier in this stage is what gives the scheduler somewhere to spread to; "try to break it" scales to 2 to watch the rule kick in.

## StatefulSet

A StatefulSet is the controller that delivers stable identity and per-pod storage. A Deployment treats its pods as interchangeable replicas (any pod can replace any other); a StatefulSet hands each pod a fixed name, a fixed DNS entry, and its own persistent volume that follows it across reschedules.

Four guarantees:

1. **Stable ordinal names.** Pods are `<sts-name>-0`, `<sts-name>-1`, ..., not the random hash generated by a Deployment's ReplicaSet. Delete `postgres-0` and its replacement is also `postgres-0`.
2. **Stable per-pod DNS.** Paired with the headless Service above, each pod gets `postgres-0.postgres-headless.<ns>.svc.cluster.local`. The name survives reschedules; the IP behind it updates.
3. **Stable per-pod storage.** `volumeClaimTemplates` creates one PVC per pod (`pgdata-postgres-0`, `pgdata-postgres-1`). When the pod is rescheduled, it re-attaches to the same PVC - same bytes on disk, same data.
4. **Ordered lifecycle.** Pods come up `0 -> 1 -> 2`, each waiting for the previous to be Ready before the next is created. Scale-down reverses it (`2 -> 1 -> 0`). Critical when one pod bootstraps from another (primary before replicas).

The trade-off: Deployments are fast and parallel; StatefulSets are sequential and careful. You pay for identity in rollout speed and scaling cost.

Workloads that need this: databases (Postgres, MySQL), distributed stores (Kafka, Cassandra, Elasticsearch, etcd), anything where pods refer to each other by name. Everything else - stateless web servers, APIs, workers - stays on Deployments.

### Manifest: `k8s/postgres/statefulset.yaml`

- `spec.serviceName: postgres-headless` - matches the headless Service above.
- `volumeMounts.pgdata -> /var/lib/postgresql/data` paired with `PGDATA=/var/lib/postgresql/data/pgdata`. The volume mounts at the parent; Postgres writes into a subdirectory inside it.
- `volumeMounts.init-sql` is a separate read-only mount of the init ConfigMap at `/docker-entrypoint-initdb.d`. Used once on first boot, then ignored.
- `volumeClaimTemplates` (not `volumes`). The StatefulSet controller creates one PVC per replica using this template, named `<template-name>-<sts-name>-<ordinal>` -> `pgdata-postgres-0`.
- `accessModes: [ReadWriteOnce]` - chooses how the PV can be mounted. The four modes:

  | Mode | Short | Scope | Typical backing |
  | --- | --- | --- | --- |
  | `ReadWriteOnce` | RWO | One node, read/write | Block storage (EBS, GCE PD, Azure Disk, kind's local-path) |
  | `ReadOnlyMany` | ROX | Many nodes, read-only | Rare in practice |
  | `ReadWriteMany` | RWX | Many nodes, read/write | Shared FS only (NFS, CephFS, EFS) - not block |
  | `ReadWriteOncePod` | RWOP | One pod only, stricter than RWO | Any (added in 1.27) |

  RWO is per-**node**, not per-pod: multiple pods on the same node could share it, but pods on different nodes cannot. Each StatefulSet replica gets its own PVC via `volumeClaimTemplates`, so RWO is fine here. On kind's single node the distinction is invisible; on a multi-node cluster, a pod rescheduled to a different node can't follow its local-path volume.
- No `storageClassName` - leaving it blank means "use the default StorageClass", which on kind is `standard` / local-path-provisioner.
- Probes use `pg_isready -U appuser -d appdb`. `pg_isready` ships in the postgres image. exec probes use literal credentials because Kubernetes does not expand `$(POSTGRES_USER)` style references in probe commands (only in container `command`/`args`). The `startupProbe` is generous (`failureThreshold: 30` × 5s = 150s) because first-boot runs `init.sql` and initializes the data directory; once it succeeds, the liveness/readiness probes take over with tighter budgets.
- `terminationGracePeriodSeconds: 30` - on pod delete, kubelet sends SIGTERM. Postgres treats SIGTERM as "smart shutdown": refuse new connections, finish in-flight transactions, checkpoint, exit. 30s is enough for a small dataset.
- `requiredDuringSchedulingIgnoredDuringExecution` with `topologyKey: kubernetes.io/hostname` - hard rule, no two `app: postgres` pods on the same node.
- `resources.limits.memory` - Postgres allocates shared buffers and per-connection `work_mem` outside anything `pg_isready` or the probes can see; once the cgroup limit is crossed, the kernel sends `SIGKILL` (OOMKill) and the StatefulSet restarts the pod, losing in-flight transactions.

### Knobs we didn't touch

The manifest above relies on defaults for three StatefulSet-specific fields. You will hit them sooner or later, so worth naming:

- **`updateStrategy`** (default: `RollingUpdate`) - how the controller rolls out template changes:

  | Value | Behavior | When to use |
  | --- | --- | --- |
  | `RollingUpdate` | One pod at a time, reverse-ordinal order (highest first) | Standard rollout |
  | `RollingUpdate` + `partition: N` | Only pods with ordinal ≥ N pick up the new template; the rest stay on the old one | Canary - "let pod-2 try the new image for a day before rolling pod-0 and pod-1" |
  | `OnDelete` | Controller writes the new template but waits for you to delete pods before recreating | Manual gating |

- **`podManagementPolicy`** (default: `OrderedReady`) - delivers guarantee #4 above:

  | Value | Behavior | When to use |
  | --- | --- | --- |
  | `OrderedReady` | Pods come up 0 → 1 → 2, each waiting for the previous to be Ready; scale-down reverses | Leader/follower bootstrap order matters (Postgres) |
  | `Parallel` | All pods come up at once; scale-down likewise | No bootstrap order to respect (sharded cache where each pod is independent) |

- **`persistentVolumeClaimRetentionPolicy`** By default, scaling down or deleting the StatefulSet leaves PVCs behind. You can opt into automatic cleanup:

  ```yaml
  spec:
    persistentVolumeClaimRetentionPolicy:
      whenDeleted: Retain   # default. keep PVCs when the StatefulSet is deleted
      whenScaled: Retain    # default. keep PVCs when replicas are reduced
  ```

  Flipping either to `Delete` is appropriate for ephemeral stateful workloads (a cache cluster you periodically rebuild); for Postgres, the safe default is what you want.

### Immutable fields

`spec.selector`, `spec.serviceName`, and `spec.volumeClaimTemplates` cannot be edited after the StatefulSet is created. `kubectl apply` returns `field is immutable`. The workaround when you're iterating on the manifest:

```bash
# Delete the StatefulSet but keep its pods and PVCs
kubectl delete sts postgres --cascade=orphan

# Re-apply the new manifest. The controller adopts the existing pods.
kubectl apply -f k8s/postgres/statefulset.yaml
```

`--cascade=orphan`: without it, `kubectl delete sts` also deletes the pods (PVCs survive either way, see the lifecycle section below)

## PodDisruptionBudget

A `PodDisruptionBudget` (PDB) tells Kubernetes "always keep at least N of my pods running". Without one, `kubectl drain` (used before node maintenance) and the cluster autoscaler will happily evict your only Postgres pod. It will be covered in s19 alongside the rest of the resilience tooling.

## LoadBalancer + cloud-provider-kind

A `Service` with `type: LoadBalancer` says: "give me an external IP that routes traffic to my pods". On a real cloud, the cloud controller manager sees the Service, calls the cloud's load-balancer API (e.g., AWS NLB), and writes the assigned IP back to `.status.loadBalancer.ingress`.

kind has no cloud. By default, LoadBalancer Services stay in `<pending>` forever. [cloud-provider-kind](https://github.com/kubernetes-sigs/cloud-provider-kind) is a small binary you run on the host that watches for LoadBalancer Services and assigns IPs from the Docker network the kind cluster lives in.

```text
host
  │  cloud-provider-kind (binary, watches the API server)
  ▼
docker network (kind)
  │  allocates IP, e.g. 172.18.0.42
  ▼
postgres-lb Service .status.loadBalancer.ingress = 172.18.0.42
```

s5 uses this for `postgres-lb` (`type: LoadBalancer`), which exists so clients outside the cluster (pgAdmin, `psql`) can reach Postgres - they can't resolve in-cluster DNS like `postgres-headless`, and they need a routable IP rather than a ClusterIP. The headless Service stays in place for in-cluster use; the two Services answer different questions:

```text
                 ┌─────────────────────┐
 users-api  ───▶ │ postgres-headless   │ ─── pod-specific DNS
 (in cluster)    │ (clusterIP: None)   │     ───▶ postgres-0
                 └─────────────────────┘

                 ┌─────────────────────┐
 psql/pgAdmin ─▶ │ postgres-lb         │ ─── kube-proxy LB
 (on host)       │ (LoadBalancer)      │     ───▶ postgres-0
                 │ ext IP 172.18.0.42  │
                 └─────────────────────┘
```

On Linux the docker network is directly routable from the host, so `psql -h 172.18.0.42` works. On macOS and Windows (Docker Desktop) the docker network is hidden behind a VM, so the assigned IP often isn't reachable from the host. The pragmatic fallback that works everywhere is `kubectl port-forward svc/postgres-lb 5432:5432` - the LoadBalancer Service still demonstrates the *k8s primitive*, port-forward just bridges the network gap for desktop clients.

### Manifest: `k8s/postgres/loadbalancer-service.yaml`

`type: LoadBalancer`, selector `app: postgres`, port 5432. cloud-provider-kind assigns it an external IP. Use it for external DB clients.

You could collapse the headless and LoadBalancer into one Service by giving the headless type `LoadBalancer`, but mixing the two is confusing - they answer different questions. Keep them separate: headless for "cluster DNS for stateful pods", LoadBalancer for "external entry point".

## Updating `k8s/users-api/configmap.yaml`

Using the per-pod name (`postgres-0.postgres-headless`) rather than the Service name (`postgres-headless`) is intentional: at one replica the two are identical, but the explicit pod ordinal makes it clear that the app is targeting the primary. If you ever scaled the StatefulSet for read replicas, you'd want writes to keep going to pod-0 specifically.

`DB_USER` / `DB_PASSWORD` (in `k8s/users-api/secret.yaml`) and `DB_PORT` / `DB_NAME` (in `k8s/users-api/configmap.yaml`) all stay the same. The app code is unchanged.

## Updating `infra/kind-config.yaml`

From s5 onward we need a multi-node cluster. Add two workers:

```yaml
nodes:
- role: control-plane
  image: kindest/node:v1.32.2
  kubeadmConfigPatches: ...
  extraPortMappings: ...
- role: worker
  image: kindest/node:v1.32.2
- role: worker
  image: kindest/node:v1.32.2
```

The `extraPortMappings` for 80 / 443 and the `ingress-ready=true` label from s3 / s4 are removed. Now that cloud-provider-kind is running, ingress-nginx gets a real LoadBalancer IP just like postgres-lb. No need to pin it to the control-plane or bind it to host ports. The 30080 NodePort mapping is kept as a reference from s2 / s3. The two workers exist to host stateful and replicated pods. The Postgres StatefulSet will land on one of the workers because (a) the control-plane has the default `node-role.kubernetes.io/control-plane:NoSchedule` taint, and (b) when we scale to 2 in "try to break it", anti-affinity will push the second pod onto the other worker.

## Recreating the cluster

The node list and `extraPortMappings` are set at cluster-creation time, so this is delete + recreate (same as every prior cluster-shape change).

```bash
kind delete cluster --name demo
kind create cluster --config infra/kind-config.yaml

kubectl get nodes
# NAME                 STATUS   ROLES           AGE   VERSION
# demo-control-plane   Ready    control-plane   60s   v1.32.2
# demo-worker          Ready    <none>          45s   v1.32.2
# demo-worker2         Ready    <none>          45s   v1.32.2
```

Reload the app images:

```bash
docker build -t users-api:local-v1 apps/users-api
docker build -t frontend:local-v1 apps/frontend
kind load docker-image users-api:local-v1 frontend:local-v1 --name demo
```

The official `postgres:18-alpine` image will be pulled from Docker Hub on first pod start - no `kind load` needed for it.

Re-install nginx-ingress and cert-manager. From s5 onward, use the **cloud** ingress-nginx manifest. It creates a `type: LoadBalancer` Service that cloud-provider-kind will assign an external IP to, consistent with how postgres-lb works. The kind-specific manifest used in s3 / s4 relied on `hostPort` and `extraPortMappings` which are no longer needed:

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/cloud/deploy.yaml
kubectl wait -n ingress-nginx --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=180s

kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
kubectl wait -n cert-manager --for=condition=Available deployment \
  --selector=app.kubernetes.io/instance=cert-manager --timeout=180s
```

## Start cloud-provider-kind

**On Linux / macOS**: run in a separate terminal (it needs to keep running):

```bash
# Install once
go install sigs.k8s.io/cloud-provider-kind@latest

sudo KUBECONFIG=$HOME/.kube/config $(go env GOPATH)/bin/cloud-provider-kind
```

> **Why this exact command?**
>
> **kubeconfig** is a file (default `~/.kube/config`) that tells `kubectl` and other tools where the API server is and what credentials to use. Kind writes the cluster's address and TLS certs there when it creates the cluster.
>
> **Why `sudo`?** `cloud-provider-kind` needs to create and remove network interfaces on the host (to give LoadBalancer services real IPs), which requires root.
>
> **Why does `sudo` break it without `KUBECONFIG=...`?** `sudo` strips most environment variables and switches to root's home directory. Root has no kubeconfig for your kind cluster, so `kubectl`-style clients fall back to `http://localhost:8080`, which doesn't exist, and the tool can't reach the API server at all.
>
> **The fix**: `KUBECONFIG=$HOME/.kube/config` is evaluated by your shell *before* sudo runs, so the fully-expanded path (e.g. `/home/mabhi/.kube/config`) is passed into the root environment, giving `cloud-provider-kind` the correct cluster address and credentials.

Once running, both `postgres-lb` and `ingress-nginx-controller` will leave `<pending>` and get real IPs from the Docker network (e.g. `172.18.0.x`). Update your hosts file to point `demo.local` at the ingress IP:

```bash
INGRESS_IP=$(kubectl get svc -n ingress-nginx ingress-nginx-controller \
  -o jsonpath='{.status.loadBalancer.ingress[0].ip}')

echo $INGRESS_IP   # confirm non-empty before writing

# If demo.local already exists in /etc/hosts (added in s3), replace it:
sudo sed -i "s/.*demo\.local/$INGRESS_IP demo.local/" /etc/hosts

# If /etc/hosts has no demo.local entry yet, add it:
grep -q demo.local /etc/hosts || echo "$INGRESS_IP demo.local" | sudo tee -a /etc/hosts
```

**On WSL2 (native Docker Engine, not Docker Desktop)** cloud-provider-kind works (no path-separator bug), but it also adds the LoadBalancer IPs as aliases on the loopback interface. The kernel then treats those IPs as local, so connections from the WSL host to e.g. `172.19.0.5` never leave the machine. kube-proxy's DNAT rules only fire on ingress traffic, not loopback.

Fix: remove the loopback aliases so traffic routes through the Docker bridge to the cloud-provider-kind proxy container instead:

```bash
# Run after cloud-provider-kind assigns IPs and you see them on lo:
ip addr show lo | grep '172\.'
# inet 172.19.0.5/32 scope global lo
# inet 172.19.0.6/32 scope global lo

# Delete each one
sudo ip addr del 172.19.0.5/32 dev lo
sudo ip addr del 172.19.0.6/32 dev lo

# should now route via the Docker bridge, not loopback
ip route get 172.19.0.5
# 172.19.0.5 dev br-<id> src 172.19.0.1 ...
```

cloud-provider-kind re-adds the aliases on reconcile, so you may need to repeat this if the LB IPs stop working after a few minutes. After removing them, update `/etc/hosts` to point `demo.local` at the ingress IP exactly as the Linux path above.

**On Windows (Docker Desktop)**: cloud-provider-kind has a path-separator bug that causes it to crash on startup. Use Linux, macOS, or WSL2 instead.

## What this looks like on AWS

s5's local-only pieces all have direct cloud equivalents:

| s5 (local)                              | EKS / AWS                                     |
| --------------------------------------- | ----------------------------------------------|
| `StatefulSet` + Postgres image          | RDS for PostgreSQL (managed)                  |
| `volumeClaimTemplates` + local-path     | EBS CSI driver provisioning `gp3` volumes     |
| Headless Service for pod DNS            | Same primitive (works the same on EKS)        |
| `type: LoadBalancer` Service            | Network Load Balancer (NLB)                   |
| cloud-provider-kind                     | AWS cloud controller manager (built into EKS) |
| `kubernetes.io/hostname` topology       | `topology.kubernetes.io/zone` (real AZs)      |

The interesting deltas in s21:

- You usually wouldn't run Postgres as a StatefulSet on EKS at all. You'd point at RDS. StatefulSets are commonly used for in-cluster infrastructure like Kafka and ES (costly). For Postgres, a managed service is often preferred in production, but the StatefulSet pattern still applies when running it in-cluster.
- The LoadBalancer Service becomes an NLB. EKS's cloud controller manager provisions the NLB and assigns it a public or VPC-internal DNS name automatically. No need for workarounds like cloud-provider-kind.
- Anti-affinity gains real meaning. `topologyKey: topology.kubernetes.io/zone` spreads replicas across AZs - the cluster survives a full AZ outage. With local-path on kind, "node failure" is a kind container restart; the lesson is the same but the stakes are higher.

## Try to break it

### 1. Delete the Postgres pod

```bash
kubectl get pod postgres-0 -o wide
# NAME         READY   STATUS    NODE          IP
# postgres-0   1/1     Running   demo-worker   10.244.1.7

kubectl delete pod postgres-0
# pod "postgres-0" deleted

kubectl get pod postgres-0 -o wide
# NAME         READY   STATUS    NODE          IP
# postgres-0   1/1     Running   demo-worker   10.244.1.8   # new pod IP
```

Pod IP changes; pod name does not. DNS for `postgres-0.postgres-headless` updates to the new IP. The PVC was never touched:

```bash
kubectl exec postgres-0 -- psql -U appuser -d appdb -c 'SELECT * FROM users;'
# (same rows as before the delete)
```

This is the whole point of StatefulSets: identity and data survive the pod.

### 2. Scale to 2 to see anti-affinity work

```bash
kubectl scale statefulset postgres --replicas=2
kubectl get pod -l app=postgres -o wide -w
# NAME         READY   STATUS    NODE
# postgres-0   1/1     Running   demo-worker
# postgres-1   0/1     Pending   <none>
# postgres-1   0/1     ContainerCreating   demo-worker2   # <- different node
# postgres-1   1/1     Running             demo-worker2
```

Note `postgres-1` landed on `demo-worker2`, not `demo-worker`. That's `podAntiAffinity` doing its job. Try forcing it to break the rule:

```bash
# cordon marks a node unschedulable. Existing pods keep running, no new pods land there.
# uncordon reverses it. Use it before draining a node for maintenance.
kubectl cordon demo-worker2
kubectl delete pod postgres-1
kubectl get pod postgres-1
# NAME         READY   STATUS    RESTARTS   AGE
# postgres-1   0/1     Pending   0          10s

kubectl describe pod postgres-1 | grep -A 10 Events
# Events:
#   Type     Reason            Age   From               Message
#   ----     ------            ----  ----               -------
#   Warning  FailedScheduling  10s   default-scheduler  0/3 nodes are available:
#                                                        1 node(s) had untolerated taint,
#                                                        1 node(s) didn't match pod anti-affinity rules.
```

`required` means *refuse to schedule*. Compare with `preferred` - the scheduler would have placed it back on `demo-worker` rather than leaving it Pending.

Recover:

```bash
kubectl uncordon demo-worker2
kubectl scale statefulset postgres --replicas=1
# postgres-1 is terminated, but pgdata-postgres-1 PVC stays (see #3).
```

Note that `postgres-1` is a **separate database** with a separate volume - this StatefulSet doesn't do replication. With users-api pointed at `postgres-0` specifically, the experiment is purely about pod placement; the app keeps working off `postgres-0`'s data.

### 3. PVC lifecycle: deleting the StatefulSet does *not* delete data

```bash
kubectl get pvc -l app=postgres
# NAME                  STATUS   VOLUME       CAPACITY   STORAGECLASS
# pgdata-postgres-0     Bound    pvc-...      1Gi        standard
# pgdata-postgres-1     Bound    pvc-...      1Gi        standard   # left over from scaling

kubectl delete statefulset postgres
# statefulset.apps "postgres" deleted

kubectl get pvc -l app=postgres
# (PVCs are still here)
```

Re-create the StatefulSet:

```bash

kubectl exec postgres-0 -- psql -U appuser -d appdb -c 'SELECT * FROM users;'
# (rows are still there)
```

To actually wipe the data:

```bash
kubectl delete statefulset postgres
kubectl delete pvc -l app=postgres
# Now the PVs are reclaimed (StorageClass default is Delete), and the host dirs are gone.
```

### 4. Kill the node that owns the data

`WaitForFirstConsumer` binds the PV on whichever node the pod first scheduled to (here, `demo-worker2`). The data lives inside that node container's filesystem. The PV's `nodeAffinity` then pins the pod to that node too - and unlike EBS on EKS, **local-path can't follow the pod to a new node**.

```bash
kubectl get pod postgres-0 -o wide
# NAME         READY   STATUS    NODE           IP
# postgres-0   1/1     Running   demo-worker2   10.244.2.5

# Simulate the node going away
docker kill demo-worker2

kubectl get nodes
# NAME                 STATUS     ROLES           AGE   VERSION
# demo-control-plane   Ready      control-plane   ...
# demo-worker          Ready      <none>          ...
# demo-worker2         NotReady   <none>          ...

# After the eviction timeout (~5m), the controller deletes postgres-0 and tries to reschedule
kubectl get pod postgres-0 -o wide
# NAME         READY   STATUS    NODE      IP
# postgres-0   0/1     Pending   <none>    <none>

kubectl describe pod postgres-0 | grep -A 5 Events
# Warning  FailedScheduling  ...  default-scheduler  0/3 nodes are available:
#   1 node(s) had volume node affinity conflict, ...
```

The PV requires `demo-worker2` and there is no `demo-worker2` to schedule onto. Pending forever until that node comes back.

Recover by starting the node container again:

```bash
docker start demo-worker2
# postgres-0 schedules on demo-worker2, re-attaches to its data
```

This is only kind specific issue. On EKS, an EBS volume detaches from the dead node and re-attaches to wherever the rescheduled pod lands (within the same AZ). You will cover this in s21.

### 5. Fill the data volume

On a real cloud with an EBS-backed PVC, the volume may run out of the requested capacity. On kind, local-path-provisioner ignores the `1Gi` request entirely.

We can't reproduce this failure mode when using kind. We can only mention the symptoms which appear once writes start failing, and the recovery commands that would work on a real StorageClass.

The symptoms postgres shows when the filesystem is out of space:

```bash
kubectl logs postgres-0 --tail=20
# PANIC:  could not write to file "pg_wal/xlogtemp.123": No space left on device
# LOG:    WAL writer process (PID 47) was terminated by signal 6: Aborted
# LOG:    terminating any other active server processes
# FATAL:  the database system is in recovery mode
```

A regular table write returns `ERROR: could not extend file ...: No space left on device` to the client and aborts the transaction; postgres keeps running. A WAL write failure is different - it triggers `PANIC`, which restarts the postmaster, and on restart the crash-recovery replay needs to write WAL too. If the disk is still full, postgres crash-loops. Either way the readiness probe (`pg_isready`) starts failing, the pod flips to `0/1`, and users-api's connection pool returns 5xx.

Diagnosing the cause:

```bash
kubectl exec postgres-0 -- df -h /var/lib/postgresql/data/pgdata
# Filesystem      Size  Used Avail Use% Mounted on
# overlay          59G   59G     0 100% /var/lib/postgresql/data/pgdata

kubectl describe pod postgres-0 | grep -A2 Events
# Warning  Unhealthy  2m  kubelet  Readiness probe failed: ...
# Warning  BackOff    1m  kubelet  Back-off restarting failed container
```

The recovery path on a CSI-backed StorageClass is PVC expansion:

```bash
# Pre-flight: does the StorageClass even allow expansion?
kubectl get storageclass standard -o jsonpath='{.allowVolumeExpansion}'
# false                              <- kind / local-path

# On EKS with the EBS CSI driver:
kubectl get storageclass gp3 -o jsonpath='{.allowVolumeExpansion}'
# true

# Expansion is a PVC edit:
kubectl patch pvc pgdata-postgres-0 \
  --type=merge \
  -p '{"spec":{"resources":{"requests":{"storage":"5Gi"}}}}'
```

The CSI driver grows the backing volume (EBS calls `ModifyVolume`), the kubelet expands the filesystem in place, and the PVC's `.status.capacity` catches up to the new request. Modern CSI drivers do this online; older ones required pod recreation, which the StatefulSet handles for you - the same PVC re-attaches.

## Backups

Worth flagging now, deferred to s15. Data survives node restarts and pod reschedules. It does **not** survive `kind delete cluster`, `kubectl delete pvc` (under the default `reclaimPolicy: Delete`), or any other event that releases the backing storage. The solution is a backup that lives outside the PVC.

The standard low-effort pattern is a `CronJob` running `pg_dump` on a schedule against `postgres-0.postgres-headless`, writing to a separate PVC (or eventually S3). s15 introduces `Job` / `CronJob` / `DaemonSet` properly and the actual manifest lands there alongside the Flyway migrations init-container. For richer guarantees (rotation, off-cluster destination, point-in-time recovery via WAL archiving) the operator in s20 takes over.

Takeaway for s5: **a StatefulSet manages availability of the pod, not durability of the data.** Backups are a separate concern at every stage from here on.
