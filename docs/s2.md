# s2 - Deployment + Service

> **Tag:** `s2`
> Goal: replace the naked Pod with a Deployment (2 replicas, rolling updates), expose it via a ClusterIP Service, and move configuration into a ConfigMap and Secret.

s1 showed what a Pod is and how probes work. It also showed three things a Pod cannot do on its own:

- auto-restart when deleted.
- run replicas.
- give other workloads a stable address to reach it.

s2 solves all these three issues.

---

## Prerequisites

If the s1 pod is still running, delete it first to avoid a name collision:

```bash
kubectl delete pod users-api --ignore-not-found
```

Start postgres on the host (same as s1):

```bash
docker compose -f local/docker-compose.yml up -d postgres
```

The image is already loaded into kind from s1. No rebuild needed unless you wiped the cluster.

## Namespace

A **namespace** is a logical partition inside a cluster. All objects in s2 land in the `default` namespace because no namespace is specified in the YAML files.

```bash
kubectl get pods                     # implicitly queries the default namespace
kubectl get pods -n default          # same, explicit
kubectl get pods --all-namespaces    # everything in the cluster
```

Namespaces affect DNS: the full in-cluster address of the Service is `users-api.default.svc.cluster.local`. From within the same namespace the short name `users-api` resolves because CoreDNS appends the namespace suffix automatically. Cross-namespace callers must use the full name.

Namespaces do not provide network isolation on their own. A Pod in `namespace-a` can still reach a Service in `namespace-b` by its full DNS name unless a NetworkPolicy blocks it.

## ConfigMap

A **ConfigMap** stores non-sensitive configuration as plain key-value pairs. Think of it as a `.env` file that lives in the cluster and can be mounted into any Pod that needs it.

```bash
kubectl apply -f k8s/configmap.yaml
kubectl get configmap users-api-config -o yaml
```

The keys (`DB_HOST`, `DB_PORT`, `DB_NAME`) become environment variable names in the container when referenced via `envFrom`. Compare this to `pod.yaml` where each var was written inline under `env:`.

---

## Secret

A **Secret** has the same structure as a ConfigMap but:

- its values are base64-encoded
- RBAC policies can restrict access to Secrets independently of ConfigMaps
- `kubectl describe` redacts the values by default.

Base64 is **not encryption**. It is encoding. Anyone with read access to the Secret object can decode the values. The purpose of Secret is access control, not confidentiality. you restrict who can `get` or `list` Secrets via RBAC, and the encoding prevents values from appearing in log lines and describe output by accident.

```bash
kubectl apply -f k8s/secret.yaml
kubectl get secret users-api-secret -o yaml
```

The values appear base64-encoded in the output. To verify they round-trip correctly:

```bash
kubectl get secret users-api-secret -o jsonpath='{.data.DB_USER}' | base64 --decode
# appuser
```

In production you would never commit a Secret to git. You would use an external secrets operator that injects values at deploy time - AWS Secrets Manager, HashiCorp Vault, or Sealed Secrets. This file exists here for learning only.

Two ways to write Secret values:

| Field | Format | Use when |
| ----- | ------ | -------- |
| `data:` | base64-encoded | Generated by tooling, CI/CD pipelines |
| `stringData:` | plain text, k8s encodes it | Writing by hand, readability |

## Deployment

A **Deployment** is a controller that manages a ReplicaSet, which manages Pods. The ownership chain is:

```text
Deployment → ReplicaSet → Pod(s)
```

The Deployment never touches Pods directly. It creates and updates ReplicaSets, and the ReplicaSet's job is to ensure exactly `N` copies of the Pod template are running at all times. If a Pod dies, the ReplicaSet sees "actual=1, desired=2" and creates a replacement immediately.

### Selector immutability

`spec.selector.matchLabels` is **immutable**. It cannot be changed after the Deployment is created. Attempting to `apply` a file with a different selector returns a validation error. The only way to change it is to delete the Deployment and recreate it, which also deletes all its Pods.

```bash
# demo: try to change the selector on a live Deployment
kubectl patch deployment users-api -p '{"spec":{"selector":{"matchLabels":{"app":"wrong"}}}}'
# Error: ... field is immutable
```

```bash
kubectl apply -f k8s/deployment.yaml
kubectl get pods -l app=users-api -w
```

Both Pods should reach `READY 1/1`. Notice the generated names: `users-api-<rs-hash>-<pod-hash>`. The first hash identifies the ReplicaSet (tied to the Pod template); the second is the Pod's unique suffix.

Inspect the full ownership chain:

```bash
kubectl get deployment users-api
kubectl get replicaset
kubectl get pods -l app=users-api
kubectl describe deployment users-api
```

Verify that `envFrom` injected the ConfigMap and Secret values:

```bash
kubectl exec -it <pod-name> -- env | grep DB
# DB_HOST=host.docker.internal
# DB_PORT=5432
# DB_NAME=appdb
# DB_USER=appuser
# DB_PASSWORD=secret
```

## Service

A **Service** gives a stable network identity to a dynamic set of Pods - a DNS name and a virtual IP. Pods are ephemeral; they come and go and get a new IP each time. A Service solves this by watching Pods that match a label selector and keeping an up-to-date list of their IPs in an **Endpoints** object. Anything inside the cluster that wants to reach the API talks to the Service, not the Pods directly.

```bash
kubectl apply -f k8s/service.yaml
kubectl get service users-api
kubectl get endpoints users-api
```

The Endpoints object lists the IPs of all Pods currently passing their readiness probe. This is what the Service actually routes to. When a Pod's readiness probe fails, its IP is automatically removed from Endpoints so traffic stops reaching it.

### port vs targetPort

In `service.yaml`, `port: 80` is what callers inside the cluster connect to. `targetPort: 3000` is the port the container is actually listening on. They are kept separate so the Service's external contract (`port: 80`) stays stable even if the app changes its internal listening port.

```bash
# caller connects to port 80 on the Service. kube-proxy rewrites to pod:3000
kubectl run -it --rm curl-test --image=curlimages/curl --restart=Never \
  -- curl http://users-api:80/health
```

You can also set `targetPort` to a named string that matches a `containerPort.name` in the Pod spec. This lets you change the actual port number in the Pod without touching the Service YAML at all.

### How traffic actually flows: kube-proxy

When you talk to a Service's ClusterIP, the traffic never actually hits a process listening at that IP. The ClusterIP is virtual. It only exists as an iptables (or ipvs) rule on every node, installed by **kube-proxy**.

kube-proxy watches the Endpoints object and rewrites the destination of packets headed for the ClusterIP to one of the real Pod IPs using DNAT (Destination NAT). The kernel does this before the packet leaves the node. The Pod never knows traffic came via a Service. This is why the Service "just works" even though nothing is actually listening at the ClusterIP.

```text
┌─────────────────────────────────────────────────────────────────┐
│                          NODE                                   │
│                                                                 │
│   ┌─────────────┐                                               │
│   │   Client    │                                               │
│   │    Pod      │                                               │
│   └──────┬──────┘                                               │
│          │                                                      │
│          │  dst: 10.96.0.1:80  (ClusterIP)                      │
│          ▼                                                      │
│   ╔══════════════════════════════════════════╗                  │
│   ║           KERNEL NETFILTER               ║                  │
│   ║                                          ║                  │
│   ║   iptables / IPVS rules                  ║                  │
│   ║   (installed by kube-proxy)              ║                  │
│   ║                                          ║                  │
│   ║   10.96.0.1:80  ──DNAT──►  10.244.x.x    ║                  │
│   ║                            (real Pod IP) ║                  │
│   ╚══════════════════════════════════════════╝                  │
│          │                                                      │
│          │  dst: 10.244.2.5:80  (Pod IP)  ◄── rewritten!        │
│          ▼                                                      │
│   ┌──────────────┐     ┌──────────────┐     ┌──────────────┐    │
│   │   Pod A      │     │   Pod B      │     │   Pod C      │    │
│   │ 10.244.2.5   │     │ 10.244.2.6   │     │ 10.244.2.7   │    │
│   └──────────────┘     └──────────────┘     └──────────────┘    │
│                                                                 │
│                    ▲                                            │
│                    │  watches Endpoints object                  │
│             ┌──────┴──────┐                                     │
│             │ kube-proxy  │◄──── kube-apiserver                 │
│             └─────────────┘                                     │
└─────────────────────────────────────────────────────────────────┘

  ClusterIP 10.96.0.1 has NO socket, NO process, NO NIC.
  It is a pure iptables fiction that lives only in DNAT rules.
```

### Service types

| Type | Reachable from | Use case |
| ---- | -------------- | -------- |
| `ClusterIP` (default) | Inside the cluster only | Pod-to-pod communication |
| `NodePort` | Outside the cluster via node IP + high port | Dev/testing without a load balancer |
| `LoadBalancer` | Outside via a cloud load balancer (ELB, etc.) | Production on a cloud provider |
| `ExternalName` | Maps to an external DNS name | Routing to services outside the cluster |

For s2, we are using ClusterIP. External access via HTTP routing will be added in s3 with Ingress.

### Hit the API

Port-forward to the Service:

```bash
kubectl port-forward service/users-api 3000:80
```

The output `127.0.0.1:3000 -> 3000` means local port 3000 tunnels to the Pod's port 3000 (the `targetPort`). The `80` in the command selects which Service port to use, which then resolves to `targetPort: 3000`. It bypasses the ClusterIP entirely. Port-forward goes directly to a Pod.

```bash
# in another terminal
curl http://localhost:3000/health
curl http://localhost:3000/users
```

Prove that cluster-internal DNS works by running a temporary pod:

```bash
kubectl run -it --rm dns-test --image=curlimages/curl --restart=Never \
  -- curl http://users-api/health
```

`http://users-api` resolves to the ClusterIP via the in-cluster DNS server (CoreDNS). Full name is `users-api.default.svc.cluster.local`. Within the same namespace, the short name `users-api` is enough.

### NodePort for ad-hoc external access

`port-forward` is great for a quick check from your terminal, but it dies with the terminal session and only the local machine can hit it. When you want a stable port that anything on the host network can reach - a browser, a teammate on the same LAN, a load-test tool - deploy a dedicated NodePort Service alongside the existing ClusterIP one. This is how you would do it in a real debugging session: the production Service is never touched.

```bash
kubectl apply -f k8s/service-nodeport-debug.yaml
kubectl get service users-api-debug
# TYPE: NodePort, PORT(S): 80:30080/TCP
```

`service-nodeport-debug.yaml` creates a second Service object named `users-api-debug`. It uses the same `selector: app: users-api`, so it routes to the same Pods. The ClusterIP Service `users-api` is untouched and keeps serving internal traffic normally.

The Service listens on port `30080` on **every node** in the cluster. Hitting any node at that port lands you on a healthy Pod via the same kube-proxy DNAT rules. `nodePort` is optional; if omitted, k8s picks a free port in the `30000-32767` range.

**kind caveat:** kind nodes are docker containers, so node ports are not reachable from the host unless you mapped them with `extraPortMappings` at cluster creation. Without that mapping, NodePort works inside the cluster but a `curl localhost:30080` from your laptop will hang. Two ways around it for this stage:

```bash
# option A: docker port-map after the fact via a sidecar container - clunky
# option B: just docker exec into the kind node and curl from there
docker exec -it demo-control-plane curl http://localhost:30080/health
```

On a real cluster (k3s on a VM, EKS node, bare metal) the node IP is directly routable and `http://<node-ip>:30080` Just Works. NodePort is also the foundation that `LoadBalancer` Services are built on - a cloud LB simply points at the NodePort on every node.

Delete when done; the ClusterIP Service continues unaffected:

```bash
kubectl delete -f k8s/service-nodeport-debug.yaml
```

## Rolling Updates

The rolling update strategy controls how the Deployment replaces Pods when something in `spec.template` changes - most commonly the container image. Changing `replicas` does not trigger a rolling update; that is just scaling.

Our Deployment has:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 1
```

With `replicas: 2`, this is how it looks during an update:

```bash
users-api-abc-1   Running      # v1
users-api-abc-2   Running      # v1
users-api-xyz-1   Pending      # v2 spinning up  (Surge)
users-api-xyz-1   Running
users-api-abc-1   Terminating  # (Remove)
users-api-xyz-2   Pending      # v2 spinning up  (Surge)
users-api-xyz-2   Running
users-api-abc-2   Terminating  # (Remove)
```

At no point are both old Pods removed simultaneously. The Service's Endpoints object only includes Pods whose readiness probe is passing, so traffic automatically shifts to new Pods only once they are healthy. If the new image is broken, the rollout stalls. The old Pods keep serving rather than silently killing live traffic.

Build a second image tag to try it:

```bash
docker build -t users-api:local-v2 apps/users-api
kind load docker-image users-api:local-v2 --name demo
```

Trigger the update:

```bash
kubectl set image deployment/users-api users-api=users-api:local-v2
kubectl rollout status deployment/users-api
```

`kubectl set image` edits the live object in the cluster directly. After running it, `deployment.yaml` in git still says `users-api:local-v1`. This out-of-sync situation is also called **drift**. The cluster state diverges from the source of truth in git. In real workflows you bump the image tag in the YAML file and `kubectl apply`, so git always reflects what is running.

During the rollout, watch the ReplicaSet list. You will briefly see two RS objects (one for v1, one for v2):

```bash
kubectl get replicaset
```

The old RS is kept at 0 replicas for rollback. History and rollback:

```bash
kubectl rollout history deployment/users-api
kubectl rollout undo deployment/users-api
kubectl rollout status deployment/users-api
```

To roll back to a specific revision rather than just the previous one:

```bash
kubectl rollout history deployment/users-api --revision=1   # inspect what was in that revision
kubectl rollout undo deployment/users-api --to-revision=1   # apply it
```

The Deployment retains old ReplicaSets up to `revisionHistoryLimit` (default: 10). ReplicaSets beyond that limit are garbage-collected. If you set it to 0, `rollout undo` stops working.

### The Endpoints-removal / SIGTERM race

When a Pod is replaced during a rolling update, two things happen concurrently:

1. The Pod is removed from Endpoints so the Service stops routing new requests to it.
2. The container receives SIGTERM.

These are **not atomic**. kube-proxy propagates the Endpoints change by updating iptables rules on every node, which takes a few hundred milliseconds. During that window, traffic can still be routed to a Pod that has already started shutting down, causing connection resets for in-flight requests. The client gets a Connection reset by peer / ECONNRESET error. If it was a POST/PUT, the server may have partially processed it; the client has no way to know.

The standard fix is a `preStop` sleep in the container spec:

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "5"]
```

This delays SIGTERM by 5 seconds, giving kube-proxy time to drain the Pod from iptables before the process starts shutting down. The total time until SIGKILL is `terminationGracePeriodSeconds` (default: 30s), so a 5s preStop still leaves 25s for the app to finish draining in-flight requests.

## Watching things side by side

The most effective way to observe what Kubernetes is doing during scaling, rolling updates, or probe failures is to run watchers in two terminals simultaneously.

```bash
# Run in a new terminal
kubectl get pods -l app=users-api -w

# Run in a new terminal
kubectl get endpoints users-api -w
```

Now trigger something - delete a pod, scale up, break a probe, or run `kubectl set image`. In Terminal 1 you see the Pod lifecycle (Pending → Running → Ready). In Terminal 2 you see exactly when each Pod IP enters or leaves the Endpoints list (i.e., when the Service starts or stops routing to it). The gap between a Pod showing `Running` and its IP appearing in Endpoints is the readiness probe window.

## Try to break it

### 1. Kill a pod - watch self-healing

```bash
# terminal 1
kubectl get pods -l app=users-api -w

# terminal 2
kubectl delete pod <one-pod-name>
```

The ReplicaSet detects "actual=1, desired=2" and creates a replacement within seconds. The Service endpoint count never drops to zero.

### 2. Broken image - stalled rollout

```bash
kubectl set image deployment/users-api users-api=users-api:does-not-exist
kubectl rollout status deployment/users-api   # hangs

# terminal 2 - old pods are still running and serving
kubectl get pods -l app=users-api
kubectl get endpoints users-api               # IPs unchanged

kubectl rollout undo deployment/users-api     # recover
```

The new Pods enter `ImagePullBackOff` and never become Ready. Their IPs never enter Endpoints. Traffic stays on the old Pods. The rollout stalls rather than breaking the live service.

If a rollout gets stuck, Kubernetes won't wait forever. After 10 minutes (`progressDeadlineSeconds`) of no progress, it gives up and marks the deployment as failed. But, the old Pods keep running so your app stays up. Any CI/CD pipeline watching the rollout will see the failure and can alert you.

```bash
kubectl describe deployment users-api | grep -A5 Conditions
```

## 3. Stop postgres - watch endpoints drain

```bash
# terminal 1
kubectl get endpoints users-api -w

# terminal 2
docker compose -f local/docker-compose.yml stop postgres
```

Within 3 × 5s = 15s the readiness probe fails on both Pods (`/health` returns 503 when DB is unreachable). Their IPs drain from Endpoints. Restart postgres:

```bash
docker compose -f local/docker-compose.yml start postgres
```

The IPs return to Endpoints as readiness probes pass again.

### 4. Wrong selector - silent routing failure

> **Demo only.** In a real incident you would fix the selector by editing the Service YAML and re-applying, not by patching live. We use `kubectl patch` here purely to break and restore the selector in one command without touching any file.

```bash
# break it
kubectl patch service users-api -p '{"spec":{"selector":{"app":"wrong-label"}}}'
kubectl get endpoints users-api
# NAME        ENDPOINTS   AGE
# users-api   <none>      ...

# fix it
kubectl patch service users-api -p '{"spec":{"selector":{"app":"users-api"}}}'
kubectl get endpoints users-api   # IPs return
```

The Service exists but selects zero Pods. Traffic to the ClusterIP goes nowhere.

### 5. Scale to zero

```bash
kubectl scale deployment users-api --replicas=0
kubectl get endpoints users-api               # <none>
kubectl port-forward service/users-api 3000:80
curl http://localhost:3000/health             # connection refused
kubectl scale deployment users-api --replicas=2
```

The Service persists but has no Pods behind it. Scaling to zero can be used in dev environments to save resources overnight.

## What pods still cannot do / what's next

The Service is `ClusterIP`. It is only reachable from inside the cluster. There is no way for a browser or external client to reach the API without `kubectl port-forward`.

Stage s3 uses Ingress for getting external HTTP traffic in - with domain-based routing and path routing - and introduces the frontend Deployment, showing two services behind a single entry point. Stage s4 then layers TLS termination on top via cert-manager.
