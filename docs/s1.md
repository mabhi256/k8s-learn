# s1 - Pod basics

> **Tag:** `s1`
> Goal: run a single pod manually, observe its lifecycle, and understand liveness/readiness probes.

A **Pod** is the smallest deployable unit in Kubernetes

- A wrapper around one or more containers that share a network and storage.
- In this stage there is no auto-restart, no load balancing, and no service discovery.
- If you delete the pod it stays deleted.

---

## Prerequisites

Postgres still runs via Docker Compose (no in-cluster DB until s4). Start only the postgres service. The API pod will connect to it via `host.docker.internal`:

```bash
docker compose -f local/docker-compose.yml up -d postgres
```

## Start the kind cluster

[kind](https://kind.sigs.k8s.io/) (Kubernetes IN Docker) runs a full k8s cluster as Docker containers on your machine.

```bash
# first time only
kind create cluster --name demo

# for subsequent runs, container already exists.
docker start demo-control-plane
```

Verify the cluster is reachable:

```bash
kubectl cluster-info
# Kubernetes control plane is running at https://127.0.0.1:<port>
```

## kubectl context

A **context** is a named combination of `cluster + user + namespace`. kubectl reads the active context from `~/.kube/config` to know which cluster to talk to.

```bash
kubectl config get-contexts          # list all contexts
kubectl config current-context       # show the active one  →  kind-demo
kubectl config use-context kind-demo # switch to it
```

## Load the image into kind

kind has its own image cache separate from Docker's. `imagePullPolicy: Never` in `pod.yaml` tells k8s not to contact a registry, but the image still has to exist inside kind's cache first.

```bash
docker build -t users-api:local apps/users-api
kind load docker-image users-api:local --name demo
```

`imagePullPolicy` has three values:

| Value | Behavior |
| ----- | -------- |
| `Never` | Never pull. Image must already be on the node. kind-only. |
| `IfNotPresent` | Pull only if not cached. Default for non-`latest` tags. |
| `Always` | Pull on every pod start. Default for `latest` and untagged images. |

`Never` only works here because kind pre-loads the image. On any real cluster (EKS, GKE, AKS) you would use `IfNotPresent` with a proper registry.

## Apply the pod

```bash
kubectl apply -f k8s/pod.yaml
```

`kubectl apply` is declarative. It reads the desired state from the file and reconciles the cluster toward it. Re-running the same command is safe (idempotent).

## Labels

Labels are arbitrary key-value pairs attached to any Kubernetes object:

```yaml
metadata:
  labels:
    app: users-api
```

At this stage the label is just metadata. Nothing in s1 selects on it. But it enables filtering in kubectl:

```bash
kubectl get pod -l app=users-api
```

In s2, the Deployment's `selector.matchLabels` uses this label to know which Pods it owns, and the Service uses it to know which Pods to route traffic to. The label on the Pod is how both bindings work.

## Resource requests and limits

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 250m
    memory: 256Mi
```

**Requests** are what the scheduler uses. It finds a node with enough unallocated CPU and memory to satisfy the request. The container is not pinned to that amount. It can use more if the node has headroom.

**Limits** are enforced at runtime:

- CPU: throttled at the limit. Never killed for CPU overuse.
- Memory: if the container exceeds the limit, the kernel OOM-kills it. Kubernetes restarts the container.

`100m` CPU = 100 millicores = 0.1 of one core. `128Mi` memory = 128 mebibytes = 128 × 1024² bytes. Kubernetes uses binary suffixes (`Ki`, `Mi`, `Gi`) not decimal (`K`, `M`, `G`). `128Mi ≠ 128M` (the latter is 128,000,000 bytes).

The relationship between requests and limits determines the Pod's **QoS class**, which controls eviction order when a node runs low on memory:

| QoS class | Condition | Evicted |
| --------- | --------- | ------- |
| `Guaranteed` | requests == limits for all resources | Last |
| `Burstable` | requests < limits (this pod) | Middle |
| `BestEffort` | no requests or limits set | First |

## Watch it start

```bash
kubectl get pod users-api -w
# Pending → ContainerCreating → Running
```

`READY 0/1` means the readiness probe hasn't passed yet. Once `/health` returns 200 it flips to `1/1`.

## Explore the pod

```bash
# full detail: node assignment, image, probe config, events
kubectl describe pod users-api

# current logs
kubectl logs users-api

# logs from the previous (crashed) container - useful after restarts
kubectl logs users-api --previous

# shell into the running container
kubectl exec -it users-api -- sh
  wget -qO- http://localhost:3000/health
  env | grep DB
  exit
```

## Hit the API

`kubectl port-forward` tunnels a local port directly to the pod. This is for debugging only, not how traffic reaches pods in production.

```bash
kubectl port-forward pod/users-api 3000:3000
# in another terminal:
curl http://localhost:3000/health
curl http://localhost:3000/users
```

## Understanding Probes

The three probes fire in sequence and serve different purposes:

| Probe | Question | On failure |
| ----- | -------- | ---------- |
| startup | Has the app finished initializing? | Restart (up to threshold) |
| liveness | Is the process still alive? | Restart the container |
| readiness | Is the container ready to serve traffic? | Remove from Service endpoints |

Kubernetes runs the startup probe first. Only once it passes does k8s begin polling liveness and readiness.

**Startup probe**: uses a high `failureThreshold` (30 × 2s = 60s window) to give the app time for expensive one-time work that you don't want re-checked every few seconds at runtime. Example: startup probe waits for a 2GB ML model to load into memory (could take 30–90s); readiness probe then checks that a test inference completes within a latency threshold. Once the startup probe passes, it retires permanently.

**Liveness probe**: checks only that the process is still responding. In real apps, liveness rarely checks anything beyond "is the process responding." Some add a deadlock check (e.g., JVM apps) or verify the event loop isn't blocked. The rule: if the fix requires a restart, fail liveness; if the fix is waiting or upstream recovery, fail readiness instead. `/live` always returns 200. It only confirms the process is running, never checks the DB. If the DB goes down temporarily, liveness should NOT restart healthy pods.

**Readiness probe**: reflects dynamic runtime state that startup never sees: circuit breaker open/closed, downstream service degraded, connection pool exhausted, or the pod entering graceful shutdown. A startup probe just fires once and retires; readiness keeps polling. `/health` returns 503 when the DB is unreachable, gating traffic so requests don't hit a pod that can't serve them.

Although startup and readiness both use `/health`, they have different budgets and objectives. Startup waits out a one-time initialization window; readiness checks ongoing runtime health every few seconds.

If the pod shows restarts at startup, `checkDB()` failed (postgres unreachable) and the app called `process.exit(1)`. Kubernetes saw the container exit and restarted it with exponential backoff (10s → 20s → 40s → ...).

### Startup probe flow in the app

The app simulates expensive startup work (`setTimeout` for 15s) so you can observe this in real time:

```text
t=0s   Express starts listening. /live → 200, /health → 503 (dbReady=false)
t=0s   Startup probe fires its first check → 503. Failure 1/30. k8s waits.
t=2s   Startup probe fires again → 503. Failure 2/30. Still waiting.
  ...  (every 2s, 503 - heavy work is still running)
t=15s  setTimeout resolves. checkDB() runs. dbReady becomes true.
t=16s  Startup probe fires → 200. Startup probe PASSES and retires.
t=16s  k8s begins polling liveness (/live) and readiness (/health).
t=16s  Readiness probe passes → pod enters Ready state (READY 1/1).
```

Key observations:

- `/live` returned 200 the entire time. The liveness probe would never have killed the pod even if it had been running.
- The startup probe's 60s budget (30 × 2s) comfortably covers the 15s delay plus DB init time.
- If the heavy work had taken longer than 60s, the startup probe would exceed `failureThreshold` and the container would be restarted, same as a crash.

To watch this live:

```bash
kubectl get pod users-api -w           # watch READY flip from 0/1 → 1/1
kubectl logs users-api -f              # see the "heavy startup tasks" log lines
kubectl describe pod users-api         # Events section shows each probe state change
kubectl get events --field-selector involvedObject.name=users-api -w
```

### What `get events` does and doesn't show

`kubectl get events` only surfaces abnormal conditions - probe failures, OOM kills, image pull errors, backoff restarts. It does **not** emit an event when the startup probe passes or when the pod becomes Ready. That transition happens silently.

This is by design: probes fire every few seconds, so emitting a success event each time would flood etcd and make events useless.

| What you want to know | Where to look |
| --------------------- | ------------- |
| Did startup probe pass? | `kubectl get pod` → `READY 1/1`, or `kubectl describe pod` → `Conditions` |
| Why did something fail? | `kubectl get events` - failures and crashes appear here |
| Probe failure detail | `kubectl describe pod` → `Events` section at the bottom |

The rule: **failures → events, success → status**. Use `kubectl get pod -w` to observe the Ready transition, not `get events`.

## What pods cannot do on their own

- `kubectl delete pod users-api`: the pod is gone permanently, nothing recreates it.
- No way to run multiple replicas.
- No stable DNS name or IP for other workloads to reach it.

All three are solved in s2 with Deployments and Services.

## Cleanup

```bash
kubectl delete pod users-api
docker compose -f local/docker-compose.yml down
```
