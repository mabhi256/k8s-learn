# s22 - Ambient Mesh + Gateway API (Istio)

> **Tag:** `s22`
>
> **Goal**: remove the per-Pod Envoy sidecar from s14. Move mTLS to a per-node `ztunnel` (L4), make the heavyweight L7 proxy an opt-in **waypoint**, and drive both edge and east-west routing through the Kubernetes **Gateway API** (`Gateway` + `HTTPRoute`) - the successor to the frozen `Ingress` resource. Same security guarantees as s14, a fraction of the footprint, and the modern routing API that s23 builds on.

s14 gave every Pod its own Envoy sidecar. That works, but its cost grows linearly with the fleet. This stage migrates the s14 mesh to ambient and swaps the s3 nginx-ingress for the Gateway API.

---

## What the sidecar cost us

Concretely, from s14:

| Pain | Sidecar model | Why it hurts |
| --- | --- | --- |
| **Per-Pod overhead** | Every Pod carries a full Envoy (~30-50MB, CPU). | A 200-Pod cluster runs 200 Envoys whether or not those Pods need L7 features. |
| **Upgrade = restart** | New Istio version → `rollout restart` every meshed workload to re-inject. | Disruptive, and couples mesh upgrades to app rollouts. |
| **Job / CronJob lifecycle** | The sidecar stays alive after the main container exits, so the Pod never reaches `Completed`. | s14 worked around this by *not* injecting Jobs (losing mTLS for them). |
| **Injection foot-guns** | Forgot the namespace label? | Silent plaintext. |

None of these are bugs. They're inherent to "one proxy per Pod." Ambient changes the unit of deployment.

---

## Two layers: ztunnel and waypoint

Ambient splits the sidecar's job into two independent layers. You always get L4; you opt into L7 only where you need it.

| Layer | Component | Scope | Handles | Cost |
| --- | --- | --- | --- | --- |
| **L4 (secure overlay)** | `ztunnel` | One per node (DaemonSet) | mTLS, L4 authorization, TCP telemetry | Tiny, shared by every Pod on the node |
| **L7 (optional)** | waypoint | One per namespace or service (Envoy `Deployment`) | HTTP routing, retries, timeouts, traffic splitting, L7 authz, circuit breaking | Only deployed where L7 is actually needed |

In ambient mode, **mTLS is no longer tied to a proxy in your Pod.** A Pod joins the mesh by a namespace label. No sidecar, no restart. L7 features (`VirtualService`/`DestinationRule` equivalents) move to a separate waypoint proxy. Traffic only passes through it when a route or policy requires it.

```text
                         ┌────────────────────────────────┐
                         │             istiod             │
                         │  - issues SPIFFE certs         │
                         │  - pushes xDS to ztunnels      │
                         │    and waypoints               │
                         └─────┬────────────────────┬─────┘
              certs + xDS      │                    │  xDS
              ┌────────────────┘                    └──────────────┐
   ┌──────────┴───────────────┐              ┌─────────────────────┴────┐
   │ node A                   │              │ node B                   │
   │  ┌────────────────────┐  │   HBONE      │  ┌────────────────────┐  │
   │  │ ztunnel (DaemonSet)│  │   mTLS       │  │ ztunnel (DaemonSet)│  │
   │  │ L4, :15008         │◀─┼──────────────┼─▶│ L4, :15008         │  │
   │  └─────────┬──────────┘  │  (ciphertext)│  └─────────┬──────────┘  │
   │   capture  │ istio-cni   │              │   capture  │ istio-cni   │
   │  ┌─────────┴──────────┐  │              │  ┌─────────┴──────────┐  │
   │  │ users-api (no SC)  │  │              │  │ notify-api (no SC) │  │
   │  └────────────────────┘  │              │  └────────────────────┘  │
   └──────────────────────────┘              └──────────────────────────┘

  When L7 is required, ztunnel routes through a waypoint first:

  users-api ─▶ ztunnel ─▶ [ waypoint: Envoy, per-ns ] ─▶ ztunnel ─▶ notify-api
                            ┌─────────────────────┐
                            │ HTTPRoute/GRPCRoute │
                            │ weights · retries   │
                            │ timeouts · L7 authz │
                            │ outlier detection   │
                            └─────────────────────┘
```

`SC` = sidecar. 
`SPIFFE` = Secure Production Identity Framework for Everyone. The standard that defines how workloads get a cryptographic identity (a SPIFFE ID, formatted as `spiffe://<trust-domain>/ns/<namespace>/sa/<serviceaccount>`) so mTLS can be tied to a service, not an IP.
`xDS` = the Envoy config API family (Listener/Route/Cluster/Endpoint Discovery Service) that istiod uses to push routes and policies to proxies. 

### ztunnel and HBONE

ztunnel ("zero-trust tunnel") is a per-node Rust proxy. istio-cni redirects each Pod's traffic into the node's ztunnel. ztunnel uses the same SPIFFE identities as the s14 sidecars and encrypts traffic between nodes via **HBONE** (HTTP-Based Overlay Network Environment): mutual-TLS inside an HTTP/2 `CONNECT` on port **15008**.

> **`istio-cni` is not a CNI plugin.** Despite having "CNI" in it, `istio-cni` is an Istio-internal DaemonSet that hooks into the CNI plugin chain only to set up iptables intercept rules that redirect Pod traffic into ztunnel (ambient) or the sidecar (s14). The actual CNI job (assigning pod IPs, routing between nodes) is still done by Calico, Cilium, kindnet, or whatever CNI the cluster was installed with. Without a CNI underneath, Pods would never get IP addresses and `istio-cni` would have no traffic to intercept.

`tcpdump` between two nodes shows TLS ciphertext on `:15008`, not protobuf. The only difference is *who* encrypts it - a shared node proxy instead of a sidecar present per Pod.

### Waypoints and the L7 layer

A **waypoint** is an Envoy `Deployment` which routes L7 traffic. You deploy one per namespace (default) or per service-account / service. It enforces:

- `HTTPRoute` / `GRPCRoute` rules (routing, weighted traffic splitting, header matching).
- Retries, timeouts.
- L7 `AuthorizationPolicy` (by method, path, header).
- Outlier detection / circuit breaking (the s14 `DestinationRule` job).

Crucially, **L4 needs no waypoint** (ztunnel does mTLS and L4 authz for free), and **L7 requires one**. If you only need encryption and identity-based allow/deny, you never deploy a waypoint at all. That's the cost saving: in a 200-Pod cluster, maybe three namespaces run a waypoint each, instead of 200 sidecars.

| Use case | Realistic example |
| --- | --- |
| **L7 AuthorizationPolicy** | Only `checkout-service` can `POST /v1/charge` on `payment-api`; every other caller gets 403 at the proxy |
| **Retry on specific status codes** | Retry on `503` with 1 s backoff - rolling deploys when the old pod is gone but the new one isn't ready yet. |
| **JWT validation** | Validate OIDC tokens from your IdP at the mesh layer before the request reaches the app. Invalid tokens are rejected by the waypoint; your service never needs auth middleware. |
| **Traffic mirroring** | Mirror 5 % of production traffic to a shadow `v2` deployment to load-test before the canary goes live - no user impact, real traffic shape. |
| **Canary routing** | Route 5 % of production traffic to `v2` canary - real users. |
| **Fault injection** | Inject a 200 ms delay on 10 % of requests to `inventory-api` to check whether `orders-api` handles slow upstreams gracefully. Standard game-day exercise. |
| **Outlier detection** | Eject a pod from the load-balancing pool after 3 consecutive 5xx responses. Prevents a single bad instance from dragging p99 latency up while an on-call engineer investigates. |

## Gateway API

The Gateway API is the successor to the Ingress API. It is a more expressive, role-oriented way to configure traffic routing in Kubernetes.

### The problem

The `Ingress` API combined listener config, TLS, and routing into a single resource, forcing controllers to express every difference through annotations, with no clear boundary between infrastructure ownership and routing ownership.

Gateway API separates **infrastructure** (`Gateway`, owned by ops) from **routing** (`HTTPRoute`, owned by app teams), and standardizes traffic splitting and header matching into the spec instead of vendor annotations.

### The resources

| Resource | Scope | What it does | Who owns it |
| --- | --- | --- | --- |
| `GatewayClass` | Cluster | Defines the controller implementation (e.g., Envoy, nginx) | Platform / Cluster operator |
| `Gateway` | Namespace | An actual proxy instance with listeners (ports, hostnames, TLS) | Infra team |
| `HTTPRoute` | Namespace | Routing rules: match → backend, with weights | App team |
| `GRPCRoute` | Namespace | Same, gRPC-aware (method-level matching) | App team |

Istio ships two `GatewayClass`es:

- `istio`: north-south ingress. Istio auto-provisions an Envoy `Deployment` + `Service` at the edge (the replacement for nginx-ingress and for the old Istio `Gateway` CRD).
- `istio-waypoint`: east-west. This *is* a waypoint proxy.

### North-south vs east-west (GAMMA)

An `HTTPRoute` attaches to a parent via `parentRefs`. The parent type determines the traffic direction:

- **North-south** (`parentRef` → `Gateway`): handles external traffic entering the cluster at the edge proxy.
- **East-west** (`parentRef` → `Service`): handles in-cluster traffic between services via **GAMMA** (Gateway API for Mesh). It the same `HTTPRoute` kind, but attached to a Service and enforced by that service's waypoint proxy. It replaces Istio's `VirtualService` for mesh traffic.

In s22 this means two migrations:

- the s14 `VirtualService` (east-west canary) becomes `HTTPRoute` attached to the `users-api` Service
- the s3 `Ingress` becomes a `Gateway` + `HTTPRoute`

## Setup

The two data planes (sidecar / ambient) can coexist during migration, which is how you'd do it on a live cluster.

> **Coming from s14?** s14 uses `istioctl install --set profile=demo -y`, which manages state outside of Helm. You cannot layer the Helm charts on top — Helm has no record of the existing install and will conflict. Uninstall `istioctl`-managed Istio first, then follow the Helm steps below:
>
> ```bash
> kubectl label namespace default istio-injection-   # remove sidecar label
> istioctl uninstall --purge -y
> kubectl delete namespace istio-system
> ```

1. **Reinstall Istio with the ambient profile** (adds `ztunnel` DaemonSet + `istio-cni`; keeps `istiod`):

   Ambient mode ships as four separate Helm charts. Install them in order — each one depends on the previous.

   ```bash
   helm repo add istio https://istio-release.storage.googleapis.com/charts
   helm repo update

   kubectl create namespace istio-system

   # CRDs + cluster-wide resources
   helm install istio-base istio/base -n istio-system --set defaultRevision=default

   # Control plane
   helm install istiod istio/istiod -n istio-system --set profile=ambient --wait

   # CNI node agent — redirects pod traffic into ztunnel
   helm install istio-cni istio/cni -n kube-system --set profile=ambient

   # ztunnel DaemonSet (per-node L4 proxy)
   helm install ztunnel istio/ztunnel -n istio-system --wait
   ```

   ```bash
   ## istioctl equivalent (imperative, not GitOps-friendly):
   # istioctl install --set profile=ambient -y
   ```

   > **Ubuntu / kind gotcha - "too many open files":** if `istio-cni-node` and `ztunnel` pods crash immediately with inotify errors, the host kernel limits are exhausted. Fix on the host before retrying:
   >
   > ```bash
   > sudo sysctl fs.inotify.max_user_instances=512
   > sudo sysctl fs.inotify.max_user_watches=524288
   >
   > # persist across reboots:
   > echo "fs.inotify.max_user_instances=512"  | sudo tee -a /etc/sysctl.conf
   > echo "fs.inotify.max_user_watches=524288" | sudo tee -a /etc/sysctl.conf
   > sudo sysctl -p
   > ```
   >
   > The pods recover on their own after the limits are raised.

2. **Install the Gateway API CRDs**:

   ```bash
   kubectl get crd gateways.gateway.networking.k8s.io >/dev/null 2>&1 || \
     kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.5.1/standard-install.yaml
   ```

3. **Keep `PeerAuthentication` `PERMISSIVE`** mesh-wide so sidecar Pods, ambient Pods, and not-yet-migrated Pods all interoperate (same lesson as s14).

   **kubectl**: check that no mesh-wide PeerAuthentication exists (cluster default is PERMISSIVE):

   ```bash
   kubectl get peerauthentication -A
   # No resources found
   ```

   **Helm**: verify the users-api chart is not carrying a STRICT override from s14:

   ```bash
   helm get values users-api -n default
   # USER-SUPPLIED VALUES:
   # null
   ```

   `null` means `istio.peerAuthentication.enabled=false`, so the mesh defaults to PERMISSIVE. If it shows `STRICT`, the step 5 Helm upgrade set it to `false` alongside disabling the L7 templates.

4. **Per namespace**: remove the sidecar injection label, add the ambient label, and restart once to shed the sidecars:

   ```bash
   kubectl label ns default istio-injection-                       # stop injecting
   kubectl label ns default istio.io/dataplane-mode=ambient        # join ambient
   kubectl rollout restart deploy,statefulset -n default           # drop existing sidecars
   ```

5. **Remove the s14 sidecar-era L7 resources and the s3 Ingress**:

   - `k8s/istio/virtual-service.yaml` → `HTTPRoute` (`httproute-canary.yaml`, `httproute-edge.yaml`).
   - `k8s/istio/destination-rule.yaml` → per-version Services + `HTTPRoute` `backendRefs`; outlier detection moves onto the waypoint.
   - The s3 nginx `Ingress` → `Gateway` + `HTTPRoute`.

   The frontend `Ingress` is a standalone manifest (`k8s/ingress.yaml`) — no chart wraps it, so use `kubectl delete` for that one.

   ```bash
   kubectl delete -f k8s/ingress.yaml
   ```

   **Helm (disable the templates via chart values):**

   ```bash
   # Turn off all s14 Istio templates in one shot
   helm upgrade users-api ./helm/users-api -n default \
     --reuse-values \
     --set istio.peerAuthentication.enabled=false \
     --set istio.virtualService.enabled=false \
     --set istio.destinationRule.enabled=false
   ```

   ```bash
   ## kubectl equivalent 
   # kubectl delete -f k8s/istio/virtual-service.yaml
   # kubectl delete -f k8s/istio/destination-rule.yaml
   ```

6. **Deploy the Istio Gateway and HTTPRoute** (replaces the nginx Ingress deleted above):

   `k8s/gateway/gateway.yaml` declares two listeners — HTTP on 80 and HTTPS on 443 with TLS termination using the cert-manager `demo-local-tls` secret created in s3.

   `k8s/gateway/httproute-edge.yaml` adds a `URLRewrite` filter on the `/api` rule to strip the prefix before forwarding — the same role that nginx's `rewrite-target: /$2` annotation played. The `backendRef` port must match the Service's exposed port (80), not the container port (3000).

   Apply both:

   ```bash
   kubectl apply -f k8s/gateway/gateway.yaml
   kubectl apply -f k8s/gateway/httproute-edge.yaml

   # Istio auto-creates the gateway Deployment + Service — wait for an IP:
   kubectl get svc -l gateway.networking.k8s.io/gateway-name=demo-gateway
   ```

   The `default-deny-ingress` NetworkPolicy blocks all ingress to pods in `default` by default, including the auto-provisioned `demo-gateway-istio` pod. Apply the gateway NetworkPolicy to allow external traffic on ports 80 and 443:

   ```bash
   kubectl apply -f k8s/network-policies/gateway.yaml
   ```

   Update `/etc/hosts` to point `demo.local` at the new Istio gateway IP instead of the old nginx ingress IP. Also add `grafana.demo.local` — it uses the nginx ingress controller (deployed in s12), which has a different IP from the Istio gateway:

   ```bash
   GATEWAY_IP=$(kubectl get svc -l gateway.networking.k8s.io/gateway-name=demo-gateway \
     -o jsonpath='{.items[0].status.loadBalancer.ingress[0].ip}')
   sudo sed -i "s/.*demo\.local/$GATEWAY_IP demo.local/" /etc/hosts

   GRAFANA_IP=$(kubectl get ingress prom-grafana -n lgtm \
     -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
   # Add if not present, update if already there:
   grep -q "grafana\.demo\.local" /etc/hosts \
     && sudo sed -i "s/.*grafana\.demo\.local/$GRAFANA_IP grafana.demo.local/" /etc/hosts \
     || echo "$GRAFANA_IP grafana.demo.local" | sudo tee -a /etc/hosts

   grep demo.local /etc/hosts   # verify both entries
   ```

   The `users-api` and `frontend` NetworkPolicies also need updating: add the gateway pod as an allowed source, and add port 15008 so ztunnel can tunnel traffic to them (same fix already applied to postgres in the HBONE gotcha below):

   ```bash
   kubectl apply -f k8s/network-policies/users-api.yaml
   kubectl apply -f k8s/network-policies/frontend.yaml
   ```

   Verify end-to-end:

   ```bash
   curl -sk https://demo.local/api/users   # should return JSON
   curl -sk -o /dev/null -w "%{http_code}" https://demo.local/   # should return 200
   ```

8. **Deploy a waypoint** only for namespaces/services that need L7 (the canary, retries, L7 authz):

   **Preferred (GitOps):**
   ```bash
   kubectl apply -f k8s/gateway/waypoint.yaml
   kubectl label service users-api istio.io/use-waypoint=default-waypoint
   ```

   **Imperative (quick test only):**
   ```bash
   # istioctl waypoint apply --namespace default --enroll-namespace
   ```

   > **`--enroll-namespace` labels the namespace, not individual services.**
   >
   > `istioctl waypoint apply --enroll-namespace` creates the `Gateway` object **and** adds `istio.io/use-waypoint=default-waypoint` to the `default` **namespace**. It does not touch individual services.
   >
   > The separate `kubectl label service users-api ...` step labels the **service** object specifically. These are two different opt-in scopes:
   > - **Namespace label** → all services in the namespace route through the waypoint
   > - **Service label** → only that service routes through the waypoint (more granular)
   >
   > If you ran `istioctl waypoint apply --enroll-namespace` first and then `kubectl label service users-api ...`, the service label is redundant (both point to the same waypoint) but harmless. The service-level label is more specific and takes precedence if they ever conflict.

   > **Why declarative, not `istioctl` or Helm?**
   >
   > - **Not Helm** — The waypoint is a namespace-scoped runtime object (`Gateway` + a generated `Deployment`), not part of the Istio control-plane Helm charts. Helm manages the Istio infrastructure (istiod, ztunnel, CNI); the waypoint is an optional, per-namespace concern that belongs with your app manifests, not the platform layer.
   >
   > - **Not `istioctl waypoint apply`** — This is an imperative command: it creates the object in-cluster but nothing is committed to git. If the cluster is rebuilt or the namespace is recreated, the waypoint is gone with no record of it. It's fine for local experimentation but breaks GitOps.
   >
   > - **Yes `kubectl apply -f`** — The YAML lives in `k8s/gateway/waypoint.yaml`, is committed to the repo, and can be reconciled by Argo CD / Flux like any other manifest. This is the GitOps-correct approach.

   Then deploy the canary — one Service per version replaces the s14 `DestinationRule` subsets, and the `HTTPRoute` sets the 90/10 weight split:

   ```bash
   kubectl apply -f k8s/users-api/services-v1-v2.yaml   # one Service per version
   kubectl apply -f k8s/gateway/httproute-canary.yaml   # 90/10 weighted split

   # Generate traffic and watch the split in Grafana (s12 dashboards + Istio metrics):
   hey -z 60s -c 20 https://demo.local/api/users
   ```

9. **Flip back to `STRICT`** once everything is on ztunnel and all NetworkPolicies allow port 15008 (see gotcha #4):

   **Helm (matches how s14 set STRICT):**

   ```bash
   helm upgrade users-api ./helm/users-api -n default \
     --reuse-values \
     --set istio.peerAuthentication.enabled=true \
     --set istio.peerAuthentication.mode=STRICT
   ```
   
   ```bash
   ## kubectl equivalent
   # kubectl apply -f k8s/istio/peer-authentication.yaml   # mode: STRICT
   ```

> **Preview (s15)**: ambient removes the never-completing sidecar problem that affects Jobs in sidecar mode. A Job pod can exit cleanly because there's no envoy to drain. You'll see this with CronJobs in s15.

## mTLS and authorization in ambient

`PeerAuthentication` is unchanged from s14 (`STRICT`, `PERMISSIVE`, `DISABLE`) but ztunnel enforces it at L4 instead of a sidecar. Within the mesh, traffic is mTLS by default.

`AuthorizationPolicy` splits by layer:

| Policy granularity | Enforced by | Waypoint required? |
| --- | --- | --- |
| L4: source identity (SPIFFE), port | ztunnel | No |
| L7: HTTP method, path, header, JWT claims | waypoint | **Yes** |

So "allow only `frontend` to call `users-api`" needs no waypoint. "Allow `frontend` to `GET /users` but not `DELETE`" needs one. If you write an L7 policy without a waypoint, Istio can't enforce the L7 conditions.

## Sidecar (s14) vs ambient (s22)

| | Sidecar (s14) | Ambient (s22) |
| --- | --- | --- |
| Data plane unit | Envoy per Pod | ztunnel per node + optional waypoint per ns/service |
| Join the mesh | Inject sidecar, restart Pod | Label namespace, no restart |
| mTLS (L4) | Sidecar | ztunnel |
| L7 features | Always present (every sidecar is full Envoy) | Only where a waypoint is deployed |
| Per-Pod overhead | ~30-50MB each | ~0 (shared node ztunnel) |
| Data-plane upgrade | `rollout restart` every workload | Roll the ztunnel DaemonSet; Pods untouched |
| Readiness gate | `istio.io/ready` on every Pod | None |
| Jobs/CronJobs | Sidecar blocks completion | Complete normally |
| L7 traffic API | `VirtualService` + `DestinationRule` | Gateway API `HTTPRoute` / `GRPCRoute` |

Ambient is the recommended model for new installs. Sidecar is still fully supported and is what most existing production meshes run.

## Try to break it

### 1. L7 policy with no waypoint

Apply an `AuthorizationPolicy` that matches on HTTP method or path, but don't deploy a waypoint:

```yaml
spec:
  rules:
    - to:
        - operation:
            methods: ["DELETE"]   # L7 condition
```

ztunnel can't see L7, so the rule silently doesn't apply the way you expect. `DELETE` still gets through (or the whole policy is treated as L4-only). `istioctl analyze` flags it. Fix: enroll the service in a waypoint.

### 2. HTTPRoute backendRef points at a non-existent Service

```yaml
backendRefs:
  - name: users-api-v3   # doesn't exist
    port: 3000
```

The `HTTPRoute` status shows a `ResolvedRefs: False` condition with reason `BackendNotFound`. Traffic to that weight is dropped (returns 500s). Always check `kubectl describe httproute` after applying. The route's `status.parents[].conditions` is the Gateway API equivalent of `istioctl analyze`.

### 3. Forgot the Gateway API CRDs

```bash
kubectl apply -f k8s/gateway/gateway.yaml
# error: no matches for kind "Gateway" in version "gateway.networking.k8s.io/v1"
```

kind doesn't ship the Gateway API CRDs. They are not part of core Kubernetes. Install them separately (command above). This is the #1 first-time stumble.

### 4. NetworkPolicy blocks HBONE port 15008 → startup crash loop

In ambient mode, all pod-to-pod mTLS traffic is tunneled by ztunnel over **HBONE on port 15008**. If you have a `default-deny-ingress` NetworkPolicy (common with mesh security setups), your pod-specific allow rules must include port 15008 or the ztunnel can't reach the destination.

Symptom: pods crash in `CrashLoopBackOff` with the startup probe failing:

```
error="connection timed out, maybe a NetworkPolicy is blocking HBONE port 15008: deadline has elapsed"
```

The app's heavy startup task (e.g. DB connection) never succeeds, `/health` stays 503 forever, and the startup probe eventually kills the pod. This can look like a probe misconfiguration when the real issue is a blocked outbound tunnel.

Fix: add port 15008 alongside your application port in every NetworkPolicy in the ambient namespace — not just the DB. In this setup that means `postgres.yaml`, `users-api.yaml`, and `frontend.yaml`:

```yaml
ports:
  - port: 5432    # application port
    protocol: TCP
  - port: 15008   # HBONE — required for ztunnel mTLS tunneling
    protocol: TCP
```

Any service that receives mesh traffic in the ambient namespace needs port 15008 open in its ingress NetworkPolicy. Check all policies if you see the timeout error.

### 5. Namespace labeled for both injection and ambient

```bash
kubectl label ns default istio-injection=enabled
kubectl label ns default istio.io/dataplane-mode=ambient
```

A Pod can't be in both data planes. Istio rejects/ignores the ambient enrollment for sidecar-injected Pods. Pick one per namespace; during migration, remove `istio-injection` before adding the ambient label.

### 6. Gateway pod blocked by default-deny → 503 on every request

When Istio provisions the `demo-gateway-istio` pod, it is subject to the same `default-deny-ingress` NetworkPolicy as every other pod in `default`. There is no allow rule for it out of the box, so external traffic on ports 80 and 443 is silently dropped.

Symptom: TLS handshake succeeds (the pod accepts TCP) but every request returns 503 `connection_termination` immediately. Enabling debug logging on the gateway shows `upstream_reset_before_response_started` with a ~10 s delay (the upstream connect timeout), not a fast 4xx.

Diagnosis: check that a NetworkPolicy allows the gateway pod:

```bash
kubectl get networkpolicy -n default
# look for a policy targeting gateway.networking.k8s.io/gateway-name=demo-gateway
```

Fix: `k8s/network-policies/gateway.yaml` — no `from` selector is needed because the traffic comes from outside the cluster (LoadBalancer):

```yaml
podSelector:
  matchLabels:
    gateway.networking.k8s.io/gateway-name: demo-gateway
ingress:
  - ports:
      - port: 80
      - port: 443
```

### 7. Path prefix not stripped → 500 from users-api

The s3 nginx Ingress used `nginx.ingress.kubernetes.io/rewrite-target: /$2` to strip `/api` before forwarding. Without the equivalent in the HTTPRoute, a request to `/api/users` arrives at users-api as `/api/users`, which is not a valid route and returns 500.

Symptom: `curl https://demo.local/api/users` returns 500; `curl http://localhost:3000/users` from inside the pod returns 200.

Fix: add a `URLRewrite` filter with `ReplacePrefixMatch` on the `/api` rule in `httproute-edge.yaml`:

```yaml
filters:
  - type: URLRewrite
    urlRewrite:
      path:
        type: ReplacePrefixMatch
        replacePrefixMatch: /
```

### 8. backendRef port must be the Service port, not the container port → 503

The HTTPRoute `backendRef` resolves through the Service, so the port must be the Service's exposed port (80 for both `users-api` and `frontend`), not the container port (3000 for `users-api`). Using port 3000 in the `backendRef` gives a 503; the HTTPRoute status still shows `ResolvedRefs: True` because the Service exists — the mismatch is invisible to the status condition.

Diagnosis:

```bash
istioctl proxy-config clusters deploy/demo-gateway-istio.default | grep users-api
# shows port 80, not 3000 — match what the Service exposes
kubectl get svc users-api -o jsonpath='{.spec.ports[*].port}'
```

Fix: set `port: 80` in the `backendRef` to match the Service spec.

## Debugging cheatsheet

### ztunnel

```bash
# All ztunnel pods
kubectl logs -n istio-system -l app=ztunnel

# Follow in real time
kubectl logs -n istio-system -l app=ztunnel -f

# On a specific node
kubectl logs -n istio-system -l app=ztunnel \
  --field-selector spec.nodeName=<node-name>

# Filter for a specific pod's traffic (find its IP first)
kubectl get pod <pod> -o wide   # get IP
kubectl logs -n istio-system -l app=ztunnel | grep <pod-ip>

# Raise log level at runtime (no restart needed)
kubectl exec -n istio-system <ztunnel-pod> -- \
  curl -s -X POST localhost:15000/logging?level=debug

# Check which pods ztunnel sees as ambient-enrolled
kubectl get pods -n default -o wide
istioctl ztunnel-config workloads

# Verify mTLS is active between two pods
istioctl ztunnel-config connections --namespace default
```

### waypoint

```bash
# Find the waypoint pod (it's a regular Deployment in your app namespace)
kubectl get pods -n default -l gateway.networking.k8s.io/managed-by=istio

# Live logs
kubectl logs -n default -l gateway.networking.k8s.io/managed-by=istio -f

# Filter for a specific upstream or route
kubectl logs -n default -l gateway.networking.k8s.io/managed-by=istio | grep users-api

# Raise log level at runtime
WAYPOINT=$(kubectl get pod -n default -l gateway.networking.k8s.io/managed-by=istio \
  -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n default $WAYPOINT -- \
  curl -s -X POST localhost:15000/logging?level=debug

# Check Envoy listener/route/cluster config on the waypoint
istioctl proxy-config listeners deploy/default-waypoint.default
istioctl proxy-config routes deploy/default-waypoint.default
istioctl proxy-config clusters deploy/default-waypoint.default

# Confirm a service is enrolled in the waypoint
kubectl get service users-api -o jsonpath='{.metadata.labels}'
# should show: "istio.io/use-waypoint":"default-waypoint"

# Check waypoint status (is the Gateway Accepted/Programmed?)
kubectl get gateway default-waypoint -n default
kubectl describe gateway default-waypoint -n default
```
