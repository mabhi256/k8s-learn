# s15 - Jobs, CronJobs, and DaemonSets

> **Tag:** `s15`
> Goal: run work that isn't a long-lived HTTP server. Use a Job for one-off DB migrations, a CronJob for recurring backups, and understand DaemonSets (already seen in s12 via Alloy and node-exporter).

Every workload so far has been a Deployment: a process that runs forever and gets replaced when it crashes. But some work is finite (run a migration, seed data) or scheduled (nightly backup). Kubernetes has first-class primitives for both.

---

## The three workload types

| Workload | Controller | Lifetime | Restarts on failure? | Example |
| --- | --- | --- | --- | --- |
| **Deployment** | ReplicaSet | Forever (until deleted) | Yes, always | users-api, notify-api |
| **Job** | Job controller | Until completion | Yes, up to `backoffLimit` | DB migration, data import |
| **CronJob** | CronJob controller | Creates a Job on schedule | Per the Job's policy | pg_dump backup, report generation |
| **DaemonSet** | DaemonSet controller | Forever, one per node | Yes, always | Alloy (s12), node-exporter, kube-proxy |

---

## Jobs

A Job creates one or more Pods and ensures a specified number of them successfully terminate. Once the required number of completions is reached, the Job is complete.

| Field | Default | What it does |
| --- | --- | --- |
| `spec.completions` | 1 | How many Pods must succeed for the Job to be "Complete". |
| `spec.parallelism` | 1 | How many Pods to run concurrently. |
| `spec.backoffLimit` | 6 | How many retries before marking the Job as "Failed". Exponential backoff (10s, 20s, 40s, ...). |
| `spec.activeDeadlineSeconds` | none | Hard timeout. If the Job hasn't finished by then, all Pods are killed and the Job is marked Failed. |
| `spec.ttlSecondsAfterFinished` | none | Auto-delete the Job (and its Pods) N seconds after completion. Without this, finished Jobs pile up. |

### Completion modes

| Mode | Behavior |
| --- | --- |
| `NonIndexed` (default) | Each Pod is identical. Job succeeds when `completions` Pods have exited 0. |
| `Indexed` | Each Pod gets an index (0, 1, 2, ...) via `JOB_COMPLETION_INDEX` env var. Use for parallel batch processing where each Pod handles a slice of work. |

### initContainers vs standalone Jobs for DB migrations

Two patterns for running a migration before the app starts:

| Pattern | How it works | Trade-off |
| --- | --- | --- |
| **initContainer** | Migration container runs inside the app Pod, before the app container starts. Pod only becomes Ready after the migration succeeds. | Simple. But every Pod runs the migration on startup (idempotent SQL handles this). Blocks rolling updates if the migration is slow. |
| **Standalone Job** | A separate Job runs the migration. The Deployment waits (or doesn't). | Decoupled. Migration runs once. But you need orchestration (Helm hooks, ArgoCD sync waves) to order Job-before-Deployment. |

For this stage we use the initContainer pattern. It's simpler and doesn't require orchestration. Flyway and golang-migrate both support idempotent execution (skip already-applied migrations), so running them per-Pod is safe.

## CronJobs

A CronJob creates a Job on a cron schedule. The schedule uses standard cron syntax (5 fields: minute, hour, day-of-month, month, day-of-week).

| Field | Default | What it does |
| --- | --- | --- |
| `spec.schedule` | required | Cron expression. `"0 2 * * *"` = daily at 2 AM UTC. |
| `spec.timeZone` | UTC | IANA time zone (e.g. `"America/New_York"`). Available since K8s 1.27. |
| `spec.concurrencyPolicy` | `Allow` | What to do if the previous Job is still running when the next one fires. |
| `spec.startingDeadlineSeconds` | none | If the CronJob misses its window by this many seconds, skip it. |
| `spec.successfulJobsHistoryLimit` | 3 | How many completed Jobs to keep (for log inspection). |
| `spec.failedJobsHistoryLimit` | 1 | How many failed Jobs to keep. |

### Concurrency policies

| Policy | Behavior |
| --- | --- |
| `Allow` | Multiple Jobs can run simultaneously. Fine if they don't conflict. |
| `Forbid` | Skip the new Job if the previous one is still running. Use for exclusive work (backup that holds a lock). |
| `Replace` | Kill the running Job and start a new one. Use when only the latest run matters. |

### pg_dump as a CronJob

A `pg_dump` backup is the classic CronJob example: run nightly, dump Postgres to a file, store it somewhere. In kind, "somewhere" is a PVC. In production, it's S3 via a sidecar or the backup tool's native S3 support.

The Pod needs the Postgres credentials. Reference the same Secret the app uses (`users-api` Secret from s5). Use `PGPASSWORD` or a `.pgpass` file so `pg_dump` doesn't prompt.

## DaemonSets

A DaemonSet ensures exactly one Pod runs on every (or a subset of) node(s). When a new node joins, the DaemonSet controller schedules a Pod on it. When a node is removed, the Pod is garbage collected.

We've already used DaemonSets in s12: Alloy (log shipping) and node-exporter (node metrics) are both DaemonSets from their respective Helm charts. kube-proxy is a DaemonSet too.

### When to use a DaemonSet

- **Node-level agents:** log shippers, monitoring agents, security scanners.
- **Storage plugins:** CSI node drivers (EBS CSI in s24).
- **Network plugins:** Calico (s7), kube-proxy, Cilium.

You rarely write your own DaemonSet for application workloads. They're almost exclusively for infrastructure.

### Scheduling

DaemonSets ignore most scheduling constraints (affinity, taints) by default. To restrict a DaemonSet to a subset of nodes, use `spec.template.spec.nodeSelector` or `spec.template.spec.affinity`. Tolerations let it run on tainted nodes (e.g. control-plane nodes).

## Commands

```bash
# 1. Apply the migration initContainer change (re-deploy users-api)
#    After updating the deployment YAML to include the flyway initContainer:
kubectl apply -f k8s/users-api/deployment.yaml
kubectl rollout status deploy/users-api

# Or via Helm (if using the chart):
helm upgrade users-api helm/users-api -n default

# 2. Run a one-off data seed Job
kubectl apply -f k8s/jobs/db-seed.yaml
kubectl get jobs -w
# Wait for COMPLETIONS to show 1/1

# Inspect logs
kubectl logs job/db-seed

# 3. Apply the backup CronJob
kubectl apply -f k8s/jobs/db-backup.yaml
kubectl get cronjobs

# Trigger it manually (don't wait for the schedule)
kubectl create job --from=cronjob/db-backup db-backup-manual
kubectl logs job/db-backup-manual
```

### Verify

```bash
# Check the initContainer ran before the app
kubectl describe pod -l app=users-api | grep -A5 "Init Containers"
# Should show the migration container with State: Terminated, Reason: Completed

# Check the CronJob's history
kubectl get jobs -l app=db-backup
# successfulJobsHistoryLimit keeps the last 3

# Check the backup PVC
kubectl exec -it deploy/postgres -- ls -la /backups/
```

## What this looks like on AWS

| s15 (kind) | EKS / AWS |
| --- | --- |

## Try to break it

### 1. initContainer fails, app never starts

Point the migration container at the wrong database host:

```bash
kubectl describe pod -l app=users-api
# Init Containers:
#   migrate:
#     State: Waiting
#       Reason: CrashLoopBackOff
```

The app container never starts. The Pod stays in `Init:CrashLoopBackOff` state. This is by design: a failed migration should not let a broken schema serve traffic. Fix the connection string and the Pod will start.

### 2. CronJob piles up failed Jobs

Set `backoffLimit: 0` and point pg_dump at a wrong host. Every cron tick creates a new Job that fails immediately:

```bash
kubectl get jobs
# db-backup-28535820   0/1   ... Failed
# db-backup-28535880   0/1   ... Failed
# db-backup-28535940   0/1   ... Failed
```

With `concurrencyPolicy: Allow`, these pile up. With `Forbid`, only one runs at a time but each still fails. `failedJobsHistoryLimit` controls how many corpses remain.

### 3. ttlSecondsAfterFinished missing

Run the seed Job 10 times. Without `ttlSecondsAfterFinished`, every completed Job and its Pod stay in the cluster:

```bash
kubectl get jobs
# db-seed-1   1/1   Completed   5m
# db-seed-2   1/1   Completed   4m
# ... 8 more
```

They're not harmful, but they clutter `kubectl get pods` (Completed pods), consume etcd storage, and make it hard to spot real issues. Always set `ttlSecondsAfterFinished` on one-off Jobs.

## Diff

### New: `k8s/jobs/db-seed.yaml`

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-seed
  namespace: default
spec:
  ttlSecondsAfterFinished: 300
  backoffLimit: 3
  template:
    metadata:
      labels:
        app: db-seed
    spec:
      restartPolicy: Never
      containers:
        - name: seed
          image: postgres:16
          command:
            - sh
            - -c
            - |
              psql "$DATABASE_URL" <<'SQL'
              INSERT INTO users (name, email)
              VALUES
                ('Alice', 'alice@example.com'),
                ('Bob', 'bob@example.com'),
                ('Charlie', 'charlie@example.com')
              ON CONFLICT (email) DO NOTHING;
              SQL
          env:
            - name: DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: users-api
                  key: DATABASE_URL
```

### New: `k8s/jobs/db-backup.yaml`

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: db-backup
  namespace: default
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      ttlSecondsAfterFinished: 86400
      backoffLimit: 2
      activeDeadlineSeconds: 600
      template:
        metadata:
          labels:
            app: db-backup
        spec:
          restartPolicy: Never
          containers:
            - name: backup
              image: postgres:16
              command:
                - sh
                - -c
                - |
                  TIMESTAMP=$(date +%Y%m%d-%H%M%S)
                  pg_dump "$DATABASE_URL" | gzip > "/backups/backup-${TIMESTAMP}.sql.gz"
                  echo "Backup written to /backups/backup-${TIMESTAMP}.sql.gz"
                  ls -lh /backups/
              env:
                - name: DATABASE_URL
                  valueFrom:
                    secretKeyRef:
                      name: users-api
                      key: DATABASE_URL
              volumeMounts:
                - name: backup-storage
                  mountPath: /backups
          volumes:
            - name: backup-storage
              persistentVolumeClaim:
                claimName: db-backups
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-backups
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
```

### Changed: `k8s/users-api/deployment.yaml`

Add a Flyway-style migration initContainer. The init container runs before the app starts and applies pending SQL migrations.

```diff
    spec:
      serviceAccountName: users-api
+     initContainers:
+       - name: migrate
+         image: postgres:16
+         command:
+           - sh
+           - -c
+           - |
+             psql "$DATABASE_URL" <<'SQL'

+               id SERIAL PRIMARY KEY,
+               name VARCHAR(255) NOT NULL,
+               email VARCHAR(255) UNIQUE NOT NULL,
+               created_at TIMESTAMP DEFAULT NOW()
+             );
+             SQL
+         env:
+           - name: DATABASE_URL
+             valueFrom:
+               secretKeyRef:
+                 name: users-api
+                 key: DATABASE_URL
      containers:
        - name: users-api
```
