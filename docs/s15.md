# s15 - Jobs, CronJobs, and DaemonSets

> **Tag:** `s15`
> Goal: run work that isn't a long-lived HTTP server. Use a Job for one-off DB migrations, a CronJob for recurring backups, and understand DaemonSets (already seen in s12 via Alloy and node-exporter).

Every workload so far has been a Deployment: a process that runs forever and gets replaced when it crashes. But some work is finite (run a migration, seed data) or scheduled (nightly backup). Kubernetes has first-class primitives for both.

---

## The three workload types

| Workload | Controller | Lifetime | Restarts on failure? | Example |
| --- | --- | --- | --- | --- |
| **Deployment** | ReplicaSet | Forever (until deleted) | Yes, always | users-api, notify-api |
| **Job** | Job controller | Until completion | Yes, up to `backoffLimit` | DB migration, data import |
| **CronJob** | CronJob controller | Creates a Job on schedule | Per the Job's policy | pg_dump backup, report generation |
| **DaemonSet** | DaemonSet controller | Forever, one per node | Yes, always | Alloy (s12), node-exporter, kube-proxy |

## initContainers

An initContainer is a special container that runs **before** any app containers start in a Pod. Kubernetes runs all init containers sequentially, waits for each to exit 0, then starts the main containers. If any init container fails, the whole Pod restarts.

```text
init-container-1 → init-container-2 → [all succeed] → app container starts
```

They share the same volumes and network namespace as the main containers, which makes them useful for setup work that must complete before the app is ready.

### Why we use an initContainer for migrations

The `users-api` Deployment includes a `migrate` initContainer that runs `CREATE TABLE IF NOT EXISTS users ...` via `psql` before the app starts:

- The schema is guaranteed to exist before the app container receives any traffic.
- If the migration fails (wrong DB host, bad credentials), the app never starts.
- It runs on every Pod start, which covers rolling updates and cluster restarts, not just the first boot.

### Why we removed the postgres init-configmap

We previously had a `postgres-init` ConfigMap mounted into Postgres at `/docker-entrypoint-initdb.d`. This is a Postgres feature — scripts in that directory run automatically when the database first boots with an empty data directory.

The problem: **it only runs once, ever.** The moment the PVC has data, Postgres ignores that directory completely. So the init-configmap never actually guarantees the schema exists — it just happened to create it the very first time we booted the cluster.

The initContainer on `users-api` solves this properly. It runs `CREATE TABLE IF NOT EXISTS` every time a `users-api` Pod starts — before the app comes up. This means:

- The app is always responsible for its own schema. It doesn't rely on Postgres being set up a specific way.
- It works on a fresh cluster, after a cluster restart, after a rolling update, or if you restore the PVC from a backup.
- If the schema creation fails for any reason, the Pod won't start — you get a clear signal instead of the app booting against a broken database.

The init-configmap was putting schema responsibility on the database layer (a Postgres implementation detail) rather than the application layer (where it belongs). The initContainer moves ownership to `users-api`.

## Jobs

A Job creates one or more Pods and ensures a specified number of them successfully terminate. Once the required number of completions is reached, the Job is complete.

| Field | Default | What it does |
| --- | --- | --- |
| `spec.completions` | 1 | How many Pods must succeed for the Job to be "Complete". |
| `spec.parallelism` | 1 | How many Pods to run concurrently. |
| `spec.backoffLimit` | 6 | How many retries before marking the Job as "Failed". Exponential backoff (10s, 20s, 40s, ...). |
| `spec.activeDeadlineSeconds` | none | Hard timeout. If the Job hasn't finished by then, all Pods are killed and the Job is marked Failed. |
| `spec.ttlSecondsAfterFinished` | none | Auto-delete the Job (and its Pods) N seconds after completion. Without this, finished Jobs pile up. |

### Completion modes

| Mode | Behavior |
| --- | --- |
| `NonIndexed` (default) | Each Pod is identical. Job succeeds when `completions` Pods have exited 0. |
| `Indexed` | Each Pod gets an index (0, 1, 2, ...) via `JOB_COMPLETION_INDEX` env var. Use for parallel batch processing where each Pod handles a slice of work. |

### initContainers vs standalone Jobs for DB migrations

Two patterns for running a migration before the app starts:

| Pattern | How it works | Trade-off |
| --- | --- | --- |
| **initContainer** | Migration container runs inside the app Pod, before the app container starts. Pod only becomes Ready after the migration succeeds. | Simple. But every Pod runs the migration on startup (idempotent SQL handles this). Blocks rolling updates if the migration is slow. |
| **Standalone Job** | A separate Job runs the migration. The Deployment waits (or doesn't). | Decoupled. Migration runs once. But you need orchestration (Helm hooks, ArgoCD sync waves) to order Job-before-Deployment. |

For this stage we use the initContainer pattern. It's simpler and doesn't require orchestration. Production-grade migration tools like Flyway and golang-migrate support idempotent execution (they track applied migrations in a `schema_migrations` table and skip already-done ones), so running them per-Pod is safe.

### Migration tool comparison

All three approaches use the same initContainer pattern — only the image and command differ.

#### Raw psql (this stage)

```yaml
- name: migrate
  image: postgres:16
  command: [sh, -c]
  args:
    - |
      psql "postgresql://$DB_USER:$DB_PASSWORD@$DB_HOST:$DB_PORT/$DB_NAME" <<'SQL'
      CREATE TABLE IF NOT EXISTS ...;
      SQL
  envFrom:
    - configMapRef:
        name: users-api-config
    - secretRef:
        name: users-api-secret
```

Idempotency is your responsibility. `CREATE TABLE IF NOT EXISTS` works for the initial schema, but you end up with a growing pile of `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements all re-running on every Pod start. There's no record of which statements have already been applied, so you can never safely remove old ones or know the current schema version.

#### golang-migrate

Migration files are baked into a custom image. Your repo layout:

```text
migrations/
  001_create_users.up.sql
  001_create_users.down.sql
  002_add_email_index.up.sql
  002_add_email_index.down.sql
```

Dockerfile:

```dockerfile
FROM migrate/migrate:v4
COPY migrations/ /migrations
```

initContainer:

```yaml
- name: migrate
  image: your-registry/users-api-migrations:v2
  args:
    - -path=/migrations
    - -database=postgresql://$(DB_USER):$(DB_PASSWORD)@$(DB_HOST):$(DB_PORT)/$(DB_NAME)?sslmode=disable
    - up
  envFrom:
    - configMapRef:
        name: users-api-config
    - secretRef:
        name: users-api-secret
```

golang-migrate tracks applied migrations in a `schema_migrations` table and skips already-applied ones. The image tag pins the exact set of migrations for that release — rolling back the deployment also rolls back to the correct migration image.

#### Flyway

Same pattern — bake migration files into a custom image. Flyway expects them at `/flyway/sql` and uses a `V<n>__` naming convention:

```text
migrations/
  V1__create_users.sql
  V2__add_email_index.sql
```

Dockerfile:

```dockerfile
FROM flyway/flyway:10
COPY migrations/ /flyway/sql
```

initContainer:

```yaml
- name: migrate
  image: your-registry/users-api-migrations:v2
  args: [migrate]
  env:
    - name: FLYWAY_URL
      value: jdbc:postgresql://$(DB_HOST):$(DB_PORT)/$(DB_NAME)
    - name: FLYWAY_USER
      valueFrom:
        secretKeyRef:
          name: users-api-secret
          key: DB_USER
    - name: FLYWAY_PASSWORD
      valueFrom:
        secretKeyRef:
          name: users-api-secret
          key: DB_PASSWORD
```

Flyway tracks applied migrations in a `flyway_schema_history` table. No down migrations in the free tier — rollback means writing a new forward migration.

| | Raw psql | golang-migrate | Flyway |
| --- | --- | --- | --- |
| Image size | ~80 MB | ~10 MB | ~200 MB |
| Migration tracking | Manual (`IF NOT EXISTS`) | Automatic (`schema_migrations` table) | Automatic (`flyway_schema_history` table) |
| Migration files | Inline SQL in YAML | `.sql` files, versioned numerically | `.sql` files, versioned with `V1__` prefix |
| Rollback support | Manual | `.down.sql` files | Paid (Teams/Enterprise) |
| Best fit | Simple schemas, one table | Go/cloud-native stacks | Java/enterprise stacks |

## CronJobs

A CronJob creates a Job on a cron schedule. The schedule uses standard cron syntax (5 fields: minute, hour, day-of-month, month, day-of-week).

| Field | Default | What it does |
| --- | --- | --- |
| `spec.schedule` | required | Cron expression. `"0 2 * * *"` = daily at 2 AM UTC. |
| `spec.timeZone` | UTC | IANA time zone (e.g. `"America/New_York"`). |
| `spec.concurrencyPolicy` | `Allow` | What to do if the previous Job is still running when the next one fires. |
| `spec.startingDeadlineSeconds` | none | If the CronJob misses its window by this many seconds, skip it. |
| `spec.successfulJobsHistoryLimit` | 3 | How many completed Jobs to keep (for log inspection). |
| `spec.failedJobsHistoryLimit` | 1 | How many failed Jobs to keep. |

### Concurrency policies

| Policy | Behavior |
| --- | --- |
| `Allow` | Multiple Jobs can run simultaneously. Fine if they don't conflict. |
| `Forbid` | Skip the new Job if the previous one is still running. Use for exclusive work (backup that holds a lock). |
| `Replace` | Kill the running Job and start a new one. Use when only the latest run matters. |

### pg_dump as a CronJob

A `pg_dump` backup is the classic CronJob example: run nightly, dump Postgres to a file, store it somewhere. In kind, it would be a PVC. In production, it's S3 via a sidecar or the backup tool's native S3 support.

The Pod needs the Postgres credentials. Reference the same Secret the app uses (`users-api` Secret from s5). Use `PGPASSWORD` or a `.pgpass` file so `pg_dump` doesn't prompt.

### Raw YAML vs Helm for CronJobs

A CronJob is a **persistent, long-lived resource** — the same category as a Deployment. This matters for Helm:

| | Raw `kubectl apply` | Helm chart |
| --- | --- | --- |
| Lifecycle | Manual delete to remove | `helm uninstall` removes everything |
| `helm ls` visibility | Invisible | Tracked |
| Values overrides | Edit YAML directly | `--set schedule=...` or `values.yaml` |
| Upgrade behaviour | Re-applies unchanged | Diffs and patches |

**Rule of thumb:** if a resource sticks around after `kubectl apply` (Deployment, Service, CronJob, PVC), it belongs in a Helm chart. If it runs once and you discard it (a seed Job, a manual trigger), raw `kubectl apply` is fine.

The seed Job (`db-seed`) is intentionally outside Helm — you run it once, it completes, and `ttlSecondsAfterFinished` cleans it up. A one-off Job as a Helm hook is awkward: Helm doesn't re-run hooks on `helm upgrade` without `helm.sh/hook-delete-policy: before-hook-creation`, and the Job name collides on the second upgrade. Raw `kubectl apply` is simpler for one-offs.

The backup CronJob (`db-backup`) and its PVC belong in a Helm chart. Both configs are shown in the Diff below so you can compare them side by side.

## DaemonSets

This stage covers the four Kubernetes workload primitives together. Deployment was s1. Job and CronJob are the main work above. DaemonSet is the fourth.

A DaemonSet ensures exactly one Pod runs on every (or a subset of) node(s). When a new node joins, the DaemonSet controller schedules a Pod on it automatically. When a node is removed, the Pod is garbage collected.

### When to use a DaemonSet

- **Node-level agents:** log shippers, monitoring agents, security scanners.
- **Storage plugins:** CSI node drivers (EBS CSI in s24).
- **Network plugins:** Calico (s7), kube-proxy, Cilium.

You rarely write your own DaemonSet for application workloads. They're almost exclusively for infrastructure.

### Hands-on: inspect Alloy

You already have a DaemonSet running from s12. Alloy (log shipping) and node-exporter (node metrics) are both DaemonSets installed by their Helm charts.

```bash
# See all DaemonSets across namespaces
kubectl get daemonset -A

# One Alloy Pod per node — the NODE column shows which node each Pod is on
kubectl get pods -n lgtm -l app.kubernetes.io/name=alloy -o wide

# Read the DaemonSet spec — notice there is no `replicas` field
kubectl describe daemonset -n lgtm -l app.kubernetes.io/name=alloy
```

The `DESIRED` / `CURRENT` / `READY` counts in `kubectl get daemonset` equal the number of nodes in the cluster, not a replica count you set. Scale the cluster (add a node) and the DaemonSet controller places a new Pod on it without any intervention.

### Scheduling

DaemonSets ignore most scheduling constraints (affinity, taints) by default. To restrict a DaemonSet to a subset of nodes, use `spec.template.spec.nodeSelector` or `spec.template.spec.affinity`. Tolerations let it run on tainted nodes (e.g. control-plane nodes).

## Commands

```bash
# 1. Apply the migration initContainer change (re-deploy users-api)
# Note: this resets canary/istio flags to their defaults i.e. removes the v2 canary
#       Deployment and VirtualService from s14.
helm upgrade users-api helm/users-api -n default
kubectl rollout status deploy/users-api
# kubectl apply -f k8s/users-api/deployment.yaml

# 2. Run a one-off data seed Job (one-offs stay raw kubectl — Helm hooks are awkward for this)
kubectl apply -f k8s/jobs/db-seed.yaml
kubectl get jobs -w
# Wait for COMPLETIONS to show 1/1

# Inspect logs
kubectl logs job/db-seed
# If you see "failed to create fsnotify watcher: too many open files", that's a kind/WSL
# inotify limit — not a Job issue. Fix: see fresh-start.md Step 0.

# 3. Install the backup CronJob via Helm (lifecycle tracked, values overridable)
helm install db-backup helm/db-backup -n default
# kubectl apply -f k8s/jobs/db-backup.yaml

# Override the schedule without editing YAML:
helm upgrade db-backup helm/db-backup -n default --set schedule="*/5 * * * *"

# Trigger it manually
kubectl create job --from=cronjob/db-backup db-backup-manual
kubectl logs job/db-backup-manual
```

### Verify

```bash
# Check the initContainer ran before the app
kubectl describe pod -l app=users-api | grep -A5 "Init Containers"
# Should show the migration container with State: Terminated, Reason: Completed

# Check the CronJob's history
kubectl get jobs -l app=db-backup
# successfulJobsHistoryLimit keeps the last 3

# The backups are on a PVC (db-backups), so they persist across job runs.
# Spin up a reader pod
kubectl run backup-reader --image=busybox --restart=Never \
  --overrides='{"spec":{"volumes":[{"name":"b","persistentVolumeClaim":{"claimName":"db-backups"}}],"containers":[{"name":"backup-reader","image":"busybox","command":["sleep","3600"],"volumeMounts":[{"name":"b","mountPath":"/backups"}]}]}}' 

# Wait for it to be ready, then exec in
kubectl exec -it backup-reader -- ls -la /backups/

# Then copy from it
kubectl cp backup-reader:/backups/backup-20260614-185835.sql.gz ./backup.sql.gz

# Clean up once you're done exploring/copying
kubectl delete pod backup-reader
```

## Try to break it

### 1. initContainer fails, app never starts

Point the migration container at the wrong database host:

```bash
kubectl describe pod -l app=users-api
# Init Containers:
#   migrate:
#     State: Waiting
#       Reason: CrashLoopBackOff
```

The app container never starts. The Pod stays in `Init:CrashLoopBackOff` state. This is by design: a failed migration should not let a broken schema serve traffic. Fix the connection string and the Pod will start.

### 2. CronJob piles up failed Jobs

Set `backoffLimit: 0` and point pg_dump at a wrong host. Every cron tick creates a new Job that fails immediately:

```bash
kubectl get jobs
# db-backup-28535820   0/1   ... Failed
# db-backup-28535880   0/1   ... Failed
# db-backup-28535940   0/1   ... Failed
```

With `concurrencyPolicy: Allow`, these pile up. With `Forbid`, only one runs at a time but each still fails. `failedJobsHistoryLimit` controls how many corpses remain.

### 3. ttlSecondsAfterFinished missing

Run the seed Job 10 times. Without `ttlSecondsAfterFinished`, every completed Job and its Pod stay in the cluster:

```bash
kubectl get jobs
# db-seed-1   1/1   Completed   5m
# db-seed-2   1/1   Completed   4m
# ... 8 more
```

They're not harmful, but they clutter `kubectl get pods` (Completed pods), consume etcd storage, and make it hard to spot real issues. Always set `ttlSecondsAfterFinished` on one-off Jobs.
