# s7 - NetworkPolicy (default-deny + explicit allows)

> **Tag:** `s7`
> Goal: stop every Pod from being able to dial every other Pod. Swap kindnet for a CNI that actually enforces NetworkPolicy (Calico), apply a default-deny baseline in the namespace, then allowlist the four flows we established in s6.

s6 wired up the second service (notify-api) and the gRPC calls. Functionally everything works, but security-wise the cluster is a flat network: the frontend Pod could connect to Postgres directly, an attacker who pwns notify-api could exfiltrate users-api data, and there's no way to even *write* a rule that says "no it can't" without a CNI that enforces one. s7 fixes that.

- Replaces kind's default CNI (`kindnet`) with Calico, which enforces NetworkPolicy.
- Applies a default-deny ingress policy in `default`.
- Adds one allowlist policy per accepted flow.
- Leaves egress wide open (proper egress lockdown lives in s15 alongside the rest of security hardening).

---

## CNI: why Calico

kind uses `kindnet` as its CNI by default. It handles pod networking but ignores NetworkPolicies. The Kubernetes API server accepts and stores NetworkPolicy objects in etcd but are never enforced. We need to add a CNI plugin which actively watches and translates those policies into iptables/eBPF rules.

| CNI | What it is | When to pick it |
| --- | --- | --- |
| **kindnet** | The default kind CNI. Pod networking only, no NetworkPolicy enforcement. | Stages that don't use NetworkPolicy (s0..s6). |
| **Calico** | iptables-based by default. Long-running, very common in production. Enforces standard `NetworkPolicy`, plus its own `GlobalNetworkPolicy` CRD. | This stage. Mirrors the standard EKS setup (AWS VPC CNI for routing + Calico add-on for policy). |
| **Cilium** | eBPF-based. Adds L7 policy, observability (Hubble), and can replace kube-proxy. Heavier, more features. | When you need L7 policies, service-mesh-like behavior without a mesh, or you're running at a scale where eBPF wins. Overkill for s7. |

The CNI you pick locally does not have to match the CNI you'd pick on EKS. For learning standard NetworkPolicy semantics, Calico is the closest match to the EKS default path and the easiest to install on kind.

### On AWS

On EKS, the **AWS VPC CNI** is the default and handles routing (each Pod gets a VPC IP). It does not enforce NetworkPolicy on its own. Either:

- Install **Calico** as an EKS add-on. The VPC CNI continues to route; Calico enforces NetworkPolicy. This is the most common production combo.
- Use **AWS-managed NetworkPolicy** (a newer feature where the VPC CNI itself enforces a subset of policies). Fewer features than Calico, but no extra add-on to run.
- Or replace the VPC CNI with **Cilium** end-to-end if you want eBPF and L7 features.

## Recreate the cluster with Calico

### `infra/kind-config.yaml`

Add the networking block to disable kindnet:

```yaml
networking:
  disableDefaultCNI: true
  podSubnet: 192.168.0.0/16
```

`192.168.0.0/16` is Calico's default Pod subnet. You can pick something else, but then you also have to override Calico's installation. Easier to use its default.

### Recreate

In a dedicated terminal, start `cloud-provider-kind` and leave it running:

```bash
sudo KUBECONFIG=$HOME/.kube/config $(go env GOPATH)/bin/cloud-provider-kind
```

Recreate cluster in the main terminal

```bash
kind delete cluster --name demo
kind create cluster --config infra/kind-config.yaml

# Without a CNI installed, every node is NotReady. Expected.
kubectl get nodes
# NAME                 STATUS     ROLES           AGE
# demo-control-plane   NotReady   control-plane   30s
# demo-worker          NotReady   <none>          25s
# demo-worker2         NotReady   <none>          25s
```

### Install Calico

```bash
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.1/manifests/calico.yaml

kubectl -n kube-system rollout status ds/calico-node --timeout=180s
kubectl get nodes
# All three should now be Ready.
```

### Reload everything else

The cluster is brand new, so reload all images and reinstall ingress + cert-manager exactly as in s5/s6:

```bash
docker build -t users-api:local-v1  apps/users-api
docker build -t notify-api:local-v1 apps/notify-api
docker build -t frontend:local-v1   apps/frontend
kind load docker-image users-api:local-v1 notify-api:local-v1 frontend:local-v1 --name demo

kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/cloud/deploy.yaml
kubectl wait -n ingress-nginx --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=180s

kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
kubectl wait -n cert-manager --for=condition=Available deployment \
  --selector=app.kubernetes.io/instance=cert-manager --timeout=180s

# Postgres, users-api, notify-api, frontend, tls, ingress - same as s6
kubectl apply -f k8s/postgres/
kubectl apply -f k8s/notify-api/
kubectl apply -f k8s/users-api/
kubectl apply -f k8s/frontend/
kubectl apply -f k8s/tls/
kubectl apply -f k8s/ingress.yaml
```

## NetworkPolicy

Kubernetes default: any Pod can reach any other Pod on any port. NetworkPolicy switches that to an allowlist model per Pod.

Policy rule: once a Pod is selected by at least one NetworkPolicy that declares `Ingress` in `policyTypes`, its ingress is governed. Only traffic matching an `ingress` rule in *any* selecting policy is permitted; everything else is dropped. Pods not selected by any such policy stay wide open.

`policyTypes` can also include `Egress`. Declaring only `[Ingress]` leaves outbound traffic at the cluster default (allow all) unless a separate policy with `Egress` selects the same Pods.

### Default-deny baseline

`default-deny.yaml` blocks all ingress in two properties:

- `podSelector: {}`: empty selector matches every Pod in the namespace.
- `policyTypes: [Ingress]` with no `ingress:` field. Every Pod is now governed, but nothing is allowed through.

```text
empty podSelector → every Pod is selected
policyTypes: [Ingress] → ingress is now governed
no ingress: entries → nothing is allowed
result: all ingress blocked
```

The other allowlist policies (frontend.yaml, postgres.yaml, etc.) are additive on top of this. They don't replace the default-deny; they add allowed paths. The final decision for any packet is: "does at least one policy that selects this destination Pod have an ingress rule that permits this source/port?" If not, it's dropped.

### What gets allowed

| Connection | Without policy | With s7 policies |
| --- | --- | --- |
| ingress-nginx -> frontend :80 | allowed | allowed |
| ingress-nginx -> users-api :3000 | allowed | allowed |
| frontend Pod -> users-api :3000 | allowed | allowed |
| users-api -> postgres :5432 | allowed | allowed |
| users-api -> notify-api :50051 | allowed | allowed |
| host (via LB) -> notify-api :50051 | allowed | allowed |
| frontend -> postgres :5432 | allowed | **dropped** |
| postgres -> notify-api :50051 | allowed | **dropped** |
| any Pod -> notify-api :50051 | allowed | **dropped** |

### The pattern for each allow rule

Each allowlist policy targets a destination Pod set and describes which sources may reach it:

- **`podSelector`**: selects the *destination* Pods this policy applies to (e.g., `app: postgres`).
- **`policyTypes: [Ingress]`**: we're only filtering inbound traffic to those Pods.
- **`ingress[].from[]`**: a list of allowed sources. The list is an **OR**: traffic from any matching source is permitted.
- **`ingress[].ports[]`**: scopes the allow to a specific port and protocol. Omitting this field means any port is permitted from the matched sources.

Each `from[]` entry can carry:

| Entry shape | Meaning |
| --- | --- |
| `podSelector` only | Pods by label in the **same namespace** as the policy |
| `namespaceSelector` only | **Any Pod** in namespaces whose labels match |
| Both in one entry | AND - the source must match both the namespace and the Pod label |
| Both as two separate entries | OR - either condition is sufficient |

**Two items in `from[]` = OR** (traffic matches if *either* rule is satisfied):

```yaml
from:
- namespaceSelector:
    matchLabels:
      name: frontend     # rule 1
- podSelector:
    matchLabels:
      app: backend       # rule 2
```

Allows traffic from *any pod in the frontend namespace* **OR** *any pod labeled `app: backend`* (even from other namespaces).

**One item in `from[]` with both selectors = AND** (traffic must satisfy *both*):

```yaml
from:
- namespaceSelector:
    matchLabels:
      name: frontend     # condition A
  podSelector:
    matchLabels:
      app: backend       # condition B
```

Allows traffic only from pods labeled `app: backend` that are **also** in the `frontend` namespace.

### Ingress-controller traffic is from a different namespace

`kubernetes.io/metadata.name` is a label the Kube-API server auto-applies to every namespace, set to the namespace's own name. You can use it in a `namespaceSelector` without manually labeling any namespace. It's stable across all Kubernetes distributions.

### Egress

s7 doesn't handle egress. Locking it down properly means also writing an allow rule for `kube-dns` (in `kube-system`) or every Pod loses name resolution. We touch one egress example in "Try to break it" and defer a real egress lockdown to s15.

## Apply order

```bash
# NetworkPolicy LAST (so you don't lock yourself out during the initial apply)
kubectl apply -f k8s/network-policies/
```

The order isn't strictly required. NetworkPolicy comes last as a habit: if a policy you wrote is broken, the cluster still works long enough for you to fix it.

Verify:

```bash
kubectl get networkpolicy
# NAME                          POD-SELECTOR   AGE
# default-deny-ingress          <none>         5s
# allow-ingress-frontend        app=frontend   5s
# allow-ingress-users-api       app=users-api  5s
# allow-ingress-notify-api      app=notify-api 5s
# allow-ingress-postgres        app=postgres   5s
```

## How the pieces fit

```text
                                    kind cluster (3 nodes, Calico CNI)
────────────────────────────────────────────────────────────────────────────────────

browser / curl ─────HTTPS:443─────▶ ingress-nginx (LoadBalancer, ext IP from CPK)
                                            │
                                            ▼
                                    ┌──────────────┐
                                    │  frontend    │
                                    └──────────────┘
                                            │  /api/...   (allowed: ingress-nginx -> frontend)
                                            ▼
                                    ┌──────────────┐  TCP:5432   ┌──────────────┐
host (grpcurl)                      │  users-api   │────────────▶│  postgres    │
    │  TCP:50051                    └──────┬───────┘             └──────────────┘
    │                                      │  gRPC:50051
    ▼                                      ▼
notify-api-lb ────────────────────▶ ┌──────────────┐
                                    │  notify-api  │
                                    └──────────────┘

NetworkPolicy:
  default-deny-ingress  selects every Pod   (baseline)
  allow-ingress-frontend         in:  ns=ingress-nginx
  allow-ingress-users-api        in:  ns=ingress-nginx, app=frontend
  allow-ingress-notify-api       in:  app=users-api  (+ LB)
  allow-ingress-postgres         in:  app=users-api
```

Calico's `calico-node` DaemonSet runs on every node. It programs iptables (or eBPF) per Pod to enforce the policies. The Service / kube-proxy layer is unchanged; the filter is purely on the destination Pod.

## What this looks like on AWS

| s7 (local) | EKS / AWS |
| --- | --- |
| Calico replacing kindnet | AWS VPC CNI (routing) + **Calico add-on** (NetworkPolicy enforcement). Same NetworkPolicy YAML. |
| Pod IPs from `192.168.0.0/16` (Calico's default) | Pod IPs from your VPC subnet (each Pod gets a real ENI/IP). |
| LoadBalancer Service IP from cloud-provider-kind | NLB provisioned by AWS LB Controller. NetworkPolicy still applies on the receiving Pod. |
| Ingress allow rule keyed off `kubernetes.io/metadata.name` | Same |

The YAML in [k8s/network-policies/](../k8s/network-policies/) is portable as-is. The enforcement engine (Calico add-on vs AWS-managed NetworkPolicy vs Cilium) is a cluster-level choice.

## Try to break it

### 1. Delete the default-deny policy, watch isolation evaporate

`deploy/frontend` is a resource-qualified target. `kubectl` picks any running pod from that Deployment for you, so you don't need to look up the random pod name suffix.

```bash
kubectl exec deploy/frontend -- sh -c 'timeout 2 nc -zv postgres-headless 5432' 2>&1 || true
# punt!
# command terminated with exit code 143
# punt! is busybox netcat's termination message

kubectl delete -f k8s/network-policies/
kubectl exec deploy/frontend -- sh -c 'timeout 2 nc -zv postgres-headless 5432'
# postgres-headless (10.96.x.x:5432) open

kubectl apply -f k8s/network-policies/
# back to blocked
```

### 2. notify-api is no longer dialable from anywhere

The "any Pod to notify-api" test from s6 now fails:

```bash
kubectl create configmap notify-proto \
  --from-file=notify.proto=apps/notify-api/src/notify.proto

kubectl run debug --rm -it --restart=Never \
  --image=fullstorydev/grpcurl \
  --overrides='{
    "spec": {
      "volumes": [{"name":"proto","configMap":{"name":"notify-proto"}}],
      "containers": [{
        "name":"debug",
        "image":"fullstorydev/grpcurl",
        "args":["-plaintext","-d","{\"user_id\":1,\"email\":\"c@c\",\"action\":\"CREATE\"}",
                "-import-path","/proto","-proto","notify.proto",
                "notify-api:50051","notify.Notify/SendNotification"],
        "volumeMounts":[{"name":"proto","mountPath":"/proto"}]
      }]
    }
  }'
# hangs, then times out

kubectl delete configmap notify-proto
```

Only `app=users-api` Pods can reach `notify-api:50051` (plus the LB, which is also allowlisted in `allow-ingress-notify-api`). The debug Pod has no `app=users-api` label, so the policy drops the packet.

### 3. Lock down postgres egress

A real egress policy needs to keep DNS working. Apply it inline for testing:

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: postgres-egress
spec:
  podSelector:
    matchLabels:
      app: postgres
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - port: 53
          protocol: UDP
EOF

kubectl exec postgres-0 -- sh -c 'timeout 2 wget -q -O- https://example.com'
# External egress is blocked (hangs, exits 143).

kubectl delete networkpolicy postgres-egress
```

### 4. Forget the namespace selector on the ingress rule

Apply a broken version of `allow-ingress-users-api` with `namespaceSelector` removed, so the AND-condition now only matches Pods labeled `app.kubernetes.io/name: ingress-nginx` in the **same** namespace (`default`):

```bash
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-users-api
spec:
  podSelector:
    matchLabels:
      app: users-api
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: ingress-nginx
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - port: 3000
          protocol: TCP
EOF

curl -k https://demo.local/api/users
# 502 / connection times out at the ingress
```

Restore the correct policy:

```bash
kubectl apply -f k8s/network-policies/users-api.yaml
curl -k https://demo.local/api/users
# 200 / working again
```

The ingress controller lives in `ingress-nginx`, so without `namespaceSelector` the policy never matches its Pods and the traffic is dropped. This is the most common NetworkPolicy bug: forgetting that cross-namespace selectors need both selectors set.

#### AND vs OR

In a NetworkPolicy `from` rule, whether selectors combine as **AND** or **OR** depends entirely on the YAML list structure:

**AND: same list item (correct policy):**

```yaml
from:
  - namespaceSelector:
      matchLabels:     
        kubernetes.io/metadata.name: ingress-nginx
    podSelector:    
      matchLabels:
        app.kubernetes.io/name: ingress-nginx
  - podSelector:
      matchLabels:
        app: frontend
```

Allows traffic from

- pods labeled `ingress-nginx` that **also live in the `ingress-nginx` namespace**, OR
- pods labeled `frontend`

**OR: separate list items (broken version above):**

```yaml
from:
  - podSelector:
      matchLabels:
        app.kubernetes.io/name: ingress-nginx
  - podSelector:
      matchLabels:
        app: frontend
```

Allows any pod labeled `ingress-nginx` in **any namespace**.

Without `namespaceSelector`, a `podSelector` alone only looks for matching pods within the **same namespace as the target i.e. users-api** (`default` here). There are no ingress-nginx pods in `default`, so the rule never matches and all ingress-controller traffic is dropped.
