# s12 - LGTM observability stack (Loki + Grafana + Tempo + Mimir)

> **Tag:** `s12`
> Goal: install the **three pillars** of observability (metrics, logs, traces) using Helm. Instrument `users-api` with `prom-client` so it exposes `/metrics` (sets up s13's custom-metric HPA on RPS). Add OpenTelemetry tracing to both apps so a single request shows up as one distributed trace across the gRPC hop.

---

## The three pillars

| Pillar | Question | Component | Storage |
| --- | --- | --- | --- |
| **Metrics** | "Is the system healthy *right now*? Is it healthier than yesterday?" | Prometheus (scraper) | Mimir (long-term store) |
| **Logs** | "What did this specific request *say* on its way through?" | Grafana Alloy (shipper) | Loki |
| **Traces** | "Where did the time go inside this one request?" | OpenTelemetry SDK + Collector | Tempo |

Metrics tell you p95 doubled; only a trace tells you which hop did it.

---

## Why "LGTM"

**L**oki, **G**rafana, **T**empo, **M**imir. Prometheus is part of the lineup too but predates the acronym. The OpenTelemetry Collector is the upstream-agnostic glue.

Alternatives, briefly:

| Stack | Shape | Trade-off |
| --- | --- | --- |
| **LGTM + Prometheus + OTel** | OSS, each component swappable | What we're using. Self-hosted complexity. |
| **Datadog / New Relic / Honeycomb** | SaaS, one agent, one bill | Easy to start, hard to leave. Cost scales with volume. |
| **ELK** (Elasticsearch + Logstash + Kibana) | Logs-first, metrics/traces bolted on | Heavyweight for logs alone. Mature, common in enterprise. |
| **Jaeger + Prometheus + Loki** | Separate UIs per pillar | Works fine; you give up Grafana's "click from metric to trace to log" correlation. |

## Architecture

```text
                          ┌────────────────┐         ┌──────────────┐
                          │   users-api    │ ──RPS── │   /metrics   │◀─────┐
                          │   (Express)    │         │  prom-client │      │ 
                          └───────┬────────┘         └──────────────┘      │ scrape
                                  │ gRPC                                   │ 15s
                                  ▼                     ┌─────────────┐    │
                          ┌────────────────┐            │ Prometheus  │────┘ 
                          │   notify-api   │            │ (kube-prom- │
                          │     (gRPC)     │            │   stack)    │
                          └───────┬────────┘            └─────┬───────┘
                                  │                           │ remote_write
                      OTLP traces │ (both apps)               ▼
                                  ▼                     ┌─────────────┐
                          ┌────────────────┐            │    Mimir    │
                          │ OTel Collector │            │ (long-term  │
                          │     :4317      │            │  metrics)   │
                          └───────┬────────┘            └─────┬───────┘
                                  │ OTLP                      │
                                  ▼                           │
                          ┌────────────────┐                  │
                          │     Tempo      │                  │
                          └───────┬────────┘                  │
                                  │                           │
   pod stdout ──Alloy──▶  ┌────────────────┐                  │
                          │      Loki      │                  │
                          └───────┬────────┘                  │
                                  │                           │
                                  └─────────┐         ┌───────┘
                                            ▼         ▼
                                          ┌─────────────┐
                                          │   Grafana   │
                                          │ (logs +     │
                                          │  metrics +  │
                                          │  traces)    │
                                          └─────────────┘
```

Read it as three independent pipelines that converge on Grafana:

- **Metrics:** apps expose `/metrics` → Prometheus scrapes → remote-writes to Mimir → Grafana queries Mimir (or Prometheus directly for fresh data).
- **Logs:** apps write to stdout → kubelet writes to `/var/log/pods/...` → Alloy tails the files → pushes to Loki → Grafana queries Loki.
- **Traces:** OTel SDK in each app exports spans over OTLP → OTel Collector batches → forwards to Tempo → Grafana queries Tempo.

Each pipeline can fail independently. None of them is on the request path; the app keeps serving traffic even if Tempo is down.

## Components

All values files live under `helm/values/`, mirroring the `metrics-server.values.yaml` pattern from s11. For each chart the doc highlights the *interesting* keys. Defaults you don't override come from `helm show values <repo>/<chart>`.

### `kube-prometheus-stack` (Prometheus + Grafana + Alertmanager + node-exporter + kube-state-metrics)

The flagship chart. One install brings up:

- **Prometheus** + the **Prometheus Operator** (so you can declare scrape targets as `ServiceMonitor` / `PodMonitor` CRDs instead of editing `prometheus.yml`).
- **Grafana**, pre-wired as a data source for the bundled Prometheus.
- **Alertmanager** (we don't author alerts in s12; the install is free).
- **node-exporter** (per-node CPU/memory/disk/network) and **kube-state-metrics** (deployment/pod/replica counts as metrics).

Without the operator you edit a giant scrape config and reload Prometheus by hand; with it, dropping a `ServiceMonitor` CRD next to your Service is enough.

#### `helm/values/kube-prometheus-stack.values.yaml`

- `retention: 6h` - Prometheus is a hot buffer, not the long-term store. Mimir holds the durable copy. On EKS this becomes Amazon Managed Prometheus.
- `serviceMonitorSelectorNilUsesHelmValues: false` - by default the operator only watches ServiceMonitors that carry the chart's release label. Flip it off to make Prometheus watch *all* ServiceMonitors cluster-wide.
- ServiceMonitors for both apps live in `lgtm`; each one's `namespaceSelector` points back at `default` where the Services live.
- `additionalDataSources` - the bundled Grafana auto-discovers the in-chart Prometheus. Loki, Tempo, and Mimir live in separate releases; you wire them in by hand.

### `loki` (logs)

Single-binary mode. Loki is normally a sharded distributed system (ingester / querier / compactor / index-gateway), but the chart ships a `SingleBinary` deployment mode that crams everything into one Pod with filesystem storage. Fine for kind, identical query API to the distributed shape.

#### `helm/values/loki.values.yaml`

The default values file spins up the full distributed topology even when `deploymentMode: SingleBinary`. Explicitly zeroing them is what actually saves the resources.

### `alloy` (log shipping)

Grafana Alloy is the unified collector replacing Promtail / Grafana Agent. DaemonSet on every node, tails each pod's stdout out of `/var/log/pods/`, parses k8s labels, ships to Loki.

#### `helm/values/alloy.values.yaml`

Alloy uses a Terraform-ish config language called *River*. It has blocks with `name "label" { ... }`. The `loki.source.kubernetes` block is the one that tails the kubelet's pod logs; the relabel block lifts namespace/pod/app onto every line so you can query `{namespace="default", app="users-api"}` in Grafana.

> **WSL2 — `failed to create fsnotify watcher: too many open files`**
> Alloy opens one inotify watch per pod log file. WSL2's kernel default (`max_user_watches=8192`) is too low once the LGTM stack + Istio sidecars are running. Fix:
>
> ```bash
> sudo sysctl fs.inotify.max_user_watches=524288
> sudo sysctl fs.inotify.max_user_instances=512
> ```
>
> This resets on WSL restart. To persist: `echo -e 'fs.inotify.max_user_watches=524288\nfs.inotify.max_user_instances=512' | sudo tee /etc/sysctl.d/99-inotify.conf`

### `tempo` (traces)

Single-binary mode again. Receives OTLP (OpenTelemetry Protocol) from the OTel Collector, stores trace blocks on filesystem.

#### `helm/values/tempo.values.yaml`

`receivers.otlp.protocols.grpc:4317` is the standard OTLP gRPC port OTel Collector's exporter will write here. Tempo can also receive Jaeger / Zipkin / OpenCensus directly; we don't enable them because everything in this stage speaks OTLP natively.

### `mimir` (long-term metrics)

Prometheus `remote_write`s every sample to Mimir, which fans out across shards and persists to object storage. In kind, "object storage" is the local filesystem; in EKS, it's S3.

The full distributed chart (`grafana/mimir-distributed`) is heavy - ingesters, distributors, queriers, store-gateways, compactor, ruler. For learning, drop replicas to 1 across the board.

#### Why Mimir when we already have Prometheus?

| Limitation | What happens in practice | How Mimir fixes it |
| --- | --- | --- |
| **Retention is local and short** | Default 15 days on disk. Prometheus restarts (OOM, node drain, upgrade) wipe the TSDB entirely. | Mimir persists every sample to durable object storage (S3 / filesystem). Data survives restarts and lives as long as you want. |
| **Single-node write path** | Prometheus is a single process. High cardinality (millions of label combinations) or fast-moving fleets overwhelm it. | Mimir shards ingestion across distributor → ingester replicas; horizontally scales write and query paths independently. |
| **No cross-cluster query** | Each Prometheus instance only knows its own scrape targets. Querying across clusters or tenants requires federation hacks. | Mimir is multi-tenant by design; a single Grafana query can span all tenants. |

**Prometheus is the scraper; Mimir is the store.**

#### `helm/values/mimir.values.yaml`

`zoneAwareReplication: { enabled: false }` is a kind quirk. Without it Mimir wants 3 zones' worth of ingester replicas and your single-node cluster can't satisfy the anti-affinity rule.

> **Caveat:** Mimir on a single filesystem PV defeats Mimir's whole purpose (durability via replicated object storage). This is purely for learning the wiring. Real deployments point at S3 / GCS / Azure Blob.

### `opentelemetry-collector` (trace fan-in)

The Collector is a generic pipeline: receivers → processors → exporters. In s12 it has exactly one job - receive OTLP traces from the apps, batch them, forward to Tempo. We deploy it as a `Deployment` (not DaemonSet) because we're only handling traces; node-local metrics scraping is Prometheus's job.

#### `helm/values/otel-collector.values.yaml`

The `contrib` image is the one with non-core receivers and exporters. Defaults ship the `core` image, which doesn't include things like the Kafka receiver or the AWS exporters. For s12 either works, but `contrib` is the production-realistic choice.

The `batch` processor groups spans before export, drops the per-span network overhead by 100x. Adding `memory_limiter` is the next thing you'd put in production.

## Instrumenting the apps

### `users-api` - metrics + traces + request logs

Use the latest at `npm install` time. The OTel `0.5x` versions track the *experimental* spec; they're stable enough for production and the only published line for sdk-node.

#### `apps/users-api/src/tracing.ts` - new file

`getNodeAutoInstrumentations()` pulls in HTTP, Express, pg, and gRPC patchers automatically. Each one wraps a module at require-time and emits spans around the calls you'd otherwise have to trace by hand.

#### `apps/users-api/src/metrics.ts` - new file

`req.path` would create a new Prometheus series for every unique URL (`/users/1`, `/users/2`, ...), making the metric unbounded. `req.route?.path` uses the matched Express route pattern (`/users/:id`), so the number of series stays fixed.

s13's HPA uses a custom-metric `http_requests_total` per pod.

#### `apps/users-api/src/index.ts`

**Why tracing must be first.** OpenTelemetry's auto-instrumentation works by *patching modules at require-time*. If `import express` runs before `import "./tracing"`, the Express module is already loaded and the patcher has nothing to wrap.

**Pino for request + app logs.** `pino-http` emits one JSON line per request to stdout; the same `pino` instance handles app logs, so format/level/`req.id` stay consistent in Loki. Register before `express.json()` so rejected bodies still log.

### `notify-api` - traces + logs

No `/metrics` here, just spans so the gRPC hop appears as a child of the users-api request, plus pino for structured log output.

#### `apps/notify-api/src/tracing.ts`

Same shape as users-api's, with `service.name=notify-api`:

The gRPC auto-instrumentation wraps the gRPC server, so each `sendNotification` becomes a child span of the users-api request. The trace context propagates over the gRPC `traceparent` metadata header automatically.

#### `apps/notify-api/src/server.ts`

`import "./tracing";` at the very top. A shared `pino()` instance replaces all `console.log/error` calls. gRPC servers have no HTTP request lifecycle, so `pino-http` is not used here; the handler logs request fields manually with `logger.info({ userId, email, action }, ...)`.

## What is a ServiceMonitor

Before Prometheus can scrape an app it needs a *scrape config*. The old way was editing `prometheus.yml` by hand and restarting Prometheus. The Prometheus Operator replaces that with a CRD: declare a `ServiceMonitor`, and the operator generates the scrape config automatically.

```text
 namespace: default
 ┌─────────────────────────────────────────────────────────────┐
 │                                                             │
 │  ┌─────────────────┐        ┌──────────────────────────┐    │
 │  │  users-api Pod  │        │  Service                 │    │
 │  │  :3000/metrics  │◀───────│  port name: "http"       │    │
 │  └─────────────────┘        │  selector: app=users-api │    │
 │                             └─────────────┬────────────┘    │
 └───────────────────────────────────────────│─────────────────┘
                                             │ namespaceSelector
                                             │ points here
 namespace: lgtm                             │
 ┌───────────────────────────────────────────│─────────────────┐
 │                                           │                 │
 │  ┌────────────────────────────────────────▼───────────────┐ │
 │  │  ServiceMonitor CRD                                    │ │
 │  │    selector.matchLabels: app.kubernetes.io/name=users-api│
 │  │    namespaceSelector.matchNames: [default]             │ │
 │  │    endpoints.port: http                                │ │
 │  └────────────────────────────────────────┬───────────────┘ │
 │                                           │                 │
 │                         watches           │                 │
 │  ┌───────────────────────────────────┐    │                 │
 │  │  Prometheus Operator              │◀───┘                 │
 │  │  (kube-prometheus-stack)          │                      │
 │  └──────────────────┬────────────────┘                      │
 │                     │ generates scrape config               │
 │                     ▼                                       │
 │  ┌───────────────────────────────────┐                      │
 │  │  Prometheus                       │                      │
 │  │  scrapes /metrics every 15 s      │                      │
 │  └───────────────────────────────────┘                      │
 └────────────────────────────────────────────────────────────-┘
```

Three things must align for a scrape to appear:

1. **Service port name matches**: the ServiceMonitor refers to a port by *name* (`http`), not number. If the Service port is unnamed or has a different name, the scrape is silently skipped.
2. **Label selector matches**: `selector.matchLabels` must select the Service, not the Pod. The Operator reads the Service's `spec.selector` to find the backing Pods.
3. **Operator scope is wide enough**: `serviceMonitorSelectorNilUsesHelmValues: false` in the Prometheus values makes the operator watch *all* ServiceMonitors cluster-wide, not just the ones it installed itself.

## Wiring it up in Kubernetes

### `helm/users-api/templates/servicemonitor.yaml`

The `ServiceMonitor` CRD (from `kube-prometheus-stack`) tells Prometheus where to scrape. The Prometheus operator translates it into a scrape entry automatically.

The ServiceMonitor lives in `lgtm` (hardcoded in `metadata.namespace`) so all monitoring config is co-located there; `namespaceSelector.matchNames: [default]` points it back at the Service in `default`.

The Service template from s11 already names its port `http`, so the `port: http` here matches. If the port were unnamed (or numeric-only), the ServiceMonitor would silently not match (see "Try to break it" #2).

### `helm/users-api/values.yaml`

`OTEL_*` env vars are the standard names the OTel SDK reads on its own.

### `helm/users-api/values.schema.json`

A targeted guard on the values most likely to fail silently, catching typos like `serviceMonitor.enabld: true` at `helm lint` instead of `kubectl apply`. Not exhaustive.

`additionalProperties: false` is added to each validated object (`hpa`, `serviceMonitor`) so a typo like `hpa.minReplica` (missing the `s`) fails loudly instead of being silently ignored. It's omitted from the top-level object because many fields there (`image`, `service`, `env`, etc.) are intentionally left out of the schema.

### Verify in Grafana

```bash
# Port-forward Grafana (optional)
kubectl -n lgtm port-forward svc/prom-grafana 3000:80
# open http://localhost:3000, login admin / admin
```

Grafana is exposed via the same nginx ingress as `demo.local`, so no port-forward is needed.

**WSL2 (Windows):** WSL2 auto-forwards ports 80/443 to `127.0.0.1` on Windows, so use `127.0.0.1`, not the ingress LB IP. Open Notepad as administrator, edit `C:\Windows\System32\drivers\etc\hosts`, and add:

```text
127.0.0.1 grafana.demo.local
```

> Always edit the hosts file in Notepad (admin) directly. PowerShell pipeline tricks (`... | Set-Content`) silently wipe the file on encoding mismatch.

**Linux:** Docker runs natively so the kind LB IP is directly routable from the host. Get the ingress IP and add it to `/etc/hosts`:

```bash
INGRESS_IP=$(kubectl -n ingress-nginx get svc ingress-nginx-controller -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
echo "$INGRESS_IP grafana.demo.local" | sudo tee -a /etc/hosts
```

Then open `https://grafana.demo.local` in the browser. Login `admin / admin`.

```bash
# Confirm Prometheus is scraping users-api
kubectl -n lgtm port-forward svc/prom-kube-prometheus-stack-prometheus 9090:9090
# Status → Targets → users-api should be UP

# Generate some traffic
hey -z 30s -c 10 https://demo.local/api/users

# Trigger the gRPC hop to notify-api (POST creates a user and calls notify-api)
curl -k -X POST https://demo.local/api/users \
  -H "Content-Type: application/json" \
  -d '{"name":"testuser","email":"test@example.com"}'
```

Then in Grafana → Explore:

| Pillar | Data source | Query |
| --- | --- | --- |
| Metrics | Mimir | `rate(http_requests_total{job="users-api"}[1m])` |
| Logs | Loki | `{namespace="default", app="users-api"} \|= "GET /users"` |
| Traces | Tempo | TraceQL: `{ service.name="users-api" }`; open a trace from a POST; you should see a `notify-api` child span underneath |

Two pre-built dashboards are loaded automatically via the `grafana_dashboard: "1"` label on their ConfigMaps:

| Dashboard | File | What it shows |
| --- | --- | --- |
| **Apps – Metrics** | `k8s/grafana/metrics-dashboard.yaml` | RPS by route, error rate, p50/p95/p99 latency, Node.js heap, event loop lag, pod restarts, container CPU - sourced from **Mimir** |
| **Apps – Logs & Traces** | `k8s/grafana/apps-dashboard.yaml` | Structured log stream with JSON parsing and coloured status codes - sourced from **Loki** |

The metrics dashboard has a `Job` variable that auto-populates from `label_values(http_requests_total, job)`, so it only shows services that actually expose this counter.

> **Note:** GET requests only produce `users-api` spans. The `notify-api` child span appears only on `POST /users` and `DELETE /users/:id`, which are the two routes that make the gRPC call.

## How the pieces find each other

A few magic strings tie the stack together. Knowing them saves the "why won't this scrape" debug session.

| String | Where it appears | Where it must match |
| --- | --- | --- |
| `http` (port name) | `service.yaml` `ports[].name` | `servicemonitor.yaml` `endpoints[].port` |
| `app.kubernetes.io/name: users-api` | `_helpers.tpl` selectorLabels | `servicemonitor.yaml` `selector.matchLabels` |
| `monitoring.coreos.com/v1` | `servicemonitor.yaml` apiVersion | CRD installed by `kube-prometheus-stack` |
| `serviceMonitorSelectorNilUsesHelmValues: false` | `kube-prometheus-stack.values.yaml` | The Prometheus Operator's filter - if `true`, ServiceMonitors without the right release label are ignored |
| `OTEL_EXPORTER_OTLP_ENDPOINT` env var | apps' tracing.ts (reads it), Helm/k8s env (sets it) | `http://otel-collector-opentelemetry-collector.lgtm.svc:4317`; the Helm release name (`otel-collector`) becomes a prefix in the service name |
| `otlp/tempo.endpoint: tempo:4317` | otel-collector values | Tempo's OTLP receiver port |
| `loki.write.endpoint.url` | alloy config | Loki's gateway service |
| `remoteWrite.url` | kube-prometheus-stack values | Mimir's `/api/v1/push` endpoint |

When a pillar goes silent, it's almost always one of these strings that drifted.

## What this looks like on AWS

| s12 (kind) | EKS / AWS |
| --- | --- |
| `kube-prometheus-stack` in cluster, retention 6h | Same chart, same scraper, `remoteWrite` to **AMP (Amazon Managed Prometheus)** instead of self-hosted Mimir |
| Mimir on a filesystem PV | **AMP** (the managed equivalent). Or self-hosted Mimir backed by **S3**. |
| Grafana via port-forward | **AMG (Amazon Managed Grafana)**, SSO via IAM Identity Center |
| Loki on filesystem | Self-hosted Loki on **S3**, *or* **CloudWatch Logs** + the CloudWatch data source in Grafana |
| Tempo on filesystem | Self-hosted Tempo on **S3**, *or* **AWS X-Ray** with the X-Ray data source |
| Alloy as DaemonSet | Same, plus **IRSA** so it can write to CloudWatch / S3 |
| OTel Collector as Deployment | Same. Often also run as a DaemonSet for node-local metric scraping (gateway + agent pattern). |

Cross-AZ writes cost real money, so you co-locate the collector with its storage backend and sample traces aggressively before they hit Tempo.

## Try to break it

### 1. ServiceMonitor selector mismatch, watch Prometheus ignore the target

Two variants of the same gotcha:

```yaml
# helm/users-api/values.yaml
serviceMonitor:
  enabled: true
# but kube-prometheus-stack has:
# serviceMonitorSelectorNilUsesHelmValues: true   ← the default, restrictive
```

Or rename the Service port from `http` to `web`, leaving the ServiceMonitor still pointing at `port: http`.

```bash
kubectl -n lgtm port-forward svc/prom-kube-prometheus-stack-prometheus 9090:9090
# Status → Targets - users-api is missing entirely.
```

`kubectl describe servicemonitor users-api` won't tell you anything is wrong. The operator silently doesn't generate a scrape config when the selector doesn't match. This is the #1 ServiceMonitor footgun in real clusters.

Fix:

```bash
# Either flip the selector
helm upgrade prom prometheus-community/kube-prometheus-stack \
  -n lgtm -f helm/values/kube-prometheus-stack.values.yaml \
  --set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false

# Or align the port name
kubectl edit svc users-api    # rename the port back to "http"
```

### 2. OTel Collector down, prove the app still serves traffic

```bash
kubectl -n lgtm scale deploy otel-collector-opentelemetry-collector --replicas=0
hey -z 30s -c 10 https://demo.local/api/users
# 200s all the way through. Latency unchanged. No new traces in Tempo.
kubectl -n lgtm scale deploy otel-collector-opentelemetry-collector --replicas=1
# Traces resume within ~10s.
```

The OTel SDK buffers spans in memory and drops on overflow; it does *not* block the request path waiting for the collector. This is by design. A broken telemetry pipeline must never take down the app. Same property is why pulling Tempo or Mimir offline doesn't bring users-api with it.

- **s21** (Security hardening) revisits the `observability` namespace: NetworkPolicy for cross-namespace scrape paths, PSS labels, External Secrets for the Grafana admin password (`adminPassword: "admin"` is exactly the kind of plaintext value External Secrets is for).

```bash
helm uninstall prom            -n lgtm
helm uninstall alloy           -n lgtm
helm uninstall mimir           -n lgtm
helm uninstall loki            -n lgtm
helm uninstall tempo           -n lgtm
helm uninstall otel-collector  -n lgtm

# PVCs from StatefulSets aren't deleted by helm uninstall
kubectl -n lgtm delete pvc --all

kubectl delete namespace lgtm

# Disable ServiceMonitors (tracing/metrics code stays, just has nowhere to send data)
helm upgrade users-api helm/users-api \
  --set serviceMonitor.enabled=false
kubectl delete -f k8s/notify-api/servicemonitor.yaml
```

PVCs from `volumeClaimTemplates` survive `helm uninstall`. Needs to be deleted manually.
