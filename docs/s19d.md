# s19d - Image Scanning & Runtime Detection (Trivy + Falco)

> **Tag:** `s19d`
> Goal: find vulnerabilities before deployment and detect anomalous behavior at runtime. Trivy scans container images for known CVEs. Falco watches Linux syscalls for suspicious activity. They are complementary: Trivy catches known-bad images, Falco catches unexpected behavior from images that passed Trivy.

The cluster now controls what runs (s19b) and what talks to what (s19c). But nothing checks whether the images themselves contain known vulnerabilities, and nothing watches for anomalous behavior at runtime. This sub-stage adds both layers.

---

## Trivy (Image Scanning)

Trivy scans container images for known CVEs. Run it as:

1. **Pre-deploy** (CI pipeline): scan the image before pushing to registry. Block the pipeline on critical CVEs.
2. **In-cluster** (Trivy Operator): scan running images continuously. Report vulnerabilities as `VulnerabilityReport` CRDs.

For kind, run Trivy as a CLI tool:

```bash
trivy image users-api:local-v3 --format=json
```

### Example output

The JSON is large (one object per CVE); the fields that matter for triage are `PkgName`, `PkgPath`, `Severity`, and `FixedVersion`:

```json
{
  "PkgName": "protobufjs",
  "PkgPath": "app/node_modules/protobufjs/package.json",
  "VulnerabilityID": "CVE-2026-54269",
  "Severity": "MEDIUM",
  "InstalledVersion": "7.6.1",
  "FixedVersion": "7.6.3, 8.6.0",
  ...
},
{
  "PkgName": "undici",
  "PkgPath": "usr/local/lib/node_modules/npm/node_modules/undici/package.json",
  "VulnerabilityID": "CVE-2026-12151",
  "Severity": "HIGH",
  "InstalledVersion": "6.26.0",
  "FixedVersion": "6.27.0, 7.28.0, 8.5.0",
  ...
}
```

No Critical findings, so a Kyverno policy gated on Critical-only (s19e) would let this image through. `protobufjs` (and `@opentelemetry/core`, not shown above) are real app dependencies — `PkgPath` starts with `app/node_modules/...` — and worth bumping. `undici`'s `PkgPath` starts with `usr/local/lib/node_modules/npm/node_modules/...`: that's **npm's own bundled copy**, shipped as part of the Node.js base image, not something `users-api` depends on or imports. Since the container's `CMD` is `node dist/src/index.js` and never invokes `npm`, that code path doesn't execute at runtime; it's attack surface only if someone gets a shell in the container and runs `npm` themselves. This is a useful reminder that Trivy reports what's *present* in the image, not what's *reachable* — triage by `PkgPath` before prioritizing a fix.

For production, the Trivy Operator runs as a controller and produces Kubernetes-native reports that can feed into Kyverno policies (e.g. deny images with critical CVEs).

## Falco (Runtime Threat Detection)

Trivy catches known CVEs before a container runs. Falco catches anomalous behavior while it runs.

Falco watches Linux syscalls via an eBPF probe. When a container makes a syscall that matches a rule (spawning a shell, writing to `/etc/passwd`, opening a socket to an unexpected address, reading `/etc/shadow`), Falco fires an alert. The container is not stopped (Falco is detection, not prevention), but the alert feeds into your incident response pipeline.

### How it works

```text
┌─────────────────────────────────────┐
│  Container                          │
│  (users-api, postgres, kube-proxy)  │
└──────────────────┬──────────────────┘
                   │ syscalls
                   ▼
┌─────────────────────────────────────┐
│  Falco eBPF probe (per node)        │
│  - intercepts syscalls              │
│  - evaluates against rule set       │
│  - fires alert on match             │
└──────────────────┬──────────────────┘
                   │ alert
                   ▼
┌─────────────────────────────────────┐
│  Output                             │
│  stdout → Alloy → Loki (s12)        │
│  or falcosidekick → web UI (below), │
│  Slack, PagerDuty, ...              │
└─────────────────────────────────────┘
```

### Install

Falco ships with two kernel drivers. For kind, the **modern eBPF** driver works without loading a kernel module. Like every component since s18b, it's installed as an ArgoCD Application. Similar to `keda` and `cert-manager`, Falco has its own chart repo and only our custom values (tuning, resources, etc.) live in our repo.

Falco has no downstream CRs the way Kyverno (s19b) and ESO (s19a) do — nothing else in this repo depends on a CRD it creates — so it's a single Application at the default `0` wave, same as `keda`/`cnpg`, instead of needing an operator/resources split.

### Kyverno rejects the default chart values

Falco is the first infra chart in this repo to actually collide with s19b's Kyverno policies.

`deny-privileged` (Enforce, cluster-wide) is a real security invariant — no namespace should run privileged containers by default, Falco included — so the fix is to make Falco actually comply, in `helm/values/falco.values.yaml`: `driver.modernEbpf.leastPrivileged: true`. Without it, `driver.kind: modern_ebpf` still runs the container `privileged: true`; this setting swaps that for four capabilities instead: `BPF`, `SYS_RESOURCE`, `PERFMON`, `SYS_PTRACE`.

`require-labels`, on the other hand, isn't a security control — it's a naming convention for this repo's own hand-authored manifests (`app: users-api`, etc.), and it doesn't match the `app.kubernetes.io/name` convention every third-party Helm chart uses instead. Falco's bundled falcosidekick UI made this concrete: its Redis StatefulSet has no values field to add a literal `app` label at all (the chart's `customLabels` option is documented as applying "to all resources" but the StatefulSet template doesn't actually reference it — a chart gap, not something fixable from our side). Rather than special-case every third-party chart's resources one at a time, `require-labels` in `k8s/security/kyverno-policies.yaml` is scoped to `namespaces: [default]` — the same restriction s19b already applies to PSS `restricted`, enforcing the convention only where we author the manifests.

### Default rules

Falco ships with hundreds of rules. The most relevant for this project:

| Rule | What triggers it |
| --- | --- |
| `Terminal shell in container` | `exec` into a running container (`kubectl exec -it ... bash`) |
| `Write below etc` | Any write to `/etc/` inside a container |
| `Read sensitive file untrusted` | Reading `/etc/shadow`, `/etc/sudoers`, SSH keys |
| `Outbound Connection to C2 Servers` | Connection to known malicious IPs |
| `Unexpected outbound connection destination` | Outbound to IPs not in an allowlist (requires config) |
| `Container run as root user` | Any container started as UID 0 |

### Custom rules

The Falco chart takes custom rules through a `customRules` key in values: each entry is a filename mounted into `/etc/falco/rules.d/`, with the rule text as its value. `helm/values/falco.values.yaml` adds one, `users-api unexpected outbound`:

- Alerts if users-api opens a connection to anything other than postgres or notify-api.
- Checks the destination against two lists, `postgres_addrs` and `notify_api_addrs`.
- Both lists start empty — Service ClusterIPs aren't pinned in the manifests, so they're only known once the Service exists (`kubectl get svc <name> -o jsonpath='{.spec.clusterIP}'`).
- Until filled in, every outbound connection matches.

### Alerting: view alerts without Slack

`kubectl logs`-grepping the Falco DaemonSet, like the Verify step below does, doesn't scale past a demo. Falcosidekick fans alerts out to 50+ outputs (Slack, PagerDuty, email, webhooks, Elasticsearch...), but there's no real Slack workspace here to send to. Rather than standing up a mock incoming-webhook receiver just to watch JSON payloads land somewhere, use falcosidekick's own bundled web UI — a real, first-class output, not a stand-in for one:

```yaml
falcosidekick:
  webui:
    enabled: true
    customLabels:
      app: falco-falcosidekick-ui
    redis:
      customLabels:
        app: falco-falcosidekick-ui-redis
```

The UI ships with its own bundled Redis for alert storage (`falcosidekick.webui.redis`) — no external Redis needed for a lab cluster. Once synced:

```bash
# Find the UI Service name (fullname depends on the release name)
kubectl -n falco get svc

# Port-forward to it locally (default UI port is 2802)
kubectl -n falco port-forward svc/falco-falcosidekick-ui 2802:2802
```

Open `http://localhost:2802` (default login `admin:admin`, set via `falcosidekick.webui.user`) and the same "Terminal shell in container" alert from the Verify step below shows up there within a few seconds — no log-grepping required.

### Trivy vs Falco

| | Trivy | Falco |
| --- | --- | --- |
| **When** | Before deployment (static scan) | At runtime (dynamic detection) |
| **What** | Known CVEs in image layers | Anomalous syscall behavior |
| **Action** | Block CI pipeline | Fire alert (detection, not prevention) |
| **Misses** | Zero-days, logic bugs, misconfiguration | Known-good processes doing expected things |

Run both: Trivy stops known-bad images from deploying; Falco catches unexpected behavior from images that passed Trivy.

## Commands

```bash
# 1. Scan images with Trivy (local CLI check, not a cluster change)
trivy image users-api:local-v3
trivy image notify-api:local-v2

# The manual equivalent of step 2, if you weren't GitOps-managing this
# (this is what k8s/argocd/infra/falco.yaml does for you):
# helm repo add falcosecurity https://falcosecurity.github.io/charts
# helm repo update
# helm install falco falcosecurity/falco \
#   -n falco --create-namespace \
#   -f helm/values/falco.values.yaml

# 2. Commit the Falco Application + values file, then push
git add k8s/argocd/infra/falco.yaml helm/values/falco.values.yaml
git commit -m "feat(security): add Falco runtime detection via ArgoCD"
git push

# 3. Wait for ArgoCD to sync, then for the Falco DaemonSet to be ready
kubectl get application -n argocd falco
kubectl -n falco rollout status daemonset/falco
```

### Verify

```bash
# Check Falco pods are running
kubectl -n falco get pods

# Trigger a Falco alert: exec into a container
kubectl exec -it deploy/users-api -- sh
# Falco logs: "Terminal shell in container"

# Check Falco logs
kubectl -n falco logs -l app.kubernetes.io/name=falco --tail=500 --since=10m | grep -i "terminal shell"

# Or, with the web UI enabled: port-forward and check http://localhost:2802 instead
kubectl -n falco port-forward svc/falco-falcosidekick-ui 2802:2802
```

## What this looks like on AWS

| s19d (kind) | EKS / AWS |
| --- | --- |
| Trivy CLI | **Amazon ECR image scanning** (built-in) or Trivy Operator in-cluster. |
| Falco (modern eBPF, kind/WSL) | **Amazon GuardDuty for EKS** (managed runtime threat detection via eBPF, no DaemonSet to run). Same alerts, zero ops overhead. |
| Falcosidekick + bundled web UI | Same, or GuardDuty findings surface directly in Security Hub instead of a separate UI. For anything beyond a lab, point `webui.externalRedis` at **Amazon ElastiCache** instead of the bundled Redis pod. |
