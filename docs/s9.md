# s9 - RBAC (Roles, Bindings, and Human Access)

> **Tag:** `s9`
> Goal: control what authenticated callers can do against the API server. Set up an `alice` user in a `devs` group, bind the built-in `view` ClusterRole to the group, and verify alice can list pods but not delete them.

s8 was AuthN for workloads: every Pod gets its own ServiceAccount, and the API-server token is removed where it isn't needed. s9 is AuthZ: once the API server knows *who* is calling, RBAC decides *what* they're allowed to do.

RBAC in practice is mostly about giving humans (devs, SREs, CI) scoped access to `kubectl`. Workloads-calling-the-API is a smaller pattern (operators, leader-election libraries, controllers). We lead with the human case because that's what you'll actually write.

---

## AuthN happens before RBAC, and it's cluster-specific

RBAC only kicks in after the API server has decided who the caller is. That step (AuthN) uses a different mechanism on every kind of cluster:

| Cluster | How a "user" or "group" is identified |
| --- | --- |
| kind / kubeadm | x509 client certs. The cert's `CN (Common Name)` is the username; each `O (Organization)` is a group. |
| EKS | IAM identity, mapped through **EKS Access Entries** to a Kubernetes user/group. |
| GKE / AKS / self-managed | OIDC token (Google, Okta, Azure AD). Group memberships come from token claims. |
| All of them | ServiceAccount tokens for workloads, not humans. |

The RBAC YAML (`Role`, `RoleBinding`, etc.) is identical across all of these. Only the AuthN wiring differs. This stage uses x509 certs because that's what kind supports natively. s21 swaps in EKS Access Entries and the YAML is unchanged.

## The four primitives

| Object | Scope | What it answers |
| --- | --- | --- |
| `Role` | One namespace | "What can be done in *this* namespace?" |
| `ClusterRole` | Cluster-wide | "What can be done, anywhere?" Also used for non-namespaced resources (Nodes, PVs). |
| `RoleBinding` | One namespace | "Bind a `Role` or `ClusterRole` to a Subject, scoped to *this* namespace." |
| `ClusterRoleBinding` | Cluster-wide | "Bind a `ClusterRole` to a Subject across all namespaces." |

Subjects in a binding are one of three kinds:

| Kind | Source of identity |
| --- | --- |
| `User` | A human, identified by the AuthN mechanism above (cert CN, IAM identity, OIDC sub). |
| `Group` | A set of humans (cert `O`, IAM group, OIDC group claim). |
| `ServiceAccount` | A workload identity. Requires `namespace`. |

Two combinations matter most:

- **`ClusterRoleBinding` + built-in `ClusterRole`**: the standard pattern for human access. Bind `view`, `edit`, `admin`, or `cluster-admin` to a `Group`.
- **`RoleBinding` + custom `Role`**: when a workload (or a human) needs a narrowly-scoped permission that no built-in role covers.

There is also **`RoleBinding` + `ClusterRole`**. The role is defined once cluster-wide, but each binding scopes it to one namespace. This is how `edit` gets reused: one definition, dozens of namespace bindings.

---

## Built-in ClusterRoles

Kubernetes ships four "user-facing" ClusterRoles that cover the common access tiers. You almost never need to write your own for human access. Pick one of these and bind it.

| ClusterRole | Permissions |
| --- | --- |
| `view` | Read-only on most resources in a namespace. **Excludes Secrets** (because Secrets are readable credentials). |
| `edit` | Read/write on most namespace resources. Excludes Roles/RoleBindings (can't grant itself more access) and namespace-scoped quota objects. |
| `admin` | Like `edit` plus the ability to manage Roles and RoleBindings *within the namespace*. Still can't create new namespaces or touch cluster-scoped resources. |
| `cluster-admin` | Everything, everywhere. The break-glass role. |

`view` + `ClusterRoleBinding` to a group is the typical "read access for devs" pattern. `edit` + per-namespace `RoleBinding` is the typical "team owns these namespaces" pattern.

## Hands-on: give `alice` (group `devs`) read-only access

We'll use Kubernetes' built-in CSR API to sign alice's client cert.

### 1. Generate alice's key and CSR

```bash
mkdir -p .rbac && cd .rbac

openssl genrsa -out alice.key 2048
openssl req -new -key alice.key -out alice.csr \
  -subj "/CN=alice/O=devs"
```

The `CN=alice/O=devs` is what RBAC will see: username `alice`, member of group `devs`.

### 2. Submit the CSR to Kubernetes

```bash
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: alice
spec:
  request: $(cat alice.csr | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  usages:
    - client auth
  expirationSeconds: 2592000  # 30 days
EOF
```

`signerName: kubernetes.io/kube-apiserver-client` is the built-in signer that produces certs the API server will trust for client AuthN. It's enabled by default on kind and on every kubeadm/EKS cluster.

### 3. Approve it and pull the signed cert

```bash
kubectl certificate approve alice

kubectl get csr alice -o jsonpath='{.status.certificate}' | base64 -d > alice.crt
```

`kubectl certificate approve` is itself an RBAC-gated action. You're effectively saying "I, the admin, vouch for this identity." On a real cluster this is done by a controller (like `cert-manager`) or CI gate (like Github Actions), not manually.

### 4. Add alice as a kubeconfig context

```bash
kubectl config set-credentials alice \
  --client-certificate=$PWD/alice.crt \
  --client-key=$PWD/alice.key \
  --embed-certs=true

kubectl config set-context alice \
  --cluster=kind-demo \
  --user=alice
```

`--embed-certs=true` inlines the cert and key into the kubeconfig so the files aren't needed at runtime. `--cluster=kind-demo` is whatever your kind cluster context is named. Check with `kubectl config get-clusters`.

### 5. Try it before the binding exists

```bash
kubectl --context=alice get pods
# Error from server (Forbidden): pods is forbidden: User "alice" cannot list resource "pods"
```

The cluster knows who alice is (AuthN succeeded), but she has no permissions at all. That's RBAC denying by default.

### 6. Bind `view` to the `devs` group

```bash
kubectl apply -f k8s/rbac/devs-view.yaml
```

[k8s/rbac/devs-view.yaml](../k8s/rbac/devs-view.yaml) is a `ClusterRoleBinding`:

- **Subject** is the `Group` named `devs`. Any client cert with `O=devs` matches. Add bob with `/CN=bob/O=devs` and he gets the same access with no YAML change.
- **roleRef** is the built-in `view` ClusterRole.
- A `ClusterRoleBinding` (not a `RoleBinding`) makes the grant cluster-wide. Alice can list pods in *every* namespace, not just `default`.

### 7. Verify

```bash
kubectl --context=alice get pods
# NAME                          READY   STATUS
# users-api-xxx                 1/1     Running
# ...

kubectl --context=alice get pods -A
# (lists pods in every namespace; view is cluster-wide)

kubectl --context=alice delete pod users-api-xxx
# Error from server (Forbidden): pods "users-api-xxx" is forbidden:
# User "alice" cannot delete resource "pods" in API group "" in the namespace "default"

kubectl --context=alice get secrets
# Error from server (Forbidden): secrets is forbidden:
# User "alice" cannot list resource "secrets"
```

`view` deliberately excludes Secrets. If alice needs read access to one specific Secret (e.g., a non-sensitive config-style Secret), that's where a *custom* Role comes in.

### `kubectl auth can-i` - verify without switching contexts

```bash
# ClusterRoleBinding grants view to the group devs, 
# not to the user alice directly
kubectl auth can-i get pods --as=alice
# no
kubectl auth can-i get pods --as=alice --as-group=devs
# yes
kubectl auth can-i delete pods --as=alice
# no
kubectl auth can-i delete pods --as=alice --as-group=devs
# no
kubectl auth can-i get secrets --as=alice --as-group=devs
# no
```

`--as` runs the auth check as another user using *your* kubeconfig credentials, so you don't have to switch contexts to check. `--as-group` adds group memberships.

You can also check what's in alice's kubeconfig:

```bash
kubectl config view --context=alice --minify

grep client-certificate-data ~/.kube/config | head -1 | awk '{print $2}' | base64 -d | openssl x509 -noout -subject
```

### Create bob, carol, and dave

The rest of this stage uses `--as=bob`, `--as=carol`, and `--as=dave` in `kubectl auth can-i` checks. Those impersonation flags don't require real certs, but to actually switch contexts and run commands as those users, create them the same way you created alice.

```bash
# bob - member of devs (same access as alice)
openssl genrsa -out bob.key 2048
openssl req -new -key bob.key -out bob.csr -subj "/CN=bob/O=devs"

# carol - member of ns-owners (admin in default namespace)
openssl genrsa -out carol.key 2048
openssl req -new -key carol.key -out carol.csr -subj "/CN=carol/O=ns-owners"

# dave - member of platform (cluster-admin)
openssl genrsa -out dave.key 2048
openssl req -new -key dave.key -out dave.csr -subj "/CN=dave/O=platform"
```

Submit and approve all three:

```bash
for user in bob carol dave; do
  cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: $user
spec:
  request: $(cat $user.csr | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  usages:
    - client auth
  expirationSeconds: 2592000
EOF
  kubectl certificate approve $user
  kubectl get csr $user -o jsonpath='{.status.certificate}' | base64 -d > $user.crt
done
```

Add them to kubeconfig:

```bash
for user in bob carol dave; do
  kubectl config set-credentials $user \
    --client-certificate=$PWD/$user.crt \
    --client-key=$PWD/$user.key \
    --embed-certs=true

  kubectl config set-context $user \
    --cluster=kind-demo \
    --user=$user
done
```

Now `kubectl --context=bob get pods` works the same as alice (both are in `devs`). Carol and dave contexts let you verify the higher tiers directly rather than relying only on `--as` impersonation.

## Comparing the manifests

| Manifest | Object kind | Subject | roleRef | Scope | Notes |
| --- | --- | --- | --- | --- | --- |
| [devs-view.yaml](../k8s/rbac/devs-view.yaml) | `ClusterRoleBinding` | `Group: devs` | built-in `view` | every namespace | Any cert with `O=devs` inherits |
| [sre-edit.yaml](../k8s/rbac/sre-edit.yaml) | `RoleBinding` | `Group: sre` | built-in `edit` | `default` only | RoleBinding on a ClusterRole scoped to one namespace |
| [ns-owners-admin.yaml](../k8s/rbac/ns-owners-admin.yaml) | `RoleBinding` | `Group: ns-owners` | built-in `admin` | `default` only | Can create Roles/RoleBindings in `default` to delegate access; cannot touch cluster-scoped resources |
| [platform-cluster-admin.yaml](../k8s/rbac/platform-cluster-admin.yaml) | `ClusterRoleBinding` | `Group: platform` | built-in `cluster-admin` | everywhere | No restrictions, including modifying this binding. Control group membership outside K8s (IDP/IaC) |
| [ci-restarter.yaml](../k8s/rbac/ci-restarter.yaml) | `Role` + `RoleBinding` | `ServiceAccount: ci` | custom `Role` | `default` only | Lets a CI pipeline restart `users-api` and nothing else. [See below.](#ci-restarter-least-privilege-for-ci) |

### ci-restarter: least-privilege for CI

A CI/CD pipeline (GitHub Actions, Jenkins, etc.) needs to run `kubectl rollout restart deployment/users-api` after pushing a new image. That command sends a `PATCH` to the `apps/deployments` resource. It writes a restart annotation to the pod template.

The Role grants exactly that and nothing else:

```yaml
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    resourceNames: ["users-api"]
    verbs: ["get", "patch"]
```

`get` is needed because `rollout restart` reads the current resource before patching it. `resourceNames: ["users-api"]` pins the grant to one deployment. The CI job can't restart anything else, read Secrets, or delete Pods.

The subject is a `ServiceAccount`, not a `Group`. CI jobs authenticate with a token, not a client cert. `ci-restarter.yaml` creates the `ci` ServiceAccount, then grants it exactly these two verbs. In a real pipeline, you'd extract that SA's token as a CI secret and use it to authenticate `kubectl` in your pipeline environment.

Step 6 only applied `devs-view.yaml`. Apply the rest before running the `can-i` checks below:

```bash
kubectl apply -f k8s/rbac
```

### What each tier can and can't do

`kubectl auth can-i` answers questions about any identity without switching contexts. Use `--as-group` to simulate group membership:

```bash
# view (devs): read-only across all namespaces, secrets excluded
kubectl auth can-i get pods --as=alice --as-group=devs            # yes
kubectl auth can-i delete pods --as=alice --as-group=devs         # no
kubectl auth can-i get secrets --as=alice --as-group=devs         # no
kubectl auth can-i create rolebindings --as=alice --as-group=devs # no

# edit (sre): write namespace resources, still can't touch RBAC objects
kubectl auth can-i create deployments --as=bob --as-group=sre     # yes
kubectl auth can-i delete pods --as=bob --as-group=sre            # yes
kubectl auth can-i get secrets --as=bob --as-group=sre            # yes
kubectl auth can-i create rolebindings --as=bob --as-group=sre    # no
kubectl auth can-i get nodes --as=bob --as-group=sre              # no

# admin (ns-owners): everything edit can do, plus manage Roles/RoleBindings in the namespace
kubectl auth can-i create rolebindings --as=carol --as-group=ns-owners -n default   # yes
kubectl auth can-i create clusterrolebindings --as=carol --as-group=ns-owners       # no
kubectl auth can-i create namespaces --as=carol --as-group=ns-owners                # no
kubectl auth can-i get nodes --as=carol --as-group=ns-owners                        # no

# cluster-admin (platform): no restrictions
kubectl auth can-i create namespaces --as=dave --as-group=platform          # yes
kubectl auth can-i get nodes --as=dave --as-group=platform                  # yes
kubectl auth can-i delete clusterrolebindings --as=dave --as-group=platform # yes
kubectl auth can-i '*' '*' --as=dave --as-group=platform                    # yes
```

- **edit**: write access (create, update, delete workload resources). Secrets become readable.
- **admin**: can now create and delete `Role` and `RoleBinding` objects *in the same namespace*. This lets `admin` holders delegate access to others, but only within the namespace they own.
- **cluster-admin**: cluster-scoped resources (Nodes, PVs, Namespaces, CRDs, ClusterRoleBindings). `admin` is namespace-bound even as a `ClusterRoleBinding`; `cluster-admin` has no fence.

`cluster-admin` is the break-glass role. On a shared cluster, it's typically held only by the platform/infra team, not handed out as individual user certs.

## Custom Role fields

A `Role` is a list of `rules`. Each rule has four fields:

| Field | What it means | Examples |
| --- | --- | --- |
| `apiGroups` | Which API group the resource belongs to | `""` = core (Pods, Services, ConfigMaps); `"apps"` = Deployments/StatefulSets; `"batch"` = Jobs |
| `resources` | Resource type, lowercase plural | `configmaps`, `pods`, `deployments`, `pods/log` (subresource) |
| `verbs` | Allowed operations | Read: `get`, `list`, `watch`. Write: `create`, `update`, `patch`, `delete`. Special: `deletecollection`, `*`. |
| `resourceNames` | (optional) Pin to specific named objects | `["app-config"]` - only this ConfigMap. Omit = all of that resource type. |

## ServiceAccounts as subjects

The same RBAC primitives also bind to ServiceAccounts. If a workload genuinely needs to call the API server (operators, leader-election, controllers), this is how you scope what it's allowed to do:

```yaml
subjects:
  - kind: ServiceAccount
    name: my-controller
    namespace: default
```

s8 set every workload's `automountServiceAccountToken: false` because none of our four services call the API server. If one ever needs to, two things change: change its SA's automount back to `true`, and add a `RoleBinding` (or `ClusterRoleBinding`) with the SA as subject. The Role itself is written the same way - `apiGroups` / `resources` / `verbs` / `resourceNames`.

This pattern shows up again in s20 (operators) where a custom controller naturally needs to watch and modify the CRDs it owns.

### 1. Drop the binding, see access disappear

```bash
kubectl delete clusterrolebinding devs-view
kubectl --context=alice get pods
# Error from server (Forbidden): pods is forbidden: User "alice" cannot list resource "pods"
```

Re-apply:

```bash
kubectl apply -f k8s/rbac/devs-view.yaml
```

### 2. Watch the `resourceNames`-on-`list` gotcha bite

Apply this Role + RoleBinding for alice inline (no file needed):

```bash
kubectl apply -f - <<'EOF'
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: configmap-resourcenames-gotcha
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    resourceNames: ["app-config"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alice-configmap-gotcha
  namespace: default
subjects:
  - kind: User
    name: alice
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: configmap-resourcenames-gotcha
  apiGroup: rbac.authorization.k8s.io
EOF
```

> **Prerequisite:** alice must not have any other bindings that grant broader configmap access (e.g. the `devs-view` ClusterRoleBinding from the previous exercise). Remove it first:

```bash
kubectl delete clusterrolebinding devs-view
```

Create the ConfigMaps first (as admin):

```bash
kubectl create configmap app-config --from-literal=key=value
kubectl create configmap other-config --from-literal=key=value
```

Then:

```bash
kubectl --context=alice get configmaps
# Error from server (Forbidden): cannot list resource "configmaps"
# The API server can't honor a resourceNames filter on a collection request (list), so it doesn't grant the list permission at all.

kubectl --context=alice get configmap app-config
# NAME         DATA   AGE
# app-config   1      ...
# works because get is a named-resource operation

kubectl --context=alice get configmap other-config
# Error from server (Forbidden): cannot get resource "configmaps"
```

Why: `list` hits `/apis/apps/v1/namespaces/default/deployments` (a collection URL, no name in the path). Kubernetes has nowhere to apply the `resourceNames` filter, so it drops it. `get` hits `.../deployments/users-api` (name is in the URL), so the filter works.

Re-apply RBACs:

```bash
kubectl apply -f k8s/rbac/devs-view.yaml
```

### 3. Inspect what a built-in ClusterRole actually grants

```bash
kubectl describe clusterrole view | head -50
# PolicyRule:
#   Resources                            Non-Resource URLs  Resource Names  Verbs
#   ---------                            -----------------  --------------  -----
#   bindings                             []                 []              [get list watch]
#   configmaps                           []                 []              [get list watch]
#   ...
```

The built-ins are just YAML like anything else. If `view` isn't quite what you want, you can write a custom one or use **role aggregation** (label your rules and they get added to a built-in role automatically. Covered briefly in the Kubernetes docs under "aggregated ClusterRoles").
