# s19b - Admission Control (Pod Security Standards + Kyverno)

> **Tag:** `s19b`
> Goal: control what's allowed to run in the cluster. Pod Security Standards enforce a privilege baseline via namespace labels. Kyverno adds fine-grained admission policies: require labels, deny privileged containers, require resource limits.

Every Deployment so far runs containers with default privileges: root user, all Linux capabilities, writable filesystem. No policy rejects a misconfigured Pod before it starts. This sub-stage adds two layers of admission control: a built-in Kubernetes mechanism (PSS) and a policy engine (Kyverno).

---

## Pod Security Standards (PSS)

### The three profiles

PSS is a built-in Kubernetes feature (no extra controller). It defines three profiles, enforced at the namespace level:

| Profile | What it allows | Use case |
| --- | --- | --- |
| `privileged` | Everything. No restrictions. | System namespaces (`kube-system`, `istio-system`) |
| `baseline` | Blocks the most dangerous capabilities: `hostNetwork`, `hostPID`, `privileged` containers. Allows `runAsNonRoot: false`. | Namespaces running infrastructure tools that need some elevated access |
| `restricted` | Baseline + requires `runAsNonRoot: true`, drops all capabilities, disallows privilege escalation, requires `seccomp: RuntimeDefault` | Application namespaces (`default`) |

### Enforcement modes

Each namespace label can set three independent modes:

| Mode | Behavior |
| --- | --- |
| `enforce` | Reject Pods that violate the profile |
| `audit` | Allow the Pod but write a warning to the audit log |
| `warn` | Allow the Pod but show a warning to the `kubectl` user |

Start with `warn` + `audit` on `restricted` to find violations without breaking anything. Once all workloads comply, flip to `enforce`.

### Making your containers PSS-restricted compliant

Most violations come from missing `securityContext` fields. Add to every container:

```yaml
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault
  readOnlyRootFilesystem: true
```

`readOnlyRootFilesystem: true` is not required by PSS but is a best practice. It prevents an attacker from writing to the container filesystem (e.g. dropping a reverse shell). If the app needs to write temp files, mount an `emptyDir` at the write path.

### What each field actually does

| Field | What it means | Notes |
| --- | --- | --- |
| `runAsNonRoot: true` | The kubelet refuses to start the container if the image's default user resolves to UID 0. It doesn't pick a UID for you. | Combine with `runAsUser` to guarantee which non-root UID is used. |
| `runAsUser: 1000` | Explicitly sets the UID the process runs as, overriding whatever the image's `Dockerfile USER` says. | `1000` is just a convention (many base images pre-create a UID 1000 user). Any non-zero UID works; distroless "nonroot" images often default to `65532`. Pair with `runAsGroup` to also pin the GID, and `fsGroup` (pod-level) to control ownership of mounted volumes. |
| `allowPrivilegeEscalation: false` | Sets the kernel's `no_new_privs` flag, blocking a process from gaining more privileges than its parent (e.g. via a setuid binary). | Narrower than `privileged: true`. A container can be non-privileged and still escalate if this isn't set. |
| `capabilities.drop: ["ALL"]` | Linux capabilities split root's power into ~40 discrete pieces (`NET_BIND_SERVICE` = bind ports < 1024, `CHOWN`, `NET_RAW` = raw sockets/ping, `SYS_ADMIN` = broad admin ops, etc). Even non-root containers keep a default set (~14 caps) unless dropped. | If you need one back, add it explicitly: `capabilities.add: ["NET_BIND_SERVICE"]`. Only `frontend` does this: nginx binds to container port `80`, a privileged port (<1024), which non-root processes can't bind without `NET_BIND_SERVICE`. `users-api` (`3000`) and `notify-api` (`50051`) listen on unprivileged ports, so they need zero capabilities back. |
| `seccompProfile.type: RuntimeDefault` | Seccomp filters which raw syscalls a process may make. `RuntimeDefault` uses the container runtime's built-in denylist (blocks ~44 dangerous syscalls: `reboot`, `mount`, `kexec_load`, etc). | Alternatives: `Unconfined` (no filtering, the old default), `Localhost` (points at a custom profile file on the node). PSS `restricted` requires `RuntimeDefault` or `Localhost`. |
| `readOnlyRootFilesystem: true` | Mounts the container's root filesystem read-only, so a compromised process can't overwrite binaries or drop a payload to disk. | Anything the app writes (temp files, caches, sockets) needs an explicit writable volume mounted at that path — see below. |

### Picking the actual `runAsUser` per container

The `runAsUser: 1000` in the snippet above is just illustrative, not a rule. `runAsNonRoot: true` only checks that the UID isn't `0` — it doesn't create a user or fix file ownership. Every base image pre-creates its own non-root user and `chown`s its writable directories (cache dirs, sockets, data dirs) to that UID. You can use a different UID and the container still starts, but crashes with permission errors the moment it touches those paths. Therefore, **use the UID the base image already provisions**
:

| Container | Base image | UID used | Why that number |
| --- | --- | --- | --- |
| `frontend` | `nginx:1.31-alpine-slim` | `101` | Alpine nginx images pre-create an `nginx` user at UID/GID 101, which already owns `/var/cache/nginx` and `/var/run`. |
| `migrate` initContainer | `postgres:16` | `999` | The official Postgres image provisions a `postgres` user at UID 999 (see `deployment.yaml:23-30`, referenced again in "Try to break it" below). |
| `users-api`, `notify-api` | `node:26-alpine` | `1000` | The official Node image provisions a `node` user at UID 1000. |

Check any image's actual UID with `docker run --rm <image> id` (or `cat /etc/passwd` for the pre-created username) before hardcoding `runAsUser` — don't assume 1000 works everywhere, as `deny-privileged` and PSS won't catch a wrong-but-non-zero UID; it'll just fail at runtime with `EACCES`.

### Why `emptyDir: {}` for `/tmp`

`emptyDir` is a Volume type Kubernetes creates fresh when the Pod is scheduled to a node. It starts empty, lives for the Pod's lifetime (survives container restarts, deleted when the Pod is deleted), and by default is backed by the node's disk. Add `medium: Memory` to back it with tmpfs (RAM) instead.

It's the right tool here because `readOnlyRootFilesystem: true` locks down everything *except* explicitly mounted paths. The app needs `/tmp` to be writable, so `deployment.yaml:56-58,96-98` mounts an `emptyDir` there — writable, but empty on every restart and never persisted.

Other volume types you'd reach for in different situations:

| Type | Use case |
| --- | --- |
| `emptyDir` | Scratch space, caches — ephemeral, node-local |
| `persistentVolumeClaim` | Data that must survive Pod rescheduling (databases, uploads) |
| `configMap` / `secret` | Mount config or credentials as files |
| `hostPath` | Mounts a directory from the node's filesystem directly — avoid in application workloads, it's a container-escape risk (this is part of what PSS `restricted` and Kyverno's `deny-privileged` guard against) |

## Kyverno (Policy Engine)

### What Kyverno does

Kyverno is a Kubernetes-native policy engine. It intercepts API requests via admission webhooks and:

- **Validates**: reject requests that violate policies (deny privileged pods, require labels).
- **Mutates**: modify requests to enforce defaults (inject resource limits, add labels).
- **Generates**: create resources in response to events (create a NetworkPolicy when a new namespace is created).

### Kyverno vs OPA Gatekeeper

**OPA Gatekeeper** is the other major policy engine for Kubernetes. It's built on Open Policy Agent (OPA), a general-purpose policy engine that works across many systems (Kubernetes, Terraform, CI pipelines, API gateways). Gatekeeper is the Kubernetes-specific adapter: it plugs OPA into the admission webhook system so you can enforce policies the same way Kyverno does. The key difference is how you write policies: Gatekeeper uses **Rego**, OPA's dedicated query language, instead of Kubernetes YAML.

| | Kyverno | OPA Gatekeeper |
| --- | --- | --- |
| Policy language | Kubernetes YAML (ClusterPolicy CRD) | Rego (a dedicated policy language) |
| Learning curve | Low for Kubernetes users | Steep (Rego is its own thing) |
| Mutation | Native | Limited (only through assign/modify) |
| Generation | Native (create resources from policies) | Not supported |
| Community | CNCF graduated | CNCF graduated |

We use Kyverno because the policies are YAML: the same language as everything else in this repo.

### Reading a `ClusterPolicy`

`k8s/security/kyverno-policies.yaml` defines three `ClusterPolicy` objects (cluster-scoped, applies everywhere unless you add a `match`/`exclude` scope). Each one breaks down like this:

- **`validationFailureAction`**: `Enforce` rejects the request at admission time, like PSS `enforce`. `Audit` allows it through but records a policy report, like PSS `audit`. The file deliberately mixes them: `require-labels` and `deny-privileged` are `Enforce` (hard blockers), but `require-resource-limits` is `Audit` — a staged rollout so you can see who'd be blocked before flipping it to `Enforce`.
- **`match.any.resources.kinds`**: which resource kinds trigger the rule. `any` means "match if any of these resource selectors match" (there's also `all` for AND-style matching across multiple conditions).
- **`validate.pattern`**: Kyverno's own declarative pattern language (not JSONPath, not Rego). It overlays the shape you specify onto the real resource and every field must match:
  - `"?*"` (used in `require-labels`) means "this field must exist and be a non-empty string." It doesn't check the label's *value*, only that it's present.
  - `"!true"` (used in `deny-privileged`) is negation: the field must not literally equal `true`. If `privileged` is absent, that also passes, since it defaults to `false`.
  - Other operators you'll see in Kyverno docs: `*` (any value, including absent), `X | Y` (OR), numeric ranges like `">1024"`, and anchors like `(field)` (only validate if the field is present) or `^(field)` (field must exist).
  - In `require-resource-limits`, the pattern nests a single-item list under `spec.containers`: Kyverno applies that one pattern element to *every* item in the real array, so you don't need one entry per container.

### Useful starter policies

| Policy | What it does |
| --- | --- |
| **Require labels** | Reject Pods/Deployments missing `app` and `team` labels |
| **Deny privileged containers** | Reject containers with `privileged: true` or `hostNetwork: true` |
| **Require resource limits** | Reject containers without `resources.limits.memory` |
| **Require non-root** | Reject containers without `runAsNonRoot: true` |
| **Restrict image registries** | Only allow images from approved registries (e.g. `ghcr.io`, your private ECR) |

## Installing Kyverno through ArgoCD, not `helm install`

Since s18b, everything in this cluster is GitOps-managed except ArgoCD's own bootstrap. Kyverno is no different: it needs an Application for the operator itself, at a low sync wave, so its `ClusterPolicy` CRD exists before ArgoCD tries to create any `ClusterPolicy` CRs.

| Application | File | What it deploys | Sync wave |
| --- | --- | --- | --- |
| `kyverno` | `k8s/argocd/infra/kyverno.yaml` | The Kyverno Helm chart (admission controller + CRDs) | `0` |
| `security-resources` | `k8s/argocd/infra/security-resources.yaml` | Everything in `k8s/security/`: the three `ClusterPolicy` CRs, plus s19a's `SecretStore`/`ExternalSecret` | `1` |

Wave `0` installs Kyverno's webhook and CRDs; wave `1` applies the policies once Kyverno can actually admit `ClusterPolicy` objects. This is the same ordering problem (and the same fix) s18b already solved for cert-manager/istio-base: an operator's own CRDs have to exist before ArgoCD can sync CRs that use them.

### The PSS namespace labels also move into Git

`pod-security.kubernetes.io/*` labels are just metadata on the `default` Namespace object, so they become a plain manifest ArgoCD can own: `k8s/security/namespace-default.yaml`.

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: default
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

`default` already exists on every cluster (Kubernetes creates it automatically), so there's nothing to create — just an object to adopt. This is the same "**adopted in place**" case s18b covered for pre-existing Helm releases: ArgoCD's three-way diff compares the manifest in Git, the live object in the cluster, and its own last-applied record. Since the `Namespace` already exists but its labels don't match Git (case 2 from that list: *resources exist but differ*), ArgoCD patches just the `pod-security.kubernetes.io/*` labels onto the live object — it doesn't delete and recreate the `Namespace`, and it doesn't touch anything already running inside it. The `CreateNamespace=true` sync option (used when a namespace *doesn't* exist yet) never comes into play here.

## Commands

```bash
# The manual equivalent, if you weren't GitOps-managing this
# (this is what k8s/argocd/infra/kyverno.yaml does for you):
# helm repo add kyverno https://kyverno.github.io/kyverno
# helm repo update
# helm install kyverno kyverno/kyverno -n kyverno --create-namespace
#
# and the PSS labels / ClusterPolicy apply would be:
# kubectl label namespace default \
#   pod-security.kubernetes.io/enforce=restricted \
#   pod-security.kubernetes.io/audit=restricted \
#   pod-security.kubernetes.io/warn=restricted
# kubectl apply -f k8s/security/kyverno-policies.yaml

# 1. Commit the Kyverno operator Application, the Namespace label
#    manifest, the ClusterPolicy CRs, and the securityContext changes
#    that make the existing Deployments PSS-restricted compliant,
#    then push. The Deployments must land in the same commit: syncing
#    the enforce=restricted label before they're compliant would break
#    their Pods.
git add k8s/argocd/infra/kyverno.yaml k8s/security/namespace-default.yaml k8s/security/kyverno-policies.yaml \
  k8s/frontend/deployment.yaml k8s/notify-api/deployment.yaml k8s/users-api/deployment.yaml
git commit -m "feat(security): add Kyverno admission control via ArgoCD"
git push

# 2. ArgoCD syncs kyverno (wave 0), then security-resources (wave 1)
#    once Kyverno's webhook and CRDs are ready.
kubectl get applications -n argocd kyverno security-resources
```

### Verify

```bash
# Test Kyverno: try to create a Pod without labels
kubectl run test --image=nginx
# Error: validation error: require-labels: ...

# Test PSS: try to create a privileged Pod
kubectl run test --image=nginx --overrides='{"spec":{"containers":[{"name":"test","image":"nginx","securityContext":{"privileged":true}}]}}'
# Error: violates PodSecurity "restricted"
```

## Try to break it

### PSS blocks a legitimate workload

`users-api`'s main container already carries the full `securityContext` block. But its `migrate` initContainer (`deployment.yaml:23-30`) runs `postgres:16` to apply the schema, and that image's default user is root. Strip the initContainer's `securityContext` and re-apply against a `restricted` namespace:

```bash
kubectl apply -f k8s/users-api/deployment.yaml
# Warning: would violate PodSecurity "restricted": ...
#   (container "migrate" must set securityContext.runAsNonRoot=true)
```

The Deployment is created but the Pod's initContainer is rejected, so the Pod never starts and `migrate` never runs. `kubectl get events` shows the violation. This is exactly why `deployment.yaml`'s `migrate` initContainer sets `runAsUser: 999` (the `postgres` image's built-in non-root user) instead of leaving it on the default root user: every container in a Pod, init or not, is checked against the namespace's PSS profile.
