# s13 - Advanced HPA + VPA

> **Tag:** `s13`
> Goal: replace the CPU-based HPA from s10 with one that scales on actual request rate, and deploy VPA to right-size Pod resource requests. Completes the autoscaling story sketched in s10.

s10 introduced HPA on CPU utilization and explained VPA. s12 added `prom-client` to users-api, giving it a `/metrics` endpoint that exposes `http_requests_total`. This stage adds a prometheus-adapter which reads that counter from Prometheus, publishes it as a Kubernetes custom metric, and the HPA scales on RPS instead of CPU.

It also adds a VPA, installed via the Fairwinds Helm chart. It watches actual CPU and memory usage, recommends right-sized `resources.requests`, and (in `Recreate` or `InPlaceOrRecreate` mode) applies them automatically.

## Lightweight Prometheus

The full LGTM stack from s12 (Mimir, Loki, Tempo, Alloy, OTel Collector) is not needed here. We install only `kube-prometheus-stack`. We need Prometheus for scraping and Grafana for ad-hoc queries.

We add a `mimir.enabled` flag (default `false`) to `kube-prometheus-stack.values.yaml`. When `false`, the `remoteWrite` block is omitted, so Prometheus won't push samples to a dead endpoint. When `true` (s12), it writes to Mimir as before.

`additionalDataSources` for Loki/Tempo/Mimir can be ignored. Grafana will show broken data source icons for missing services, but Prometheus queries still work.

Everything else stays the same.

## Architecture

```text
                    ┌────────────────┐
                    │   users-api    │
                    │  /metrics      │
                    │  (prom-client) │
                    └───────┬────────┘
                            │ http_requests_total
                            │ scraped every 15s
                            ▼
                    ┌────────────────┐
                    │   Prometheus   │
                    │  (kube-prom-   │
                    │   stack)       │
                    └───┬────────┬───┘
                        │        │
          PromQL query  │        │  metrics.k8s.io
          rate(...)     │        │  (via metrics-server)
                        ▼        ▼
            ┌──────────────┐  ┌──────────────┐
            │ prometheus-  │  │     VPA      │
            │ adapter      │  │ recommender  │
            │              │  │              │
            │ registers:   │  │ reads usage, │
            │ custom.      │  │ writes reco  │
            │ metrics.     │  │ to VPA obj   │
            │ k8s.io       │  │              │
            └──────┬───────┘  └──────┬───────┘
                   │                 │
          HPA reads│          ┌──────┴──────┐
          per-pod  │          │             │
          RPS      │          ▼             ▼
                   │    ┌──────────┐  ┌──────────────┐
                   │    │ updater  │  │  admission   │
                   │    │(evicts)  │  │  controller  │
                   │    └──────────┘  │  (mutates    │
                   │                  │   new Pods)  │
                   ▼                  └──────────────┘
            ┌──────────────┐
            │     HPA      │
            │  scales on   │
            │  http_req/s  │
            │  per pod     │
            └──────────────┘
```

Two independent autoscaling loops:

- **Horizontal (HPA):** prometheus-adapter turns a PromQL `rate()` into a per-pod custom metric. HPA reads it and adjusts `spec.replicas`. Scales the fleet size.
- **Vertical (VPA):** recommender reads actual CPU/memory from metrics-server, writes recommendations to the VPA object. In `Recreate`/`InPlaceOrRecreate` mode, updater evicts pods and admission-controller injects the right-sized `resources.requests` on re-creation. Scales each pod's resource allocation.

They don't conflict because HPA scales on RPS (a custom metric) and VPA adjusts CPU/memory requests. Neither controller looks at the same signal as the other.

## Metrics APIs

| API group | Served by | What it exposes | HPA metric type |
| --- | --- | --- | --- |
| `metrics.k8s.io` | metrics-server (s10) | Container CPU/memory from cAdvisor | `Resource` |
| `custom.metrics.k8s.io` | prometheus-adapter | Any Prometheus metric, scoped to a Kubernetes object (namespace, pod, service) | `Pods` or `Object` |
| `external.metrics.k8s.io` | prometheus-adapter, KEDA (s19) | Metrics not tied to a Kubernetes object (SQS queue depth, external DB connections) | `External` |

prometheus-adapter registers as an API server for `custom.metrics.k8s.io` (and optionally `external.metrics.k8s.io`). It receives requests from the HPA controller, translates them into PromQL queries against Prometheus, and returns the results in the format HPA expects.

## prometheus-adapter

### What it does

The HPA controller doesn't know PromQL. It speaks the Kubernetes custom metrics API: "give me metric X for pods matching label selector Y in namespace Z." prometheus-adapter sits in between. It takes that API call, maps it to a PromQL query, runs it against Prometheus, and returns the result.

### Rules

The adapter's entire configuration is a list of **rules**. Each rule has four parts:

| Field | Purpose |
| --- | --- |
| `seriesQuery` | Which Prometheus series to discover. Used at startup to build the list of available metrics. e.g. `http_requests_total{namespace!="",pod!=""}` |
| `resources` | How to map Prometheus labels to Kubernetes resource types. `overrides` maps `namespace` → `{resource: "namespace"}`, `pod` → `{resource: "pod"}`. |
| `name` | How to rename the metric for the Kubernetes API. `matches` is a regex on the series name, `as` is the replacement. e.g. `matches: "^(.*)_total$"`, `as: "${1}_per_second"` turns `http_requests_total` into `http_requests_per_second`. |
| `metricsQuery` | The PromQL expression to evaluate when HPA asks for this metric. e.g. `rate(<<.Series>>{<<.LabelMatchers>>}[2m])` |

`<<.Series>>` and `<<.LabelMatchers>>` are Go template variables the adapter fills in at query time. `<<.Series>>` becomes `http_requests_total`. `<<.LabelMatchers>>` becomes something like `namespace="default",pod="users-api-abc123"`.

So when HPA asks "what's `http_requests_per_second` for pods in namespace `default` with label `app=users-api`?", the adapter runs `rate(http_requests_total{namespace="default",pod=~"users-api-.*"}[2m])` against Prometheus and returns the per-pod results.

The `[2m]` rate window should be at least 4x the scrape interval. With a 15s scrape interval, `[2m]` gives 8 data points; enough for a stable rate calculation.

### `helm/values/prometheus-adapter.values.yaml`

**`prometheus.url` + `prometheus.port`**: where the adapter finds Prometheus. Since both live in `lgtm`, the URL is the in-cluster service name. The Helm release name `prom` produces a service called `prom-kube-prometheus-stack-prometheus`. Port defaults to `9090`.

**`rules.custom[]`**: the list of rules described above. The default chart ships with no custom rules; you must define them. Without at least one rule matching `http_requests_total`, the custom metric doesn't exist and HPA reports `<unknown>`.

**`rules.default: false`**: the chart ships default resource rules that re-expose `metrics.k8s.io` data through the adapter. Turn them off to avoid duplicating what metrics-server already provides.

## VPA via Fairwinds Helm chart

### Why Fairwinds

The official VPA project ships as raw manifests applied via a bash script (`hack/vpa-up.sh`). The Fairwinds chart wraps the same components in a proper Helm release with per-component toggles, resource requests, cert management, and `helm upgrade` support.

### What it installs

| Component | Role | Runs as |
| --- | --- | --- |
| **recommender** | Reads actual CPU/memory from metrics-server, computes target requests, writes them to the VPA object's `status.recommendation`. | Deployment |
| **updater** | Watches VPA objects. In `Recreate`/`InPlaceOrRecreate` mode, evicts pods whose requests differ too far from the recommendation. | Deployment |
| **admission-controller** | Mutating webhook. When the evicted pod is re-created, rewrites its `resources.requests` to the recommended values before the kubelet sees it. | Deployment + Service + webhook config |

The recommender is always needed. The updater and admission-controller are only needed if you want VPA to act automatically (not just recommend).

### `helm/values/vpa.values.yaml`

**`recommender.enabled`**, **`updater.enabled`**, **`admissionController.enabled`**: toggle each component independently. For `Off` mode (recommend only), you only need the recommender. For `Recreate`/`InPlaceOrRecreate`, you need all three.

**`admissionController.certGen.enabled`**: the webhook needs a TLS cert. The chart can generate a self-signed one automatically. If you have cert-manager (s4), you could point it there instead, but the built-in self-signed cert is fine for kind.

**`recommender.extraArgs`**: overrides the recommender's default behavior:

| Flag | Default | What it does |
| --- | --- | --- |
| `--history-length` | `8d` | How far back in metrics-server history the recommender looks. Longer = smoother recommendations, slower to react to step changes. |
| `--pod-recommendation-min-cpu-millicores` | `25m` | Floor on CPU recommendations. Prevents VPA from recommending 1m for an idle pod. |
| `--pod-recommendation-min-memory-mb` | `250` | Floor on memory recommendations (in MB). |
| `--oom-bump-up-ratio` | `1.2` | When a container OOMKills, multiply the current memory recommendation by this factor. |

## VPA manifest for users-api

The VPA CRD (`autoscaling.k8s.io/v1`) lives alongside the Deployment it targets, similar to how HPA does. Can be a standalone manifest in `k8s/users-api/vpa.yaml` or a Helm template in the chart.

### Key fields

**`spec.targetRef`**: points at the Deployment by `kind`, `apiVersion`, `name`. Same shape as HPA's `scaleTargetRef`. Only one VPA should target a given Deployment.

**`spec.updatePolicy.updateMode`**: controls what VPA does with its recommendations (covered in detail in [s10](./s10.md)):

| Mode | What happens |
| --- | --- |
| `Off` | Recommendations only. Read via `kubectl describe vpa`. Apply manually. |
| `Recreate` | Evict the pod, recreate with new requests. |
| `InPlaceOrRecreate` | Resize in-place if possible; evict if not (QoS class change, memory shrink). |

Start in `Off`. Read the recommendations for a few hours. If they look sane, move to `Recreate` or `InPlaceOrRecreate`.

**`spec.resourcePolicy.containerPolicies[]`**: per-container bounds:

| Field | Purpose |
| --- | --- |
| `containerName` | Which container in the pod (`"users-api"`, or `"*"` for all). |
| `minAllowed` | Floor. Prevents VPA from recommending absurdly low values (e.g. cpu: 1m). |
| `maxAllowed` | Ceiling. Prevents VPA from recommending values that won't fit on a node. |
| `controlledResources` | Which resources VPA manages: `["cpu", "memory"]`, `["cpu"]`, or `["memory"]`. |

For our setup (HPA on RPS, not CPU), setting `controlledResources: ["cpu", "memory"]` is safe. VPA adjusting CPU doesn't interfere with an RPS-based HPA.

**Two floors, not one.** `minAllowed` here looks similar to `--pod-recommendation-min-cpu-millicores` in `vpa.values.yaml`, but they operate at different layers. The `extraArgs` flag is a global floor baked into the recommender process. It applies to every VPA object in the cluster. `minAllowed` is a per-object floor declared in this specific VPA manifest. It clamps recommendations only for `users-api`. Both are active simultaneously; the effective floor is whichever is higher. In this repo both happen to be set to the same value (`25m` CPU, `64Mi`/`250MB` memory), but if you raise `minAllowed` above the global default, only `users-api` is affected. If you raise the global `extraArgs` floor, every workload is affected.

### Reading recommendations

Once the recommender has enough data (a few minutes of traffic), `kubectl describe vpa users-api` shows:

```text
Container Recommendations:
  Container Name:  users-api
  Lower Bound:     cpu: 25m    memory: 65Mi
  Target:          cpu: 47m    memory: 104Mi
  Uncapped Target: cpu: 47m    memory: 104Mi
  Upper Bound:     cpu: 200m   memory: 250Mi
```

`Target` is what VPA would apply under `Recreate` or `InPlaceOrRecreate`. `Uncapped Target` is the raw recommendation before `minAllowed`/`maxAllowed` clamp it. VPA only acts when current requests fall outside `Lower Bound` / `Upper Bound`.

## Custom-metric HPA

s10's HPA uses `type: Resource` with `name: cpu`. This stage replaces it with `type: Pods`; scale on a per-pod custom metric from `custom.metrics.k8s.io`.

### Key differences from s10

| | s10 (CPU) | s13 (RPS) |
| --- | --- | --- |
| Metric type | `Resource` | `Pods` |
| Metric name | `cpu` | `http_requests_per_second` |
| Target type | `Utilization` (% of request) | `AverageValue` (absolute number) |
| Target value | `50` (percent) | e.g. `10` (10 req/s per pod) |
| What drives scaling | CPU usage | Actual traffic volume |
| Requires | metrics-server (s10) | prometheus-adapter + Prometheus |

### Why RPS is better than CPU for web services

CPU is a *symptom*. RPS is the *cause*. A CPU-based HPA can't distinguish between "high CPU because of traffic" and "high CPU because of a CPU-bound background job" or "high CPU because of a GC storm." An RPS-based HPA scales on the signal you actually care about: how many requests each pod handles.

CPU HPA also has a sensitivity problem. The target percentage (50%) is a guess. Set it too low and you waste replicas; too high and you lag behind spikes. RPS is more direct: "I want each pod handling no more than 10 requests/second" is a measurable SLO.

The trade-off: RPS-based scaling needs the Prometheus pipeline (users-api → Prometheus → prometheus-adapter → HPA). CPU scaling only needs metrics-server. More moving parts, more to break.

### How HPA computes the desired replica count

With `type: Pods`, HPA computes the metric's value per pod, averages it, and compares against `target.averageValue`:

```text
desiredReplicas = ceil(currentReplicas × (currentAvgMetric / targetAvgMetric))
```

With 2 pods, 30 req/s total (15 each), and a target of 10:

```text
ceil(2 × (15 / 10)) = ceil(3.0) = 3
```

### Updating the Helm chart

The existing HPA template (`helm/users-api/templates/hpa.yaml`) only supports `type: Resource`. To support custom metrics you need to:

- Add a values toggle (e.g. `hpa.customMetric.enabled`, `hpa.customMetric.name`, `hpa.customMetric.targetAverageValue`) alongside the existing `targetCPUUtilizationPercentage`
- Template a `type: Pods` block when the custom metric is enabled, or fall back to the `type: Resource` block when it's not
- Remove the CPU/memory `type: Resource` entries when scaling on a custom metric (you can keep them alongside as a safety net, but HPA will scale to whichever metric needs the *most* replicas, which usually means the CPU metric is redundant)

## The safe VPA + HPA combination

Recap from [s10](./s10.md): an HPA and VPA targeting the same Deployment on the same metric (CPU) create a feedback loop. The safe combinations:

| HPA scales on | VPA controls | Why it's safe |
| --- | --- | --- |
| RPS (custom metric) | cpu + memory | HPA doesn't read CPU/memory. VPA adjusting requests doesn't change RPS. Independent signals. |
| Custom metric (queue, RPS) | cpu + memory | Same reason. |
| CPU | memory only | Different resource. |
| Anything | nothing (`Off` mode) | VPA is read-only. |

**s13's combination:** HPA on `http_requests_per_second` (custom metric via prometheus-adapter), VPA on cpu + memory. No conflict. HPA decides how many pods run; VPA decides how big each pod is.

## How the pieces find each other

| String | Where it appears | Where it must match |
| --- | --- | --- |
| `http_requests_total` | users-api `metrics.ts` counter name | prometheus-adapter rule `seriesQuery` and `metricsQuery` |
| `http_requests_per_second` | prometheus-adapter rule `name.as` | HPA `pods.metric.name` |
| `http` (port name) | Service `ports[].name` | ServiceMonitor `endpoints[].port` |
| `prom-kube-prometheus-stack-prometheus.lgtm.svc` | prometheus-adapter `prometheus.url` | Actual Prometheus service (Helm release name `prom` produces this) |
| `namespace`, `pod` labels | Prometheus stores from ServiceMonitor discovery | prometheus-adapter `resources.overrides` must map them |
| `[2m]` rate window | prometheus-adapter `metricsQuery` | Must be >= 4x ServiceMonitor `interval` (15s x 4 = 60s min) |

When the custom metric shows `<unknown>` in `kubectl get hpa`, it's almost always one of these strings that doesn't match.

## Commands

> **Raw manifests vs Helm:** `k8s/users-api/` and `helm/users-api/templates/` are kept in sync. They produce equivalent objects. Use whichever you prefer; the commands below use Helm. If you apply a raw manifest first (`kubectl apply -f`) and then run `helm upgrade`, Helm will error because it doesn't own the resource. Either delete and let Helm recreate it, or skip the raw-manifest step entirely.

Assumes s11 state: metrics-server installed, users-api Helm chart exists, `prom-client` instrumentation and ServiceMonitor template are in the code from s12, but no observability stack is running.

```bash
# 1. Add repos
helm repo add metrics-server       https://kubernetes-sigs.github.io/metrics-server/
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo add fairwinds-stable     https://charts.fairwinds.com/stable
helm repo update

# 1. metrics-server (installed via Helm in s11; re-install if cluster was recreated)
helm install metrics-server metrics-server/metrics-server \
  -n kube-system -f helm/values/metrics-server.values.yaml
kubectl -n kube-system rollout status deploy/metrics-server --timeout=120s

# 2. Namespace (ServiceMonitor template hardcodes this)
kubectl create namespace lgtm

# 3. Prometheus + Grafana (strip remoteWrite and extra data sources from the s12 values file first)
# To also enable Mimir, append: -f helm/values/kube-prometheus-stack.mimir.values.yaml
helm install prom prometheus-community/kube-prometheus-stack \
  -n lgtm -f helm/values/kube-prometheus-stack.values.yaml

# 4. prometheus-adapter (needs Prometheus up first)
helm install prometheus-adapter prometheus-community/prometheus-adapter \
  -n lgtm -f helm/values/prometheus-adapter.values.yaml

# 5. VPA (Fairwinds)
helm install vpa fairwinds-stable/vpa \
  -n lgtm -f helm/values/vpa.values.yaml

# 6. Rebuild users-api and upgrade with ServiceMonitor enabled
docker build -t users-api:local-v3 apps/users-api
kind load docker-image users-api:local-v3 --name demo
helm upgrade users-api helm/users-api -n default
```

### Verify Prometheus is scraping

```bash
kubectl -n lgtm port-forward svc/prom-kube-prometheus-stack-prometheus 9090:9090
# http://localhost:9090/targets → users-api should be UP

# Generate some traffic
hey -z 30s -c 10 https://demo.local/api/users
```

### Verify the custom metric exists

```bash
kubectl get --raw "/apis/custom.metrics.k8s.io/v1beta1/namespaces/default/pods/*/http_requests_per_second" | jq .
```

Each pod should have a non-zero `value`. If the list is empty or the API returns 404, the adapter hasn't matched the series yet. Check that Prometheus is scraping and that the counter name in `metrics.ts` matches `seriesQuery` in the adapter values.

### Verify HPA is reading the custom metric

```bash
kubectl get hpa users-api
```

The `TARGETS` column should show a real number instead of `<unknown>`:

```text
NAME        REFERENCE              TARGETS       MINPODS   MAXPODS   REPLICAS
users-api   Deployment/users-api   2500m/10      2         10        2
```

`<unknown>` means HPA can't reach the custom metric. Either the adapter isn't running, the rule doesn't match the series, or the metric name in the HPA spec doesn't match `name.as` in the adapter rule.

### Load test to confirm HPA scales

```bash
# Watch in two terminals
kubectl get hpa users-api -w
kubectl get pod -l app=users-api -w

# Generate load
hey -z 2m -c 50 https://demo.local/api/users
```

Expected:

1. `http_requests_per_second` per pod climbs above the target.
2. HPA adds pods.
3. Per-pod RPS drops back toward the target as traffic spreads.
4. After `hey` stops, ~5 minutes later replicas tick back down.

### Apply VPA and verify

```bash
helm upgrade users-api helm/users-api -n default
```

**Step 1: confirm all three VPA components are running:**

```bash
kubectl -n lgtm get pods -l app.kubernetes.io/name=vpa
```

Expected: `vpa-recommender`, `vpa-updater`, and `vpa-admission-controller` all `1/1 Running`.

**Step 2: confirm the webhook is registered:**

```bash
kubectl get mutatingwebhookconfigurations | grep vpa
# vpa-webhook-config   1   <age>
```

If missing, the admission controller isn't wired up and new pods won't get resized requests.

**Step 3: wait a few minutes, then check for recommendations:**

```bash
kubectl describe vpa users-api
```

Look for `Conditions: Type: RecommendationProvided, Status: True` and a populated `Recommendation` block:

```text
Container Recommendations:
  Container Name:  users-api
  Lower Bound:     cpu: 25m    memory: 100Mi
  Target:          cpu: 49m    memory: 100Mi
  Uncapped Target: cpu: 49m    memory: 100Mi
  Upper Bound:     cpu: 500m   memory: 512Mi
```

`Uncapped Target` matching `Target` means `minAllowed`/`maxAllowed` aren't clamping the recommendation.

The `Events` section will show `EvictedPod` entries once the updater starts acting:

```text
Normal  EvictedPod  12m  vpa-updater  VPA Updater evicted Pod users-api-... to apply resource recommendation.
```

**Step 4: confirm pods received the recommended requests:**

```bash
kubectl describe pod -l app=users-api | grep -A4 Requests
```

Expected `cpu` and `memory` to match VPA's `Target`. If `cpu` shows the `minAllowed` floor instead of `Target`, the evictions happened before the recommender had enough data. The updater won't re-evict as long as the current value is within `[Lower Bound, Upper Bound]`. Force the current recommendation onto all pods with a rollout restart:

```bash
kubectl rollout restart deployment/users-api
kubectl describe pod -l app=users-api | grep "cpu:"
# New pods: cpu: <limit>  then  cpu: <target>  (limits then requests, alternating per pod)
# Once rollout completes, all pods show the Target value
```

## Try to break it

### 1. prometheus-adapter can't find the series

Rename the counter in `metrics.ts` to `http_req_total` but leave the adapter rule pointing at `http_requests_total`. Or change the ServiceMonitor namespace selector so Prometheus stops scraping.

```bash
kubectl get hpa users-api
# http_requests_per_second: <unknown>/10
```

The adapter has nothing to query. HPA reports `<unknown>` and never scales. This is the custom-metrics equivalent of the "missing `resources.requests.cpu`" gotcha from s10.

Fix: align the counter name across `metrics.ts`, the adapter's `seriesQuery`, and `metricsQuery`. Check Prometheus → Status → Targets → verify users-api is being scraped. Then check the series exists in Prometheus's expression browser.

### 2. VPA `Recreate` mode: evictions and the CPU-HPA feedback loop

Both effects share the same starting point - VPA in `Recreate` mode. So run them in sequence.

**Step 1**: flip VPA to `Recreate`:

```bash
# Verify the manifest before running
helm template users-api helm/users-api -n default \
  --set vpa.enabled=true \
  --set vpa.updateMode=Recreate

# Note down the current revision
helm history users-api

# Apply the manifest. template -> upgrade
helm upgrade users-api helm/users-api -n default \
  --set vpa.enabled=true \
  --set vpa.updateMode=Recreate

# To see the actual rendered manifests that were applied
helm get manifest users-api -n default
```

**Observe evictions**: HPA still on the custom metric, only VPA mode changed. If the recommender decides requests need changing, the updater evicts a pod mid-traffic. If your deployment is running at minReplicas: 2 (the floor set by HPA), and VPA evicts one pod to resize it, we are suddenly at 50% capacity, until the new pod pulls image and passes readiness probe.

```bash
hey -z 5m -c 100 https://demo.local/api/users &
kubectl get pod -l app=users-api -w
# A pod goes Evicted/Terminating, then a replacement Pending → Running
#
# There are multiple windows when both the pods are evicted simultaneously
# ...
# users-api-5566d95f69-s8vl8   0/1     Running   0             70m   ← evicted
# users-api-5566d95f69-9nhn7   0/1     Running   3 (69m ago)   83m   ← evicted 
# ...

kubectl describe vpa users-api  # check Recommendation: Target values
```

With PDBs (s22) `PodDisruptionBudget` of `minAvailable: 1`, it would let VPA evict at most one pod at a time. So we won't have a window when all the pods are evicted. Continuous evictions also seem to be sabotaging HPA's scale-up signal.

- Load increases → custom metric rises → HPA considers scaling up
- VPA evicts a pod to resize it → pod restarts fresh with zero metric history
- The per-pod metric average drops (new pod reports 0)
- HPA sees "average is fine, no need to scale"
- Repeat

**Step 2**: additionally flip HPA to CPU-based scaling:

```bash
helm upgrade users-api helm/users-api -n default \
  --set hpa.customMetric.enabled=false \
  --set vpa.enabled=true \
  --set vpa.updateMode=Recreate
```

> **Note**: `helm upgrade` resets to chart defaults on each run. `--set` flags from a previous upgrade are not carried forward. Always repeat all flags you want active, or pass `--reuse-values` to carry forward the previous release's values.

Now both conditions for the feedback loop are active - **in theory**:

1. VPA raises `requests.cpu` from 100m to 200m.
2. The pod's CPU utilization (as a percent of 200m) drops.
3. HPA sees lower utilization, scales down.
4. Fewer pods → more load per pod → utilization rises again.
5. HPA scales back up. VPA raises requests further. Loop.

In practice this oscillation is hard to observe in a 5-minute window. VPA's updater needs several minutes of observation before it evicts and resizes pods. HPA will likely just pin at `maxReplicas` for the duration of the load test.

**Undo** both steps:

```bash
helm rollback users-api <revision>
```

## What's next
