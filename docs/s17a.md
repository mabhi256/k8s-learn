# s17a - KEDA (Event-Driven Autoscaling)

> **Tag:** `s17a`
> Goal: replace the prometheus-adapter + custom-metric HPA from s13 with KEDA. One `ScaledObject` CR replaces three moving parts (adapter, custom metric registration, HPA) and adds scale-to-zero, cron triggers, and external event sources.

s13 showed that scaling on RPS (a custom metric) is better than scaling on CPU for web services. But the wiring was complex: prometheus-adapter translates PromQL into the custom metrics API, you write adapter rules with Go templates, and debug with `kubectl get --raw`. KEDA wraps all of that into a single CRD.

---

## What KEDA is

KEDA (Kubernetes Event-Driven Autoscaling) is a CNCF graduated project. It sits between event sources and the HPA controller:

```text
Event sources                    KEDA                         Kubernetes
─────────────  ──────────────────────────────────────────────────────────
Prometheus     ─┐
SQS queue      ─┤                                         ┌──────────────┐
Kafka topic    ─┼──▶  ScaledObject  ──▶  KEDA operator ──▶│     HPA      │
Cron schedule  ─┤     (your CR)         (creates/         │  (native)    │
Redis list     ─┤                        manages HPA)     └──────┬───────┘
PostgreSQL     ─┘                                                │
                                                          scales │
                                                                 ▼
                                                          ┌──────────────┐
                                                          │  Deployment  │
                                                          └──────────────┘
```

KEDA doesn't replace the HPA controller. It creates and manages an HPA object for you, filling in the custom/external metric values by querying the event source directly. When load drops to zero, KEDA scales the Deployment to 0 replicas (something vanilla HPA can't do: `minReplicas` must be >= 1).

---

## KEDA vs prometheus-adapter (s13)

| | prometheus-adapter (s13) | KEDA |
| --- | --- | --- |
| **Install** | Helm chart + custom rules YAML | Helm chart (no rules config needed) |
| **Config per metric** | Adapter rule (seriesQuery, metricsQuery, name, resources) + HPA manifest | ScaledObject CR (trigger type + query, all in one) |
| **Supports Prometheus** | Yes (its only job) | Yes (one of 60+ scalers) |
| **Supports external sources** | Only if you write PromQL against a Prometheus that has the data | Native: SQS, Kafka, Redis, PostgreSQL, HTTP, cron, ... |
| **Scale to zero** | No (HPA minReplicas >= 1) | Yes. KEDA intercepts at 0→1 and 1→0 transitions. |
| **Debug** | `kubectl get --raw /apis/custom.metrics.k8s.io/...` | `kubectl describe scaledobject`, `kubectl get hpa` |

KEDA is strictly more capable. The only reason to keep prometheus-adapter is if you need the raw `custom.metrics.k8s.io` API for non-KEDA consumers (rare).

## Architecture

```text
┌────────────────────────────────────────────────────────────┐
│  KEDA (installed in keda namespace)                        │
│                                                            │
│  ┌────────────────────┐  ┌──────────────────────────────┐  │
│  │  keda-operator     │  │  keda-metrics-apiserver      │  │
│  │  - watches         │  │  - serves external.metrics.  │  │
│  │    ScaledObjects   │  │    k8s.io API                │  │
│  │  - creates/updates │  │  - HPA reads metrics from    │  │
│  │    HPA objects     │  │    here                      │  │
│  └──────────┬─────────┘  └──────────────────────────────┘  │
│             │                                              │
└─────────────┼──────────────────────────────────────────────┘
              │ creates
              ▼
       ┌──────────────┐          ┌──────────────────┐
       │     HPA      │  reads   │  Prometheus      │
       │  (managed    │◀─────────│  (event source)  │
       │   by KEDA)   │  metrics │                  │
       └──────┬───────┘          └──────────────────┘
              │ scales
              ▼
       ┌──────────────┐
       │  Deployment  │
       │  users-api   │
       └──────────────┘
```

Two components:

- **keda-operator**: watches `ScaledObject` / `ScaledJob` CRs. Creates, updates, and deletes HPA objects. Handles the 0↔1 scaling transitions (HPA can't do 0→1 because there are no pods to measure).
- **keda-metrics-apiserver**: registers as an API server for `external.metrics.k8s.io`. When HPA queries a metric, this component calls the configured scaler (Prometheus, SQS, etc.) and returns the value.

## ScaledObject CRD

The `ScaledObject` is KEDA's core CRD. It replaces both the prometheus-adapter rule and the HPA manifest.

### Key fields

**`spec.scaleTargetRef`**: the workload to scale (Deployment or StatefulSet). Same concept as HPA's `scaleTargetRef`.

**`spec.minReplicaCount`**: floor. Can be `0` for scale-to-zero. Default is `0`.

**`spec.maxReplicaCount`**: ceiling. Default is `100`.

**`spec.cooldownPeriod`**: seconds to wait after the last trigger fires before scaling to `minReplicaCount`. Prevents flapping. Default is `300` (5 minutes).

**`spec.pollingInterval`**: how often KEDA checks the event source. Default is `30` seconds.

**`spec.triggers[]`**: the list of event sources. Each trigger has a `type` and `metadata` specific to that scaler. Multiple triggers can coexist: KEDA scales to whichever demands the most replicas.

## Scalers

KEDA has 60+ scalers. The ones relevant to this project:

| Scaler | Trigger type | What it scales on | Use case |
| --- | --- | --- | --- |
| **Prometheus** | `prometheus` | Any PromQL query result | RPS, error rate, queue depth exposed via Prometheus |
| **Cron** | `cron` | Time-based schedule | Pre-scale for known traffic patterns (business hours) |
| **PostgreSQL** | `postgresql` | Row count from a SQL query | Work queue backed by a Postgres table |
| **CPU / Memory** | `cpu`, `memory` | Same as vanilla HPA Resource metric | Drop-in replacement for s10's HPA |
| **Kafka** | `kafka` | Consumer group lag | Event-driven microservices |
| **AWS SQS** | `aws-sqs-queue` | Approximate message count | Background job processing (s24) |

### Prometheus scaler

Replaces the entire prometheus-adapter setup from s13. Instead of writing adapter rules, you put the PromQL query directly in the trigger:

```yaml
triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prom-kube-prometheus-stack-prometheus.lgtm.svc:9090
      query: sum(rate(http_requests_total{namespace="default",service="users-api"}[2m]))
      threshold: "10"
```

`threshold` is the target value. KEDA divides the query result by the threshold to compute the desired replica count: `ceil(queryResult / threshold)`. With 50 req/s total and a threshold of 10, KEDA wants 5 replicas.

The `query` is any valid PromQL. Unlike prometheus-adapter, you don't need to think about per-pod vs. total: just write the query that returns the number you want to scale on. If you want per-pod RPS, divide by replica count in the query. If you want total RPS, use `sum()` and set the threshold to "total RPS I want per pod x expected pod count."

### Cron scaler

Scale on a time schedule. Useful for predictable traffic patterns:

```yaml
triggers:
  - type: cron
    metadata:
      timezone: "America/New_York"
      start: "0 8 * * 1-5"
      end: "0 18 * * 1-5"
      desiredReplicas: "5"
```

Between 8 AM and 6 PM on weekdays: 5 replicas. Outside that window: `minReplicaCount` (could be 0). Combine with a Prometheus trigger so the cron sets a floor and the Prometheus trigger scales above it.

## Scale to zero

When all triggers report 0 (no traffic, empty queue), KEDA scales the Deployment to 0 replicas. When a new event arrives, KEDA scales to 1 (the "activation" step) and then hands off to HPA for further scaling.

Activation happens via `spec.triggers[].metadata.activationThreshold`: the minimum metric value that triggers a scale-from-zero. Default is `0` (any non-zero value activates).

Scale-to-zero is most useful for:

- **Dev/staging environments**: no traffic at night → 0 pods → save resources.
- **Background workers**: no messages in queue → 0 pods. Message arrives → scale up, process, scale back down.
- **Batch APIs**: infrequently called endpoints that don't need a warm pod.

The trade-off is cold starts. After scaling to zero, the first request waits 5-15 seconds while the Pod schedules and the container starts. That's fine for background workers, but too slow for user-facing APIs.

---

## ScaledJob

KEDA can also scale Jobs (not just Deployments). A `ScaledJob` creates Jobs in response to events:

| | ScaledObject | ScaledJob |
| --- | --- | --- |
| Target | Deployment / StatefulSet | Creates new Jobs |
| Lifecycle | Long-running pods, scaled up/down | One-shot Jobs, created per event batch |
| Use case | HTTP APIs, gRPC services | Message queue consumers, batch processing |

For users-api, `ScaledObject` is correct. `ScaledJob` is for workloads where each "unit of work" should be a separate Job (e.g., process one SQS message per Job).

## Commands

### Removed (from s13)

Delete the manual HPA if it still exists. KEDA manages its own HPA.

```bash
kubectl delete hpa users-api
# Or if using Helm, set hpa.enabled: false in users-api values
```

Also uninstall prometheus-adapter (KEDA's Prometheus scaler replaces it):

```bash
helm uninstall prometheus-adapter -n lgtm
```

### Install and apply

```bash
# 1. Install KEDA
helm repo add kedacore https://kedacore.github.io/charts
helm repo update

# Pin 2.19.0: KEDA 2.20+ requires K8s 1.33, kind uses 1.32
helm install keda kedacore/keda -n keda --create-namespace --version 2.19.0 -f helm/values/keda.values.yaml

# 2. Wait for KEDA to be ready
kubectl -n keda rollout status deploy/keda-operator
kubectl -n keda rollout status deploy/keda-operator-metrics-apiserver

# 3. Deploy users-api with KEDA ScaledObject enabled
helm upgrade users-api helm/users-api

# 4. Verify KEDA created an HPA
kubectl get hpa
# NAME                          REFERENCE              TARGETS     MINPODS   MAXPODS
# keda-hpa-users-api            Deployment/users-api   0/10 (avg)  1         10
```

### Verify scaling

```bash
# Generate load
hey -z 2m -c 50 https://demo.local/api/users

# Watch in parallel
kubectl get hpa -w
kubectl get pods -l app=users-api -w

# Check the ScaledObject status
kubectl describe scaledobject users-api
```

### Tuning for burst traffic

Out of the box, a 50-concurrency load test (`hey -z 2m -c 50`) will produce mostly 503s. The defaults are tuned for gradual traffic, not sudden spikes. Three settings to adjust:

- **`minReplicaCount`**: raise from 1 to 2-3 so pods are already running when the burst hits.
- **`pollingInterval`**: lower from 15s to 5s so KEDA detects the spike faster.
- **`query` rate window**: shorten `[2m]` to `[30s]` so the PromQL result reacts to traffic within seconds, not minutes.

```yaml
keda:
  minReplicaCount: 2
  pollingInterval: 5
  prometheus:
    query: sum(rate(http_requests_total{namespace="default",service="users-api"}[30s]))
```

The underlying problem is latency in the feedback loop: KEDA polls every `pollingInterval`, the `rate()` window smooths out spikes, and new pods still need time to pass readiness probes. Tightening these values won't eliminate 503s entirely during a cold burst, but it cuts them dramatically.

## Try to break it

### 1. Wrong Prometheus URL in the trigger

```yaml
metadata:
  serverAddress: http://wrong-prometheus:9090
```

KEDA logs the error but doesn't crash. The ScaledObject shows `status: Unknown`. The managed HPA reports `<unknown>` for the metric. KEDA falls back to `minReplicaCount` (or 0 if configured).

```bash
kubectl describe scaledobject users-api
# Conditions:
#   Type: Active  Status: Unknown  Message: error querying prometheus
```
