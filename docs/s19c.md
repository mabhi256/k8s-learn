# s19c - Egress NetworkPolicy

> **Tag:** `s19c`
> Goal: lock down outbound traffic. A default-deny egress policy blocks all outbound connections, then explicit rules allowlist only the destinations each service needs.

s7 introduced ingress NetworkPolicy: default-deny inbound, allowlist per service. But egress was left wide open. Any compromised Pod can phone home to any IP on the internet. This sub-stage closes that gap.

---

## Default-deny egress

```yaml
spec:
  podSelector: {}
  policyTypes:
    - Egress
```

This blocks all outbound traffic for every Pod in the namespace. Nothing can reach anything, not even DNS.

## Allowlist pattern

After default-deny, add explicit egress rules:

| Destination | Why | Rule |
| --- | --- | --- |
| **kube-dns** (CoreDNS) | DNS resolution | Port 53 UDP/TCP to `kube-system` namespace |
| **Postgres** | Database access | Port 5432 to Pods matching `app: postgres` |
| **notify-api** | gRPC calls | Port 50051 to Pods matching `app: notify-api` |
| **Prometheus** | Metrics scraping (reverse: Prometheus reaches in) | Not needed in egress; Prometheus initiates |
| **External APIs** | If the app calls external services | Specific CIDR blocks or use a proxy |

The DNS allowlist is the most commonly forgotten rule. Without it, even allowed Pod-to-Pod traffic fails because names can't resolve.

`default-deny-egress` has `podSelector: {}` — it blocks **every** Pod in the namespace, not just the app you're thinking about. That includes CNPG's `postgres`/`postgres-pooler-rw` Pods themselves (`cnpg.io/cluster: postgres`), which need their own egress rule to originate connections: DNS (to resolve their own backend), 5432/8000 to peer instances (pooler → primary, replication, instance-manager health), and the Kubernetes API (`10.96.0.1/32:443`, for CNPG's instance manager to report status/do leader election). Forgetting this one doesn't break the pods you're testing — it silently breaks Postgres's own connection pooler, which then breaks anything that routes through it. See [k8s/network-policies/egress-postgres.yaml](../k8s/network-policies/egress-postgres.yaml).

## Where these files go

The egress policies are `NetworkPolicy` resources, the same kind as the s7 ingress policies already in `k8s/network-policies/` — and that directory already has a GitOps home: the `network-policies` Application at [k8s/argocd/infra/network-policies.yaml](../k8s/argocd/infra/network-policies.yaml) (sync wave `1`, since s18b) syncs everything in it. So the new files land there too, not in `k8s/security/` — `k8s/security/` is reserved for CRs that depend on an operator's CRDs (ESO's `SecretStore`/`ExternalSecret`, Kyverno's `ClusterPolicy` from s19b), and a plain `NetworkPolicy` has no such dependency.

## Dry run before committing

These are plain manifests (no Helm chart involved, unlike `users-api`), so there's no `helm template` step — just `kubectl` against the manifests directly.

```bash
# Client-side: catches YAML/schema errors, no cluster round-trip
kubectl apply --dry-run=client -f k8s/network-policies/egress-default-deny.yaml -f k8s/network-policies/egress-users-api.yaml -f k8s/network-policies/egress-postgres.yaml
```

Success looks like this — one line per object, each ending in `(dry run)`:

```
networkpolicy.networking.k8s.io/default-deny-egress created (dry run)
networkpolicy.networking.k8s.io/users-api-egress created (dry run)
networkpolicy.networking.k8s.io/postgres-egress created (dry run)
```

`created (dry run)` (rather than `configured (dry run)`) also confirms these are new objects — nothing by these names exists live yet. If a file were broken you'd get a non-zero exit and an error instead of that line.

**What client-side dry-run does *not* catch**, since it only checks YAML syntax and object schema against the client's cached OpenAPI definitions:
- Kyverno admission rules or PSS restricted (from s19b) rejecting the object — only `--dry-run=server` runs admission.
- Whether the `podSelector`/`namespaceSelector` labels actually match anything live (e.g. `app: users-api`, `cnpg.io/cluster: postgres`) — a typo'd label passes schema validation fine but silently matches zero Pods. Check with:
  ```bash
  kubectl get pods -l app=users-api --show-labels
  kubectl get pods -l cnpg.io/cluster=postgres --show-labels
  ```

```bash
# Server-side: also runs admission (Kyverno policies from s19b, PSS restricted), still no changes applied
kubectl apply --dry-run=server -f k8s/network-policies/egress-default-deny.yaml -f k8s/network-policies/egress-users-api.yaml -f k8s/network-policies/egress-postgres.yaml

# Diff against what's currently live in the cluster
kubectl diff -f k8s/network-policies/egress-default-deny.yaml -f k8s/network-policies/egress-users-api.yaml -f k8s/network-policies/egress-postgres.yaml
```

`--dry-run=server` is the one worth trusting here: since these `NetworkPolicy` objects go through the `network-policies` Application, ArgoCD's own sync is effectively a server-side apply, so this reproduces what ArgoCD will do on push. `kubectl diff` needs the objects to already exist live to show anything — for brand-new files like these it'll just show a full add, same as `kubectl apply --dry-run=client -o yaml`.

## Commands

```bash
# Commit the egress NetworkPolicies to the directory ArgoCD already syncs.
# ArgoCD's network-policies Application picks these up on its next sync.

# Test egress: exec into users-api and try to reach the internet
# (this image has no curl — busybox's wget/nc applets exist but aren't
# symlinked, so `command -v curl/wget/nc` finds nothing; call them via `busybox`)
kubectl exec -it deploy/users-api -- busybox wget -T5 -O- https://httpbin.org/get
# Should timeout (egress denied)

# But internal traffic still works — nc is a TCP-level check (port open/closed),
# notify-api:50051 is gRPC (HTTP/2), so a plain wget/curl GET connects fine but then fails on the response 
# ("Resource temporarily unavailable")
kubectl exec -it deploy/users-api -- busybox nc -zv -w5 notify-api 50051
```

## Try to break it

### Default-deny egress breaks DNS

Apply the default-deny egress policy without the DNS allowlist:

```bash
kubectl exec -it deploy/users-api -- nslookup postgres-rw
# ;; connection timed out; no servers could be reached
```

Every name resolution fails. The app can't connect to Postgres (can't resolve `postgres-rw`). Fix: add the DNS egress rule allowing port 53 to `kube-system`.

### Default-deny egress breaks Postgres itself, not just the app calling it

Ship `egress-default-deny.yaml` and `egress-users-api.yaml` alone (no `egress-postgres.yaml`). `users-api` still looks fine — its own egress is allowlisted. But its `migrate` initContainer starts failing:

```
psql: error: connection to server at "postgres-pooler-rw" (10.96.113.87), port 5432 failed: FATAL:  server login has been failing, cached error: server DNS lookup failed (server_login_retry)
```

The `postgres-pooler-rw` (pgbouncer) Pod has `cnpg.io/cluster: postgres`, which matches `default-deny-egress`'s blanket `podSelector: {}` — and nothing allowlists egress *for* Postgres itself. The pooler can't resolve or reach its own backend, so every connection routed through it fails, even though the client's own egress is fine.

Fix: add `egress-postgres.yaml` (DNS + peer/pooler traffic on 5432/8000 + Kubernetes API on 443, all scoped to `cnpg.io/cluster: postgres`).

Gotcha: pgbouncer caches the login failure (`server_login_retry`) and won't retry the instant the NetworkPolicy allows it. Give it a restart or a minute of natural retry before assuming the fix didn't work.
