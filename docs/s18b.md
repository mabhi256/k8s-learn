# s18b - GitOps (ArgoCD)

> **Tag:** `s18b`
> Goal: stop running `helm install` and `kubectl apply` by hand. ArgoCD watches a Git repo and continuously reconciles cluster state to match what's committed. Every application-level Helm chart, values file, and raw manifest from previous stages becomes an `Application` CR: the LGTM observability stack, infrastructure (CNPG, KEDA, TLS, RBAC, NetworkPolicies, MinIO, Postgres), and application workloads (users-api, frontend, notify-api). s18a already moved notify-api and frontend to Helm charts, so every app workload now has a Helm source ArgoCD can manage.
>
> Cluster prerequisites (cert-manager, ingress-nginx, metrics-server, the istio mesh) are GitOps-managed too, just pulled into low sync waves so they reconcile before the apps that depend on them. The only things left outside GitOps are ArgoCD itself (it can't install itself) and the deferred istio Gateway API. See [Bootstrap prerequisites](#bootstrap-prerequisites).

So far, deploying means SSHing (or exec'ing) into a shell and running Helm/kubectl commands. This provides us no audit trail, no review process, no rollback beyond "who remembers the last command?" GitOps fixes this by making Git the single source of truth. ArgoCD is the controller that enforces it.

---

## What GitOps is

GitOps is an operational model where:

1. **Desired state lives in Git.** Every manifest, Helm chart, and values file is committed and reviewed.
2. **An agent reconciles.** A controller (ArgoCD) watches the repo and the cluster. When they diverge (someone edits a Deployment by hand, or a new commit lands), it reconciles.
3. **Git is the audit log.** Who changed what, when, and why is the Git history. `kubectl edit` doesn't exist in a GitOps world.

### Push vs Pull

| Model | How deployments happen | Tool example |
| --- | --- | --- |
| **Push** (CI/CD) | CI pipeline runs `kubectl apply` or `helm upgrade` after a successful build | GitHub Actions, Jenkins |
| **Pull** (GitOps) | An in-cluster agent polls Git, detects drift, applies changes | ArgoCD, Flux |

Push has a credentials problem: CI needs cluster creds (`KUBECONFIG`), which are long-lived and hard to scope. Pull inverts it: ArgoCD runs inside the cluster with a ServiceAccount, and only needs read access to the Git repo.

Push deploys when CI runs (on merge). Pull deploys continuously — it also catches manual `kubectl` edits and reverts them (drift detection).

## ArgoCD vs Flux

| | ArgoCD | Flux |
| --- | --- | --- |
| Architecture | Central server + UI + API. One ArgoCD manages many apps. | Per-cluster controllers. No central UI (Weave GitOps is optional). |
| UI | Built-in web UI with sync status, diff viewer, logs | No built-in UI |
| Multi-tenancy | AppProject CRD scopes repos + clusters per team | Kubernetes RBAC + namespaced source CRDs |
| Helm support | Native rendering of charts | HelmRelease CRD (Helm controller) |
| CRD model | `Application`, `ApplicationSet`, `AppProject` | `GitRepository`, `Kustomization`, `HelmRelease`, `HelmRepository` |
| Community | CNCF graduated | CNCF graduated |

We use ArgoCD because the UI makes it easier to see what's happening, and the `Application` CRD model maps directly to "one app = one Helm release or one directory."

## Architecture

```text
┌────────────────────────────────────────────────────────────┐
│  ArgoCD (argocd namespace)                                 │
│                                                            │
│  ┌──────────────────────┐  ┌────────────────────────────┐  │
│  │  argocd-server       │  │  argocd-repo-server        │  │
│  │  - API + UI          │  │  - clones Git repos        │  │
│  │  - serves dashboard  │  │  - renders Helm templates  │  │
│  └──────────────────────┘  │  - caches manifests        │  │
│                            └────────────────────────────┘  │
│  ┌──────────────────────┐  ┌────────────────────────────┐  │
│  │  argocd-application- │  │  argocd-dex-server         │  │
│  │  controller          │  │  - SSO integration         │  │
│  │  - reconcile loop    │  │  - (Optional)              │  │
│  │  - detects drift     │  │  - (Not used here)         │  │              │  │  - syncs to cluster  │  └────────────────────────────┘  │ 
│  └──────────────────────┘                                  │ 
│                                                            │
└────────────────────────────────────────────────────────────┘
         │                              ▲
         │ applies manifests            │ polls (3 min default)
         ▼                              │
  ┌──────────────┐              ┌───────┴──────────┐
  │  Kubernetes  │              │  Git repository  │
  │  cluster     │              │  (this repo)     │
  └──────────────┘              └──────────────────┘
```

The application-controller is the core. Every 3 minutes (configurable) it:

1. Asks the repo-server for the rendered manifests from Git.
2. Compares them to what's in the cluster.
3. If they differ (drift), marks the Application as `OutOfSync`.
4. If auto-sync is enabled, applies the diff. Otherwise, waits for a human to click "Sync" or run `argocd app sync`.

## Application CRD

An `Application` is ArgoCD's unit of deployment. It maps a **source** (Git repo + path, or Helm chart) to a **destination** (cluster + namespace).

### Key fields

**`spec.source.repoURL`**: the Git repository URL. For this project, it's the repo itself.

**`spec.source.path`**: the directory within the repo. For Helm charts, this is the chart directory (e.g. `helm/users-api`). For plain manifests, it's the directory to `kubectl apply` (e.g. `k8s/users-api`).

**`spec.source.targetRevision`**: the Git ref to track. `HEAD` for main branch, or a specific branch/tag. For external Helm charts, this is a semver constraint like `"87.*"` or `"2.*"`. ArgoCD picks the highest matching version from the chart repository. To find the current major version for a chart:

```bash
helm repo update
helm search repo prometheus-community/kube-prometheus-stack --versions | head -5
# NAME                                              CHART VERSION   APP VERSION
# prometheus-community/kube-prometheus-stack        87.2.1          v0.91.0
# → use targetRevision: "87.*"
```

**`spec.source.helm.valueFiles`**: list of values files to pass to `helm template`. Replaces `-f` flags on the CLI.

**`spec.destination.server`**: the cluster API server URL. `https://kubernetes.default.svc` for the local cluster.

**`spec.destination.namespace`**: where to deploy the resources.

**`spec.syncPolicy.automated`**: enable auto-sync. Without this, ArgoCD detects drift but doesn't fix it.

**`spec.syncPolicy.automated.prune`**: delete resources in the cluster that aren't in Git. Without this, ArgoCD only adds/updates, never removes. Set to `true` for full GitOps (cluster matches Git exactly).

**`spec.syncPolicy.automated.selfHeal`**: revert manual `kubectl` edits. If someone scales a Deployment by hand, ArgoCD reverts it to the Git-defined value.

### Single source vs multi-source

When the Helm chart and the values file are in the same Git repo, a single `source` with `path:` is enough:

```yaml
# users-api: chart and values both live in k8s-learn
source:
  repoURL: https://github.com/mabhi256/k8s-learn.git
  targetRevision: HEAD
  path: helm/users-api              # chart is here
  helm:
    valueFiles:
      - values.yaml                 # relative to the chart directory
```

When the Helm chart is in an external repo (e.g., keda from `kedacore.github.io/charts`) but the values file is in your Git repo, a single `source` can only point at one repo. You need `sources` (plural) with a `ref`:

```yaml
# keda: chart is external, values are in k8s-learn
sources:
  # Source 1: clone your Git repo and name it "values"
  - repoURL: https://github.com/mabhi256/k8s-learn.git
    targetRevision: HEAD
    ref: values                     # arbitrary name, doesn't deploy anything,
                                    # just makes the repo contents addressable

  # Source 2: the Helm chart to actually deploy
  - repoURL: https://kedacore.github.io/charts
    chart: keda
    targetRevision: "2.*"
    helm:
      valueFiles:
        - $values/helm/values/keda.values.yaml
                                    # $values = root of Source 1's repo
```

`ref: values` tells ArgoCD "clone this repo and let other sources reference its files as `$values/...`". The ref name is arbitrary. The ref source doesn't deploy anything on its own.

If you use `$values/...` inside a single `source` (without a `ref` to resolve it), ArgoCD silently fails: the app shows `Unknown` sync status with no error message.

## AppProject

An `AppProject` scopes what an Application can do:

- **Source repos**: which Git repos the Application can pull from.
- **Destinations**: which clusters and namespaces it can deploy to.
- **Cluster resources**: which cluster-scoped resources (ClusterRole, Namespace, CRD) it can create.

The default `AppProject` allows everything. Create scoped projects for teams: the `platform` project can deploy CRDs and cluster-scoped resources; the `apps` project can only deploy to `default` namespace.

## App of Apps pattern

Instead of creating each `Application` CR by hand, create one "root" Application that points at a directory of Application manifests. ArgoCD applies the root, which creates the child Applications, which each sync their own source.

```text
k8s/argocd/
├── root-app.yaml              ← the one Application you apply manually
├── apps/                      ← application workloads
├── lgtm/                      ← observability stack
└── infra/                     ← cluster infrastructure
```

The root Application uses `directory.recurse: true` to discover all Application manifests across subdirectories, with an `exclude` to skip itself:

```yaml
source:
  path: k8s/argocd
  directory:
    recurse: true
    exclude: root-app.yaml
```

`kubectl apply -f k8s/argocd/root-app.yaml` is the only manual command. Everything else is managed by ArgoCD from Git.

Grouping is purely organizational: ArgoCD treats every YAML file it finds as an Application CR. The subdirectory names (`apps/`, `lgtm/`, `infra/`) have no effect on sync behavior or ordering. Sync waves (set per Application via annotations) control the deploy order.

## Why `kubectl apply`, not `helm install`

Up to this point, every component was deployed with `helm install` or `helm upgrade`. The root Application is the exception: it's a single 15-line CRD instance, not a Helm chart. There's nothing to template, no values to override, no release lifecycle to track. Wrapping it in a chart would add files and complexity for zero benefit.

More importantly, ArgoCD **replaces** `helm install/upgrade` for everything it manages. The child Applications (users-api, kube-prometheus, etc.) each point at a Helm chart directory via `spec.source.helm`, but ArgoCD never runs `helm install`. It runs `helm template` to render the manifests, then applies the raw Kubernetes resources itself using its own applicator. There is no Helm release Secret, no `helm list` entry, no Helm state in the cluster.

The deployment model changes:

| | Before ArgoCD | After ArgoCD |
| --- | --- | --- |
| **You run** | `helm install users-api ./helm/users-api -f values.yaml` | `git push` |
| **What happens** | Helm renders templates, creates K8s resources, stores release state in a Secret | ArgoCD runs `helm template`, applies K8s resources directly, tracks state in the Application CR |
| **Release tracking** | `helm list` shows the release | `kubectl get applications -n argocd` shows sync status |
| **Upgrades** | `helm upgrade users-api ...` | Commit new values to Git; ArgoCD detects the diff and syncs |

The bootstrap is two manual commands:

1. `helm install argocd` (installs the ArgoCD operator itself, which *is* a complex chart with values)
2. `kubectl apply -f root-app.yaml` (creates one CRD instance that kicks off the app-of-apps)

After that, Git is the only interface.

### Bootstrap prerequisites

A handful of cluster-level components must exist *before* the application and observability Applications can sync: cert-manager provides the CRDs the `tls` app uses, the istio mesh injects sidecars, metrics-server backs the HPAs, and ingress-nginx fronts every `Ingress`. These are now GitOps-managed too, pulled into low sync waves so they reconcile first:

| Component | Application(s) | Sync wave | Depended on by |
| --- | --- | --- | --- |
| **cert-manager** (controller + CRDs) | `cert-manager` | `-2` | `tls` app, kube-prometheus admission-webhook certs (`ca-issuer`) |
| **ingress-nginx** | `ingress-nginx` | `-2` | argocd-server, users-app, grafana ingresses |
| **metrics-server** | `metrics-server` | `-2` | `kubectl top`, native cpu/memory HPAs (istio) |
| **istio mesh** | `istio-base` (CRDs), `istiod` | `-2`, `-1` | mesh-enabled workloads |

Wave `-2` installs the CRD-bearing and cluster-addon charts first; `istiod` sits at `-1` so istio's CRDs (from `istio-base`) exist before the control plane renders. The `tls` app (also wave `-1`) then has cert-manager's webhook ready before it creates `ClusterIssuer`/`Certificate` CRs.

**ArgoCD itself** stay outside GitOps. It can't install itself and needs a manual `helm install` (see the bootstrap commands above).

`prometheus-adapter` is intentionally absent: KEDA's prometheus scaler (via `external.metrics.k8s.io`) replaces it, so no custom-metrics adapter runs.

Versions for these four are **pinned** to the running releases (cert-manager `v1.20.2`, ingress-nginx `4.15.1`, metrics-server `3.13.1`, istio `1.30.1`) rather than floating a major like the app charts. They underpin the cluster (CRDs, mesh, ingress, metrics), and pinning makes the first sync a clean in-place adoption instead of an unplanned upgrade. Bump them deliberately later.

## Adopting already-running workloads

If the cluster already has workloads running from previous `helm install` or `kubectl apply` commands, ArgoCD can adopt existing resources, but only when the resource names match exactly.

Helm bakes the release name into every resource name (e.g. `helm install prom kube-prometheus-stack` creates `prom-prometheus-node-exporter`). ArgoCD renders the same chart under its own Application name (e.g. `kube-prometheus`), producing `kube-prometheus-prometheus-node-exporter`. These are different resources to Kubernetes. ArgoCD creates its set; the old set keeps running. For DaemonSets that bind a hostPort (like node-exporter on port 9100), the new pods stay Pending because the old pods already occupy the port.

Only two releases in this project have a name mismatch: `prom` (ArgoCD Application: `kube-prometheus`) and `http-add-on` (ArgoCD Application: `keda-http`). These must be `helm uninstall`-ed immediately after applying the root Application (step 7 in the Commands section). Deleting the old release removes its resources, freeing ports and cluster-scoped names so ArgoCD's versions can schedule.

### What gets adopted in place

Every other Helm release was installed under the same name as its ArgoCD Application (e.g. `helm install users-api` → Application `users-api`). The rendered resource names match exactly, so ArgoCD's three-way diff finds the existing Deployments, Services, etc. and takes ownership:

1. **Resources exist and match Git**: ArgoCD labels them as managed and reports `Synced`. Nothing changes in the cluster.
2. **Resources exist but differ**: ArgoCD patches them to match Git.
3. **Resources don't exist yet**: ArgoCD creates them.

| Namespace | Adopted releases |
| --- | --- |
| `lgtm` | alloy, loki, tempo, otel-collector, dashboards, vpa |
| `default` | users-api, notify-api, frontend, db-backup |
| `cnpg-system` | cnpg |
| `keda` | keda |
| `kube-system` | metrics-server |
| `istio-system` | istio-base, istiod |

The old Helm release Secrets linger in `helm list` but are harmless. Do **not** `helm uninstall` these: that deletes the live resources (ArgoCD recreates them, but with a needless outage).

`istio-ingressgateway` has no ArgoCD Application (Gateway API is deferred) and stays as a manual Helm release.

### Why cert-manager and ingress-nginx moved to Helm charts

In previous stages, both were installed from static manifests (`kubectl apply -f <url>`). ArgoCD needs a source to reconcile against, so there are two options:

1. **Vendor the manifests**: download the YAML, commit it to a directory like `k8s/cert-manager/`, point the Application at it. This is what the `tls` and `rbac` Applications do with our own small manifests. But cert-manager's static manifest is ~6,000 lines of upstream YAML we don't own. Version bumps mean downloading a new file and reviewing a massive diff.
2. **Use the official Helm chart**: ArgoCD pulls directly from the chart repo, the version is one line in `targetRevision`, and overrides go in a small values file. Both cert-manager and ingress-nginx publish official charts.

Either approach works. We went with Helm charts because vendoring large upstream manifests adds maintenance burden for no benefit when an official chart exists.

Because the original install was `kubectl apply`, the existing resources carry a `last-applied-configuration` annotation. ServerSideApply ignores it, but on the larger cert-manager CRDs it can still block a patch. If a CRD sync errors, strip the annotation as described in [ServerSideApply and large CRDs](#serversideapply-and-large-crds).

## Sync waves and hooks

When multiple resources need to deploy in order (CRDs before CRs, Namespace before Deployments), use sync waves:

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"  # deploys before wave 0
```

Lower waves sync first. Default is `0`. This project uses: `-2` for cluster prerequisites (cert-manager, ingress-nginx, metrics-server, istio-base CRDs), `-1` for things that depend on those CRDs (istiod, rbac, tls), `0` for operators, `1` for application CRs.

Hooks run at specific sync phases:

| Hook | When it runs |
| --- | --- |
| `PreSync` | Before the sync (e.g. DB migration Job) |
| `Sync` | During the sync (default for all resources) |
| `PostSync` | After successful sync (e.g. smoke test, notification) |
| `SyncFail` | After a failed sync (e.g. alert) |

### Checking diffs

When an Application shows `OutOfSync`, find which resources are drifting and what fields differ:

```bash
# Which resources are out of sync?
kubectl get application <app-name> -n argocd \
  -o jsonpath='{.status.resources}' | jq '.[] | select(.status != "Synced")'

# Full diff via the ArgoCD CLI (requires port-forward or ingress to argocd-server)
argocd app diff <app-name>

# If you don't have the CLI configured, inspect the Application status directly
kubectl get application <app-name> -n argocd -o yaml | grep -A 50 'status:'
```

The first command is the most useful: it returns the `group`, `kind`, and `name` of every out-of-sync resource without needing the ArgoCD CLI. From there you can compare the live object to what the chart renders:

```bash
# See what ArgoCD would apply (the "desired" state)
helm template <release-name> <chart-path> -f <values-file> | kubectl diff -f -

# Or inspect the live object directly
kubectl get <kind> <name> -o yaml
```

## Try to break it

### 1. Drift goes undetected for 3 minutes

ArgoCD polls every 3 minutes by default. A manual `kubectl` change persists for up to 3 minutes before ArgoCD notices.

```bash
kubectl scale deploy users-api --replicas=10
# For up to 3 minutes, 10 replicas run
# Then ArgoCD reverts to the Git-defined value
```

Fix for faster detection: enable webhooks. Configure the Git repo to POST to ArgoCD on push. Or reduce `timeout.reconciliation` in `argocd-cm` ConfigMap.

### 2. Prune deletes a resource you forgot was managed

With `prune: true`, deleting a manifest from Git deletes the resource from the cluster. If you remove a ConfigMap from Git thinking it's unused, ArgoCD deletes it. Any Pod mounting it fails on next restart.

```bash
# Remove configmap.yaml from Git, push
# ArgoCD syncs and deletes the ConfigMap
kubectl get events --sort-by='.lastTimestamp' | grep ConfigMap
```

Mitigation: ArgoCD marks resources with `argocd.argoproj.io/sync-options: Delete=false` to protect them from pruning.

### 3. Self-heal fights KEDA (or any autoscaler)

KEDA scales a Deployment's replicas based on metrics. With `selfHeal: true`, ArgoCD sees the replica count diverge from Git and reverts it, creating a tug-of-war: KEDA scales up, ArgoCD scales back down, repeat.

The fix: tell ArgoCD to ignore the `replicas` field on Deployments, and force that ignorance during syncs:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
  syncPolicy:
    syncOptions:
      - RespectIgnoreDifferences=true
```

`ignoreDifferences` alone only suppresses the diff in the UI and status. Without `RespectIgnoreDifferences=true`, ArgoCD still resets replicas during an actual sync. Both are required.

This applies to any external controller that mutates Deployment fields: KEDA, HPA, VPA (for resource requests/limits). Identify the drifting field, add it to `ignoreDifferences`, and enable `RespectIgnoreDifferences`.

### 4. Self-heal reverts a legitimate hotfix

With `selfHeal: true`, emergency `kubectl` changes get reverted. You patch a broken image tag via `kubectl set image`, ArgoCD reverts it to the Git version within 3 minutes.

The GitOps answer: even for emergencies, commit to Git. The trade-off is speed — a 2-minute PR merge vs. a 5-second `kubectl set image`. Teams compromise by having an "emergency" branch that ArgoCD watches, or temporarily disabling selfHeal.

## Notes

### kube-prometheus-stack admission webhook Jobs

The kube-prometheus-stack chart creates short-lived Jobs (`kube-prometheus-kube-prome-admission-create` and `-patch`) to generate self-signed certificates for its ValidatingWebhookConfiguration. These Jobs run, complete, and get garbage-collected. ArgoCD tracks them as managed resources, so the next sync fails with "Resource batch/Job/... is missing, it might have been deleted."

The fix: since we already run cert-manager, tell the chart to use it for webhook certs instead of the self-signed Job approach. In the values file:

```yaml
prometheusOperator:
  admissionWebhooks:
    certManager:
      enabled: true
      issuerRef:
        name: ca-issuer
        kind: ClusterIssuer
```

This eliminates the Jobs entirely. cert-manager issues and renews the webhook certificate via a `Certificate` CR.

### Istio webhook OutOfSync

Both `istio-base` and `istiod` show `OutOfSync` even with `automated` sync and `selfHeal: true` enabled. The out-of-sync resources are `ValidatingWebhookConfiguration`s:

- `istio-base`: `istiod-default-validator`
- `istiod`: `istio-validator-istio-system`

The cause: istiod's webhook controller injects a `caBundle` (and may flip `failurePolicy`) into these webhook configs after every sync. ArgoCD sees the live state differs from what the Helm chart rendered, marks the app OutOfSync, syncs again, and istiod mutates the fields again. The cycle never settles.

The fix uses two ArgoCD features together:

1. **`ignoreDifferences`** tells ArgoCD to exclude specific fields from the diff. Ignoring `/webhooks` on the `ValidatingWebhookConfiguration` kind covers `caBundle`, `failurePolicy`, and any other fields istiod manages:

   ```yaml
   spec:
     ignoreDifferences:
       - group: admissionregistration.k8s.io
         kind: ValidatingWebhookConfiguration
         jsonPointers:
           - /webhooks
   ```

2. **`RespectIgnoreDifferences=true`** sync option prevents ArgoCD from overwriting the ignored fields during sync. Without this, ArgoCD still ignores the diff for status purposes but resets the fields on the next sync, and istiod mutates them right back:

   ```yaml
   syncOptions:
     - RespectIgnoreDifferences=true
   ```

This pattern applies to any operator that mutates its own resources post-apply (cert-manager's webhook `caBundle` is another common case). Identify the drifting fields with `kubectl get application <name> -n argocd -o jsonpath='{.status.resources}' | jq '.[] | select(.status != "Synced")'`, then add the matching `ignoreDifferences` entry.

### ServerSideApply and large CRDs

When you run `kubectl apply` or `helm install`, Kubernetes uses **client-side apply**. The client (kubectl/Helm) stores the entire manifest in the `kubectl.kubernetes.io/last-applied-configuration` annotation on the resource. On the next apply, the client diffs the new manifest against this annotation to figure out what changed.

This works fine for small resources, but CRDs can be enormous. The KEDA `scaledjobs.keda.sh` CRD contains a full OpenAPI v3 schema that's over 260 KB of YAML. When the client writes that entire manifest into a single annotation, it hits Kubernetes' hard limit: **262144 bytes (256 KiB) for all annotations on one resource**. The apply fails with:

```text
metadata.annotations: Too long: may not be more than 262144 bytes
```

A related error, **"counter cannot decrease in value"**, shows up when Kubernetes rejects a CRD patch because the new schema has fewer validation rules than the old one. Kubernetes enforces this to prevent breaking existing CRs, and client-side apply's patch strategy makes it easy to trigger.

**Server-side apply (SSA)** avoids both problems. Instead of storing the full manifest in an annotation, the API server tracks field ownership in `managedFields` metadata, which has no size limit. The `ServerSideApply=true` sync option tells ArgoCD to use SSA:

```yaml
syncOptions:
  - ServerSideApply=true
```

The KEDA and kube-prometheus-stack Applications both need this because their CRDs are too large for client-side apply.

**Adopting CRDs from a previous `helm install`**: when ArgoCD takes over resources that were originally installed with client-side apply, the stale `last-applied-configuration` annotation is already on the CRD. SSA doesn't write new annotations, but it also doesn't remove old ones. The oversized annotation still sits on the resource and can block patches. Fix by stripping the annotation:

```bash
# KEDA CRDs
kubectl get crd -l app.kubernetes.io/part-of=keda-operator -o name | \
  xargs -I{} kubectl annotate {} kubectl.kubernetes.io/last-applied-configuration-

# kube-prometheus-stack CRDs (if the same error appears)
kubectl get crd -l app.kubernetes.io/part-of=kube-prometheus-stack -o name | \
  xargs -I{} kubectl annotate {} kubectl.kubernetes.io/last-applied-configuration-

# cert-manager CRDs (required, not optional). cert-manager was installed from a
# static manifest via `kubectl apply`, so all 6 CRDs carry the annotation (the
# acme/issuer ones are ~140 KB). Without stripping, the cert-manager Application
# stays OutOfSync.
kubectl get crd -l app.kubernetes.io/name=cert-manager -o name | \
  xargs -I{} kubectl annotate {} kubectl.kubernetes.io/last-applied-configuration-
```

After stripping, ArgoCD syncs cleanly with SSA. No annotation buildup going forward.

### Mimir remote-write (disabled)

The values file `helm/values/kube-prometheus-stack.mimir.values.yaml` configures Prometheus to remote-write metrics to a Mimir gateway. This is commented out in the ArgoCD Application because we use Prometheus directly without Mimir. To enable it, uncomment the second `valueFiles` entry in `k8s/argocd/lgtm/kube-prometheus.yaml`.
