# s16a - Operators and CRDs (CloudNativePG)

> **Tag:** `s16a`
> Goal: understand Custom Resource Definitions (CRDs) and operators by replacing the manual Postgres StatefulSet from s5 with CloudNativePG. The operator manages HA failover, backups, and connection pooling through a single `Cluster` CR.

Every Helm chart from s11 onward has installed CRDs: `ServiceMonitor` (kube-prometheus-stack), `VPA` (Fairwinds), `VirtualService` (Istio). We've been using CRDs without explaining the machinery.

---

## What is a CRD

A Custom Resource Definition extends the Kubernetes API with new resource types. After applying a `ServiceMonitor` CRD, the API server accepts `kind: ServiceMonitor` objects. The CRD itself just registers the type and its schema -- it doesn't do anything with the objects. That's the operator's job.

```text
┌──────────────┐   registers type   ┌─────────────────────┐
│  CRD YAML    │ ─────────────────▶ │  API server         │
│  (schema)    │                    │  now accepts        │
└──────────────┘                    │  kind: Cluster      │
                                    └──────────┬──────────┘
                                               │
                                    watches via│ informer
                                               ▼
                                    ┌──────────────────────┐
                                    │  Operator            │
                                    │  (controller-manager)│
                                    │  reconciles desired  │
                                    │  state → actual      │
                                    └──────────────────────┘
```

The CRD is the schema. The CR (Custom Resource) is an instance (like a row matching the schema). The operator is the controller that watches CRs and makes reality match.

### What is a controller

A **controller** is a control loop that runs continuously inside the cluster. It:

1. Watches a resource type via the API server's informer/watch mechanism.
2. Compares **desired state** (the spec you wrote) to **actual state** (what's running).
3. Takes whatever action is needed to close the gap -- create, update, or delete objects.
4. Repeats forever.

Kubernetes ships with built-in controllers for every core resource:

- The Deployment controller watches `Deployment` objects and manages ReplicaSets
- The ReplicaSet controller watches `ReplicaSet` objects and manages Pods
- The Node controller watches nodes and marks them `NotReady` when they stop heartbeating.
- They all run inside `kube-controller-manager`.

A controller has no opinion about *what* the resource means. It just reconciles.

### What is an operator

An **operator** is a controller that also encodes **domain knowledge about a specific application**. The term was coined by CoreOS (2016) to mean "software that does what a human operator would do" -- it knows how to install, upgrade, back up, and heal a specific stateful app.

Concretely: an operator is a controller that:

- Ships its own CRD (the schema for the high-level resource you write).
- Watches instances of that CRD.
- Does app-specific things in response: trigger a Postgres failover, coordinate a Kafka rolling restart, run a backup, update a TLS certificate.

**All operators are controllers. Not all controllers are operators.**

- The Deployment controller is a controller but not an operator. It knows nothing about what runs inside its Pods.
- CloudNativePG is an operator. It knows Postgres: WAL, replication slots, `pg_promote()`, connection pooling.

The reconcile loop is idempotent. Calling it twice with the same input produces the same result. Kubernetes relies on this: the controller may be restarted or re-queued at any time.

### Building vs using operators

| Approach | Tool | When |
| --- | --- | --- |
| **Use** an existing operator | `helm install`, apply CRs | You need managed Postgres, Redis, Kafka, etc. This stage. |
| **Build** your own operator | kubebuilder, operator-sdk | You have domain-specific lifecycle logic that doesn't exist as an operator yet. Rare for most teams. |

We focus on using operators here. Building one is a niche skill and most teams will never need it.

## Why CloudNativePG

The s5 Postgres setup is a single-replica StatefulSet. No failover, no automated backups, no connection pooling. If the Pod dies, the app is down until the StatefulSet controller recreates it and the PVC reattaches.

CloudNativePG (CNPG) is a CNCF-sandbox Postgres operator. One `Cluster` CR gives you:

| Feature | StatefulSet (s5) | CloudNativePG |
| --- | --- | --- |
| **HA failover** | None. Single replica. | Primary + N replicas. Automatic promotion on primary failure (typically <10s). |
| **Backups** | Manual `pg_dump` CronJob (s17). | Built-in: base backup + continuous WAL archiving to object storage or PVC. Point-in-time recovery. |
| **Connection pooling** | None. App connects directly. | Built-in PgBouncer sidecar. |
| **Rolling updates** | Manual. Must drain, update, restart. | Operator handles: update replicas first, switchover primary, zero-downtime. |
| **Monitoring** | None built-in. | Exports Prometheus metrics. Works with s12's ServiceMonitor. |

The trade-off: Running an operator on kind is trivial. On EKS, many teams use RDS despite the higher cost because of zero operational overhead.

## Architecture

```text
┌────────────────────────────────────────────────────────┐
│  CloudNativePG operator (Deployment, 1 replica)        │
│  watches: Cluster, Backup, ScheduledBackup CRDs        │
└────────────────────────────────────────────────────────┘
                             │ reconciles
                             ▼
┌────────────────────────────────────────────────────────┐
│  Cluster: postgres  (spec.instances: 2)                │
│                                                        │
│  ┌──────────────┐  ┌──────────────┐                    │
│  │  postgres-1  │  │  postgres-2  │   (3+ in prod)     │
│  │  (primary)   │  │  (replica)   │                    │
│  │  read-write  │  │  read-only   │                    │
│  └──────┬───────┘  └──────┬───────┘                    │
│         │ PVC             │ PVC                        │
│         │                 │                            │
│  Services:                                             │
│    postgres-rw  ──▶ primary only                       │
│    postgres-ro  ──▶ replicas (round-robin)             │
│    postgres-r   ──▶ any (primary + replicas)           │
└────────────────────────────────────────────────────────┘
```

The CloudNativePG operator creates:

- **Pods** (not a StatefulSet).
- **PVCs** per instance.
- **Services**: `-rw` for writes (always points at primary), `-ro` for read replicas, `-r` for any instance.
- **Secrets** with credentials (auto-generated or user-supplied).

### Failover

When the primary Pod fails (or the node is drained), the operator:

1. Detects the failure (via pod informer + health checks).
2. Promotes the most up-to-date replica to primary.
3. Updates the `-rw` Service to point at the new primary.
4. Reconfigures remaining replicas to follow the new primary.

Typical failover time: 5-10 seconds. Clients connected via the `-rw` Service see a brief disconnect.

## The Cluster CR

### Key fields

**`spec.instances`**: number of Postgres instances (1 primary + N-1 replicas). This lab uses `2` (1 primary + 1 replica), which already gives automatic failover: if the primary dies, the replica is promoted. Production clusters use `3+` so you still have a replica after one is promoted, and so synchronous-commit quorum survives a node loss.

**`spec.imageName`**: the Postgres image. CNPG ships curated images (`ghcr.io/cloudnative-pg/postgresql`) but accepts any Postgres image that follows the expected entrypoint contract.

**`spec.storage`**: PVC template for each instance. `size` is the volume size, `storageClass` selects the provisioner.

**`spec.bootstrap`**: how to initialize the cluster:

- `initdb`: create a fresh cluster with specified databases and owners.
- `recovery`: restore from a backup (point-in-time recovery).
- `pg_basebackup`: clone from an existing cluster.

**`spec.postgresql.parameters`**: Postgres configuration (`shared_buffers`, `max_connections`, etc.). Applied via `ALTER SYSTEM` -- no restart needed for most parameters.

**`spec.inheritedMetadata`**: annotations and labels propagated to all objects the operator creates (Pods, PVCs, Jobs). Used here to configure `holdApplicationUntilProxyStarts` so the Postgres process waits for the Istio sidecar to be ready before accepting connections.

**`spec.monitoring`**: CNPG instances export Prometheus metrics on a `metrics` port. To scrape them, create a `PodMonitor` that selects the cluster's Pods (`k8s/postgres-migration/podmonitor.yaml`). The cluster sets `monitoring.enablePodMonitor: false` because that built-in shortcut hardcodes a PodMonitor we can't customize; managing our own PodMonitor resource is the current recommendation.

**`spec.backup.retentionPolicy`**: how long base backups (and the WAL needed to recover them) are kept in the object store. The lab uses `7d`: CNPG deletes backups older than 7 days on the next backup run. Without a retention policy, backups accumulate forever.

**`spec.enableSuperuserAccess`** (not set, so defaults to off): when off, the `postgres` superuser has no password and can only be reached via local peer auth from inside the Pod. That is why the verify commands below run `psql -U postgres` *via `kubectl exec`* (inside the Pod) rather than over the network. Application traffic uses the `appuser` role from `postgres-app-credentials` instead.

## Backups

CNPG supports two backup methods:

| Method | What it stores | Recovery capability |
| --- | --- | --- |
| **Base backup** | Full data directory snapshot | Restore to the backup point |
| **WAL archiving** | Continuous stream of write-ahead log segments | Point-in-time recovery (restore to any second between backups) |

For kind, we use MinIO as a local S3-compatible object store (deployed in `k8s/minio/`). For production, backups go to S3/GCS/Azure Blob. Both use the same `barmanObjectStore` configuration in the Cluster CR.

Setting `backup.barmanObjectStore` in the Cluster CR does two things:

- it gives you a destination for on-demand and scheduled base backups, and
- it automatically enables continuous WAL archiving to that same location.

You don't configure WAL archiving separately. If the Cluster has no `barmanObjectStore`, there is no WAL archiving, and recovery is limited to whatever base backups exist.

A `ScheduledBackup` CR automates recurring base backups (`k8s/postgres/scheduled-backup.yaml`):

```yaml
spec:
  schedule: "0 0 3 * * *"  # 3 AM daily (6-field cron: sec min hour dom mon dow)
  backupOwnerReference: self
  method: barmanObjectStore
  cluster:
    name: postgres
```

Combined with WAL archiving, this gives you continuous protection: restore to any point in time between the oldest retained base backup and now. We apply this in Approach 3, after the object store is configured.

## Migrating from the s5 StatefulSet

The s5 StatefulSet creates a single Postgres Pod with a PVC. CNPG creates its own Pods and PVCs. We'll try all three bootstrap approaches, simplest first:

1. live clone (pg_basebackup)
2. dump + restore
3. object-store recovery

### Prerequisites

A few things must be in place before creating the cluster: two resources to apply (items 0 and 0b), and four conflicts inherited from earlier stages that must be fixed.

**0. Application credentials Secret.** Every bootstrap below references the `postgres-app-credentials` Secret (a `kubernetes.io/basic-auth` Secret holding `username: appuser` / `password: secret`). `initdb` uses it to create the `appuser` role, and the verify/connection steps use it to log in. Apply it before any cluster:

```bash
kubectl apply -f k8s/postgres/app-credentials.yaml
```

**0b. PodMonitor (metrics).** Independent of which bootstrap you pick, apply the PodMonitor once so Prometheus scrapes the cluster's Pods as soon as they come up. It selects `cnpg.io/cluster=postgres`, so it works across all three approaches:

```bash
kubectl apply -f k8s/postgres-migration/podmonitor.yaml
```

**1. ServiceAccount token mount:** The s5 StatefulSet created a `postgres` ServiceAccount with `automountServiceAccountToken: false` (Postgres didn't need API access). CNPG's instance manager needs the token to talk to the API server; without it, init pods fail with `open /var/run/secrets/kubernetes.io/serviceaccount/token: no such file or directory`. Rather than patching the legacy SA, the Cluster spec uses `serviceAccountTemplate` to create its own `cnpg-postgres` SA (which defaults to mounting the token). This keeps the legacy SA untouched for rollback.

**2. NetworkPolicy.** The s10 default-deny policy blocks all ingress. The old `allow-ingress-postgres` selected `app=postgres`, but CNPG pods use `cnpg.io/cluster=postgres`. The operator also needs port 8000 (instance manager health endpoint) from `cnpg-system`. Without this, the cluster gets stuck at "Instance Status Extraction Error: HTTP communication issue."

```bash
kubectl apply -f k8s/network-policies/postgres.yaml
```

The updated policy (`k8s/network-policies/postgres.yaml`) allows:

- Port 5432 from `users-api`, `db-seed`, `db-backup`, `db-restore`
- Port 5432 between CNPG pods (replication)
- Port 8000 from the `cnpg-system` namespace (operator health checks)

**3. Istio STRICT mTLS + Jobs.** The namespace uses STRICT mTLS (`k8s/istio/peer-authentication.yaml`). Every pod that connects to a mesh service needs an Istio sidecar. This creates two problems for Jobs:

- **Startup:** the main container must wait for the sidecar to be ready. Fix: `proxy.istio.io/config: '{"holdApplicationUntilProxyStarts": true}'`.
- **Shutdown:** when the main container exits, the sidecar keeps running and the pod stays `1/2 NotReady` forever. The Job never completes. Fix: the main container must tell the sidecar to quit before exiting. The `postgres:18` image has no `curl` or `wget`, so we use bash's built-in `/dev/tcp`:

```bash
exec 3<>/dev/tcp/localhost/15020 && \
  printf 'POST /quitquitquit HTTP/1.1\r\nHost: localhost\r\nContent-Length: 0\r\n\r\n' >&3 && \
  cat <&3 && exec 3>&- || true
```

This opens a raw TCP connection to the sidecar's admin port and sends the quit HTTP request. The `|| true` ensures the Job still succeeds if there's no sidecar (e.g., running without Istio).

**4. Istio port naming.** Istio identifies protocols by service port name prefix. Unrecognized names (like `postgres`) trigger protocol auto-detection, which can misparse the PostgreSQL wire protocol and drop the connection. Name database ports `tcp-postgres` so Istio treats them as opaque TCP. HTTP services (like MinIO) should use the `http-` prefix.

### Approach 1: pg_basebackup (live clone)

CNPG can clone directly from a running Postgres instance using the streaming replication protocol. No dump files, no restore Job. The old StatefulSet stays up while the clone happens. This is the simplest migration path: one CR and CNPG handles everything.

1. Install the CNPG operator.
2. Ensure the old StatefulSet is running.
3. Create the `Cluster` CR with `bootstrap.pg_basebackup` using `k8s/postgres-migration/cluster-basebackup.yaml`. CNPG connects to the old primary, streams a full base backup, and replays WAL to catch up.
4. Update the users-api connection string to point at `postgres-rw`.
5. Delete the old StatefulSet and PVC.

The `externalClusters` section in `postgres-migration/cluster-basebackup.yaml` tells CNPG where the source lives (`postgres-0.postgres-headless:5432`) and which Secret holds the password.

**Prerequisite: `postgres` superuser.** CNPG's instance manager connects as the `postgres` superuser internally for replication control, WAL management, and health checks. After `pg_basebackup` clones the data directory, the role catalog is an exact copy of the source. If the source was created with `POSTGRES_USER=appuser` (as in s5), there is no `postgres` role, and the instance manager fails with `FATAL: role "postgres" does not exist`. Create it on the source before cloning:

```bash
kubectl exec -it postgres-0 -- psql -U appuser -d appdb -c \
  "CREATE ROLE postgres WITH SUPERUSER LOGIN REPLICATION PASSWORD 'secret';"
```

**Trade-off:** minimal downtime (only the switchover moment), but the source instance must allow replication connections and stay up until the clone finishes. This is how production migrations typically work.

```bash
# Install the CNPG operator
helm repo add cnpg https://cloudnative-pg.github.io/charts
helm repo update
helm install cnpg cnpg/cloudnative-pg -n cnpg-system --create-namespace
kubectl -n cnpg-system rollout status deploy/cnpg-cloudnative-pg

kubectl apply -f k8s/postgres-migration/cluster-basebackup.yaml
kubectl get cluster postgres -w
# STATUS: Cloning → Healthy (streams base backup from postgres-0.postgres-headless, replays WAL)

kubectl get pods -l cnpg.io/cluster=postgres
# postgres-1 (primary, cloned from old), postgres-2 (replica)
```

#### Verify (same for all approaches)

```bash
kubectl describe cluster postgres

kubectl exec postgres-1 -- psql -U postgres -d appdb -c "SELECT * FROM users;"

kubectl exec postgres-2 -- psql -U postgres -d appdb -c "SELECT * FROM users;"

kubectl exec -it postgres-2 -- psql -U postgres -d appdb -c "SELECT pg_is_in_recovery();"
# Should return: t (true = replica)

kubectl get secret postgres-app-credentials -o jsonpath='{.data.username}' | base64 -d
kubectl get secret postgres-app-credentials -o jsonpath='{.data.password}' | base64 -d
# Connection: postgresql://appuser:secret@postgres-rw:5432/appdb
```

**Metrics.** Confirm the PodMonitor from Prerequisites is actually feeding Prometheus. CNPG exposes the `metrics` port on each instance Pod:

```bash
# Scrape an instance directly (sanity check the exporter is up)
kubectl exec postgres-1 -- bash -c \
  'exec 3<>/dev/tcp/localhost/9187; printf "GET /metrics HTTP/1.0\r\n\r\n" >&3; cat <&3' \
  | grep -m1 cnpg_collector_up

# In Prometheus, this query should return a series per instance:
#   cnpg_collector_up{namespace="default", pod="postgres-1"}  1
# Grafana: import CNPG dashboard 20417 (or the chart's bundled one) to see
# connections, replication lag, and WAL archiving status.
```

If no series appear, the usual causes are the same as s12/s14: the default-deny NetworkPolicy (Prometheus must be allowed to scrape the `metrics` port) or the Istio sidecar intercepting the scrape. The PodMonitor selects `cnpg.io/cluster=postgres`, so a missing label or a typo in the selector also silently yields zero targets.

Test the connection path that users-api will use: `postgres-rw` service, `appuser` credentials, `appdb` database, and the NetworkPolicy allowing ingress on port 5432. This runs a throwaway pod so we don't have to switch users-api's config between approaches.

```bash
kubectl run pg-conntest --rm -it --image=postgres:18 --restart=Never \
  --labels="app=users-api" \
  --annotations='proxy.istio.io/config={"holdApplicationUntilProxyStarts": true}' -- \
  bash -c 'psql "postgresql://appuser:secret@postgres-rw:5432/appdb" -c "SELECT count(*) FROM users;"; exec 3<>/dev/tcp/localhost/15020 && printf "POST /quitquitquit HTTP/1.1\r\nHost: localhost\r\nContent-Length: 0\r\n\r\n" >&3 && cat <&3 && exec 3>&- || true'
```

`app=users-api` satisfies the NetworkPolicy (without it the connection hangs). The sidecar is required because the namespace uses STRICT mTLS. The `/dev/tcp` call at the end posts to `/quitquitquit`, shutting down the sidecar so the pod can exit.

### Approach 2: dump + restore

Dump the data, create an empty CNPG cluster, load the dump. More manual steps than approach 1, but gives you a checkable artifact on disk.

1. `pg_dump` the existing database (the s15 CronJob already does this, or trigger it manually).
2. Create the `Cluster` CR with `bootstrap.initdb` (creates an empty `appdb` database).
3. Restore the dump into the new cluster via `k8s/postgres-migration/restore-job.yaml`. The Job mounts the `db-backups` PVC, finds the latest `.sql.gz` dump, and pipes it into the CNPG primary via `postgres-rw`.

`bootstrap.initdb` does not restore data on its own: it only creates the database and owner. The restore is a separate step because CNPG's `initdb` doesn't support loading from arbitrary dump files.

**Trade-off:** simple to understand, but requires downtime between the dump and restore. Writes to the old database after the dump are lost.

```bash
# Take a fresh dump (the restore job reads from the db-backups PVC)
helm upgrade --install db-backup ./helm/db-backup -n default
kubectl create job --from=cronjob/db-backup db-backup-final
kubectl wait --for=condition=complete job/db-backup-final --timeout=120s

# Verify the dump is not empty (should show CREATE TABLE / COPY statements)
kubectl run --rm -it check-dump \
  --image=postgres:18 --restart=Never \
  --annotations='sidecar.istio.io/inject=false' \
  --overrides='{
    "spec": {
      "containers": [{
        "name":  "check-dump",
        "image": "postgres:18",
        "command": ["sh", "-c",
          "LATEST=$(ls -t /backups/backup-*.sql.gz | head -1) && echo \"$LATEST ($(stat -c%s $LATEST) bytes)\" && gunzip -c $LATEST"
        ],
        "volumeMounts": [{"name": "b", "mountPath": "/backups"}]
      }],
      "volumes": [{
        "name": "b",
        "persistentVolumeClaim": {"claimName": "db-backups"}
      }]
    }
  }'

# Download the dump to your local machine
kubectl run dump-download --rm -i --image=postgres:18 --restart=Never \
  --annotations='sidecar.istio.io/inject=false' \
  --overrides='{
    "spec": {
      "containers": [{
        "name": "dump-download",
        "image": "postgres:18",
        "command": ["sh", "-c",
          "cat \"$(ls -t /backups/backup-*.sql.gz | head -1)\""
        ],
        "volumeMounts": [{"name": "b", "mountPath": "/backups"}]
      }],
      "volumes": [{
        "name": "b",
        "persistentVolumeClaim": {"claimName": "db-backups"}
      }]
    }
  }' > backup-local.sql.gz

kubectl apply -f k8s/postgres-migration/cluster-initdb.yaml
# (PodMonitor already applied in Prerequisites)
kubectl get cluster postgres -w
# STATUS: Creating → Healthy

kubectl get pods -l cnpg.io/cluster=postgres
# postgres-1 (primary), postgres-2 (replica)

kubectl apply -f k8s/postgres-migration/restore-job.yaml
kubectl logs job/db-restore -f
```

#### Alternative: direct pipe

For a small database you can skip the PVC and pipe directly between pods:

```bash
kubectl exec postgres-0 -- pg_dump -U appuser appdb | kubectl exec -i postgres-1 -- psql -U appuser -d appdb
```

This requires both clusters to be running at the same time. The restore Job approach above uses a Job and PVC, which gives you a checkable artifact on disk and doesn't risk silent data loss if either `kubectl exec` connection drops mid-stream.

```bash
# Restore is verified: clean up the cronjob (keep the PVC until migration is fully done)
kubectl delete cronjob db-backup
```

#### Reset for approach 3

```bash
kubectl delete cluster postgres
kubectl delete job db-restore
kubectl delete backup postgres-manual --ignore-not-found
kubectl get pods -l cnpg.io/cluster=postgres
# No resources found

# Wipe MinIO so approach 3 doesn't recover a stale base backup
kubectl exec deploy/minio -- mc rm --recursive --force local/cnpg-backups/postgres/

# Make sure the old StatefulSet is still running

```

### Approach 3: recovery from object store backup

CNPG can restore from its own backups stored in an S3-compatible object store. This is the CNPG-to-CNPG path: disaster recovery, cloning prod to staging, or point-in-time recovery.

We don't have S3 on kind, so we deploy MinIO as a local S3-compatible store. The flow:

1. Deploy MinIO (`k8s/minio/`).
2. Create a CNPG cluster with `barmanObjectStore` backup configured (`k8s/postgres/cluster.yaml`). This is the same `initdb` bootstrap, but with backup destination set to MinIO.
3. Restore the dump (same as approach 2).
4. Take a CNPG `Backup` to MinIO.
5. Delete the cluster.
6. Create a new cluster with `bootstrap.recovery` (`k8s/postgres-migration/cluster-recovery.yaml`). CNPG pulls the base backup + WAL from MinIO and rebuilds the cluster.

The `externalClusters` section in `postgres-migration/cluster-recovery.yaml` tells CNPG where the backup lives (MinIO endpoint + S3 credentials).

**Trade-off:** requires an object store, but this is how production disaster recovery works. The backup contains everything CNPG needs: no external dump files, no running source instance.

```bash
# Deploy MinIO (local S3)
kubectl apply -f k8s/minio
kubectl rollout status deploy/minio

# Allow CNPG pods to reach MinIO (default-deny blocks port 9000 otherwise)
kubectl apply -f k8s/network-policies/minio.yaml

# Create the S3 bucket CNPG will write to
kubectl exec deploy/minio -- mc alias set local http://localhost:9000 minio minio123
kubectl exec deploy/minio -- mc mb --ignore-existing local/cnpg-backups

# If re-running approach 3, wipe stale backups so recovery doesn't pull an old empty base backup.
# Skip this on a first run (the bucket is already empty).
kubectl exec deploy/minio -- mc rm --recursive --force local/cnpg-backups/postgres/ 2>/dev/null || true

# Create cluster with barmanObjectStore backup configured
kubectl apply -f k8s/postgres/cluster.yaml
kubectl get cluster postgres -w
# STATUS: Creating → Healthy

# Restore the dump (same as approach 2)
kubectl apply -f k8s/postgres-migration/restore-job.yaml
kubectl logs job/db-restore -f

# Verify the users table has data before backing up.
# If count is 0, stop and debug the restore job. Do NOT proceed to the backup step
# or you will back up an empty database and recovery will silently restore nothing.
kubectl exec postgres-1 -- bash -c "PGPASSWORD=secret psql -h localhost -U appuser -d appdb -c \"SELECT count(*) FROM users;\""

# A completed Backup CR won't re-trigger on apply, so delete it first if re-running.
kubectl delete backup postgres-manual --ignore-not-found
kubectl apply -f k8s/postgres/backup.yaml
kubectl get backup postgres-manual -w
# PHASE: Running → Completed

# Verify both base backup AND WAL segments exist in MinIO.
# Recovery fails without the base backup (data.tar + backup.info).
kubectl exec deploy/minio -- mc ls local/cnpg-backups/ --recursive
# postgres/base/...  base backup (data.tar + backup.info)
# postgres/wals/...  WAL segments (continuous archiving)

# Automate it: a ScheduledBackup takes a base backup on a cron schedule.
# (the manual Backup above is one-shot; this is the recurring version)
kubectl apply -f k8s/postgres/scheduled-backup.yaml
kubectl get scheduledbackup postgres-daily
# LAST BACKUP populates after the first scheduled run; the CR fields show next run time.

# Flush the current WAL segment so it gets archived to MinIO.
# Without this, deleting the cluster can lose the WAL the backup needs.
kubectl exec postgres-1 -- psql -U postgres -c "SELECT pg_switch_wal();"
sleep 5

# Delete the cluster (backup stays in MinIO)
kubectl delete cluster postgres
kubectl delete job db-restore

# Recover from the MinIO backup
kubectl apply -f k8s/postgres-migration/cluster-recovery.yaml
kubectl get cluster postgres -w
# STATUS: Restoring → Healthy

kubectl get pods -l cnpg.io/cluster=postgres
# postgres-1 (primary, recovered), postgres-2 (replica)

# Verify the recovered cluster has our data
kubectl exec postgres-1 -- psql -U postgres -d appdb -c "SELECT count(*) FROM users;"

# Should match the count from before the backup

# Migration complete: delete the old StatefulSet and its PVC
kubectl delete statefulset postgres
kubectl delete pvc pgdata-postgres-0
kubectl delete svc postgres-headless
```

### Update users-api to use the CNPG cluster

Update `DB_HOST` in `helm/users-api/values.yaml` from the old StatefulSet address (`postgres-0.postgres-headless`) to the CNPG read-write Service (`postgres-rw`).

```bash
# Helm path
helm upgrade users-api ./helm/users-api

# # Raw manifest path (if not using Helm)
# kubectl apply -f k8s/users-api/configmap.yaml
# kubectl apply -f k8s/users-api/deployment.yaml
# kubectl rollout restart deploy/users-api
```

**Why pods don't restart after `helm upgrade`.** If only the ConfigMap or Secret contents changed (and not the Deployment spec itself), Kubernetes sees an identical pod template and does not roll out new pods. The old pods keep running with the stale env vars.

The fix is a checksum annotation on the pod template. When the ConfigMap or Secret content changes, the checksum changes, the pod template changes, and Kubernetes triggers a rollout automatically

```yaml
# helm/users-api/templates/deployment.yaml -- under spec.template.metadata
annotations:
  checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
  checksum/secret: {{ include (print $.Template.BasePath "/secret.yaml") . | sha256sum }}
```

Without this, you need a manual `kubectl rollout restart deploy/users-api` after any ConfigMap or Secret change.

#### Verify users-api connects to CNPG

```bash
kubectl rollout status deploy/users-api --timeout=120s

# The init container runs the migration against postgres-rw.
# If it fails, the pod stays in Init:CrashLoopBackOff.
```

## What this looks like on AWS

| s16a (kind) | EKS / AWS |
| --- | --- |
| CloudNativePG operator in-cluster | Same chart. Or skip the operator entirely and use **RDS for PostgreSQL** (managed, zero ops). |
| PVC-backed storage (local-path) | **EBS CSI** volumes (gp3). Or EBS io2 for high IOPS. |
| Backups to MinIO via `barmanObjectStore` | Backups to **S3** via `barmanObjectStore`. Or RDS automated backups + snapshots. |
| WAL archiving to MinIO | WAL archiving to S3. Enables cross-region PITR. |
| PodMonitor for Prometheus | Same. Or **RDS Performance Insights** + **CloudWatch** for managed monitoring. |

CNPG on EKS is a legitimate production choice for teams that want Postgres control (extensions, major version upgrades on their schedule, custom configs). RDS is the choice when you want zero operational burden and are OK with the constraints.

## Try to break it

### 1. Kill the primary, watch automatic failover

```bash
kubectl delete pod postgres-1
kubectl get pods -l cnpg.io/cluster=postgres -w
# postgres-2 promoted to primary within ~10s
# postgres-1 recreated as replica

kubectl describe cluster postgres | grep "Current Primary"
# Should show postgres-2
```

The `-rw` Service endpoint switches automatically. Clients that reconnect see the new primary.

### 2. Scale to 1 instance, lose HA

```bash
kubectl patch cluster postgres --type merge -p '{"spec":{"instances":1}}'
# Replicas are terminated. Only the primary remains.
# Delete the primary now:
kubectl delete pod postgres-1
# Cluster is unavailable until the operator recreates the Pod and it finishes recovery.
```

With 1 instance, "failover" is just "restart and recover." No promotion, just WAL replay. Downtime is minutes, not seconds.

### 3. Connection string points at the old StatefulSet Service

After migrating from s5, if users-api still connects to the old `postgres` Service instead of `postgres-rw`, it hits the old (now deleted) Pod. Connection refused.

```bash
kubectl logs deploy/users-api | grep "ECONNREFUSED"
```

Fix: update `DATABASE_URL` to use `postgres-rw.default.svc:5432/appdb`.
