# s14 - Service Mesh (Istio)

> **Tag:** `s14`
>
> **Goal**: add mutual TLS between services and traffic management (canary releases, circuit breaking) using Istio. Every service-to-service call is encrypted and authenticated without changing application code.

In s6, users-api calls notify-api over gRPC. That traffic is plaintext inside the cluster. Anyone who can `exec` into a Pod in the namespace can tcpdump the wire. A service mesh encrypts all east-west traffic with mutual TLS, rotates certificates automatically, and gives you traffic-level controls (canary, retries, circuit breaking) without touching application code.

---

## Plaintext traffic in action

Before installing Istio, prove the traffic is sniffable. This motivates every concept that follows.

### 1. Find the notify-api Pod

```bash
kubectl get pod -l app=notify-api -o wide
NOTIFY_POD=$(kubectl get pod -l app=notify-api -o jsonpath='{.items[0].metadata.name}')
```

### 2. Open a shell inside a debug container

`tcpdump` is rarely in app images. Launch a debug container that shares the Pod's network namespace, then get a shell so you can run multiple commands:

```bash
kubectl debug -it $NOTIFY_POD \
  --image=nicolaka/netshoot \
  --target=notify-api \
  -- bash
```

`--target=notify-api` shares the Pod's network namespace. Verify you're actually in the Pod's netns before capturing:

```bash
# Inside the debug container, IP must match kubectl get pod $NOTIFY_POD -o wide
ip addr show eth0
```

### 3. Run tcpdump

```bash
# Inside the debug container
tcpdump -i any port 50051
```

> Add `-X` to print the raw payload bytes as hex alongside each `[P.]` line (`tcpdump -i any -X port 50051`). The output is binary protobuf inside HTTP/2 frames, not human-readable, but you can see the actual unencrypted bytes on the wire.

### 4. Generate traffic from another terminal

```bash
# Trigger a create/delete via the Ingress or directly through users-api
curl -k -X POST https://demo.local/api/users -H 'Content-Type: application/json' -d '{"email":"x@x.com"}'
```

### 5. Read the dump

#### TCP flag cheat sheet

Each line in tcpdump output has a `Flags [...]` field. The letters are TCP control bits:

| Flag | Full name | Meaning                                                         |
|------|-----------|-----------------------------------------------------------------|
| `S`  | SYN       | "I want to open a connection"                                   |
| `.`  | ACK       | "I received your last packet"                                   |
| `S.` | SYN+ACK   | "I'll accept your connection" (the `.` is the ACK of their SYN) |
| `P.` | PSH+ACK   | "Here is data, deliver it immediately"                          |
| `F.` | FIN+ACK   | "I'm done sending, please close"                                |
| `R`  | RST       | "Abort. Close immediately, no negotiation"                      |

The `.` alone (just ACK, no other flags) means "received, nothing to add."

#### Health probe sequence

Every few seconds the kubelet (node IP `192.168.121.64`) opens a fresh TCP connection to port 50051 to check liveness:

```text
In   192.168.121.64.49670  > notify-api.50051  [S]    length 0   ← kubelet: "open a connection"
Out  notify-api.50051      > 192.168.121.64    [S.]   length 0   ← pod: "ok, connected"
In   192.168.121.64.49670  > notify-api.50051  [.]    length 0   ← kubelet: "got it" (3-way handshake done)
In   192.168.121.64.49670  > notify-api.50051  [F.]   length 0   ← kubelet: "closing now" (sent no data at all)
Out  notify-api.50051      > 192.168.121.64    [P.]   length 9   ← pod: sends 9 bytes (HTTP/2 GOAWAY frame)
In   192.168.121.64.49670  > notify-api.50051  [R]    length 0   ← kubelet: "fine, aborting" (doesn't wait for graceful close)
```

#### gRPC call sequence

gRPC clients hold one persistent HTTP/2 connection and multiplex all RPCs over it. The TCP handshake (`[S]`) only happens once when users-api starts. Every subsequent RPC just sends data frames (`[P.]`) over that open connection. There is no new handshake per call:

```text
In   192-168-157-191.users-api...37612  > notify-api.50051  [P.]  length 105  ← users-api: RPC request (protobuf in HTTP/2 DATA frame)
Out  notify-api.50051                   > users-api...37612  [P.]  length 53   ← notify-api: RPC response
In   users-api...37612                  > notify-api.50051   [.]   length 0    ← users-api: "got it"
Out  notify-api.50051                   > users-api...37612  [P.]  length 11   ← notify-api: gRPC trailers (status code)
In   users-api...37612                  > notify-api.50051   [.]   length 0    ← users-api: "got it"
```

The 105-byte frame contains the serialised protobuf (`NotificationRequest`). The data is **not** encrypted. It's just binary-encoded protobuf inside an HTTP/2 frame, but it's not human-readable as-is. The point is anyone who can exec into a Pod and run tcpdump can capture those bytes and decode the protobuf offline.

> **Why no SYN here?** The gRPC client in `notifyClient.ts` is a module-level singleton. The TCP connection is established once when users-api starts. By the time you trigger a create/delete, tcpdump sees the call land mid-stream on an already-open connection.

### 6. After installing Istio with mTLS STRICT

Repeat the same tcpdump. The `[P.]` data frames are still there, but now contain TLS ciphertext. The Envoy sidecar terminates the TCP connection and the payload is indistinguishable from random bytes:

```text
eth0  In  IP ...users-api... > notify-api.50051: Flags [P.] ... length 89
# payload: .%.. .r..X.O..;...j..R..e....T..g.G........
```

No field names, no protobuf values. The raw TCP stream proves nothing about what was sent.

## Why a mesh

| Capability | Without mesh | With mesh |
| --- | --- | --- |
| **Encryption** | Plaintext in-cluster. "Trust the network" assumption. | mTLS between every sidecar. Certs rotate automatically. |
| **Traffic management** | Kubernetes Service round-robins. No canary, no circuit breaking. | VirtualService + DestinationRule for weighted routing, retries, timeouts. |
| **Observability** | App must export metrics/traces (s12). | Sidecar emits L7 metrics (RPS, error rate, latency) for every service without app changes. Feeds into Prometheus. |

The trade-off: a sidecar proxy (Envoy) runs next to every Pod. That's ~30MB memory and ~10ms p99 latency overhead per hop. For most web services, the security and observability win is worth it. For latency-critical paths (real-time trading, gaming), measure before committing.

This per-Pod cost is the central complaint about the sidecar model, and it's what motivates **s22**: Istio's *ambient* mode moves mTLS to a per-node proxy and makes the heavyweight L7 proxy optional, so you pay the full price only for services that actually need L7 features. This stage teaches the sidecar model first because it's the original, most widely deployed design and the one every Istio concept (injection, `PeerAuthentication`, `VirtualService`) was built around. s22 then shows what ambient changes and why.

## Istio vs Linkerd

| | Istio | Linkerd |
| --- | --- | --- |
| Proxy | Envoy (C++, heavy, battle-tested) | linkerd2-proxy (Rust, lightweight, purpose-built) |
| Features | Full: traffic management, security, observability, extensibility (Wasm, EnvoyFilter) | Focused: mTLS, retries, timeouts, basic traffic split |
| Complexity | Higher. Istiod control plane, many CRDs (Gateway, VirtualService, DestinationRule, PeerAuthentication) | Lower. Simpler CRDs, less config surface |
| Resource overhead | ~50MB per sidecar | ~20MB per sidecar |
| Community | CNCF graduated, Google/IBM backing | CNCF graduated, Buoyant |
| Learning value | More concepts to learn, more transferable to production | Faster to set up, less to configure |

We use Istio because it has more concepts worth teaching and the CRD model is broadly adopted. Linkerd is a fine choice for real workloads where you want the security with less operational overhead.

> The "resource overhead" row is the historical reason teams picked Linkerd over Istio. That comparison is specific to the **sidecar** model shown here. s22's ambient mode drops Istio's per-Pod footprint to a per-node proxy, which largely neutralizes Linkerd's lightweight-proxy advantage.

## Architecture

```text
               ┌──────────────────────────────────────┐
               │              istiod                  │
               │  (Pilot + Citadel + Galley,          │
               │   single binary)                     │
               │  - pushes Envoy config via xDS       │
               │  - issues mTLS certs via built-in CA │
               └──────────┬───────────────────────────┘
                          │ xDS + cert push
               ┌──────────┴───────────────────────────┐
               │                                      │
    ┌──────────┴──────────┐         ┌─────────────────┴─────────┐
    │  users-api Pod      │         │  notify-api Pod           │
    │  ┌───────────────┐  │  mTLS   │  ┌─────────────────────┐  │
    │  │ envoy sidecar │◀─┼─────────┼─▶│ envoy sidecar       │  │
    │  └───────┬───────┘  │         │  └───────┬─────────────┘  │
    │          │ localhost│         │          │ localhost      │
    │  ┌───────┴───────┐  │         │  ┌───────┴─────────────┐  │
    │  │  users-api    │  │         │  │  notify-api (gRPC)  │  │
    │  │  :3000        │  │         │  │  :50051             │  │
    │  └───────────────┘  │         │  └─────────────────────┘  │
    └─────────────────────┘         └───────────────────────────┘
```

The sidecar intercepts all inbound and outbound traffic via iptables rules injected by the `istio-init` init container. The app talks to `localhost`; the sidecar handles mTLS termination and origination transparently.

istiod is a single binary that consolidates three historically separate components:

**Pilot** is the config translator. It watches Kubernetes resources (Services, Endpoints, `VirtualService`, `DestinationRule`, etc.) and converts them into Envoy configuration. It then streams that config down to every sidecar using **xDS** - the Envoy discovery API protocol; a set of gRPC APIs (Listener, Route, Cluster, Endpoint discovery) that Envoy uses to receive routing and policy config dynamically, without restarts.

**Citadel** is the certificate authority. It issues a **SPIFFE** identity cert to every sidecar - a standard X.509 certificate whose Subject Alternative Name encodes the workload's service account (e.g. `spiffe://cluster.local/ns/default/sa/users-api`). This is what mTLS peers use to verify each other's identity. Certs rotate automatically every ~24h.

**Galley** validates and distributes Istio configuration. It's the API ingestion layer that checks your CRDs before Pilot acts on them.

## Sidecar injection

Istio injects the Envoy sidecar as a container in every Pod. Two methods:

| Method | How | When to use |
| --- | --- | --- |
| **Namespace label** | `istio-injection: enabled` on the namespace | Default. Every new Pod in the namespace gets a sidecar. |
| **Pod annotation** | `sidecar.istio.io/inject: "true"` on the Pod spec | Selective. Use when most Pods in the namespace shouldn't have sidecars. |

**When to use the pod annotation (opt-in) pattern:**

- **Mixed workloads**: a `platform` namespace with Prometheus, debug pods, and one real service; only the service needs Istio.
- **Batch/Job pods**: `Job` and `CronJob` pods run to completion, but the Envoy sidecar stays alive after the main container exits and blocks the Pod from completing. Easier to skip injection than to configure `EXIT_ON_ZERO_ACTIVE_CONNECTIONS`.
- **Infra pods sharing a namespace**: cert-manager, external-secrets, etc. don't benefit from mTLS or traffic management.
- **Latency/overhead-sensitive workloads**: ML training jobs or ETL pipelines where the sidecar's CPU, memory, and added latency aren't worth it.

Injection is done by a mutating admission webhook. Existing Pods don't get sidecars until they're re-created (`kubectl rollout restart`).

## mTLS with PeerAuthentication

`PeerAuthentication` controls how sidecars handle incoming mTLS:

| Mode | Behavior |
| --- | --- |
| `STRICT` | Reject any plaintext connection. Both sides must present valid mesh certs. |
| `PERMISSIVE` | Accept both mTLS and plaintext. Use during migration when not all services have sidecars yet. |
| `DISABLE` | No mTLS enforcement. |

Start with `PERMISSIVE` at the mesh level, then flip individual namespaces to `STRICT` once all their services have sidecars. A mesh-wide `STRICT` policy on day one will break any service without a sidecar (including Jobs, CronJobs, or third-party Pods that don't have injection enabled).

## Traffic management

### VirtualService

A `VirtualService` binds to a Kubernetes Service and overrides default round-robin routing:

- **Weight traffic** across subsets (canary: 90/10 split between v1 and v2).
- **Match on headers** (route internal dogfood users to v2 via a header match).
- **Inject faults** (delay 5% of requests by 3s to test timeout handling).
- **Set retries and timeouts** (retry 2x on 503, 5s total timeout).

### DestinationRule

A `DestinationRule` defines **subsets** (named groups of Pods, usually by version label) and **traffic policies** (connection pool limits, outlier detection, TLS settings).

Subsets map to Pod labels. The VirtualService references these subset names for weighted routing.

### Circuit breaking (outlier detection)

`DestinationRule.trafficPolicy.outlierDetection` ejects unhealthy endpoints:

| Field | What it does |
| --- | --- |
| `consecutive5xxErrors` | Number of 5xx before ejecting the endpoint. |
| `interval` | How often to evaluate. |
| `baseEjectionTime` | How long an ejected endpoint stays out. |
| `maxEjectionPercent` | Max % of endpoints ejectable simultaneously. |

This is client-side: the users-api sidecar stops routing to a notify-api Pod that's returning 500s. Server-side, nothing changes.

## Canary deployment walkthrough

1. Deploy `users-api` v2 alongside v1 (different Deployment, same Service selector minus the `version` label).
2. Create a `DestinationRule` with subsets `v1` and `v2`.
3. Create a `VirtualService` with `weight: 95` for v1, `weight: 5` for v2.

### Why add `version: v1` to `template.metadata.labels` and not `selector.matchLabels`

`DestinationRule` subsets work by matching **Pod labels**, not Deployment metadata. When Istio's Envoy sidecar needs to route traffic to subset `v1`, it asks the control plane for endpoints whose pods carry `version: v1`. If the v1 pods don't have that label, Istio finds zero endpoints for the subset and all traffic routed to `v1` fails, even though the pods are healthy and the Service reaches them fine.

The fix is to add `version: v1` to `template.metadata.labels` in the v1 Deployment, so the pods it creates carry the label:

```yaml
template:
  metadata:
    labels:
      app: users-api
      version: v1   # Istio DestinationRule subset v1 matches this
```

**Why not add it to `selector.matchLabels` as well?**

`selector.matchLabels` is **immutable**. Kubernetes rejects any change to it after the Deployment is created. Adding `version: v1` there would require deleting and recreating the Deployment, which takes down running pods. You don't need the selector to include `version` anyway: the selector only controls which pods the Deployment manages (rolling-update targeting). As long as the existing label (`app: users-api`) keeps matching, the Deployment works correctly. The `version` label is purely for Istio's routing. It only needs to be on the pods, not in the selector.
4. Monitor error rates in Grafana (s12's dashboards + Istio sidecar metrics).
5. If v2 is healthy, shift to 50/50, then 100.
6. Delete the v1 Deployment.

Without a mesh, this requires an Ingress controller with traffic splitting support (nginx annotations) or a dedicated tool like Flagger / Argo Rollouts. With a mesh, it's a VirtualService edit.

## How Istio integrates with existing infra

**Ingress:** Istio ships its own Ingress Gateway (an Envoy at the edge). You can use it instead of nginx-ingress, or keep nginx for north-south and Istio for east-west only. For kind, keep nginx (s3) for now. Less disruption. s22 revisits the edge: it replaces both the legacy Istio `Gateway` API and nginx-ingress with the Kubernetes **Gateway API** (`Gateway` + `HTTPRoute`), the successor to the frozen `Ingress` resource.

> **The `istio-ingressgateway` Pod name is misleading.** It's just an idle Envoy proxy the demo profile always deploys; not the Kubernetes **Gateway API** (`gateway.networking.k8s.io`), and not a replacement for your ingress controller. Installing it doesn't touch nginx, enable Gateway API (its CRDs aren't even bundled), or route any traffic. s14 uses no edge gateway at all; the move to Gateway API and retiring nginx happens in s22.

**Prometheus (s12):** Istio sidecars expose metrics on `:15020/stats/prometheus`. kube-prometheus-stack scrapes them via a PodMonitor. This gives you mesh-level RPS, error rate, and latency without app instrumentation.

**Loki (s12): sidecar logs leak into your dashboard.** `istio-proxy` runs as a second container inside every Pod. Alloy ships logs for every container it discovers. Without a filter, Grafana's logs panel shows both `users-api` logs and the verbose Envoy access log from `istio-proxy` mixed together, because both containers share the same pod label (`app=users-api`).

Two changes are needed to isolate app logs:

**1. Add a `container` label to Alloy** (`helm/values/alloy.values.yaml`).

By default the `discovery.relabel` block only extracts `namespace`, `pod`, and `app`. Add a rule for the per-container meta label so Loki indexes it as a stream label:

```yaml
rule {
  source_labels = ["__meta_kubernetes_pod_container_name"]
  target_label  = "container"
}
```

```bash
helm upgrade alloy grafana/alloy -n lgtm -f helm/values/alloy.values.yaml
```

Without this step, the `container` label doesn't exist in Loki at all, so any query that filters on it returns zero results.

**2. Add `container="$app"` to the Loki stream selector in the dashboard** (`k8s/grafana/apps-dashboard.yaml`).

Both the pod variable query and the logs panel target need the extra selector:

```logql
# before
{app="$app"}
{app="$app", pod=~"$pod"}

# after
{app="$app", container="$app"}
{app="$app", pod=~"$pod", container="$app"}
```

```bash
kubectl apply -f k8s/grafana/apps-dashboard.yaml
```

Grafana's dashboard sidecar watches ConfigMaps labelled `grafana_dashboard: "1"` and reloads automatically. Old log entries already stored in Loki won't gain the `container` label retroactively. Wait ~30s for fresh log lines to appear.

**Metrics dashboard - Prometheus vs Mimir:** The `Apps – Metrics` dashboard (`helm/dashboards`) queries either local Prometheus or Mimir depending on what is installed. The raw ConfigMap hardcodes `"uid": "mimir"`, which causes a plugin error when Mimir isn't running. The Helm chart wraps the JSON and substitutes the correct datasource uid at install time:

```bash
# Without Mimir (default; fresh-start without Mimir overlay)
helm install dashboards helm/dashboards -n lgtm

# With Mimir
helm install dashboards helm/dashboards -n lgtm --set mimir.enabled=true
# or if already installed:
helm upgrade dashboards helm/dashboards -n lgtm --set mimir.enabled=true
```

The chart lives in `helm/dashboards/`. The JSON itself is in `helm/dashboards/files/apps-metrics.json`. Edit it there, not in a raw ConfigMap.

**Surfacing v1/v2 in Grafana:** Once you deploy the canary, both dashboards need to show per-version lines so you can compare v1 and v2 side by side.

*Logs dashboard*: already works. Alloy ships logs for every container it discovers and tags each stream with pod labels. Because the v1/v2 pods carry a `version` label, Loki indexes it as a stream label automatically. The Log Volume panel queries `sum by (version) (rate({app="$app", container="$app"}[1m]))` and produces one overlapping line per version with no extra config.

*Metrics dashboard*: needs two changes, because Prometheus does **not** automatically inherit pod labels the way Loki does.

**1. Add a `relabelings` rule to every ServiceMonitor** (`k8s/users-api/servicemonitor.yaml`, `k8s/notify-api/servicemonitor.yaml`, `helm/users-api/templates/servicemonitor.yaml`):

```yaml
endpoints:
  - port: http
    path: /metrics
    interval: 15s
    relabelings:
      - sourceLabels: [__meta_kubernetes_pod_label_version]
        targetLabel: version
```

When Prometheus scrapes a pod it exposes `__meta_kubernetes_pod_label_*` meta-labels for every pod label. The relabeling rule copies the `version` pod label onto every metric scraped from that pod, so `http_requests_total` gains `version="v1"` or `version="v2"` without any app code change.

```bash
kubectl apply -f k8s/users-api/servicemonitor.yaml
kubectl apply -f k8s/notify-api/servicemonitor.yaml
# or if using Helm:
helm upgrade users-api helm/users-api -n default
```

**2. Add a `version` variable and update panel queries** (`helm/dashboards/files/apps-metrics.json`):

```bash
helm upgrade dashboards helm/dashboards -n lgtm
```

**HPA (s13):** Istio's `istio_requests_total` can replace `http_requests_total` as the HPA scaling signal via prometheus-adapter. Trade-off: coupling autoscaling to the mesh's metrics adds a dependency.

## Helm Chart vs `istioctl`

These are two different things and you need both:

| | Role | Can Helm replace it? |
| --- | --- | --- |
| **`istioctl` binary** | Local CLI for debugging, analysis, and injection | No. It's a local tool, not a K8s resource. |
| **Istio control plane** (`istiod`, `istio-base`, gateway) | Kubernetes workloads in `istio-system` | Yes. Helm is the preferred production method. |

**Use Helm to install the control plane** when:

- You want GitOps-friendly, declarative installs (values files in git, reproducible upgrades).
- You're managing Istio alongside other Helm releases (`helm list -A` gives a unified view).
- You need `helm upgrade` / `helm rollback` semantics for the control plane itself.

**Use `istioctl install` when:**

- You're doing a quick local demo and `--set profile=demo` is all you need.
- You want to validate the cluster before installing (`istioctl x precheck`).

**`istioctl` CLI commands you always need**, regardless of how Istio was installed:

- `istioctl proxy-status` — check that all sidecars are synced with istiod.
- `istioctl x describe pod <pod>` — show effective mTLS and routing policy for a pod.
- `istioctl analyze` — lint your Istio CRDs for misconfigurations.
- `istioctl proxy-config` — inspect the Envoy listener/route/cluster config pushed to a sidecar.

> **Getting the binary:** `curl -L https://istio.io/downloadIstio | sh -` (Linux/WSL). The binary version must match the control plane version.

## Commands

> **Raw manifests vs Helm:** `k8s/istio/` and `helm/users-api/templates/` are kept in sync. They produce equivalent objects. Use whichever you prefer; the Helm sections below show the `--set` flags. If you applied a raw manifest first and then run `helm upgrade`, Helm will error because it doesn't own the resource. Either delete it and let Helm recreate it, or skip the raw-manifest step entirely.

```bash
# 1. Install the Istio CLI into your home directory
cd ~
curl -L https://istio.io/downloadIstio | sh -
echo 'export PATH=$PATH:$HOME/istio-1.30.0/bin' >> ~/.bashrc
source ~/.bashrc
istioctl version --remote=false

# 2. Install Istio
# mTLS defaults to PERMISSIVE mesh-wide until you apply a PeerAuthentication
# Instead of: istioctl install --set profile=demo -y
helm install istio-base istio/base -n istio-system --create-namespace
helm install istiod istio/istiod -n istio-system
helm install istio-ingressgateway istio/gateway -n istio-system

# 3. Label namespace for sidecar injection
kubectl label namespace default istio-injection=enabled

# 4. Restart Pods to pick up sidecars
kubectl rollout restart deploy/users-api deploy/notify-api statefulset/postgres

# 5. Verify sidecars
kubectl get pods -l app=users-api -o jsonpath='{.items[0].spec.containers[*].name}'
# Should show: users-api istio-proxy

# 6. Check readiness
kubectl get pod -l app=users-api
# NAME                         READY   STATUS  ...
# users-api-664f6db946-7dnxm   2/2     Running ...
# users-api-664f6db946-92x9h   2/2     Running ...
```

You went from 1/1 (just users-api) to 2/2 because the injected istio-proxy sidecar is now a second container, and it has its own readiness probe (`HTTP :15021/healthz/ready`). When both containers pass their probes, the pod is 2/2.

### Verify mTLS

```bash
istioctl proxy-status
# All entries should show SYNCED

# Check peer authentication for a specific pod
istioctl x describe pod $(kubectl get pod -l app=users-api -o jsonpath='{.items[0].metadata.name}')
```

### Apply STRICT mTLS

```bash
helm upgrade users-api helm/users-api -n default \
  --set istio.peerAuthentication.enabled=true

# kubectl apply -f k8s/istio/peer-authentication.yaml

# Test: Pod without sidecar can't reach meshed services
kubectl run tmp --image=curlimages/curl --rm -it -- curl http://users-api:3000/health
# Connection reset (no client cert)
```

> **Note: STRICT requires a mesh-native edge gateway**: nginx ingress doesn't participate in the mesh (no sidecar, no mesh identity), so it can't send mTLS to `users-api`. Thus, external traffic breaks with 502. The real fix is to adopt the **Kubernetes Gateway API** (`Gateway` + `HTTPRoute`) for north-south traffic. Since Istio is already running for east-west, it's the natural choice: the `istio-ingressgateway` is already a mesh proxy, so traffic arriving from outside travels mesh-native all the way to the Pod. This will be covered in **s22**. Until then, rollback:
>
> ```bash
> helm rollback users-api
> ```

## What's next

- **s22** (Ambient mode + Gateway API) is the direct sequel to this stage. It removes the per-Pod sidecar you just installed: mTLS moves to a per-node `ztunnel` (L4), and the L7 features from this stage — traffic splitting, retries, the canary you did with `VirtualService` — move to an optional per-namespace **waypoint** proxy driven by the Kubernetes **Gateway API** (`HTTPRoute`). It also retires nginx-ingress (s3) in favor of `Gateway` + `HTTPRoute`.
- **s23** (Progressive delivery) automates what this stage showed manually: Argo Rollouts drives traffic weights step by step and queries Mimir (s12) to gate promotion, with an automatic rollback on a failed SLO. Built on s22's `HTTPRoute` backend rather than the `VirtualService` you edited by hand here.
- **s17** covers Jobs, CronJobs, and DaemonSets - batch workloads and node-level agents that complement the long-running Deployments we've been working with.
- **s19** (KEDA) generalizes autoscaling with event-driven triggers that can replace prometheus-adapter entirely.

## Cleanup

Uninstall in reverse order: app resources first, then the control plane.

```bash
# 1. Disable canary and Istio resources managed by the users-api chart
helm upgrade users-api helm/users-api -n default \
  --set canary.enabled=false \
  --set istio.peerAuthentication.enabled=false \
  --set istio.destinationRule.enabled=false \
  --set istio.virtualService.enabled=false

# 2. Uninstall the Istio control plane (reverse install order)
helm uninstall istio-ingressgateway -n istio-system
helm uninstall istiod -n istio-system
helm uninstall istio-base -n istio-system
kubectl delete namespace istio-system

# 3. Remove injection label and recreate pods without sidecars
kubectl label namespace default istio-injection-
kubectl rollout restart deploy/users-api deploy/notify-api statefulset/postgres
```

**If you used raw manifests instead of Helm:**

```bash
kubectl delete -f k8s/istio/
kubectl delete -f k8s/users-api/deployment-v2.yaml

# istioctl uninstall only works if Istio was installed via istioctl
istioctl uninstall --purge -y
kubectl delete namespace istio-system

kubectl label namespace default istio-injection-
kubectl rollout restart deploy/users-api deploy/notify-api
```
