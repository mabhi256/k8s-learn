# s11 - Helm (Kubernetes package manager)

> **Tag:** `s11`
> Goal: stop hand-applying YAML files. Package `users-api` as a Helm chart so it installs, upgrades, and uninstalls as one unit. Then use `helm install` to pull in third-party charts cleanly, replacing the s10 metrics-server install as a worked example.

We have 30+ manifests under `k8s/`. Every stage we've been doing `kubectl apply -f k8s/users-api/` and trusting the folder. Helm gives us three things at once:

1. **Templating + values** for env-specific overrides: same chart for dev/stage/prod.
2. **Install / upgrade / rollback as a unit**: one command to put a stack in the cluster, one to walk it back.
3. **A registry-style ecosystem** for installing things like Prometheus that ship hundreds of manifests across multiple namespaces.

s12 will lean heavily on the third-party-install side (kube-prometheus-stack, Loki, Tempo, Mimir, OTel Collector).

---

## Why a package manager for k8s

- **The same Deployment** redeployed across dev/stage/prod with different images, replicas, env. Without templating you fork the file or `sed` it, and both fail differently:
  - *Forking:* `deployment.dev.yaml`, `deployment.prod.yaml`. Six months in, the diff between them is 80 lines of "same" and 5 lines of intentional difference, indistinguishable from accidental drift. Adding one env var is N edits across N files; the one you miss fails silently at the next deploy.
  - *`sed` / `envsubst`:* regex over YAML. A `:` in a value, a `/` or `&` in a password, or a multi-line block breaks the substitution and produces invalid YAML that nobody catches until `kubectl apply` rejects it. The source of truth splits across the template and the shell script that renders it, so reviewers can't see the final manifest without running the pipeline.
- **Third-party stacks** (Prometheus operator, cert-manager, ingress-nginx) ship dozens of manifests across multiple namespaces with version-coupled CRDs. Single-command install + uninstall + version-pinning matters.
- **Rollback.** `helm rollback users-api 3` walks a release back to revision 3 in one command. `kubectl apply` has no equivalent. You'd have to keep the old YAML around and re-apply.

Alternatives, briefly:

| Tool | Shape | Sweet spot |
| --- | --- | --- |
| **Helm** | Templated charts, server-side state in cluster Secrets | "Install someone else's complex stack." Also fine for your own app. |
| **Kustomize** | Overlay-based, no templating, pure YAML patch / merge | "Manage my own app's per-env diffs." Built into `kubectl` (`-k`). |
| **Plain `kubectl apply -f`** | What we've been doing | Small projects, single env |
| **ArgoCD `Application` CRD** | Wraps either of the above, adds git-as-source-of-truth + drift detection | s18 GitOps |

Many teams use Helm and Kustomize together. Helm for third-party, Kustomize for their own apps. We're doing Helm for both in s11 to keep the moving parts down.

## Chart anatomy

```text
helm/users-api/
├── Chart.yaml              # metadata: name, version, appVersion
├── values.yaml             # default values; overridable with -f / --set
├── values.schema.json      # Helm validates values against this before rendering
├── templates/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── configmap.yaml
│   ├── secret.yaml
│   ├── serviceaccount.yaml
│   ├── hpa.yaml
│   ├── _helpers.tpl        # reusable named templates (labels, fullname)
│   └── NOTES.txt           # post-install message
└── .helmignore             # like .gitignore but for `helm package`
```

- **`Chart.yaml`:** the chart's identity card. `apiVersion: v2`, `name`, `version` (chart version, semver), `appVersion` (the *app's* version, e.g. `local-v1`). The two version fields exist so the chart can be revised without the app version changing, and vice versa.
- **`values.yaml`:** the only file most users touch. Everything in `templates/` reads from here.
- **`values.schema.json`:** optional but recommended. A [JSON Schema](https://json-schema.org/) file that Helm validates values against before rendering any template. Catches type mismatches (`"six"` where `6` is expected) and missing required fields immediately at `helm lint` / `helm install` / `helm upgrade` time, before any manifest reaches Kubernetes.
- **`templates/*.yaml`:** Go `text/template` syntax. `{{ .Values.X }}` reads from values, `{{ .Release.Name }}` is the release name, `{{ include "users-api.labels" . }}` calls a named template defined in `_helpers.tpl`.
- **`templates/_helpers.tpl`:** the `.tpl` extension means "don't render this as a manifest." It just defines named templates (label blocks, fullnames) that other files `include`.
- **`templates/NOTES.txt`:** printed after `helm install`. Good place for "your service is at https://..." lines.
- **`.helmignore`:** excludes files from `helm package`. Same idea as `.gitignore`.

## Helm templating in 5 minutes

Don't try to memorise the whole template language. The [Helm chart template guide](https://helm.sh/docs/chart_template_guide/) is the reference. The constructs you'll actually use in s11:

| Construct | What it does | Where it shows up |
| --- | --- | --- |
| `{{ .Values.image.tag }}` | Read from `values.yaml` | `image:` line in Deployment |
| `{{ .Release.Name }}` | Name passed to `helm install <name>` | `name: {{ .Release.Name }}-config` |
| `{{ include "users-api.labels" . }}` | Call a named template | label block boilerplate |
| `{{- if .Values.hpa.enabled }} ... {{- end }}` | Conditional render | wrap an entire optional resource |
| `{{ toYaml .Values.resources \| nindent 12 }}` | Render a values sub-tree as YAML at a given indent | `resources:`, `env:`, `nodeSelector:` |
| `{{ default "v1" .Values.appVersion }}` | Fallback when value missing | safe defaulting |
| `{{ $key }}: {{ $val \| quote }}` inside `range` | Loop over a map | rendering a ConfigMap's `data:` from `.Values.env` |

The trailing dash (`{{-` / `-}}`) trims whitespace before / after the action. Forgetting it produces stray blank lines; that's the #1 Helm bug and the reason `helm template` exists.

### Built-in Helm objects

Helm injects several top-level objects into every template automatically:

| Object | Value | Source |
| --- | --- | --- |
| `.Release.Name` | Name you pass to `helm install <name>` | CLI at install time |
| `.Release.Namespace` | Target namespace (`-n` flag, or `default`) | CLI at install time |
| `.Release.Service` | Always `"Helm"` | Hardcoded by Helm itself |
| `.Release.IsInstall` | `true` on first install, `false` on upgrade | Helm runtime |
| `.Release.IsUpgrade` | `true` on upgrade, `false` on install | Helm runtime |
| `.Release.Revision` | Revision counter. 1 on install, increments each upgrade/rollback | Helm runtime |
| `.Chart.Name` | `name:` field from `Chart.yaml` | `Chart.yaml` |
| `.Chart.Version` | `version:` from `Chart.yaml` | `Chart.yaml` |
| `.Values.*` | Everything in `values.yaml` (overridable via `-f` / `--set`) | `values.yaml` + CLI |

`.Release.Service` is always `"Helm"`. It exists mainly for `NOTES.txt` boilerplate (`Installed by {{ .Release.Service }}`). You'll rarely use it outside of that.

### `helm/users-api/templates/_helpers.tpl`

Four named templates: `users-api.name`, `users-api.fullname`, `users-api.labels`, `users-api.selectorLabels`.

These are created when you run `helm create`. They emit the standard k8s recommended labels (`app.kubernetes.io/name`, `app.kubernetes.io/instance`, etc.).

### `helm/users-api/templates/deployment.yaml`

Templated copy of [k8s/users-api/deployment.yaml](../k8s/users-api/deployment.yaml).

- `{{- if not .Values.hpa.enabled }}` around `replicas:` is the s10 dance made declarative. If HPA is on, the chart leaves `replicas` unset and HPA owns it. If HPA is off, the chart sets a static replica count from `.Values.replicaCount`.
- `selectorLabels` is what *immutably* identifies the pods. Once a Deployment is created the selector can't change, so the `_helpers.tpl` keeps it minimal (`app.kubernetes.io/name` + `app.kubernetes.io/instance` only). `labels` adds version, managed-by, etc. on top. Those *can* change between revisions.

Everything else in the Deployment (probes, lifecycle preStop, envFrom) stays as it was.

### `helm/users-api/templates/service.yaml`

Templated copy of [k8s/users-api/service.yaml](../k8s/users-api/service.yaml). `type` and `port` come from `.Values.service`. Selector uses `users-api.selectorLabels`.

### `helm/users-api/templates/configmap.yaml`

Replaces [k8s/users-api/configmap.yaml](../k8s/users-api/configmap.yaml). The body is a `range` over `.Values.env`:

Adding a new env var is now a one-line edit in `values.yaml`. No template change.

### `helm/users-api/templates/secret.yaml`

Templated [k8s/users-api/secret.yaml](../k8s/users-api/secret.yaml). The DB password value comes from `.Values.secrets.DB_PASSWORD` (or `--set secrets.DB_PASSWORD=...` at install time).

The template uses `stringData` (recommended for Helm) so plain strings flow in directly. No `b64enc` filter, no double-encoding risk. Kubernetes base64-encodes on admission, so `kubectl get secret -o yaml` still shows `data:` in base64, not plaintext.

> **Caveat:** plaintext passwords in `values.yaml` are fine for local kind. Production templates use External Secrets / Sealed Secrets / Vault. This is covered in s19 security hardening.

### `helm/users-api/templates/serviceaccount.yaml`

Templated [k8s/users-api/serviceaccount.yaml](../k8s/users-api/serviceaccount.yaml). Name comes from `users-api.fullname`. `automountServiceAccountToken: false` stays (s8).

### `helm/users-api/templates/hpa.yaml`

Templated [k8s/users-api/hpa.yaml](../k8s/users-api/hpa.yaml) wrapped in:

```yaml
{{- if .Values.hpa.enabled }}
#...
{{- end }}
```

Toggle the whole resource on/off from `values.yaml`; no need to `kubectl delete`.

### `helm/users-api/templates/NOTES.txt`

What gets printed after `helm install / upgrade`

### Not converted in s11

`notify-api`, `frontend`, and `postgres` stay as plain YAML for now. They would also follow the same pattern. Each one is a template version copy `k8s/<name>/` to `helm/<name>/templates/`.

## Commands

```bash
# Render templates to stdout. Use for debugging.
helm template users-api helm/users-api
helm template users-api helm/users-api --set hpa.enabled=false   # see the diff

# Lint
helm lint helm/users-api

# First install (release named "users-api" in the default namespace)
# NOTE: delete the manual install first to avoid ownership conflicts
kubectl delete -f k8s/users-api/
helm install users-api helm/users-api

# What got installed
helm list
# NAME       NAMESPACE  REVISION  STATUS    CHART             APP VERSION
# users-api  default    1         deployed  users-api-0.1.0   local-v1

# Edit values.yaml, then upgrade
helm upgrade users-api helm/users-api
helm upgrade --install users-api helm/users-api # installs if release doesn't exist

# Or override values from the CLI without touching the file
helm upgrade users-api helm/users-api --set image.tag=local-v2
helm upgrade users-api helm/users-api -f values.staging.yaml

# -f (--values): supply a file that overrides the chart's default values.yaml.
# Use cases:
#   1. Someone else's chart (e.g. Prometheus from Artifact Hub): chart ships its own
#      values.yaml; you provide overrides for your environment.
#      helm install prometheus prometheus-community/kube-prometheus-stack -f my-overrides.yaml
#
#   2. Your own chart, multiple environments: one chart, different value files per env.
#      helm template users-api helm/users-api -f helm/values/production.yaml
#      helm template users-api helm/users-api -f helm/values/staging.yaml
#
#   3. Split values by concern: layer multiple files; last one wins on conflicts.
#      helm template users-api helm/users-api -f helm/values/base.yaml -f helm/values/monitoring.yaml
#
# Precedence (lowest → highest): chart values.yaml < -f file < --set

# History (every install + upgrade is a revision)
helm history users-api

# Rollback to a previous revision
helm rollback users-api 1

# Tear down everything the release installed
helm uninstall users-api
```

Verify the cluster matches what plain `kubectl apply -f k8s/users-api/` did before:

```bash
kubectl get deploy,svc,cm,sa,hpa -l app.kubernetes.io/name=users-api
curl -k https://demo.local/api/users   # same response as s5+
```

The labels switched from `app: users-api` (manual) to `app.kubernetes.io/name: users-api` (the [k8s recommended labels](https://kubernetes.io/docs/concepts/overview/working-with-objects/common-labels/), emitted by `_helpers.tpl`). The Service selector also uses the new label, so nothing breaks. Older selectors elsewhere in the project (e.g. NetworkPolicy from s7) may need an update. `kubectl describe netpol` will tell you if the selector no longer matches.

### Migration: delete the manual install first

`helm install users-api` will error out if the objects from `kubectl apply -f k8s/users-api/` are already in the cluster. Helm refuses to take ownership of resources it didn't create. Two options:

```bash
# Option A: clean slate
kubectl delete -f k8s/users-api/
helm install users-api helm/users-api

# Option B: have Helm adopt the existing objects (Helm 3.13+)
helm install users-api helm/users-api --take-ownership
```

Option A is cleaner. Option B is the migration path for an existing cluster where downtime matters.

## Install a third-party chart: replace the s10 metrics-server install

s10 installed metrics-server with raw `kubectl apply` plus a `kubectl patch` to add `--kubelet-insecure-tls`. Remove it.

```bash
kubectl delete -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```

The apply-then-patch dance is exactly what Helm fixes. With Helm:

```bash
helm repo add metrics-server https://kubernetes-sigs.github.io/metrics-server/
helm repo update
```

Add `helm/values/metrics-server.values.yaml` with args `--kubelet-insecure-tls`

Install:

```bash
helm install metrics-server metrics-server/metrics-server \
  -n kube-system -f helm/values/metrics-server.values.yaml

kubectl -n kube-system rollout status deploy/metrics-server --timeout=120s
kubectl top nodes # wait ~30s before running this
```

One command, no post-install patch, version-pinnable via `--version`, uninstallable via `helm uninstall`. That's the value prop in a paragraph.

> **Note:** if metrics-server is already installed from s10 via `kubectl apply`, `helm install` will collide on the existing objects. Either `kubectl delete -f https://.../components.yaml` first, or use `--take-ownership`. Same migration story as users-api above.

## How it fits together

```text
            helm/users-api/
            ├── Chart.yaml
            ├── values.yaml ────┐
            └── templates/      │  (rendered through Go text/template
                                │   with .Values, .Release, .Chart in scope)
                                ▼
                      helm install / upgrade
                                │
                                ▼
                        rendered manifests
                                │
                                ▼
                     server-side apply to API
                                │
        ┌───────────────────────┴───────────────────────┐
        ▼                       ▼                       ▼
  Deployment                 Service               HPA / SA / ...
                                │
                                ▼
                          cluster Secret stored
                      "sh.helm.release.v1.users-api.v1"
```

`helm` keeps no client-side state. Every release's history lives in cluster Secrets in the release's namespace. Inspect them with:

```bash
kubectl get secret -l owner=helm
# sh.helm.release.v1.users-api.v1   helm.sh/release.v1   1
# sh.helm.release.v1.users-api.v2   helm.sh/release.v1   1
```

## What this looks like on AWS

| s11 (kind) | EKS / AWS |
| --- | --- |
| `helm install users-api helm/users-api` | Same. The chart is portable. |
| Image `users-api:local-v1` loaded via `kind load` | Image pushed to ECR. `image.repository` in `values.yaml` becomes `123456789.dkr.ecr.us-east-1.amazonaws.com/users-api`. |
| metrics-server chart with `--kubelet-insecure-tls` | metrics-server chart **without** that arg, **or** the EKS-managed metrics-server add-on. |
| `values.yaml` committed to git | `values.prod.yaml` next to the chart, sensitive bits encrypted with SOPS or sealed secrets; `helm install -f values.prod.yaml`. |
| `helm uninstall` to tear down | Same, but in production you usually wrap Helm with **ArgoCD or Flux** (s18 GitOps). They call `helm template` + apply and add drift detection on top. |

Same chart, different values. That's the whole win on AWS.

## Try to break it

### 1. Bad template syntax, watch the lint catch it

Drop a quote in `templates/deployment.yaml`:

```yaml
image: "{{ .Values.image.repository }}:{{ .Values.image.tag }    # missing }}
```

Then:

```bash
helm lint helm/users-api
# ==> Linting helm/users-api
# [ERROR] templates/deployment.yaml: parse error ...

helm template users-api helm/users-api
# Error: parse error at (users-api/templates/deployment.yaml:23): unclosed action
```

`helm template` is the fast inner-loop tool. Faster than `helm install --dry-run` because it skips the API-server round-trip.

### 2. Values type error, watch schema validation catch it

Helm's Go template renders `{{ .Values.hpa.maxReplicas }}` as a bare value with no quotes, so a string `"six"` becomes `six` in the manifest. Whether Kubernetes accepts that depends on the API server, not something you want to discover at apply time.

`values.schema.json` makes type checking Helm's responsibility. It runs before any template is rendered, before any manifest is sent to Kubernetes.

Edit `values.yaml` so `hpa.maxReplicas` is a string:

```yaml
hpa:
  maxReplicas: "six"   # should be 6, not "six"
```

```bash
helm lint helm/users-api
# ==> Linting helm/users-api
# [ERROR] values don't meet the specifications of the schema(s) in the following chart(s):
# users-api:
# - hpa.maxReplicas: Invalid type. Expected: integer, given: string

helm upgrade users-api helm/users-api
# Error: UPGRADE FAILED: values don't meet the specifications of the schema(s) in the following chart(s):
# users-api:
# - hpa.maxReplicas: Invalid type. Expected: integer, given: string
```

The failure happens inside Helm, before any manifest reaches Kubernetes. No failed revision is recorded in `helm history`. Revert `values.yaml` before continuing.

**When does `helm rollback` apply?** When the failure reaches Kubernetes, for example, a bad image tag is accepted by the API server but pods enter `ImagePullBackOff`. In that case Helm records a failed revision:

```bash
helm history users-api
# REVISION  STATUS    DESCRIPTION
# 1         deployed  Install complete
# 2         failed    Upgrade "users-api" failed: ...

helm rollback users-api 1
helm history users-api
# REVISION  STATUS    DESCRIPTION
# 3         deployed  Rollback to 1
```

The rollback creates a *new revision* that re-applies the old state. The timeline is append-only.

### 3. CLI override beats values.yaml beats defaults

```bash
helm upgrade users-api helm/users-api --set image.tag=local-v2

# Confirm what was actually used
helm get values users-api          # only the overrides
helm get values users-api --all    # merged: defaults + overrides
```

Precedence (lowest to highest): chart `values.yaml` < `-f values.staging.yaml` < `--set`.

### 4. Helm tracks state at release time, not continuously

```bash
kubectl delete deploy users-api
helm list
# users-api  default  3  deployed  ...   <-- still says "deployed"!

kubectl get deploy users-api
# Error from server (NotFound): deployments.apps "users-api" not found
```

Helm doesn't auto-heal. It thinks the deployment is fine because the last apply succeeded. `helm upgrade` (or `helm install --replace`) will reconcile, but nothing watches for drift between upgrades. ArgoCD (s18) is what adds the missing reconcile loop on top.

```bash
helm upgrade users-api helm/users-api   # back in business
```

## What's next

- **s12** uses Helm to install the full **LGTM observability stack**: Loki + Grafana + Tempo + **Mimir** (the long-term metrics store). Prometheus stays as the in-cluster scraper that `remote_write`s to Mimir. Both apps get instrumented with `prom-client` (`/metrics`) and OpenTelemetry SDKs (traces). The `helm install <repo>/<chart> -f values.yaml` pattern from this stage is the workhorse.
- **s13** stacks `prometheus-adapter` on s12's Mimir + Prometheus to scale users-api on RPS (or any custom metric). Same stage installs VPA via the Fairwinds chart - both via Helm.
- **s18 GitOps** layers ArgoCD on top of Helm. Point ArgoCD at this chart in git, it watches and reconciles drift (fixing the gap you just exercised in "try to break it" #4).
- **s22 EKS migration** keeps the chart unchanged; only `image.repository` and the values file swap.

## Cleanup

```bash
helm uninstall users-api
helm uninstall metrics-server -n kube-system   # only if you swapped it via helm

# Confirm nothing's left
helm list
helm list -n kube-system
kubectl get deploy,svc,cm,sa,hpa,secret -l app.kubernetes.io/name=users-api
```

Helm tracks release history in cluster Secrets named `sh.helm.release.v1.<release>.v<n>`. `helm uninstall` deletes them along with everything it installed. To wipe just the history (rarely needed): `kubectl delete secret -l owner=helm`.
