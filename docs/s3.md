# s3 - Ingress + Frontend

> **Tag:** `s3`
> Goal: expose the cluster to real HTTP traffic via Ingress, add the frontend Deployment, and route both services behind one entry point on a real hostname.

s2 left us with a ClusterIP Service reachable only inside the cluster. `kubectl port-forward` or a `nodeport` service worked for debugging but is not how real clusters serve users. s3 introduces an Ingress controller, adds the frontend as a second workload, and lets a browser hit the app at `http://demo.local`.

---

## What is Ingress

An **Ingress** is a Kubernetes object that defines L7 (HTTP) routing rules: which host + path should go to which Service. By itself it is just config. An **Ingress controller** is the running process that watches Ingress objects and turns them into actual proxy configuration. We use ingress-nginx, which under the hood is an nginx Deployment in the `ingress-nginx` namespace.

The Ingress YAML is a config portable across clusters; the controller is a pluggable implementation. You can swap nginx for Traefik or HAProxy and the same Ingress object still works.

### Ingress vs LoadBalancer vs NodePort

| Service type / object | How traffic enters | Cost | Use case |
| --------------------- | ------------------ | ---- | -------- |
| `ClusterIP` | Inside cluster only | Free | Pod-to-pod (s2 default) |
| `NodePort` | `<NodeIP>:<30000-32767>` | Free | Local debug, dev clusters |
| `LoadBalancer` | Cloud LB with public IP, one per Service | One LB per Service ($) | Production single-service exposure |
| `Ingress` | One cloud LB in front of the controller, then L7 routes to N Services | One LB total | Production multi-service exposure |

In a cloud, every `Service: LoadBalancer` provisions a real ELB / NLB. Ten Services means ten load balancers and ten bills. Ingress collapses this: one LB feeds the ingress controller, which then routes internally to Services by host/path. Use service type `LoadBalancer` only for protocols ingress-nginx does not handle well (raw TCP, gRPC streaming). For everything else, route through Ingress.

At this stage, there is no LB. kind's `extraPortMappings` publishes the node port to the host, so `localhost:880` reaches the controller directly. From s5 onward, when LoadBalancer Services are needed for Postgres and gRPC, we add cloud-provider-kind, which sits in front of the controller and assigns external IPs the way an NLB would in AWS. Real AWS only enters at the final stage (s20).

## Recreating the kind cluster

The s1/s2 cluster was created with the default kind config. It has no host port mapping and no labeled ingress node, so the controller has nowhere to schedule and even if it did, nothing on your machine could reach it. We need a new cluster built from `infra/kind-config.yaml`.

```bash
kind delete cluster --name demo
kind create cluster --config infra/kind-config.yaml
```

### Why `extraPortMappings`

A kind cluster runs each "node" as a Docker container. By default those containers have no published ports, so `curl http://localhost:80` hits nothing. `extraPortMappings` is the equivalent of `docker run -p 80:80` on the node container, publishing the cluster's ingress port to your host. Without it the only way in is `kubectl port-forward`, which defeats the point of Ingress.

**Why 880 instead of 80?** Port 80 is already in use by the Windows system, so we use 880 on the host side instead.

### Why pin to `kindest/node:v1.32.2`

Compatibility issue with Docker Desktop. Newer node images don't work cleanly with it, so we pin to a version that does.

If you upgrade kind in future and want to try a newer image, test with `v1.33.x` before `v1.34+`.

### Why `kubeadmConfigPatches`

**kubeadm** is the standard tool for bootstrapping a Kubernetes cluster. kind runs `kubeadm init` inside the control-plane node container to bring the cluster up. The kind config lets us patch the kubeadm `InitConfiguration` before that runs. Here we inject `node-labels: "ingress-ready=true"` so the control-plane node carries that label at registration time.

**What `kubeadm init` does:**

- Generates TLS certificates for all cluster components.
- Starts `kube-apiserver`, `kube-controller-manager`, `kube-scheduler`, and `etcd` as static Pods on the node.
- Writes `kubeconfig` files so `kubectl` can authenticate with the API server.
- Installs CoreDNS as the in-cluster DNS addon.
- Outputs a `kubeadm join` token and command that worker nodes use to register.

**What `kubeadm init` does NOT do:**

- Install `kubelet`, `kubectl`, or container runtime - those must be on the node already.
- Install a CNI network plugin (Calico, Flannel, etc.) - you apply that separately after init.
- Provision VMs, load balancers, or any infrastructure - that is Terraform / the cloud provider's job.

kind handles the "install kubelet + container runtime" part by baking everything into the node image, which is why you don't see those steps here.

The ingress-nginx kind manifest pins its controller Pod with `nodeSelector: ingress-ready: "true"`. Without the label, the controller stays Pending forever. You could label the node after the fact with `kubectl label node`, but baking it into the cluster config is reproducible and survives recreation.

### Reload images

kind's image cache does not persist across cluster deletes. Rebuild and reload both:

```bash
docker build -t users-api:local-v1 apps/users-api
docker build -t frontend:local-v1 apps/frontend
kind load docker-image users-api:local-v1 frontend:local-v1 --name demo
```

## Install nginx-ingress

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
# ...
# ingressclass.networking.k8s.io/nginx created
# validatingwebhookconfiguration.admissionregistration.k8s.io/ingress-nginx-admission created

kubectl wait --namespace ingress-nginx \
  --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller \
  --timeout=180s

# pod/ingress-nginx-controller-76f9746865-fvsst condition met            
```

This manifest installs the controller Deployment, its ServiceAccount, RBAC rules, the `nginx` IngressClass, and a Service the host port mapping reaches. The controller Pod runs nginx and watches the Kubernetes API; when an Ingress object appears or changes, it rewrites its in-memory `nginx.conf` and reloads.

`kubectl wait` makes the script pause until the controller is actually ready to handle Ingress objects. If you apply your Ingress immediately when the controller isn't running yet, your Ingress just sits unprocessed.

### How the watch-and-reload cycle works

**1. You apply an Ingress object.**
`kubectl apply -f k8s/ingress.yaml` writes a record into the API server (etcd). Nothing proxies traffic yet. It is just stored config.

**2. The controller is watching.**
The ingress-nginx Pod holds a long-lived watch against the Kubernetes API - a streaming call that pushes an event whenever an Ingress is created, updated, or deleted. The moment your `kubectl apply` lands, the API server pushes an event to the controller.

**3. Controller translates Ingress rules → nginx config.**
The controller reads your routing rules:

```yaml
host: demo.local
path: /api  → backend: users-api:80
path: /     → backend: frontend:80
```

And generates real nginx config from them:

```nginx
server {
    listen 80;
    server_name demo.local;

    location ~* /api(/|$)(.*) {
        proxy_pass http://users-api.default.svc.cluster.local:80;
    }
    location / {
        proxy_pass http://frontend.default.svc.cluster.local:80;
    }
}
```

This happens in-process inside the controller. It builds the config as a string, not by editing a file on disk.

**4. Graceful reload.**
The controller writes the new config and signals nginx to reload. nginx starts fresh worker processes with the new config, lets existing workers drain their in-flight requests, then exits the old workers. No connections are dropped.

```text
Your Ingress YAML → etcd (just stored data)
                        ↓  watch event
                    ingress-nginx controller
                        ↓  translates rules
                    nginx.conf (in memory)
                        ↓  graceful reload
                    nginx workers  ←  actual traffic lands here
```

The Ingress object never touches traffic. nginx is what proxies requests. The controller is the translator between Kubernetes config and nginx config.

Verify:

```bash
kubectl get pods -n ingress-nginx
kubectl get ingressclass
# NAME    CONTROLLER             ...
# nginx   k8s.io/ingress-nginx   ...
```

## Map `demo.local` to localhost

Real ingress routes by Host header. To make the demo feel like a real hostname instead of bare `localhost`, add a hosts file entry:

```bash
# macOS / Linux
sudo sh -c 'echo "127.0.0.1 demo.local" >> /etc/hosts'

# Windows (admin PowerShell)
Add-Content -Path $env:WINDIR\System32\drivers\etc\hosts -Value "127.0.0.1 demo.local"
```

This only changes name resolution on your machine. The kind cluster does not know `demo.local` exists. The flow is:

1. Browser/curl resolves `demo.local` to `127.0.0.1` (from hosts file).
2. TCP connection opens to `127.0.0.1:880`, which the kind container has published.
3. Request lands at ingress-nginx with `Host: demo.local`.
4. The controller matches the Host against its Ingress rules and routes accordingly.

`curl http://localhost:880/health` does *not* match (different Host header) and returns 404 from the controller's default backend.

The "default backend" is whatever the controller falls back to when no rule matches. ingress-nginx ships with a stock 404 page, but you can override it per-Ingress with `spec.defaultBackend.service` pointing at a Service of your choice.

## Frontend Deployment

```bash
kubectl apply -f k8s/frontend-deployment.yaml
kubectl apply -f k8s/frontend-service.yaml
kubectl get pods -l app=frontend
```

The frontend is just nginx serving `index.html`. A few things differ from `users-api`:

**No startup probe.** nginx starts in milliseconds with no heavy init. The startup probe exists to cover slow first-time work (cache warm-up, model loading); none of that applies here.

**Simple readiness probe (`GET /`) only.** The frontend's job is serving a static file, so the probe checks just that. We don't chain it to users-api or the DB. If the backend dies, the frontend should still load and the health badge will show "unreachable". Coupling probes across services causes Endpoints churn and failures that should stay isolated.

nginx-ingress doesn't actively health-check upstreams. It watches the Service's Endpoints, which kube-proxy populates from Pods passing their readinessProbe.

**Smaller resources.** Static serving needs a fraction of what the Node app needs.

### The previous nginx.conf

In s0 the frontend container shipped with a custom `nginx.conf` that did two things:

1. Serve `/` from `/usr/share/nginx/html`.
2. Proxy `/api/` to `users-api:3000`.

Both are gone in s3. The default `nginx:alpine` config already serves the static directory, and the Ingress now owns `/api/` routing. Keeping the old config would create a second proxy layer inside the Pod that Ingress traffic never reaches anyway.

## The Ingress object

```bash
kubectl apply -f k8s/ingress.yaml
kubectl get ingress
kubectl describe ingress users-app
```

Walk through the spec:

```yaml
spec:
  ingressClassName: nginx
  rules:
  - host: demo.local
    http:
      paths:
      - path: /api(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service: { name: users-api, port: { number: 80 } }
      - path: /
        pathType: Prefix
        backend:
          service: { name: frontend, port: { number: 80 } }
```

**`ingressClassName: nginx`** binds this Ingress to the nginx controller. With multiple controllers in a cluster (internal + public, say) this picks which one handles it.

**Host rules** match on the HTTP `Host:` header. A request to `127.0.0.1:80` with `Host: demo.local` matches; the same IP with any other Host falls through to the default backend.

**Path types:**

| pathType | Match |
| -------- | ----- |
| `Exact` | Full string match |
| `Prefix` | URL path starts with the value, by `/`-separated segments |
| `ImplementationSpecific` | Controller decides. nginx-ingress treats the value as a regex |

We use `ImplementationSpecific` for `/api(/|$)(.*)` because it is a regex with two capture groups. `Prefix` would not allow that syntax.

**Rule ordering.** In the YAML, `/api(...)` comes before `/`, but this doesn't decide route ordering. Kubernetes does not guarantee rule order. nginx-ingress generates `location` blocks where regex matches (from `ImplementationSpecific`) are evaluated before prefix matches, so `/api/users` lands on users-api even though `/` would also match it.

You may see `nginx.ingress.kubernetes.io/use-regex: "true"` paired with `rewrite-target` in other tutorials. Instead of `ImplementationSpecific`, you can write `pathType: Prefix` plus this annotation and get the same nginx config out the other end.

`ImplementationSpecific` is the Kubernetes spec's way of saying this config will only work for nginx, not for Traefik or ALB.

### What this would look like on AWS ALB

- ALB doesn't have regex paths or path rewriting at all.
- Paths are literal: exact, prefix, or `*`/`?` wildcards. So `/api(/|$)(.*)` won't work, and t
- There is no `rewrite-target` annotation that ALB's controller will read; the LB simply can't rewrite a path before forwarding.

On ALB, you need to mount the API under `/api` in the app itself:

```js
app.use('/api', usersRouter);   // routes become /api/users, /api/health
```

Then the Ingress is just literal prefixes:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: users-app
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}]'
spec:
  ingressClassName: alb
  rules:
  - host: demo.local
    http:
      paths:
      - pathType: Prefix
        path: /api
        backend: { service: { name: users-api, port: { number: 80 } } }
      - pathType: Prefix
        path: /
        backend: { service: { name: frontend, port: { number: 80 } } }
```

`ingressClassName: alb`, and the annotations all live under `alb.ingress.kubernetes.io/*`. Every controller has its own annotation namespace; the `rewrite-target` and `use-regex` annotations from nginx mean nothing to ALB's controller.

### The rewrite annotation

```yaml
annotations:
  nginx.ingress.kubernetes.io/rewrite-target: /$2
```

Without this, a request to `/api/users` hits users-api as `/api/users`, which has no matching route and returns 404 (the API only knows `/users`, `/health`, etc.). The annotation tells nginx to rewrite the path before forwarding: capture group `$2` from the regex above (everything after `/api`) becomes the upstream path. So `/api/users` → upstream `/users`.

The annotation applies to all paths on the Ingress, but the `/` rule has no capture groups, so `$2` is empty and the rewrite resolves to `/`, which is harmless.

### Label vs annotation

We use **annotations** for the rewrite rule, not labels. The distinction matters.

| | Labels | Annotations |
| --- | ------ | ----------- |
| Used by | Kubernetes core (selectors, scheduling) | External controllers, tools, operators |
| Purpose | Identity, grouping, selection | Configuration, hints, metadata |
| Queryable | Yes (`-l app=frontend`) | No |
| Indexed | Yes | No |

`rewrite-target` is not part of the Kubernetes Ingress spec. The API server stores the annotation but has no idea what it means. The nginx-ingress controller reads it and uses it to generate its own nginx config. A different controller (Traefik) would ignore this annotation and require its own equivalent.

Rule of thumb: if Kubernetes itself needs to filter or select on a value, it is a label. If only a sidecar tool needs it, it is an annotation.

## How traffic flows now

```text
Browser
  │
  │  http://demo.local:880/api/users
  │
  ▼
hosts file:  demo.local  =>  127.0.0.1
  │
  ▼
kind container port 80   (extraPortMapping)
  │
  ▼
ingress-nginx Service
  │
  ▼
ingress-nginx controller Pod (nginx)
  │
  │  matches Host: demo.local, path /api/users
  │  rewrites to /users
  │
  ▼
users-api Service (ClusterIP)
  │
  │  kube-proxy iptables DNAT (from s2)
  │
  ▼
users-api Pod
```

For `http://demo.local/` the same flow ends at the `frontend` Service and Pod instead.

## Hit the app

Postgres still runs on the host:

```bash
docker compose -f local/docker-compose.yml up -d postgres
```

Apply the s2 manifests if they are not already in the new cluster:

```bash
kubectl apply -f k8s/configmap.yaml -f k8s/secret.yaml \
              -f k8s/deployment.yaml -f k8s/service.yaml
kubectl rollout status deployment/users-api
kubectl rollout status deployment/frontend
```

Hit it:

```bash
curl -i http://demo.local:880/api/health  # users-api health, expect 200
curl -i http://demo.local:880/api/users   # list users
```

Open `http://demo.local:880` in a browser. Add a user via the form. The badge should say "healthy"; the user appears in the table. Both calls round-trip through the Ingress.

## NodePort fallback for debugging

### Bypassing Ingress to test a Service directly

If the Ingress misbehaves and you want to hit a backend Service without going through the controller, create a dedicated NodePort Service

Apply and port-forward to reach it:

```bash
kubectl apply -f k8s/users-api-nodeport.yaml
kubectl port-forward service/users-api-nodeport 8081:80

# in a separate terminal
curl http://localhost:8081/health
# {"status":"ok","db":true}

#Delete when done.
kubectl delete -f k8s/users-api-nodeport.yaml
```

The same pattern works for the frontend: point `selector: app: frontend`, `targetPort: 80`, and choose a different nodePort (e.g. `30090`).

```bash
kubectl apply -f k8s/frontend-nodeport.yaml 
kubectl port-forward service/frontend-nodeport 8080:80

# in a separate terminal
curl -i http://localhost:8080/
# expect: 200 OK + HTML

# Delete when done
kubectl delete -f k8s/frontend-nodeport.yaml 
```

### Reaching the Ingress controller directly

The ingress-nginx-controller Service is already type `LoadBalancer`, which means kind assigns it NodePorts automatically (you can see them in `kubectl get svc -n ingress-nginx`). EXTERNAL-IP stays `<pending>` on kind, but the NodePorts are live. Port-forward to bypass kind's fake LB and hit the controller directly:

```bash
kubectl port-forward -n ingress-nginx svc/ingress-nginx-controller 8080:80

# in a separate terminal
curl -H "Host: demo.local" http://localhost:8080/api/health
```

### Inspecting the generated nginx config

The controller translates your Ingress objects into a real `nginx.conf` in memory. To read the full generated config including every `server` block, `upstream`, and location:

```bash
kubectl exec -n ingress-nginx deploy/ingress-nginx-controller -- nginx -T
```

The actually generated nginx config is the authoritative source when debugging routing, not the Ingress YAML. Use it to verify rewrite rules are applied correctly and upstreams resolve to the right Services.

## Try to break it

### 1. Wrong Host header

```bash
curl -i -H 'Host: wrong.local' http://demo.local:880/health
# HTTP/1.1 404 Not Found
```

The controller matches on Host. A request with the wrong one hits the default backend.

### 2. Forget the rewrite annotation

```bash
kubectl annotate ingress users-app nginx.ingress.kubernetes.io/rewrite-target-
curl -i http://demo.local:880/api/health
# HTTP/1.1 404 Not Found    (users-api received /api/health, no such route)

# reapply correct config
kubectl apply -f k8s/ingress.yaml
```

### 3. Delete the ingress controller Pod

```bash
kubectl get pod -n ingress-nginx -w

# in a separate terminal
kubectl delete pod -n ingress-nginx -l app.kubernetes.io/component=controller

# open http://demo.local:880 in the browser
# brief window of connection refused, then Deployment recreates and traffic resumes
```

### 4. Scale frontend to zero

```bash
kubectl scale deployment frontend --replicas=0
curl -i http://demo.local:880/             # 503: no endpoints for /
curl -i http://demo.local:880/api/health   # still 200: /api path independent
kubectl scale deployment frontend --replicas=2
```

Per-path independence: each rule has its own backend Service, so one path going down does not affect the other.

### 5. Point Ingress at a non-existent Service

```bash
kubectl patch ingress users-app --type=json \
  -p='[{"op":"replace","path":"/spec/rules/0/http/paths/1/backend/service/name","value":"ghost"}]'
kubectl describe ingress users-app    # events show backend not found
curl -i http://demo.local/            # 503

# reapply correct config
kubectl apply -f k8s/ingress.yaml
```

## What's next

s4 adds TLS termination at the Ingress using cert-manager with a self-signed ClusterIssuer. The routing rules stay the same; only the protocol changes from HTTP to HTTPS.

s5 moves postgres into the cluster as a StatefulSet with a PersistentVolumeClaim, so we stop depending on the host's docker-compose postgres. That is when storage primitives enter the picture: PV, PVC, StorageClass, and the stable pod identity StatefulSets provide.
