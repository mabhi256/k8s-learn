# s6 - Multi-service (notify-api, inter-service gRPC)

> **Tag:** `s6`
> Goal: add a second workload to the cluster so we have real east-west traffic.

s6 introduces `notify-api` (a gRPC server), users-api becomes its client, and we expose notify-api both inside the cluster (ClusterIP) and to the host (LoadBalancer) for direct `grpcurl` testing.

Pod-to-pod traffic is unrestricted. s7 adds NetworkPolicy to restrict it.

---

## New service: notify-api

A gRPC server in Node. One RPC, no database, no state. Its job in the cluster is to be a second pod that someone calls.

### Why gRPC?

GRPC provides a typed contract for inter-service calls, HTTP/2 multiplexing (one TCP connection, many in-flight calls), and a binary wire format. The trade-off is that gRPC is invisible to a browser, so the public edge (s3 ingress) stays HTTP and only east-west traffic uses gRPC.

NetworkPolicy and Service routing treat gRPC like any other TCP and only matters at the application layer.

### `k8s/notify-api/deployment.yaml`

Standard Deployment, 2 replicas, port 50051. Bog-standard until s8 adds a `serviceAccountName`. Probes use gRPC's health protocol, but `httpGet` works too if you expose a `/health` HTTP endpoint on a side port. For s6 we keep it simple and skip the gRPC health probe (the readiness check is just "Pod started"); s12 will revisit observability properly.

### `k8s/notify-api/service.yaml`

`ClusterIP`, port 50051. This is the Service users-api dials. The DNS name is `notify-api.default.svc.cluster.local`, but anywhere inside the namespace `notify-api` resolves the same way.

### `k8s/notify-api/loadbalancer-service.yaml`

`type: LoadBalancer`, port 50051. Lets you call notify-api from the host with `grpcurl`. Same shape as `postgres-lb` from s5.

Cloud-Provider-Kind gives it a real external IP on kind. On EKS, an NLB fills the same role.

## users-api becomes a gRPC client

### `apps/users-api/src/notifyClient.js`

Lazy client. Reads `NOTIFY_HOST` and `NOTIFY_PORT` from env. Exposes `notify(userId, email, action)` returning a promise. Uses `grpc.credentials.createInsecure()` because the in-cluster call is plaintext (TLS at the ingress, mesh later in s14).

### `apps/users-api/src/users.js` edit

After a successful `INSERT` or `DELETE`, fire the notify call. It is best-effort: wrap in `try / catch`, log on failure, and **do not** wait on it.

For this stage we go fire-and-forget. A real system would put a queue (s16) between the two.

### `apps/users-api/configmap.yaml` adds

```yaml
NOTIFY_HOST: "notify-api"
NOTIFY_PORT: "50051"
```

## Verify with Docker Compose before touching Kubernetes

> **nginx config for local only:** The nginx reverse-proxy config lives in `local/nginx.conf` and is bind-mounted into the frontend container by docker-compose (`./nginx.conf:/etc/nginx/conf.d/default.conf:ro`). It is not baked into `apps/frontend/Dockerfile`. That file stays clean because in Kubernetes the ingress controller handles proxying and the container never needs this config.

Spin up the full stack locally to confirm notify-api starts, users-api can reach it, and the gRPC call logs correctly.

```bash
docker compose -f local/docker-compose.yml up --build -d
```

Wait a few seconds for postgres to become healthy, then create a user:

```bash
curl -s -X POST http://localhost:3000/api/users \
  -H 'content-type: application/json' \
  -d '{"name":"Ada","email":"ada@example.com"}' | jq .
```

Check notify-api logged the call:

```bash
docker compose -f local/docker-compose.yml logs notify-api
# notify-api-1  | notify-api listening on :50051
# notify-api-1  | received user_id=1 email=ada@example.com action=CREATE
```

If you have `grpcurl` installed you can also call notify-api directly on port 50051:

```bash
grpcurl -plaintext \
  -import-path apps/notify-api/src -proto notify.proto \
  -d '{"user_id":1,"email":"ada@example.com","action":"test"}' \
  127.0.0.1:50051 notify.Notify/SendNotification
# {
#   "ok": true
# }
```

Tear down before recreating the cluster:

```bash
docker compose -f local/docker-compose.yml down
```

## Recreate the cluster

The cluster was torn down at the end of s5.

In a dedicated terminal, start `cloud-provider-kind` and leave it running:

```bash
sudo KUBECONFIG=$HOME/.kube/config $(go env GOPATH)/bin/cloud-provider-kind
```

Then recreate the cluster:

```bash
kind delete cluster --name demo
kind create cluster --config infra/kind-config.yaml
```

Reinstall ingress-nginx and cert-manager:

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/cloud/deploy.yaml
kubectl wait -n ingress-nginx --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=180s

kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
kubectl wait -n cert-manager --for=condition=Available deployment \
  --selector=app.kubernetes.io/instance=cert-manager --timeout=180s
```

## Apply order and verify

```bash
# notify-api first - users-api will try to dial it
kubectl apply -f k8s/notify-api/

# Updating a running users-api (assuming we run from s5, then update configs)
kubectl apply -f k8s/users-api/configmap.yaml
kubectl rollout restart deployment/users-api
```

Verify:

```bash
kubectl get deploy,svc -l 'app in (users-api,notify-api)'
# notify-api          2/2     ...
# notify-api          ClusterIP      10.96.x.x       50051/TCP
# notify-api-lb       LoadBalancer   10.96.x.x       50051:.../TCP
```

End-to-end: create a user and watch notify-api log it.

```bash
kubectl logs -l app=notify-api -f &
curl -k -X POST https://demo.local/api/users \
  -H 'content-type: application/json' \
  -d '{"name":"Ada","email":"ada@example.com"}'
# notify-api log: received user_id=1 email=ada@example.com action=CREATE
```

External gRPC via the LoadBalancer Service:

```bash
LB=$(kubectl get svc notify-api-lb -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
grpcurl -plaintext -d '{"user_id":99,"email":"x@x","action":"CREATE"}' \
  -import-path apps/notify-api/src -proto notify.proto \
  $LB:50051 notify.Notify/SendNotification
```

## How the pieces fit

```text
                                    kind cluster (3 nodes)
────────────────────────────────────────────────────────────────────────────────────

browser / curl ─────HTTPS:443─────▶ ingress-nginx (LoadBalancer, ext IP from CPK)
                                           │
                                           ▼
                                    ┌──────────────┐
                                    │  frontend    │
                                    └──────────────┘
                                           │  /api/...
                                           ▼
                                    ┌──────────────┐   TCP:5432    ┌──────────────┐
                                    │  users-api   │──────────────▶│  postgres    │
                                    └──────┬───────┘               │ (StatefulSet)│
host (grpcurl)                             │                       └──────────────┘
     │                                     │  gRPC:50051
     ▼                                     ▼
TCP:50051────▶ notify-api-lb ─────▶ ┌──────────────┐
                                    │  notify-api  │
                                    │  gRPC :50051 │
                                    └──────────────┘
```

Every Pod can still dial every other Pod on every port - we haven't applied any NetworkPolicy yet.

## What this looks like on AWS

| s6 (local) | EKS / AWS |
| --- | --- |
| `notify-api` ClusterIP Service | Same |
| `notify-api-lb` LoadBalancer Service | **NLB** (TCP load balancer, gRPC-friendly). ALB is L7/HTTP, so it's the wrong choice for raw gRPC. The AWS Load Balancer Controller picks NLB based on annotations. |
| Pod-to-Pod plaintext gRPC | Same by default. Service mesh (s14) adds mTLS. |
| cloud-provider-kind handing out the LB external IP | The AWS Load Balancer Controller provisioning the real NLB. |

The application code is unchanged; only the LB type at the edge differs.

## Try to break it

### 1. Confirm DNS-based service discovery

```bash
kubectl exec deploy/users-api -- nslookup notify-api
# notify-api.default.svc.cluster.local
# Address: 10.96.x.x

kubectl exec deploy/users-api -- nslookup notify-api.default.svc.cluster.local
# Same VIP
```

Inside the namespace, the bare name `notify-api` is enough. The FQDN works from anywhere in the cluster.

### 2. Scale notify-api to zero, watch user creates still succeed

```bash
kubectl scale deployment notify-api --replicas=0
curl -k -X POST https://demo.local/api/users \
  -H 'content-type: application/json' \
  -d '{"name":"Grace","email":"grace@example.com"}'
# 201 - user is created in Postgres
kubectl logs -l app=users-api | tail -n 2
# notifyClient error: 14 UNAVAILABLE: no endpoints
kubectl scale deployment notify-api --replicas=2
```

This is the fire-and-forget semantic in action - notify-api outages don't break the user-creation path. The notification is dropped, the user is not.

### 3. Direct gRPC call from another Pod

grpcurl needs the proto schema to serialize the request. The server doesn't expose reflection, so mount the proto file via a ConfigMap.

```bash
kubectl create configmap notify-proto \
  --from-file=notify.proto=apps/notify-api/src/notify.proto
```

```bash
kubectl run debug --rm -it --restart=Never \
  --image=fullstorydev/grpcurl \
  --overrides='{
    "spec": {
      "volumes": [{"name":"proto","configMap":{"name":"notify-proto"}}],
      "containers": [{
        "name":"debug",
        "image":"fullstorydev/grpcurl",
        "args":["-plaintext","-d","{\"user_id\":1,\"email\":\"c@c\",\"action\":\"CREATE\"}",
                "-import-path","/proto","-proto","notify.proto",
                "notify-api:50051","notify.Notify/SendNotification"],
        "volumeMounts":[{"name":"proto","mountPath":"/proto"}]
      }]
    }
  }'
# {"ok": true}
```

Only the pod is deleted automatically when it exits (`--rm`), not the ConfigMap.

```bash
kubectl get configmap notify-proto
kubectl delete configmap notify-proto
```

Anything in the cluster can reach `notify-api:50051` right now. Even the frontend Pod. Even Postgres. This will be fixed in s7.
