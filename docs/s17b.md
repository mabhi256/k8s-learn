# s17b - KEDA HTTP Add-on (Scale-to-Zero for HTTP)

> **Tag:** `s17b`
> Goal: The HTTP add-on places an interceptor proxy between ingress and the app: it holds requests while KEDA brings pods from 0 to 1.

s17a showed that KEDA can scale a Deployment to 0 replicas, but for HTTP workloads that creates a dead end: with 0 pods, no requests reach the app, so `http_requests_total` never increases, so KEDA never scales back up. Every request gets 503 forever.

The HTTP add-on breaks the cycle by counting pending requests as the scaling metric, which works even with 0 pods.

---

## Architecture

```text
                 ┌─────────────────────────────────────────────────┐
                 │  KEDA HTTP Add-on (keda namespace)              │
                 │                                                 │
    ┌─────────┐  │  ┌──────────────────────┐    ┌───────────────┐  │
    │ nginx   │──┼─▶│  interceptor proxy   │───▶│  users-api    │  │
    │ ingress │  │  │  (holds requests     │    │  (0..N pods)  │  │
    └─────────┘  │  │   when pods = 0)     │    └───────────────┘  │
                 │  └──────────┬───────────┘                       │
                 │             │ reports pending request count     │
                 │             ▼                                   │
                 │  ┌────────────────────┐                         │
                 │  │ KEDA operator      │                         │
                 │  │ (scales 0 → 1 when │                         │
                 │  │  requests pending) │                         │
                 │  └────────────────────┘                         │
                 └─────────────────────────────────────────────────┘
```

Without the add-on, KEDA can scale to 0 but can never scale back up for HTTP traffic (no pods means no metrics). The interceptor proxy breaks the cycle: it counts pending requests as the scaling metric, which works even with 0 pods.

---

## HTTPScaledObject

The `HTTPScaledObject` replaces the regular `ScaledObject` for HTTP workloads. It tells the interceptor which hosts to proxy and how to scale.

`scaleTargetRef` must include a `name` field that points to the Deployment. Without it, the interceptor doesn't know which workload to scale, and `TARGETWORKLOAD` shows `//` instead of `apps/v1/Deployment/users-api`. Scale-from-zero silently fails: pods stay at 0 and requests hang forever.

The `scalingMetric.requestRate` replaces the Prometheus trigger from the regular ScaledObject. Instead of querying Prometheus for `http_requests_total`, the interceptor measures request rate directly. No PromQL, no adapter, no chicken-and-egg.

---

## Ingress routing

The ingress must route to the interceptor proxy instead of directly to the app. The interceptor runs in the `keda` namespace, so a cross-namespace `ExternalName` service bridges the gap.

Then the ingress backend changes from `users-api:80` to `keda-interceptor-proxy:8080`.

Since the interceptor runs in the `keda` namespace, the users-api NetworkPolicy must allow ingress from that namespace. Without it, the interceptor can't reach `users-api:3000`: pods scale up, become ready, but every request hangs until nginx returns a 504 upstream timeout.

```yaml
# in k8s/network-policies/users-api.yaml
- namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: keda
```

## Commands

### Install and apply

```bash
# 1. Install the HTTP add-on (KEDA must already be running from s17a)
helm install http-add-on kedacore/keda-add-ons-http -n keda -f helm/values/keda-http.values.yaml

# 2. Wait for the interceptor to be ready
kubectl -n keda rollout status deploy/keda-add-ons-http-interceptor

# 3. Deploy users-api with HTTP add-on enabled
# (keda.http.enabled: true in values.yaml creates the HTTPScaledObject + ExternalName service)
# Use --force-conflicts because the KEDA operator claims ownership of some HTTPScaledObject
# fields via server-side apply, which conflicts with Helm's field manager.
helm upgrade users-api helm/users-api --force-conflicts

# 4. Allow the interceptor (keda namespace) through the NetworkPolicy
kubectl apply -f k8s/network-policies/users-api.yaml

# 5. Update ingress to route through the interceptor
kubectl apply -f k8s/ingress.yaml

# 6. Verify the HTTPScaledObject is active
kubectl get httpscaledobject
kubectl describe httpscaledobject users-api
```

### Verify scale-to-zero

```bash
# Close any browser tabs hitting demo.local first.
# The frontend polls /api/health, which routes through the interceptor.
# The interceptor counts each request as in-flight concurrency,
# so the metric never reaches 0 and KEDA never scales down.

# Wait for cooldown (300s) until pods scale to 0
kubectl get deploy users-api -w
# READY: 2/2 → 1/1 → 0/0

# If pods aren't scaling down, check the interceptor queue:
kubectl port-forward -n keda svc/keda-add-ons-http-interceptor-admin 9090:9090
curl http://localhost:9090/queue
# Concurrency should be 0 for scale-to-zero to trigger

# Send a request — interceptor holds it, KEDA scales 0 → 1, request completes
curl -k https://demo.local/api/users
# Takes 5-15s (cold start), but returns 200 instead of 503
```

### Reverting to direct routing

To disable the HTTP add-on and go back to direct ingress routing:

```bash
# 1. Set keda.http.enabled: false in values.yaml
helm upgrade users-api helm/users-api

# 2. Restore ingress to point directly to users-api:80
# Change keda-interceptor-proxy:8080 back to users-api:80 in k8s/ingress.yaml
kubectl apply -f k8s/ingress.yaml

# 3. (Optional) Uninstall the HTTP add-on
helm uninstall http-add-on -n keda
```

## Try to break it

### 1. Scale-to-zero without the HTTP add-on = permanent 503

Set `minReplicaCount: 0` with the Prometheus scaler and no HTTP add-on. After cooldown, all pods terminate. The Prometheus metric stays at 0 (no pods to produce it), so KEDA never scales back up. Every request gets 503 from nginx.

Fix: either set `minReplicaCount: 1`, or install the HTTP add-on (`keda.http.enabled: true`) so the interceptor proxy can trigger scale-from-zero.

### 2. Missing scaleTargetRef.name = silent scale-from-zero failure

Omit the `name` field from `scaleTargetRef`. The HTTPScaledObject shows `READY: True` and `TARGETWORKLOAD: //`, but the interceptor has no deployment to scale. Pods stay at 0 and requests hang at the interceptor indefinitely.

Fix: set `scaleTargetRef.name` to the Deployment name. After fixing, `TARGETWORKLOAD` shows `apps/v1/Deployment/users-api`.

### 3. Helm upgrade conflict with KEDA operator field manager

The KEDA operator reconciles the HTTPScaledObject and claims server-side apply ownership of fields like `scaleTargetRef.name` and `scalingMetric.requestRate.window`. When Helm tries to set those same fields, Kubernetes rejects the update with a field manager conflict.

Fix: use `helm upgrade --force-conflicts` to let Helm take ownership of the contested fields.

### 4. Scale-to-zero + slow startup = cold-start latency

With the HTTP add-on, scale-from-zero works, but the first request takes 5-15 seconds while the pod starts and passes readiness probes. The interceptor holds the request (no 503), but the caller sees high latency.

Fix: for latency-sensitive APIs, set `minReplicaCount: 1`. Use scale-to-zero for background workers, dev/staging, or APIs where occasional cold starts are acceptable.
