# s18d - Recreating the kind Cluster

> **Tag:** `s18d`
> Goal: rebuild the cluster from scratch after a `kind delete` or when the cluster is broken beyond repair. With ArgoCD (s18b), this is much simpler than the pre-GitOps fresh-start: install Calico and ArgoCD manually, apply the root Application, and ArgoCD reconciles everything else from Git.

---

## When to use this

- `kind get clusters` shows nothing (cluster was deleted or never created).
- The cluster is broken beyond repair (stuck nodes, corrupted etcd, etc.).
- You changed `infra/kind-config.yaml` (e.g., added/removed worker nodes) and need the change to take effect.

If you only rebooted your PC, the cluster is still there: follow [wsl-restart.md](./wsl-restart.md) instead.

---

## What gets wiped

Deleting a kind cluster destroys all containers and volumes. Everything stateful is lost:

| Component | Impact |
| --- | --- |
| PostgreSQL (CNPG) | Database is empty. Schema is recreated by Flyway (users-api initContainer). |
| MinIO | Backup bucket is gone. CNPG scheduled backups start fresh. |
| Prometheus / Loki / Tempo | All metrics, logs, and traces are gone. |
| Grafana | Dashboards survive (ArgoCD recreates the ConfigMaps). Manual dashboards are lost. |
| PVCs | All recreated empty by local-path-provisioner. |
| TLS certificates | cert-manager generates a new root CA. Browser trust must be re-imported. |

Everything in Git (manifests, Helm values, docs) is unaffected. ArgoCD rebuilds the cluster state from Git.

## Commands

```bash
# 1. Delete the old cluster (skip if already gone)
kind delete cluster --name demo

# 2. Create the cluster
kind create cluster --config infra/kind-config.yaml

# 3. Install Calico CNI (nodes stay NotReady without it)
#    The API server's /openapi/v2 endpoint may be flaky right after creation
#    (no CNI -> nodes NotReady -> aggregation layer unhealthy).
#    --validate=false skips the schema download that fails with EOF.
kubectl apply --validate=false \
  -f https://raw.githubusercontent.com/projectcalico/calico/v3.29.3/manifests/calico.yaml
kubectl -n kube-system rollout status ds/calico-node --timeout=180s
kubectl get nodes   # all should be Ready

# 4. Install ArgoCD (it can't install itself)
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update
helm install argocd argo/argo-cd -n argocd --create-namespace \
  -f helm/values/argocd.values.yaml

# 5. Wait for ArgoCD
kubectl -n argocd rollout status deploy/argocd-server

# 6. Apply the root Application (everything else syncs from here)
kubectl apply -f k8s/argocd/root-app.yaml

# 7. Watch ArgoCD sync all applications
kubectl get applications -n argocd -w
# Wait until all apps show Synced / Healthy (takes 2-5 minutes).
# Some apps (db-backup, postgres) may show Progressing while StatefulSets start.

# 8. Scale down coredns (not ArgoCD-managed, kind defaults to 2 replicas)
#    To undo: kubectl scale deployment coredns -n kube-system --replicas=2
kubectl scale deployment coredns -n kube-system --replicas=1

# 9. Seed the database (schema is created by Flyway on first users-api start)
#    Wait for users-api to have started at least once (KEDA may have it at 0;
#    curl the endpoint to wake it, or scale manually):
kubectl scale deployment users-api --replicas=1
kubectl rollout status deploy/users-api --timeout=120s
kubectl delete job db-seed --ignore-not-found
kubectl apply -f k8s/jobs/db-seed.yaml
kubectl wait --for=condition=complete job/db-seed --timeout=60s
kubectl logs job/db-seed   # should show: INSERT 0 3

# 10. Start cloud-provider-kind (dedicated WSL terminal, leave running)
sudo KUBECONFIG=$HOME/.kube/config $(go env GOPATH)/bin/cloud-provider-kind
```

## Post-rebuild: browser access

After the cluster is up, restore browser access. See [wsl-restart.md](./wsl-restart.md) for the full checklist, and [wsl-browser-access.md](./wsl-browser-access.md) for first-time setup details.

### 1. Clear stale loopback aliases (WSL)

```bash
ip addr show lo | grep '172\.'
# Delete each one shown:
sudo ip addr del 172.18.0.4/32 dev lo   # repeat per IP
```

### 2. Start cloud-provider-kind (dedicated WSL terminal)

```bash
sudo KUBECONFIG=$HOME/.kube/config $(go env GOPATH)/bin/cloud-provider-kind
```

### 3. Get the ingress IP and update WSL /etc/hosts

```bash
INGRESS_IP=$(kubectl get svc -n ingress-nginx ingress-nginx-controller \
  -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
echo $INGRESS_IP   # confirm non-empty

grep -q "demo\.local" /etc/hosts \
  && sudo sed -i "s/.*demo\.local/$INGRESS_IP demo.local/" /etc/hosts \
  || echo "$INGRESS_IP demo.local" | sudo tee -a /etc/hosts
```

### 4. Find the kindccm HTTPS port (WSL)

```bash
docker ps | grep kindccm
# Look for the container with ->80/tcp and ->443/tcp (ingress-nginx, not Istio).
# Note the port before ->443/tcp (e.g. 32783).
```

### 5. Update the port proxy (Admin PowerShell)

```powershell
netsh interface portproxy delete v4tov4 listenport=443 listenaddress=127.0.0.1

# Replace 32769 with the port from step 4:
netsh interface portproxy add v4tov4 `
  listenport=443 listenaddress=127.0.0.1 `
  connectport=32769 connectaddress=127.0.0.1
```

### 6. Update Windows hosts file (Admin PowerShell, once per cluster recreate)

Windows needs `127.0.0.1` (not the cluster IP) for all `*.demo.local` hostnames. The port proxy in step 5 bridges the gap.

```powershell
# Remove stale 172.x entries:
$content = Get-Content C:\Windows\System32\drivers\etc\hosts
$content | Where-Object { $_ -notmatch '172\.\d+\.\d+\.\d+.*demo\.local' } |
  Set-Content C:\Windows\System32\drivers\etc\hosts

# Add the correct entry (all hostnames on one line):
Add-Content C:\Windows\System32\drivers\etc\hosts "127.0.0.1 demo.local grafana.demo.local argo.demo.local"
```

### 7. Re-import the root CA

A cluster recreate generates a new cert-manager root CA. The old certificate in the Windows trust store is invalid. Browsers will show a security warning until you re-import.

```bash
# WSL: extract the new CA cert
kubectl get secret demo-root-ca-tls -n cert-manager \
  -o go-template='{{index .data "ca.crt"}}' | base64 -d > /tmp/ca.crt
```

```powershell
# Admin PowerShell: delete old, import new
certutil -delstore "Root" "demo-root-ca"
$desktop = [Environment]::GetFolderPath("Desktop")
Copy-Item "\\wsl$\Ubuntu\tmp\ca.crt" "$desktop\ca.crt"
certutil -addstore -f "Root" "$desktop\ca.crt"
```

**Restart the browser** after importing (Chrome/Edge cache the old cert).

**Firefox** uses its own cert store, not Windows: Settings > Privacy & Security > Certificates > View Certificates > Authorities > Import `ca.crt`.

## Differences from pre-ArgoCD fresh-start

The old [fresh-start.md](./fresh-start.md) had 11 steps of manual `helm install` and `kubectl apply` commands in dependency order. With ArgoCD, the rebuild is:

| Pre-ArgoCD (fresh-start.md) | Post-ArgoCD (this doc) |
| --- | --- |
| Manual install of cert-manager, ingress-nginx, metrics-server, Istio, LGTM stack, CNPG, MinIO, app workloads | ArgoCD syncs all of these from Git via sync waves |
| Build and `kind load` Docker images | Same (images must be in the kind node cache) |
| 11 sequential steps with inter-dependencies | 3 manual steps (Calico, ArgoCD, root app), then ArgoCD handles the rest |
| Order matters (CRDs before resources, namespaces before workloads) | Sync waves handle ordering automatically |

The `fresh-start.md` runbook is still valid for rebuilding to a pre-ArgoCD state (s16 and earlier). For s18b+ clusters, use this doc.

## Changes in this stage

### ArgoCD Application for the main ingress

The `demo.local` Ingress resource (`k8s/ingress.yaml`) was applied manually in earlier stages and missed the GitOps migration in s18b. It has been:

1. Moved from `k8s/ingress.yaml` to `k8s/ingress/ingress.yaml` (ArgoCD `path` targets directories, not single files).
2. Given an ArgoCD Application at `k8s/argocd/infra/ingress.yaml`.

Without this, a fresh cluster has no `demo.local` Ingress and all requests return 404.

### KEDA HTTP external-scaler replica count

The KEDA HTTP Add-on external-scaler defaulted to 3 replicas. Reduced to 1 in `helm/values/keda-http.values.yaml` to save RAM on kind.

To undo: remove the `scaler` block from `helm/values/keda-http.values.yaml` (default is 3 replicas).

### db-seed job hostname fix

The seed job (`k8s/jobs/db-seed.yaml`) used `postgres-0.postgres-headless` as the database host. This was the StatefulSet DNS name from s5, before CNPG (s16) replaced it. CNPG does not create a headless service with that name. Updated to `postgres-rw` (the CNPG read-write service).
