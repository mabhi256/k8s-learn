# s16b - Connection Pooling (PgBouncer via Pooler CR)

> **Tag:** `s16b`
> Goal: add PgBouncer connection pooling between users-api and the CNPG cluster using the `Pooler` CRD. This changes the connection path from `users-api -> postgres-rw` to `users-api -> postgres-pooler-rw -> postgres-rw`.

s16a replaced the manual StatefulSet with a CNPG `Cluster` CR and pointed users-api at `postgres-rw`. That works, but every users-api replica opens its own connection pool directly to Postgres. Under load, the combined connections can exhaust `max_connections` (100 in our cluster).

---

## Why connection pooling

A Node/Go/etc. service with a connection pool *per replica* can exhaust `max_connections` under load. PgBouncer multiplexes many client connections onto a small set of backend connections.

```text
  users-api pods ──many──▶ postgres-pooler-rw (PgBouncer) ──few──▶ postgres-rw (primary)
       1000 clients              transaction pooling            25 backend conns
```

Without the pooler, the connection path is:

```text
  users-api pods ──many──▶ postgres-rw (primary)
       1000 clients         100 max_connections
```

With 6 replicas (HPA max from s13), each holding 20 connections, you hit 120 connections against a 100-connection limit. The pooler absorbs those 120 client connections and fans them into 25 backend connections.

---

## The Pooler CR

CNPG ships a `Pooler` CRD that creates a Deployment of PgBouncer pods plus a Service of the same name.

**`poolMode: transaction`**: a backend connection is returned to the pool at the end of each transaction, not when the client disconnects. This gives the highest reuse but disables session-level features (`SET`, session-scoped temp tables, prepared statements across transactions). Most web apps are fine with it; if yours relies on session state, use `session` mode.

**`instances: 2`**: two PgBouncer pods for HA (3+ in prod). If one dies, the Service routes to the other.

**`type: rw`**: the pooler only routes to the primary (via `postgres-rw`). Use `type: ro` to create a separate pool that routes to read replicas (via `postgres-ro`).

---

## Prerequisites

Two things specific to our hardened namespace:

**1. NetworkPolicy.** The pooler pods are a *new* client of the cluster, and a *new* server for users-api. The default-deny policy blocks both directions.

- **Pooler -> cluster (port 5432):** already handled. The `allow-ingress-postgres` policy in `k8s/network-policies/postgres.yaml` includes `app: postgres-pooler` in its ingress sources (applied in s16a prerequisites).
- **users-api -> pooler (port 5432):** needs a new rule. The pooler pods have label `app: postgres-pooler`; without an ingress policy selecting those pods, users-api connections hang.

```bash
kubectl apply -f k8s/network-policies/postgres.yaml
```

**2. Istio.** STRICT mTLS applies to the pooler too. The pooler template includes the `holdApplicationUntilProxyStarts` annotation so PgBouncer waits for the sidecar before accepting connections. PgBouncer speaks the raw PostgreSQL wire protocol, so the pooler Service port must use the `tcp-` prefix (same as the cluster: Istio treats it as opaque TCP).

---

## Apply

```bash
kubectl apply -f k8s/postgres/pooler.yaml
kubectl get pods -l cnpg.io/poolerName=postgres-pooler-rw
# 2 PgBouncer pods, READY 2/2 (app container + Istio sidecar)
```

---

## Point users-api at the pooler

Update `DB_HOST` in `helm/users-api/values.yaml` from `postgres-rw` to `postgres-pooler-rw`

```bash
helm upgrade users-api ./helm/users-api
```

The checksum annotation (added in s16a) triggers a rollout automatically when the ConfigMap changes.

## Verify

```bash
kubectl rollout status deploy/users-api --timeout=120s

# End-to-end: hit the API through the pooler
curl -k https://demo.local/api/users
```

### Is the pooler actually in the path?

`pg_stat_activity` won't help here. In transaction mode, PgBouncer grabs a backend connection, runs the query (~1ms), and returns it immediately. The connection is gone before any snapshot can see it.

Instead, query PgBouncer's own admin database. First find the socket path inside the pooler container:

```bash
kubectl exec <pooler-pod> -c pgbouncer -- \
  find / -name ".s.PGSQL.*" 2>/dev/null
# /controller/run/.s.PGSQL.5432
```

Then query `SHOW STATS`:

```bash
POOLER_POD=$(kubectl get pods -l cnpg.io/poolerName=postgres-pooler-rw \
  -o jsonpath='{.items[0].metadata.name}')

kubectl exec $POOLER_POD -c pgbouncer -- \
  psql -h /controller/run -p 5432 -U pgbouncer pgbouncer -c "SHOW STATS;"
```

### Generate load and read the stats

```bash
# Fire 200 requests with 50 concurrent workers
hey -n 200 -c 50 https://demo.local/api/users

# Then check the stats again
kubectl exec $POOLER_POD -c pgbouncer -- \
  psql -h /controller/run -p 5432 -U pgbouncer pgbouncer -c "SHOW STATS;"
```

The key columns in the `appdb` row:

| Column | What it tells you |
| --- | --- |
| `total_query_count` | Total queries PgBouncer forwarded to Postgres. Should match your `hey -n` count. |
| `total_server_assignment_count` | How many times PgBouncer grabbed a backend connection. Equal to `total_query_count` in transaction mode (one assignment per query). |
| `avg_query_time` | Average query duration in microseconds. ~1000 μs (1ms) for a simple SELECT. |
| `avg_wait_time` | How long clients waited for a free backend connection. Near zero means the pool is not saturated. |

If `total_query_count` climbs after your `hey` run, traffic is flowing through PgBouncer. The whole point: 50 concurrent clients, hundreds of queries, all served by 1 backend connection with near-zero wait time.

### PgBouncer logs

The pooler container also logs backend connection lifecycle events:

```bash
kubectl logs $POOLER_POD -c pgbouncer --tail=10
```

You'll see lines like:

```text
SSL established: TLSv1.3/...        # backend connection opened
closing because: server idle timeout # closed after 30s of no queries
new connection to server             # reopened on next request
```

This confirms PgBouncer opens backend connections on demand and closes them after `server_idle_timeout` (30s default).

The pooler also exports its own PgBouncer metrics (active/waiting clients, pool saturation), scrapeable with a PodMonitor the same way the cluster is.

## What this looks like on AWS

| s16b (kind) | EKS / AWS |
| --- | --- |
| `Pooler` (PgBouncer) in-cluster | Same chart. Or **RDS Proxy** for managed connection pooling (no operator needed). |

RDS Proxy is the managed equivalent: it sits between your app and RDS, handles connection pooling, and survives failovers transparently. The trade-off is cost ($$$) and less tuning control compared to running your own PgBouncer.
