# s20 - Resilience (PDB, Quotas, Priority, Backup)

> **Tag:** `s20`
> Goal: make the cluster survive disruptions gracefully. PodDisruptionBudgets limit voluntary evictions (VPA, node drains). ResourceQuotas and LimitRanges prevent namespace resource abuse. Priority classes control which workloads survive under pressure. Velero backs up and restores cluster state.

s13 showed VPA evicting Pods mid-traffic. s19 locked down security. This stage handles the operational question: when things go wrong (node drain, resource pressure, VPA eviction, accidental deletion), how do you minimize blast radius and recover?

---

## PodDisruptionBudget (PDB)

### The problem

Voluntary disruptions — node drains (`kubectl drain`), VPA evictions, cluster upgrades — can terminate multiple Pods simultaneously. With `replicas: 2` and no PDB, a `kubectl drain` on the node running both Pods kills 100% of capacity at once.

### What a PDB does

A PDB tells the eviction API: "you may disrupt at most N Pods at a time" or "at least N Pods must remain available." The drain, VPA updater, or cluster autoscaler respects this and waits.

### Key fields

| Field | What it means |
| --- | --- |
| `spec.selector` | Which Pods this PDB protects (label selector, matching the Deployment). |
| `spec.minAvailable` | Minimum Pods that must remain running during a disruption. Can be a number (`1`) or percentage (`50%`). |
| `spec.maxUnavailable` | Maximum Pods that can be down at once. Inverse of `minAvailable`. |
| `spec.unhealthyPodEvictionPolicy` | `IfHealthy` (default): only evict healthy Pods. `AlwaysAllow`: evict even unhealthy Pods (useful when stuck Pods block drains). |

Use one of `minAvailable` or `maxUnavailable`, not both.

### Choosing the right value

| Scenario | Setting | Why |
| --- | --- | --- |
| 2 replicas, can tolerate 1 down | `maxUnavailable: 1` | Drain proceeds, one Pod stays up. |
| 3+ replicas, want majority available | `minAvailable: 2` or `minAvailable: "50%"` | At least half the fleet survives. |
| Singleton (1 replica) | **Don't use a PDB** | `minAvailable: 1` blocks all drains forever. `maxUnavailable: 1` is redundant. |

### PDB and VPA (s13 callback)

Without a PDB, VPA's updater can evict all Pods at once to apply new resource recommendations. With `maxUnavailable: 1`, VPA evicts one Pod at a time, waits for the replacement to be Ready, then evicts the next.

### PDB and node drains

`kubectl drain` uses the eviction API, which respects PDBs. If draining a node would violate the PDB, the drain blocks (with a timeout). This is the mechanism that makes zero-downtime cluster upgrades possible: drain one node at a time, PDB ensures the service stays up.

## ResourceQuota

A `ResourceQuota` sets hard limits on total resource consumption within a namespace. It prevents a single namespace from monopolizing cluster resources.

### Key fields

| Resource | What it limits |
| --- | --- |
| `requests.cpu` / `requests.memory` | Total CPU/memory requests across all Pods in the namespace |
| `limits.cpu` / `limits.memory` | Total CPU/memory limits |
| `pods` | Maximum number of Pods |
| `services` | Maximum number of Services |
| `persistentvolumeclaims` | Maximum number of PVCs |
| `count/deployments.apps` | Maximum number of Deployments |

When a ResourceQuota exists in a namespace, **every Pod must specify resource requests and limits** for the resources the quota covers. Without them, the Pod is rejected. This is a common surprise: adding a ResourceQuota retroactively breaks Pods that were deployed without `resources`.

### Scoped quotas

`spec.scopes` limits the quota to specific Pod types:

| Scope | What it matches |
| --- | --- |
| `BestEffort` | Pods with no resource requests/limits |
| `NotBestEffort` | Pods with at least one resource request/limit |
| `Terminating` | Pods with `activeDeadlineSeconds` set (Jobs) |
| `NotTerminating` | Long-running Pods (Deployments, StatefulSets) |
| `PriorityClass` | Pods matching a specific PriorityClass name |

## LimitRange

A `LimitRange` sets **per-container** (or per-Pod, per-PVC) defaults and bounds within a namespace. Unlike ResourceQuota (which caps the total), LimitRange caps each individual container.

### Key fields

| Field | What it does |
| --- | --- |
| `default` | Applied to containers that don't specify their own limits. |
| `defaultRequest` | Applied to containers that don't specify their own requests. |
| `min` | Reject containers requesting less than this. |
| `max` | Reject containers requesting more than this. |
| `maxLimitRequestRatio` | Maximum ratio of limit:request. Prevents over-committing (e.g. requesting 100m CPU with a 4 CPU limit). |

LimitRange and ResourceQuota work together: LimitRange ensures every container has reasonable individual requests/limits, and ResourceQuota caps the namespace total.

## PriorityClass

A `PriorityClass` assigns a scheduling priority to Pods. When the cluster is under resource pressure, lower-priority Pods are **preempted** (evicted) to make room for higher-priority Pods.

### How preemption works

1. A high-priority Pod can't be scheduled (no node has enough resources).
2. The scheduler finds a node where evicting lower-priority Pods would free enough resources.
3. Lower-priority Pods are evicted (sent SIGTERM, then SIGKILL after `terminationGracePeriodSeconds`).
4. The high-priority Pod is scheduled on the now-free node.

### Built-in priority classes

| Class | Priority value | Used by |
| --- | --- | --- |
| `system-cluster-critical` | 2000000000 | CoreDNS, kube-proxy, CNI |
| `system-node-critical` | 2000001000 | kubelet static Pods |

User-defined classes should use values well below these (e.g. 1000 for low, 10000 for high).

### `preemptionPolicy`

| Value | Behavior |
| --- | --- |
| `PreemptLowerPriority` (default) | Can evict lower-priority Pods |
| `Never` | High priority for scheduling order, but won't evict others. Use for important-but-not-urgent workloads. |

## Velero (Backup and Restore)

### What Velero does

Velero backs up Kubernetes resources (manifests) and persistent volume data. It can:

- **Back up** all resources in a namespace (or cluster-wide) to object storage.
- **Restore** from a backup: recreate resources in the same or different cluster.
- **Schedule** recurring backups (like a CronJob for cluster state).
- **Migrate** workloads between clusters.

### What it backs up

| Component | How |
| --- | --- |
| Kubernetes resources | API server export (like `kubectl get -o yaml` for everything) |
| PV data | Volume snapshots (CSI) or file-level backup (Restic/Kopia) |

### Velero on kind

On kind there's no cloud snapshot API. Velero uses **Kopia** (file-level backup) to back up PV data to a local MinIO instance (or a PVC). This is for learning the workflow — the actual backup target is unreliable on a kind cluster since everything is on the same disk.

In production (EKS), Velero uses **EBS snapshots** for PVs and **S3** for resource manifests.

```bash
  -f helm/values/velero.values.yaml

# 5. Create a backup
velero backup create full-backup --include-namespaces default

# 6. Check backup status
velero backup describe full-backup
velero backup logs full-backup
```

### Verify PDB

```bash
# Check PDB status
kubectl get pdb users-api-pdb
# NAME             MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS
# users-api-pdb    N/A             1                 1

# Try to drain a node (kind has one worker node)
kubectl drain kind-worker --ignore-daemonsets --delete-emptydir-data
# If both users-api Pods are on this node, drain will block after evicting one
# (PDB allows only 1 unavailable at a time)

# Uncordon to let Pods reschedule
kubectl uncordon kind-worker
```

## Try to break it

### 1. PDB blocks node drain forever

Set `minAvailable: 2` with only 2 replicas. Drain the node that hosts one:

```bash
kubectl drain kind-worker --ignore-daemonsets --timeout=30s
# error: cannot evict pod as it would violate the pod's disruption budget
```

The drain blocks because evicting would leave 1 available (< `minAvailable: 2`). This is a common production issue with tight PDBs during cluster upgrades.

Fix: use `maxUnavailable: 1` instead. Or temporarily relax the PDB during maintenance.

### 2. ResourceQuota silently blocks HPA scaling

HPA tries to add a 4th replica, but the namespace quota only has room for 3 Pods' worth of CPU requests:

```bash
kubectl get hpa users-api
# REPLICAS: 3 (target says 5, but can't scale)

kubectl get events --sort-by='.lastTimestamp' | grep -i quota
# "exceeded quota: requests.cpu"
```

HPA doesn't report quota failures in its status — it just can't scale. Check Events for the real error. Size quotas with HPA `maxReplicas` in mind.

### 3. Velero backup misses CRDs

Velero backs up resources it knows about. If you install a CRD after Velero (e.g. KEDA's ScaledObject) and don't restart Velero's API discovery, those resources may be missing from the backup.

```bash
velero backup describe full-backup --details | grep ScaledObject
# (missing)
```

Fix: `velero backup create` with `--include-cluster-resources=true` and ensure Velero has RBAC to read all resource types.
