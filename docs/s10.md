# s10 - HPA (Pod-level horizontal autoscaling)

> **Tag:** `s10`
> Goal: stop hardcoding `replicas: 2`. HPA scales **out** (more Pods) when load rises, using `metrics.k8s.io` served by metrics-server.

One of two fixed numbers in the Deployment YAML gets replaced this stage: the replica count. s10 introduces HPA and walks through the conceptual contrast with its vertical sibling, **VPA** (which adjusts `resources.requests` instead of replica count). VPA's install needs three extra controllers and is cleaner to do via Helm — so we cover its concepts here, then actually deploy it in [s12](./s12.md), after [s11](./s11.md) introduces Helm.

The bigger siblings (KEDA for queue/cron/Prometheus signals in s15, Karpenter for node-level scaling in s20) come later.

---

## HPA - HorizontalPodAutoscaler

A `HorizontalPodAutoscaler` watches one or more metrics and scales a Deployment / StatefulSet / ReplicaSet between `minReplicas` and `maxReplicas`. The classic metric is "CPU averaged across all Pods, as a percent of each Pod's request."

```text
                    metrics-server
                          │
                          ▼  (reads cAdvisor on each kubelet, every 15s)
                  metrics.k8s.io API
                          │
                          ▼  (HPA polls every 15s by default)
                    HPA controller
                          │
                          ▼  (reconciles desired replicas)
              Deployment/users-api  -->  spec.replicas
```

The HPA controller lives in `kube-controller-manager`. It writes to the Deployment's `spec.replicas`, and the Deployment controller does the actual scale.

### `k8s/users-api/hpa.yaml`

**`scaleTargetRef`** points to the workload the HPA controls - a Deployment, StatefulSet, or ReplicaSet identified by `kind`, `apiVersion`, and `name`. Only one HPA should target a given workload at a time.

**`minReplicas` / `maxReplicas`** are the hard floor and ceiling. HPA never goes below `minReplicas` even at zero load, and never exceeds `maxReplicas` even if every metric says it should. `minReplicas` defaults to 1 if omitted; `maxReplicas` is required.

**`metrics[]`** is what to scale on. Each entry has a `type`:

| Type | What it measures | Requires |
| --- | --- | --- |
| `Resource` | CPU or memory on a container, as `Utilization` (% of `requests`) or `AverageValue` (absolute) | in-built |
| `ContainerResource` | Like `Resource` but targets one named container in a multi-container Pod | Nothing extra |
| `Pods` | A custom metric aggregated per Pod (e.g., requests/sec) | Custom metrics adapter |
| `Object` | A single metric from one named object (e.g., Ingress RPS) | Custom metrics adapter |
| `External` | A metric from outside the cluster (e.g., SQS queue depth) | External metrics adapter — the foundation KEDA builds on in s15 |

For `Resource` / `cpu` / `Utilization`: the target is `averageUtilization`, a percent. HPA aims to keep the average CPU across all running Pods at that percentage of each Pod's `resources.requests.cpu`. Above target → add replicas. Below target (sustained) → remove replicas.

**`behavior`** (not used here): `spec.behavior.scaleUp` and `spec.behavior.scaleDown` let you tune how fast and how far HPA moves in each direction — number of replicas per step, cool-down windows. Scale-up is fast, scale-down is slow by default (5-minute `behavior.scaleDown.stabilizationWindowSeconds`): traffic spikes shouldn't pile in a queue waiting for capacity, but brief lulls shouldn't kill capacity you'll need again 30 seconds later.

**The Deployment's container must have a `resources.requests` entry for every resource the HPA scales on.** HPA computes "50% of request", so without a request there's nothing to take 50% of - it silently reports `<unknown>` for that metric and never scales. Scaling on CPU requires `requests.cpu`; scaling on memory requires `requests.memory`; scaling on both requires both.

### Why not `apiVersion: autoscaling/v1`?

`autoscaling/v1` only supports CPU utilization. `autoscaling/v2` adds:

- Memory targets (`name: memory`).
- Multi-metric (the HPA scales to whichever metric needs the most replicas).
- Custom and external metrics (the foundation KEDA builds on in s15).
- `behavior` block to tune scale-up / scale-down rates.

### Coexisting with manual replicas

`spec.replicas` on the Deployment and HPA both want to set the replica count. But once an HPA exists, the HPA wins. `kubectl scale deployment users-api --replicas=5` works for a few seconds, then HPA reconciles back to whatever its metric says.

If you keep `spec.replicas: 2` in the Deployment YAML and reapply it, HPA will undo the change. To avoid the churn, either:

- Remove `spec.replicas` from the YAML once HPA owns it.
- Or set `spec.replicas` to `null`, which has the same effect.

GitOps tools like ArgoCD (s16) handle this drift.

## VPA - VerticalPodAutoscaler

HPA scales **horizontally** (more Pods, same per-Pod size). VPA scales **vertically** (same Pod count, bigger or smaller `resources.requests`/`limits` per Pod).

VPA is not built into Kubernetes. It ships as a separate project (`autoscaling.k8s.io/v1` CRD plus three controllers):

- **recommender** reads usage from metrics-server, writes recommendations to the VPA object.
- **updater** acts on Pods whose current requests are too far off (only in `Recreate` or `InPlaceOrRecreate` mode). It evicts them, or in case of `InPlaceOrRecreate`, asks the kubelet to resize the container in place when it can.
- **admission-controller** is a mutating webhook that rewrites the Pod spec on creation to inject the recommended requests.

### Why you'd want it

You wrote `resources.requests.cpu: 100m, memory: 128Mi` on day one. After a month of real traffic, the Pod actually uses 350m and 400Mi at p95. Two problems:

- **Throttling and OOMKills.** Containers are throttled when they exceed the CPU limit and killed when they exceed the memory limit. Under-requesting causes pain.
- **Scheduling lies.** The scheduler reserves the *request*, not the *actual usage*. Under-requesting means the scheduler over-packs nodes and the kubelet later evicts under memory pressure.

VPA's recommender watches actual usage (default 8-day history window) and emits a target. You either apply it manually or let VPA do it.

### Update modes

`spec.updatePolicy.updateMode` controls what VPA does with its recommendation:

| Mode | Behavior |
| --- | --- |
| `Off` | Recommend only. Read recommendations via `kubectl describe vpa`. Apply manually. |
| `Initial` | Set requests at Pod creation, never change a running Pod. |
| `Recreate` | Evict the Pod, recreate it with the new requests. Disruptive - relies on the Deployment / ReplicaSet to roll a replacement. |
| `InPlaceOrRecreate` | Ask the kubelet to resize the container in place; fall back to evict-and-recreate when it can't (QoS class change, memory shrink with no `RestartContainer` policy, Windows Pods, static CPU/memory manager, etc.). |
| `Auto` | Deprecated since VPA v1.4.0. Currently an alias for `Recreate`; don't use in new manifests. |

`Off` is the right starting mode. `Recreate` causes Pod churn, which is fine for stateless workloads behind a Service but a problem for StatefulSets like Postgres (s5).

`InPlaceOrRecreate` leans on the **in-place Pod resize** feature. When the kubelet accepts the resize, the container keeps running with new CPU/memory limits and no restart. It still falls back to eviction in the cases the kubelet can't handle in place, so PDB (s18) still matters.

### Shape of a VPA object

A VPA points at a workload via `targetRef` (same Deployment the HPA targets), sets `updatePolicy.updateMode`, and constrains the recommendation with `resourcePolicy.containerPolicies[].minAllowed` / `maxAllowed`. Once applied, the recommender starts building a usage window and exposes its output under `status.recommendation`:

```text
Container Recommendations:
  Container Name:  users-api
  Lower Bound:   cpu: 35m    memory: 78Mi
  Target:        cpu: 47m    memory: 104Mi
  Uncapped Target: cpu: 47m  memory: 104Mi
  Upper Bound:   cpu: 200m   memory: 250Mi
```

`Target` is what VPA would apply under `Recreate` or `InPlaceOrRecreate`. VPA only acts when current requests fall outside `Lower`/`Upper Bound`.

We'll author and apply this manifest once VPA is installed via Helm.

## HPA vs VPA

They answer different questions:

| Question | Answered by |
| --- | --- |
| "Is this Pod doing too much work?" | HPA - spawn more Pods |
| "Did I guess this Pod's CPU/memory request wrong?" | VPA - resize requests |

**Do not point both an HPA and a VPA at the same Deployment with overlapping resources.** They fight: HPA reads CPU utilization and adds Pods to bring it down; VPA reads CPU utilization and *raises the request*, which lowers utilization %, which makes HPA scale down, which... etc.

Safe combinations:

| HPA scales on | VPA controls | Safe? |
| --- | --- | --- |
| CPU | memory only | yes - different signals |
| CPU | cpu + memory | **no** - feedback loop |
| Custom metric (RPS, queue depth) | cpu + memory | yes - HPA isn't reading CPU |
| anything | nothing (`updateMode: Off`) | yes - VPA is read-only |

The pattern we'll land on once VPA is installed: HPA on CPU, VPA in `Off` mode covering memory. You get HPA's reactive scale-out plus VPA's offline right-sizing recommendation, with no feedback loop.

KEDA (s15) is often paired with VPA for the same reason - KEDA scales horizontally on queue depth, VPA right-sizes the Pod that drains it. Neither controller looks at the same signal.

## Commands

### Install metrics-server (HPA needs it; VPA will too)

HPA has no metrics of its own. It reads from the metrics API, which is served by `metrics-server`. kind doesn't ship it. (Same install will serve VPA when we add it.)

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# kind kubelets serve self-signed certs that metrics-server doesn't trust
kubectl patch deployment metrics-server -n kube-system --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

kubectl -n kube-system rollout status deploy/metrics-server --timeout=120s
kubectl top nodes # may take some time
# NAME                 CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
# demo-control-plane   ...
```

`--kubelet-insecure-tls` is a kind quirk. EKS clusters don't need it.

### Apply HPA and verify

```bash
# Make sure metrics-server is reporting
kubectl top pod -l app=users-api
# NAME                         CPU(cores)   MEMORY(bytes)
# users-api-xxxx               2m           45Mi

kubectl apply -f k8s/users-api/hpa.yaml

kubectl get hpa users-api # wait ~30s for metrics-server to scrape some data 
# NAME        REFERENCE              TARGETS         MINPODS   MAXPODS   REPLICAS
# users-api   Deployment/users-api   cpu: 1%/50%     2         6         2
```

If `TARGETS` shows `<unknown>/50%` for more than a minute or two:

```bash
kubectl describe hpa users-api
# Check the "Events" and "Conditions" section.
# "the HPA was unable to compute the replica count" => metrics-server isn't reporting yet,
# or the Deployment has no resources.requests.cpu.
```

### Load test

Install `hey` once: `go install github.com/rakyll/hey@latest`.

```bash
# In two terminals, watch
kubectl get hpa users-api -w
kubectl get pod -l app=users-api -w

# In another, generate load
hey -z 2m -c 50 https://demo.local/api/users
```

Expected timeline:

1. CPU climbs above 50%.
2. HPA's `TARGETS` column moves above 50%.
3. Within ~15 seconds, replicas tick up (2 -> 3 -> 4 -> ...).
4. CPU drops back toward 50% as load spreads across new Pods.
5. After `hey` stops, ~5 minutes later replicas tick back down to 2.

The asymmetric scale timing is intentional. Fast up: traffic spikes shouldn't pile in a queue waiting for capacity. Slow down: brief lulls shouldn't kill capacity you'll need again 30 seconds later.

## What this looks like on AWS

| s10 (local) | EKS / AWS |
| --- | --- |
| metrics-server on kind | metrics-server add-on on EKS. Or use **prometheus-adapter** if you want HPA on custom metrics (queue depth, RPS, etc). |
| HPA on CPU | Same. Pair with **Cluster Autoscaler** or **Karpenter** so the cluster also adds nodes when Pods stay Pending. |
| Pods scale up; nodes are fixed (kind cluster is static) | HPA scales Pods; Karpenter watches Pending Pods and adds the cheapest node type that fits. The HPA / Karpenter pair is the standard "react to load" duo on EKS. |
| `--kubelet-insecure-tls` flag on metrics-server | Not needed - EKS kubelets serve certs signed by a CA metrics-server already trusts. |

The HPA YAML is the same on kind and EKS. The difference is node scaling: on kind, a Pending Pod stays Pending; on EKS, Karpenter adds a new node in ~30 seconds. Karpenter handles node-side scaling; VPA handles Pod-side sizing.

## Try to break it

### 1. Forget the CPU request, watch HPA give up

```bash
kubectl patch deployment users-api --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/resources/requests/cpu"}]'

# wait ~30s
kubectl get hpa users-api
# users-api   ...   cpu: <unknown>/50%   2   6   2
```

HPA can't compute "% of request" without a request. Add it back:

```bash
kubectl apply -f k8s/users-api/deployment.yaml
```

### 2. Hit `maxReplicas` and watch HPA stop adding Pods

```bash
hey -z 5m -c 200 https://demo.local/api/users >/dev/null &
kubectl get hpa users-api -w
# users-api   ...   cpu: 230%/50%   2  6  6
```

Replicas top out at 6 even though CPU is 4x the target. `maxReplicas` is the hard ceiling. The HPA never crosses it. This is where node-level autoscaling would normally pick up the slack (Karpenter / Cluster Autoscaler on EKS). On kind, you'd just bump `maxReplicas` or accept the saturated baseline.

### 3. Scale manually, watch HPA undo it

```bash
kubectl scale deployment users-api --replicas=5
kubectl get deploy users-api -w
# ...
# users-api   5/5   ...
# wait ~5m / scale-down stabilization window
# users-api   2/2   ...   (HPA reconciled back to its metric-driven value)
```

Once an HPA owns the scale, manual `kubectl scale` is a temporary edit. This is the right behavior - it would be surprising if someone could disable autoscaling by accident.

kubectl delete -f k8s/users-api/hpa.yaml
