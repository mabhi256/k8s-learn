# s21 - Advanced Scheduling

> **Tag:** `s21`
> Goal: control where Pods land. Node affinity pins workloads to specific node types. Pod anti-affinity spreads replicas across failure domains. Taints and tolerations reserve nodes for specific workloads. Topology spread constraints distribute Pods evenly.

So far the scheduler has placed Pods wherever they fit. That's fine on a single-node kind cluster, but in production with heterogeneous nodes (different instance types, AZs, GPU vs CPU), you need to control placement. This stage covers the four mechanisms the scheduler uses.

---

## How the scheduler decides

The scheduler runs two phases for each pending Pod:

1. **Filtering (predicates)**: eliminate nodes that can't run the Pod. Reasons: insufficient resources, taints the Pod doesn't tolerate, node selectors that don't match, affinity rules that exclude the node.
2. **Scoring (priorities)**: rank remaining nodes. Factors: spreading Pods across zones, preferring nodes with images already cached, respecting soft affinity preferences.

The highest-scored node wins. If no node passes filtering, the Pod stays `Pending`.

---

## Node affinity

Node affinity constrains which nodes a Pod can be scheduled on, based on **node labels**.

### `nodeSelector` (simple)

The original, simplest mechanism. A map of label key-value pairs. The Pod is only scheduled on nodes that have **all** the listed labels.

```yaml
spec:
  nodeSelector:
    kubernetes.io/os: linux
    node.kubernetes.io/instance-type: m5.xlarge
```

### `nodeAffinity` (expressive)

More powerful: supports `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt` operators, and soft preferences.

| Rule type | Field | Behavior |
| --- | --- | --- |
| **Required** | `requiredDuringSchedulingIgnoredDuringExecution` | Pod won't schedule if no node matches. Hard constraint. |
| **Preferred** | `preferredDuringSchedulingIgnoredDuringExecution` | Scheduler tries to match but falls back if no node qualifies. Soft constraint. |

`IgnoredDuringExecution` means: if a node's labels change after scheduling, the Pod is **not** evicted. It stays where it is. (A `RequiredDuringExecution` variant was proposed but never implemented.)

### Common node labels

| Label | Set by | Example values |
| --- | --- | --- |
| `kubernetes.io/os` | kubelet | `linux`, `windows` |
| `kubernetes.io/arch` | kubelet | `amd64`, `arm64` |
| `topology.kubernetes.io/zone` | cloud provider (or manually) | `us-east-1a`, `eu-west-1b` |
| `node.kubernetes.io/instance-type` | cloud provider | `m5.xlarge`, `r6g.large` |
| Custom labels | you (`kubectl label node`) | `workload=gpu`, `team=data` |

On kind, nodes don't have cloud labels. You can add them manually for testing:

```bash
kubectl label node kind-worker topology.kubernetes.io/zone=zone-a
kubectl label node kind-worker2 topology.kubernetes.io/zone=zone-b
```

## Pod affinity and anti-affinity

Pod affinity/anti-affinity constrains where a Pod schedules **relative to other Pods**, not nodes.

### Anti-affinity (spread replicas)

"Don't schedule two users-api Pods on the same node" (or same zone):

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: users-api
        topologyKey: kubernetes.io/hostname
```

`topologyKey` defines the failure domain:
- `kubernetes.io/hostname`: spread across nodes.
- `topology.kubernetes.io/zone`: spread across AZs.

**Required** anti-affinity on `hostname` with 3 replicas means you need at least 3 nodes. If you only have 2, the third Pod stays `Pending`. Use **preferred** anti-affinity when you want best-effort spreading without blocking scheduling.

### Affinity (co-locate)

"Schedule users-api on the same node as its Postgres" (for low-latency access):

```yaml
affinity:
  podAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: postgres
          topologyKey: kubernetes.io/hostname
```

Co-location is almost always `preferred`, not `required`. You don't want the app Pod to be unschedulable if Postgres moves to a different node.

## Taints and tolerations

Taints are the inverse of affinity: instead of attracting Pods, taints **repel** them. A taint on a node says "no Pod may schedule here unless it explicitly tolerates this taint."

### Taint effects

| Effect | What happens to Pods that don't tolerate the taint |
| --- | --- |
| `NoSchedule` | Not scheduled on the node. Already-running Pods are unaffected. |
| `PreferNoSchedule` | Scheduler avoids the node but uses it if nothing else fits. Soft version. |
| `NoExecute` | Not scheduled, **and** already-running Pods are evicted (unless they tolerate within `tolerationSeconds`). |

### Common use cases

| Taint | Purpose |
| --- | --- |
| `node-role.kubernetes.io/control-plane:NoSchedule` | Keep workloads off the control plane (set by kubeadm, kind). |
| `workload=gpu:NoSchedule` | Reserve GPU nodes for GPU workloads only. |
| `dedicated=team-data:NoSchedule` | Isolate nodes for a specific team. |
| `node.kubernetes.io/unreachable:NoExecute` | Set automatically by the node controller when a node goes down. |

### Tolerations in the Pod spec

```yaml
tolerations:
  - key: workload
    operator: Equal
    value: gpu
    effect: NoSchedule
```

A toleration with `operator: Exists` matches any value for that key. An empty key with `operator: Exists` matches all taints (the "tolerate everything" escape hatch — use only for DaemonSets that must run everywhere).

## Topology spread constraints

Topology spread constraints are the modern replacement for pod anti-affinity when the goal is **even distribution** rather than strict avoidance.

### The problem with anti-affinity

Anti-affinity is binary: either a Pod can co-exist on a domain (node/zone) or it can't. It doesn't help with "I want 6 replicas spread evenly across 3 zones (2 per zone)" — anti-affinity can only say "don't put two on the same zone" (which limits you to 3 replicas across 3 zones).

### How topology spread works

```yaml
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: users-api
```

| Field | What it means |
| --- | --- |
| `maxSkew` | Maximum difference in Pod count between the most-loaded and least-loaded domain. `1` means "at most 1 Pod difference between any two zones." |
| `topologyKey` | The failure domain (zone, node, region). |
| `whenUnsatisfiable` | `DoNotSchedule` (hard) or `ScheduleAnyway` (soft, but adds a scoring penalty). |
| `labelSelector` | Which Pods to count (must match the Pods being spread). |

With 6 replicas across 3 zones and `maxSkew: 1`: the scheduler ensures 2-2-2 distribution. If one zone has 3 and another has 1, the skew (3-1=2) exceeds `maxSkew: 1`, so the next Pod must go to the zone with 1.

### Topology spread vs anti-affinity

| | Pod anti-affinity | Topology spread |
| --- | --- | --- |
| Goal | "Never co-locate" | "Distribute evenly" |
| Scales with replicas | No — required anti-affinity caps replicas at domain count | Yes — works with any replica count |
| Granularity | Binary (same domain = forbidden) | Numeric (max N difference between domains) |
| Use case | Singleton-per-node (DaemonSet without a DaemonSet) | Multi-replica services across zones |

## Commands

```bash
# 1. Label kind nodes with fake zones (kind has no cloud labels)
kubectl label node kind-worker topology.kubernetes.io/zone=zone-a
kubectl label node kind-worker2 topology.kubernetes.io/zone=zone-b

# 2. Apply the updated deployment with scheduling constraints
kubectl apply -f k8s/users-api/deployment.yaml
kubectl rollout status deploy/users-api

# 3. Verify Pod placement
kubectl get pods -l app=users-api -o wide
# Check NODE column — Pods should be on different nodes

# 4. Add a taint and test
kubectl taint nodes kind-worker workload=special:NoSchedule

# Try to schedule a Pod without the toleration
kubectl run test --image=nginx
kubectl get pod test -o wide
# Should land on kind-worker2 (not the tainted node)
kubectl delete pod test

# 5. Remove the taint
kubectl taint nodes kind-worker workload=special:NoSchedule-
```

### Verify topology spread

```bash
# Scale up and check distribution
kubectl scale deploy/users-api --replicas=4
kubectl get pods -l app=users-api -o wide
# With maxSkew: 1 across 2 zones: expect 2 Pods per zone
```

## What this looks like on AWS

| s21 (kind) | EKS / AWS |
| --- | --- |
| Manual node labels for zones | **Automatic**: EKS sets `topology.kubernetes.io/zone` from the AZ the node runs in |
| Topology spread across fake zones | Topology spread across **real AZs**. Critical for HA. |
| Taints set manually | **Karpenter** (s24) creates tainted node pools automatically (GPU nodes, spot instances) |
| Anti-affinity on `hostname` | Same, but with **dozens of nodes**, anti-affinity actually distributes across hardware |
| No real multi-zone benefit | Cross-AZ traffic costs money ($0.01/GB). Co-locate chattier services in the same zone. |

## Try to break it

### 1. Required anti-affinity makes Pods unschedulable

Set required (`requiredDuringScheduling`) pod anti-affinity on `hostname` with 3 replicas on a 2-node kind cluster:

```bash
kubectl get pods -l app=users-api
# 2 Running, 1 Pending

kubectl describe pod <pending-pod>
# Events: 0/2 nodes are available: 2 nodes didn't match pod anti-affinity rules
```

The third Pod has nowhere to go. Fix: use `preferredDuringScheduling` or add a third node.

### 2. Taint without toleration blocks everything

```bash
kubectl taint nodes kind-worker dedicated=platform:NoSchedule
kubectl taint nodes kind-worker2 dedicated=platform:NoSchedule
# Both nodes tainted. No Pod can schedule unless it tolerates.

kubectl run test --image=nginx
kubectl get pod test
# STATUS: Pending (forever)

# Fix: remove taints
kubectl taint nodes kind-worker dedicated=platform:NoSchedule-
kubectl taint nodes kind-worker2 dedicated=platform:NoSchedule-
```

### 3. Topology spread with `maxSkew: 1` blocks scaling

With 2 zones and `maxSkew: 1`, if one zone's node is full (resource-wise), the scheduler can't place a Pod in the other zone because it would create a skew > 1.

```bash
kubectl scale deploy/users-api --replicas=6
kubectl get pods -l app=users-api
# Some Pending if one zone's node is at capacity
```

Fix: use `whenUnsatisfiable: ScheduleAnyway` to allow uneven distribution as a fallback.
