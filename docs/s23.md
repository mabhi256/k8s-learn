# s23 - Progressive Delivery (Argo Rollouts)

> **Tag:** `s23`
> Goal: automate what s22 showed manually. Instead of editing `HTTPRoute` weights by hand and watching dashboards, Argo Rollouts drives the canary step-by-step and queries Mimir (s12) to gate promotion. A failed SLO triggers an automatic rollback before users notice.

s22 put traffic routing on the Gateway API and did a canary by hand: you edited `HTTPRoute` `backendRefs` weights, watched error rates in Grafana, and promoted or rolled back manually. That works for demos but fails in production — it's manual, error-prone, and doesn't scale. Progressive delivery automates the same loop: shift traffic incrementally, measure the metric, promote or abort automatically.

We build on s22's sidecar-free stack deliberately. The mesh is the future-facing one — ambient ztunnel for mTLS, an optional waypoint for L7 — and routing is the Gateway API, not Istio's frozen `VirtualService`. So Argo Rollouts drives an `HTTPRoute` here via its Gateway API traffic-router plugin, which is the model that carries forward to any Gateway API implementation (Istio, Envoy Gateway, Contour), not just Istio.

---

## What progressive delivery adds

| Capability | Plain `Deployment` rolling update | Argo Rollouts |
| --- | --- | --- |
| Traffic splitting | No — all traffic goes to new pods as they start | Yes — canary gets a configurable percentage via the Gateway API `HTTPRoute` |
| Metric-gated promotion | No | Yes — `AnalysisTemplate` queries Mimir; abort on breach |
| Automated rollback | No — you run `kubectl rollout undo` | Yes — failed `AnalysisRun` triggers automatic abort |
| Blue/green preview | No | Yes — preview Service gets new version before go-live |
| Pause-and-resume | No | Yes — canary pauses at each step until promoted or timed out |

## The `Rollout` CRD

A `Rollout` is a drop-in replacement for a `Deployment`. The pod template (`spec.template`) is identical. Only `spec.strategy` changes.

### Key fields

**`spec.strategy.canary`**: enables canary delivery.

| Field | What it does |
| --- | --- |
| `steps` | Ordered list of canary steps: `setWeight`, `pause`, `analysis` |
| `canaryService` | Service that points exclusively at canary pods |
| `stableService` | Service that points exclusively at stable pods |
| `trafficRouting.plugins` | The Gateway API plugin; names the `HTTPRoute` Argo Rollouts manages (from s22) |

**`spec.strategy.blueGreen`**: enables blue/green delivery.

| Field | What it does |
| --- | --- |
| `activeService` | Service routing live traffic |
| `previewService` | Service routing preview traffic (new version only) |
| `autoPromotionEnabled` | If `false`, promotion requires a manual `kubectl argo rollouts promote` |
| `scaleDownDelaySeconds` | How long to keep the old ReplicaSet after promotion |

## Canary strategy in detail

### Steps

A canary rollout proceeds through a list of steps in order:

```yaml
steps:
  - setWeight: 10          # shift 10% to canary
  - pause: {duration: 2m}  # wait 2 minutes
  - analysis:              # run AnalysisTemplate
      templates:
        - templateName: error-rate
  - setWeight: 50          # shift 50% to canary
  - pause: {duration: 5m}
  - setWeight: 100         # full promotion
```

If the `AnalysisRun` fails, the controller aborts: sets the canary weight back to 0, scales down the canary ReplicaSet, and marks the Rollout as `Degraded`. No manual intervention needed.

### How traffic splitting works with the Gateway API

The Argo Rollouts Gateway API plugin mutates the `HTTPRoute` at each `setWeight` step. It rewrites the `backendRefs` weights (stable vs canary Service) automatically — you never edit the `HTTPRoute` directly when a Rollout is managing it. The s22 waypoint (or edge `Gateway`) enforces the new weights immediately, the same way it did when you edited them by hand.

The plugin is not built into the controller — install it via the `argo-rollouts-config` ConfigMap (see Commands). This indirection is why the field is `trafficRouting.plugins` rather than a first-class `trafficRouting.gatewayAPI`.

```text
Before rollout:   stable=100%, canary=0%
After setWeight:10  stable=90%, canary=10%
After analysis pass + setWeight:50  stable=50%, canary=50%
After full promotion:  stable=0% (old), canary=100% (new, now stable)
```

## `AnalysisTemplate` and `AnalysisRun`

An `AnalysisTemplate` defines a metric query. When a step references it, the controller creates an `AnalysisRun` that periodically evaluates the query.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: error-rate
  namespace: default
spec:
  metrics:
    - name: error-rate
      interval: 1m
      successCondition: result[0] < 0.01   # < 1% error rate
      failureLimit: 3                       # fail after 3 consecutive bad measurements
      provider:
        prometheus:
          address: http://prom-kube-prometheus-stack-prometheus.lgtm.svc:9090
          query: |
            sum(rate(http_requests_total{namespace="default",service="users-api",status=~"5.."}[2m]))
            /
            sum(rate(http_requests_total{namespace="default",service="users-api"}[2m]))
```

`successCondition` is a CEL expression. `result[0]` is the scalar from the PromQL query. With `failureLimit: 3`, three consecutive bad measurements abort the rollout. A single bad measurement followed by a good one resets the failure count.

### Analysis phases

| Phase | Meaning |
| --- | --- |
| `Running` | AnalysisRun is actively collecting measurements |
| `Successful` | All metric conditions passed; rollout may proceed |
| `Failed` | `failureLimit` exceeded; rollout aborts |
| `Inconclusive` | Result was ambiguous (e.g. Prometheus returned no data) |
| `Error` | Could not query the metric source |

`Inconclusive` and `Error` can be configured to fail or pass. Default is fail-safe: treat them as failure.

## Blue/green strategy

Blue/green is simpler than canary: the new version runs alongside the old one and gets 100% of traffic on promotion. There's no gradual shift.

```text
Before promotion:
  activeService  ──▶  blue pods  (old version, live traffic)
  previewService ──▶  green pods (new version, no live traffic)

After promotion:
  activeService  ──▶  green pods (new version, now live)
  previewService ──▶  blue pods  (old version, scaled down after delay)
```

Use cases:

- **Instant cutover**: when gradual traffic shift isn't needed (batch APIs, internal tools).
- **Smoke test before go-live**: route QA traffic to `previewService` while production still uses the old version.
- **Zero-downtime**: new pods are ready before any traffic switches.

## Commands

```bash
# 1. Install Argo Rollouts controller (values enable the Gateway API plugin)
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update
helm install argo-rollouts argo/argo-rollouts \
  -n argo-rollouts --create-namespace \
  -f helm/values/argo-rollouts.values.yaml

# 2. Install the kubectl plugin (WSL/Linux)
curl -LO https://github.com/argoproj/argo-rollouts/releases/latest/download/kubectl-argo-rollouts-linux-amd64
chmod +x kubectl-argo-rollouts-linux-amd64
sudo mv kubectl-argo-rollouts-linux-amd64 /usr/local/bin/kubectl-argo-rollouts

# 3. The Gateway API plugin needs RBAC to edit HTTPRoutes
kubectl apply -f k8s/users-api/gatewayapi-plugin-rbac.yaml

# 4. Apply the AnalysisTemplate and the s22 HTTPRoute (now pointing at stable+canary)
kubectl apply -f k8s/users-api/analysis-template.yaml
kubectl apply -f k8s/gateway/httproute-canary.yaml

# 5. Apply the Rollout (replaces the Deployment)
kubectl apply -f k8s/users-api/rollout.yaml

# 6. Watch the rollout status
kubectl argo rollouts get rollout users-api --watch
```

### Trigger a canary

```bash
# Update the image tag in the Rollout (equivalent to kubectl set image for a Deployment)
kubectl argo rollouts set image users-api users-api=users-api:local-v4

# Watch it step through the canary
kubectl argo rollouts get rollout users-api --watch
# STATUS: Paused (waiting at the pause step)

# Manually promote past a pause step (if you don't want to wait)
kubectl argo rollouts promote users-api

# Abort the rollout manually
kubectl argo rollouts abort users-api
```

### Verify the AnalysisRun

```bash
# List AnalysisRuns
kubectl get analysisrun

# See the measurements
kubectl describe analysisrun <name>
# Metrics:
#   Name: error-rate
#   Phase: Running
#   Measurements:
#     Phase: Successful  Value: 0.002
#     Phase: Successful  Value: 0.000

# Check what weight the HTTPRoute is at
kubectl get httproute users-api -o jsonpath='{.spec.rules[0].backendRefs}'
```

| --- | --- |

## Try to break it

### 1. AnalysisTemplate points at the wrong Prometheus URL

```yaml
provider:
  prometheus:
    address: http://wrong-prometheus:9090
```

The AnalysisRun enters `Error` phase immediately. By default, `Error` counts as failure. After `failureLimit` errors, the rollout aborts.

```bash
kubectl describe analysisrun <name>
# Phase: Error
# Message: error querying prometheus: ...
```

### 2. Failure threshold too tight

Set `successCondition: result[0] < 0.001` (0.1% error rate) on a service with occasional 500s from normal traffic. Every canary aborts immediately. The stable version never changes.

Lesson: base your failure threshold on your actual p99 error rate in steady state. Check Mimir/Grafana before writing the condition.

### 3. Edit the HTTPRoute directly while a Rollout manages it

```bash
kubectl edit httproute users-api
# manually set the canary backendRef weight to 0
```

Argo Rollouts will overwrite your change on the next reconcile (within seconds). The plugin owns the `HTTPRoute` `backendRefs` weights once a `Rollout` references it. Treat them as read-only.

### 4. Delete the canary Service while a canary is in flight

```bash
kubectl delete svc users-api-canary
```

The controller recreates it immediately. But for the brief window, the `HTTPRoute` `backendRef` resolves to nothing (`ResolvedRefs: False`) — traffic to the canary weight returns errors until the Service is back.

## Diff

### New: `k8s/users-api/rollout.yaml`

Replaces `k8s/users-api/deployment.yaml`. The pod template is identical; only `kind` and `spec.strategy` change.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: users-api
  namespace: default
spec:
  replicas: 3
  selector:
    matchLabels:
      app: users-api
  template:
    metadata:
      labels:
        app: users-api
    spec:
      serviceAccountName: users-api
      containers:
        - name: users-api
          image: users-api:local-v3
          ports:
            - containerPort: 3000
          envFrom:
            - secretRef:
                name: users-api
  strategy:
    canary:
      canaryService: users-api-canary
      stableService: users-api-stable
      trafficRouting:
        plugins:
          argoproj-labs/gatewayAPI:
            httpRoute: users-api      # the s22 HTTPRoute
            namespace: default
      steps:
        - setWeight: 10
        - pause: {duration: 2m}
        - analysis:
            templates:
              - templateName: error-rate
        - setWeight: 50
        - pause: {duration: 5m}
        - setWeight: 100
```

### New: `k8s/users-api/services-canary-stable.yaml`

Two additional Services that Argo Rollouts uses to split traffic:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: users-api-stable
  namespace: default
spec:
  selector:
    app: users-api
  ports:
    - port: 3000
      targetPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: users-api-canary
  namespace: default
spec:
  selector:
    app: users-api
  ports:
    - port: 3000
      targetPort: 3000
```

Argo Rollouts manages the pod selectors on these Services automatically. You define them; the controller owns their `spec.selector` during a rollout.

### New: `helm/values/argo-rollouts.values.yaml`

The `controller.trafficRouterPlugins` block registers the Gateway API plugin — without it, `trafficRouting.plugins.argoproj-labs/gatewayAPI` is unknown and the Rollout errors:

```yaml
controller:
  replicas: 1
  resources:
    requests:
      cpu: 50m
      memory: 128Mi
    limits:
      memory: 256Mi
  trafficRouterPlugins:
    trafficRouterPlugins: |-
      - name: argoproj-labs/gatewayAPI
        location: https://github.com/argoproj-labs/rollouts-plugin-trafficrouter-gatewayapi/releases/download/v0.4.0/gatewayapi-plugin-linux-amd64

dashboard:
  enabled: true
  service:
    type: ClusterIP
```

### New: `k8s/users-api/gatewayapi-plugin-rbac.yaml`

The plugin runs inside the controller, which needs permission to read and patch `HTTPRoute`s (not granted by the default chart):

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: argo-rollouts-gatewayapi
rules:
  - apiGroups: ["gateway.networking.k8s.io"]
    resources: ["httproutes"]
    verbs: ["get", "list", "watch", "update", "patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: argo-rollouts-gatewayapi
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: argo-rollouts-gatewayapi
subjects:
  - kind: ServiceAccount
    name: argo-rollouts
    namespace: argo-rollouts
```

### Changed: `k8s/gateway/httproute-canary.yaml` (the s22 HTTPRoute)

Point the route's `backendRefs` at the stable and canary Services so Argo Rollouts has two weights to drive. The plugin rewrites these weights at each `setWeight` step:

```diff
  spec:
    parentRefs:
      - group: ""
        kind: Service
        name: users-api
    rules:
      - backendRefs:
-         - name: users-api-v1
+         - name: users-api-stable
            port: 3000
-           weight: 90
+           weight: 100
-         - name: users-api-v2
+         - name: users-api-canary
            port: 3000
-           weight: 10
+           weight: 0
```

In s22 you set the weights by hand (90/10). Here they start at 100/0 and Argo Rollouts owns them for the duration of every rollout.
