# s4 - TLS at the Ingress

> **Tag:** `s4`
> Goal: terminate HTTPS at the Ingress using cert-manager. Keep every routing rule from s3 unchanged; only the protocol flips from HTTP to HTTPS, and HTTP gets redirected to it.

s3 published the app at `http://demo.local:880`, but the website is still insecure and every byte on the wire is plaintext. s4 puts a TLS leaf certificate in front of the ingress controller. The cert is issued in-cluster by cert-manager, chained off a self-signed Root CA that we also create in-cluster. Trust the root once and the leaf is valid in your browser and `curl` without `-k`.

The routing logic from s3 (host + path rules, `/api` rewrite, default backend) does not change. Only:

- The Ingress gains a `tls:` block and a `cert-manager.io/cluster-issuer` annotation.
- nginx-ingress now listens on 443 in addition to 80, and redirects 80 to 443.
- The kind cluster gains a third `extraPortMapping` so the host can reach 443.

---

## What TLS at the ingress means

TLS termination at the ingress is the default model in Kubernetes: the LB (or in our case, the nginx-ingress controller acting as one) decrypts inbound HTTPS, then forwards plaintext HTTP to the backend Service. Pod-to-pod traffic inside the cluster stays unencrypted unless something else (a service mesh) wraps it.

```text
Client  --HTTPS-->  ingress-nginx  --HTTP-->  Service  -->  Pod
        (TLS terminates here ^)
```

Why not encrypt all the way to the Pod? Two reasons:

- The cluster network is the trust boundary in most setups. Anything that can talk to a Pod has already been admitted by NetworkPolicy / RBAC / kube-proxy rules. End-to-end TLS adds cert plumbing in every workload for marginal benefit.
- Re-encrypting at every hop forces every app container to ship a cert. cert-manager + ingress is one place to manage certs; mTLS at every hop is N places.

When you do want pod-to-pod encryption (compliance, multi-tenant clusters, zero-trust internal networks), the answer is a service mesh (Istio / Linkerd, coming in s11) which transparently wraps every connection in mTLS without app changes. s4 is just edge TLS.

## cert-manager

cert-manager ships as a controller plus a bundle of CRDs - custom `kind`s the API server doesn't ship with by default. Applying the install manifest in the next section does two things you'll see directly:

1. **Six new kinds get registered.** After install, `kubectl api-resources | grep cert-manager` lists `ClusterIssuer`, `Issuer`, `Certificate`, `CertificateRequest`, `Order`, `Challenge`. Before install, the API server rejects `kind: ClusterIssuer` with "no matches for kind".
2. **Three Deployments come up in the `cert-manager` namespace** (`cert-manager`, `cert-manager-webhook`, `cert-manager-cainjector`). The main one watches those six kinds and reconciles them - "saw a new `Certificate`, create a `CertificateRequest`, ask the referenced `Issuer` to sign it, write the result to a Secret."

You write YAML for three of those kinds. The rest are internal state cert-manager creates on your behalf.

| Object | What it is | Lifetime |
| --- | --- | --- |
| `ClusterIssuer` | A cluster-scoped CA configuration. Says "this is how to mint new certs." Can be `selfSigned`, `ca`, `acme` (Let's Encrypt), `vault`, etc. | Long-lived. One per CA. |
| `Certificate` | A request for a leaf cert. Names the hostnames, the issuer, the secret to write to. cert-manager keeps it renewed before expiry. | Long-lived. One per workload cert. |
| `Secret` (kind `kubernetes.io/tls`) | The actual `tls.crt` + `tls.key` + (optionally) `ca.crt`. Produced by cert-manager from a Certificate. This is what Ingress / Pods consume. | Tracks the Certificate. |

There's also a namespaced `Issuer` (same shape as `ClusterIssuer` but scoped). Use `ClusterIssuer` when one CA serves multiple namespaces (our case: the root lives in `cert-manager` but issues leaves for `default`). Use `Issuer` when each team / namespace runs its own CA.

The other three kinds (`CertificateRequest`, `Order`, `Challenge`) track issuance state. You rarely touch them directly but can be used for debugging. `kubectl describe certificaterequest` is the first stop when a Certificate stays `Ready=False`.

## Why a CA chain, not independent self-signed leaves

You could point one `selfSigned` ClusterIssuer at every leaf directly, but then each leaf is its own root. The browser warns per hostname with no way to dismiss it permanently. Instead we build one root and have it sign every leaf, so trusting the root once covers all current and future hostnames:

```text
ClusterIssuer: selfsigned-bootstrap   (type: selfSigned)
        │  signs once
        ▼
Certificate: demo-root-ca             (isCA: true, ns: cert-manager)
        │  writes
        ▼
Secret: demo-root-ca-tls              (root tls.crt + tls.key)
        │  referenced by
        ▼
ClusterIssuer: ca-issuer              (type: ca)
        │  signs all workload certs
        ▼
Certificate: demo-local-tls  →  Secret: demo-local-tls  →  Ingress: users-app
```

`selfsigned-bootstrap` is used exactly once to mint the root; after that, `ca-issuer` signs every workload cert. `selfsigned-bootstrap` plays the role of a public root CA, `ca-issuer` plays the role of an intermediate like Let's Encrypt's `R3` or AWS's ACM Private CA. Difference is who runs the root and how trust gets distributed (you, via manual import vs. browser vendors via OS updates).

## `k8s/cert-issuers.yaml`

Three objects, applied top-to-bottom:

- `selfsigned-bootstrap` (ClusterIssuer, `selfSigned`): signs the root once, then never used again.
- `demo-root-ca` (Certificate, `isCA: true`, namespace `cert-manager`): the root. Long duration (10y) since rotating it means re-trusting everywhere.
- `ca-issuer` (ClusterIssuer, `ca`, `secretName: demo-root-ca-tls`): what every workload cert references.

**Gotcha:** the root Certificate *must* live in the `cert-manager` namespace. A `ca` ClusterIssuer reads its source secret from wherever the cert-manager controller runs. Put it elsewhere and `ca-issuer` stays `Ready=False` with "secret not found". Leaf certs can live anywhere.

---

## `k8s/certificate.yaml`

- `dnsNames`: goes into the cert's SAN. Browsers match on SAN, not CN. List every hostname this cert covers.
- `issuerRef`: points at `ca-issuer`. The signed cert lands in the `demo-local-tls` Secret.
- `secretName`: Secret name in the same namespace, type `kubernetes.io/tls`. Keys: `tls.crt`, `tls.key`, `ca.crt`.

You could omit this file and let the Ingress's `cert-manager.io/cluster-issuer` annotation auto-create the Certificate. Explicit is clearer for the tutorial. `kubectl get certificate` shows the object directly.

---

## Changes in Ingress

- `spec.tls`: names the secret + host. nginx-ingress mounts the cert and starts serving HTTPS.
- `cert-manager.io/cluster-issuer: ca-issuer`: wires cert-manager in. Redundant with the explicit Certificate but harmless.
- `nginx.ingress.kubernetes.io/ssl-redirect: "true"`: 308 redirect from HTTP to HTTPS. Already the default once `tls:` is present; setting it explicitly is documentation.

Path rules and rewrite annotation unchanged. TLS is purely additive.

## Recreating the kind cluster (for port 443)

`extraPortMappings` are set at cluster-creation time, so adding 443 means delete + recreate (same as s3 did for 880).

```bash
kind delete cluster --name demo
kind create cluster --config infra/kind-config.yaml

# Reload images
docker build -t users-api:local-v1 apps/users-api
docker build -t frontend:local-v1 apps/frontend
kind load docker-image users-api:local-v1 frontend:local-v1 --name demo

# nginx-ingress
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
kubectl wait -n ingress-nginx --for=condition=ready pod \
  --selector=app.kubernetes.io/component=controller --timeout=180s

# cert-manager
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/latest/download/cert-manager.yaml
kubectl wait -n cert-manager --for=condition=Available deployment \
  --selector=app.kubernetes.io/instance=cert-manager --timeout=180s
```

Wait on cert-manager before applying issuers. Its webhook validates `ClusterIssuer` / `Certificate` on admission; apply too early and you get `failed calling webhook`.

## Issue the certs and apply the ingress

```bash
kubectl apply -f k8s/cert-issuers.yaml
kubectl get clusterissuer
# NAME                    READY   AGE
# selfsigned-bootstrap    True    5s
# ca-issuer               True    5s

kubectl get certificate -n cert-manager demo-root-ca
# NAME           READY   SECRET                AGE
# demo-root-ca   True    demo-root-ca-tls      10s
```

If `ca-issuer` is `Ready=False` with "secret not found", the root cert hasn't been issued yet. Wait a few seconds and re-check. If it stays false, look at `kubectl describe certificate -n cert-manager demo-root-ca` for the actual error.

```bash
kubectl apply -f k8s/certificate.yaml
kubectl get certificate demo-local-tls
# NAME             READY   SECRET           AGE
# demo-local-tls   True    demo-local-tls   5s

kubectl get secret demo-local-tls -o json | jq '.data | keys'
# ["ca.crt","tls.crt","tls.key"]
```

Confirm the leaf chains to the root:

```bash
kubectl get secret demo-local-tls -o jsonpath='{.data.tls\.crt}' | base64 -d \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
# subject= CN=demo-local-tls
# issuer = CN=demo-root-ca
# notBefore=...
# notAfter=...
# X509v3 Subject Alternative Name: DNS:demo.local
```

Now apply the s2/s3 manifests (re-applying after cluster recreate) and the updated Ingress:

```bash
docker compose -f local/docker-compose.yml up -d postgres
kubectl apply -f k8s/configmap.yaml -f k8s/secret.yaml \
              -f k8s/deployment.yaml -f k8s/service.yaml \
              -f k8s/frontend-deployment.yaml -f k8s/frontend-service.yaml
kubectl rollout status deployment/users-api
kubectl rollout status deployment/frontend
kubectl apply -f k8s/ingress.yaml
kubectl describe ingress users-app | grep -A2 TLS
# TLS:
#   demo-local-tls terminates demo.local
```

Confirm nginx picked up the cert:

```bash
kubectl exec -n ingress-nginx deploy/ingress-nginx-controller -- nginx -T 2>/dev/null \
  | grep -E 'ssl_certificate|server_name demo.local' | head -5
```

## Hit it (insecure first)

```bash
curl -kv https://demo.local/api/health
# *  Server certificate:
# *   subject: CN=demo-local-tls
# *   issuer: CN=demo-root-ca
# > GET /api/health HTTP/2
# < HTTP/2 200
# {"status":"ok","db":true}
```

`-k` tells curl to skip cert verification. The handshake works because nginx is serving the leaf, but curl reports the issuer (`demo-root-ca`) is unknown to the OS trust store. Same in the browser: page loads, padlock is red.

Confirm the HTTP→HTTPS redirect:

```bash
curl -i http://demo.local:880/api/health
# HTTP/1.1 308 Permanent Redirect
# Location: https://demo.local/api/health
```

## Trust the root CA on the host

Export `demo-root-ca`'s public cert from the cluster:

```bash
kubectl get secret -n cert-manager demo-root-ca-tls -o jsonpath='{.data.tls\.crt}' \
  | base64 -d > demo-root-ca.crt
```

Install it into the current user's trust store.

```bash
# Linux (Debian/Ubuntu)
sudo cp demo-root-ca.crt /usr/local/share/ca-certificates/demo-root-ca.crt
sudo update-ca-certificates
```

Restart the browser. Re-run curl without `-k`:

```bash
curl -v https://demo.local/api/health
# *  Server certificate:
# *   SSL certificate verify ok.
# {"status":"ok","db":true}
```

Open `https://demo.local` in a browser. Padlock should be solid. Check if the cert chain shows `demo-local-tls` issued by `demo-root-ca`.

Trust is per-machine. Anyone else who hits this cluster would need to import the same root, or you'd give each developer their own. In a corporate setting the root would be pushed to all machines via MDM.

## How traffic flows now

```text
Browser
  │
  │  https://demo.local/api/users
  │
  ▼
hosts file:  demo.local => 127.0.0.1
  │
  ▼
kind container port 443 (extraPortMapping 443:443)
  │
  ▼
ingress-nginx Service (LoadBalancer, port 443)
  │
  ▼
ingress-nginx controller Pod (nginx)
  │  ┌────────────────────────────────────────┐
  │  │ TLS handshake using demo-local-tls     │
  │  │ Cert chain: demo.local <- demo-root-ca │
  │  │ Verified against host trust store      │
  │  └────────────────────────────────────────┘
  │
  │  decrypted HTTP request
  │  Host: demo.local, path /api/users
  │  rewrite to /users
  │
  ▼
users-api Service (ClusterIP, plaintext HTTP)
  │
  ▼
users-api Pod
```

The TLS box sits inside the controller Pod. Everything past it is plaintext HTTP, same as in s3. The Service and Pod have no idea TLS is involved.

For `/` the same flow ends at the frontend Service and Pod. A request to plain `http://demo.local:880/...` lands at the controller on port 80, which returns a 308 redirect to the `https://` URL.

## What this looks like on AWS ALB

On EKS with the AWS Load Balancer Controller, the in-cluster pieces of s4 mostly disappear:

- **ACM** issues the cert. You request a cert in AWS Certificate Manager for `demo.example.com`, validate via DNS, and get an ARN. No cert-manager needed for public certs.
- **ALB** terminates TLS. You attach the cert via an annotation:

  ```yaml
  metadata:
    annotations:
      alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS": 443}]'
      alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:us-east-1:1234:certificate/xxxx
      alb.ingress.kubernetes.io/ssl-redirect: '443'
  spec:
    ingressClassName: alb
  ```

- **No `tls:` block needed in the Ingress spec.** ALB reads the cert from ACM via the ARN; it doesn't load a Kubernetes Secret. `spec.tls` is silently ignored.
- **No `cert-manager.io/cluster-issuer` annotation.** That's nginx-and-cert-manager territory.

Teams still run cert-manager on EKS for *internal* hostnames that ACM can't easily handle (private CA workflows, internal-only domains), or to drive ACM Private CA programmatically, or for non-ALB ingress controllers that do consume Kubernetes TLS Secrets. selfsigned-bootstrap → root → ca-issuer → leaf : is the local equivalent of *running your own ACM Private CA*. s18 will swap this whole stack for real ACM.

## Try to break it

### 1. Delete the leaf Secret

```bash
kubectl delete secret demo-local-tls
kubectl get certificate demo-local-tls -w
# READY flips to False briefly, then back to True
kubectl get secret demo-local-tls
# recreated
```

cert-manager owns the Secret via owner reference on the Certificate. Deleting it triggers a new `CertificateRequest`, which the `ca-issuer` signs from the root. The Ingress picks up the new Secret automatically. nginx-ingress watches Secret events and reloads.

### 2. Patch dnsNames to the wrong host

```bash
kubectl patch certificate demo-local-tls --type=merge \
  -p '{"spec":{"dnsNames":["wrong.local"]}}'
# wait a few seconds for re-issuance
curl -v https://demo.local/api/health
# * SSL: no alternative certificate subject name matches target host name 'demo.local'
```

The handshake succeeds at the TCP/TLS layer but the cert's SAN no longer contains `demo.local`, so curl (and any well-behaved client) rejects it. Restore:

```bash
kubectl apply -f k8s/certificate.yaml
```

### 3. Delete the ca-issuer ClusterIssuer

```bash
kubectl delete clusterissuer ca-issuer
curl -k https://demo.local/api/health
# still 200; existing Secret unchanged
```

Existing certs keep working because the Secret is already minted. But the next renewal (or any new Certificate referencing `ca-issuer`) will fail with `failed to find clusterIssuer`. Re-apply `cert-issuers.yaml` to recover.

### 4. Force HTTP and watch the redirect

```bash
curl -i http://demo.local:880/api/health
# HTTP/1.1 308 Permanent Redirect
# Location: https://demo.local/api/health

curl -iL http://demo.local:880/api/health
# follows the redirect, lands on HTTPS, returns 200
```

`-L` makes curl follow redirects. Browsers do this automatically; clients like `wget`, `httpie`, and most language HTTP libs follow by default.

## What's next

s5 moves Postgres into the cluster as a StatefulSet with a PersistentVolumeClaim, so we stop depending on the host's docker-compose Postgres. This uses storage primitives: PV, PVC, StorageClass, and the stable pod identity that StatefulSets provide. It also requires a multi-node kind cluster so anti-affinity and topology spread have something to demonstrate.

s11 brings mTLS / pod-to-pod encryption via a service mesh, which is the *other* half of "TLS in Kubernetes". s4 covers north-south (client to cluster); s11 covers east-west (pod to pod).

cert-manager and the ingress controller can stay. The trusted root cert on your host can stay too. It's only valid for certs `ca-issuer` signed, and `ca-issuer` is gone with the cluster. Removing it later:

```bash
# Linux (Debian/Ubuntu)
sudo rm /usr/local/share/ca-certificates/demo-root-ca.crt
sudo update-ca-certificates --fresh
```
