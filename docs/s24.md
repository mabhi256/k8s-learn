# s24 - EKS Migration

> **Tag:** `s24`
> Goal: move everything from kind to a real AWS EKS cluster. Replace local substitutes with cloud-native equivalents: ALB for ingress, EBS CSI for storage, IRSA for IAM, Karpenter for node autoscaling, ECR for images, Secrets Manager for secrets.

This is the only stage that runs on real AWS infrastructure. Every concept from s0-s23 was taught on kind with local equivalents. This stage swaps them for cloud-native implementations and shows what changes (very little Kubernetes YAML) and what doesn't (the application code, the architectural patterns).

---

## What changes, what doesn't

| Component | kind (s0-s23) | EKS (s24) | What changes in YAML |
| --- | --- | --- | --- |
| **Cluster** | `kind create cluster` | `eksctl create cluster` | Different tool, same Kubernetes API |
| **Ingress** | nginx-ingress + cloud-provider-kind LB | **AWS ALB** via AWS Load Balancer Controller | Ingress annotations change, controller changes |
| **Storage** | local-path provisioner | **EBS CSI driver** (gp3 volumes) | StorageClass name, provisioner |
| **Container registry** | `kind load docker-image` | **ECR** (push/pull from registry) | Image names go from `users-api:local-v3` to `123456789.dkr.ecr.region.amazonaws.com/users-api:v3` |
| **Secrets** | ESO Fake provider (s19) | ESO with **AWS Secrets Manager** | SecretStore provider config |
| **IAM** | Not applicable | **IRSA** (IAM Roles for Service Accounts) | ServiceAccount annotations |
| **Node scaling** | Manual (kind nodes are fixed) | **Karpenter** (provisions nodes on demand) | New CRDs: NodePool, EC2NodeClass |
| **DNS** | `/etc/hosts` entries | **Route 53** or external DNS | Ingress gets a real domain |
| **TLS** | Self-signed certs (cert-manager, s4) | **ACM** (AWS Certificate Manager) certificates on ALB | Ingress annotations for ACM cert ARN |
| **Human auth** | x509 client certs (s9) | **EKS Access Entries** (IAM → k8s user mapping) | AWS console config, no YAML change |
| **Scheduling** | nodeSelector, affinity, taints, topology spread (s21) | Same — but zone topology becomes real (us-east-1a/b/c) | `topology.kubernetes.io/zone` values change |

Everything else — Deployments, Services, ConfigMaps, HPA/KEDA, ArgoCD, Kyverno policies, PDBs, NetworkPolicies — is **identical**. That's the point of Kubernetes: the workload definition is portable.

## Cluster setup with eksctl

`eksctl` is the official CLI for creating EKS clusters. It wraps CloudFormation.

### Cluster config

```yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: k8s-learn
  region: us-east-1
  version: "1.31"
```

### Key decisions

**Node groups vs Karpenter:** eksctl can create managed node groups (fixed instance types, ASG-based). But since we're installing Karpenter, we create a minimal node group for the system components and let Karpenter handle everything else.

**VPC:** eksctl creates a new VPC with public and private subnets across 3 AZs. For production, you'd use an existing VPC. For learning, the auto-created VPC is fine.

**Add-ons:** EKS manages some DaemonSets as add-ons (VPC CNI, CoreDNS, kube-proxy, EBS CSI). eksctl can install them declaratively.

## IRSA (IAM Roles for Service Accounts)

### The problem

AWS services (S3, Secrets Manager, SQS) need IAM credentials. Without IRSA, you'd put AWS access keys in a Secret — the same anti-pattern s19 fixed with ESO. IRSA eliminates long-lived credentials entirely.

### How it works

```text
┌──────────────┐     ┌──────────────────┐     ┌──────────────┐
│  Pod           │     │  EKS OIDC         │     │  AWS STS      │
│  (with SA      │────▶│  provider          │────▶│  (assumes     │
│   annotation)  │     │  (validates token) │     │   IAM role)    │
└──────────────┘     └──────────────────┘     └──────────────┘
                                                      │
                                                      ▼
                                               ┌──────────────┐
                                               │  AWS service  │
                                               │  (S3, SM,     │
                                               │   SQS, etc.)  │
                                               └──────────────┘
```

1. The ServiceAccount is annotated with `eks.amazonaws.com/role-arn: arn:aws:iam::...:role/...`.
2. EKS injects a projected JWT token into the Pod.
3. The AWS SDK sees the token and calls STS `AssumeRoleWithWebIdentity`.
4. STS validates the token against the EKS OIDC provider and returns temporary credentials.
5. The Pod uses these credentials to access AWS services.

No access keys. Credentials rotate automatically (token lifetime is ~12 hours). Each ServiceAccount gets its own IAM role, following least privilege.

### Which workloads need IRSA

| Workload | IAM permissions needed |
| --- | --- |
| **External Secrets Operator** | `secretsmanager:GetSecretValue` for Secrets Manager |
| **AWS Load Balancer Controller** | `elasticloadbalancing:*`, `ec2:Describe*`, etc. |
| **Karpenter** | `ec2:RunInstances`, `ec2:TerminateInstances`, `iam:PassRole`, etc. |
| **Velero** | `s3:*` for backup storage, `ec2:CreateSnapshot` for EBS backups |
| **cert-manager** (if using Route53 DNS01) | `route53:ChangeResourceRecordSets` |

Application Pods (users-api) don't need IRSA unless they directly call AWS services.

## AWS Load Balancer Controller

### What it replaces

On kind, nginx-ingress handles Ingress resources and cloud-provider-kind provides a fake LoadBalancer IP. On EKS, the AWS Load Balancer Controller watches Ingress resources and provisions **real ALBs** (Application Load Balancers).

### Key differences

| | nginx-ingress (kind) | AWS LB Controller (EKS) |
| --- | --- | --- |
| Load balancer | Software (nginx Pod) behind a fake LB IP | Actual AWS ALB (managed by AWS) |
| TLS termination | cert-manager + self-signed certs | **ACM certificate** on the ALB |
| Scaling | HPA on the nginx Pod | ALB scales automatically (AWS-managed) |
| Cost | Free | ALB hourly cost + LCU charges |

### Ingress annotations

The ALB controller uses annotations to configure the ALB:

```yaml
metadata:
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:...
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
```

The `spec.rules` and `spec.tls` stay mostly the same — only the annotations change.

## Karpenter (Node Autoscaling)

### What it replaces

On kind, nodes are fixed (you get what `kind create cluster` gives you). In production, you need nodes to scale with demand. The Cluster Autoscaler (the old way) scales **existing** ASG node groups. Karpenter replaces it with a more flexible model.

### Karpenter vs Cluster Autoscaler

| | Cluster Autoscaler | Karpenter |
| --- | --- | --- |
| Node provisioning | Scales existing ASG/managed node groups | Directly calls EC2 `RunInstances` — no ASG needed |
| Instance selection | Fixed to what the ASG defines | Chooses from all matching instance types at launch time (price/capacity aware) |
| Speed | 2-5 minutes (ASG scaling + node bootstrap) | 60-90 seconds (direct EC2 API + fast bootstrap) |
| Bin-packing | Limited (ASG granularity) | Optimal (considers pending Pod requirements) |
| Spot instances | Supported via mixed-instance ASG | Native: spot + on-demand in the same pool |
| Node consolidation | No (only scales down empty nodes) | Yes: consolidates by replacing underutilized nodes with smaller ones |

### Key CRDs

**`NodePool`**: defines scheduling constraints (instance families, AZs, spot vs on-demand, taints, limits). Pods that match the NodePool's requirements trigger node provisioning.

**`EC2NodeClass`**: defines AWS-specific configuration (AMI, subnet, security group, instance profile). Referenced by the NodePool.

```text
Pending Pod → Karpenter checks NodePools → matches → reads EC2NodeClass → launches EC2 instance → Pod scheduled
```

### Consolidation

Karpenter continuously evaluates whether nodes can be consolidated:

| Type | What it does |
| --- | --- |
| **Deletion** | Removes a node if all its Pods can move to other existing nodes |
| **Replacement** | Replaces a node with a smaller/cheaper one if the current one is underutilized |

Consolidation respects PDBs (s20): it won't evict Pods if doing so would violate a disruption budget.

## EBS CSI Driver

The EBS CSI driver replaces kind's `local-path` provisioner. It provisions real EBS volumes for PVCs.

EKS includes it as a managed add-on. You configure a StorageClass:

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
provisioner: ebs.csi.aws.com
parameters:
  type: gp3
volumeBindingMode: WaitForFirstConsumer
```

`WaitForFirstConsumer` ensures the volume is created in the same AZ as the Pod. Without it, the volume might be in a different AZ and the Pod can't mount it.

## ECR (Elastic Container Registry)

Replace `kind load docker-image` with pushing to ECR:

```bash
# Create repository
aws ecr create-repository --repository-name users-api

# Login
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin 123456789.dkr.ecr.us-east-1.amazonaws.com

# Tag and push
docker tag users-api:local-v3 123456789.dkr.ecr.us-east-1.amazonaws.com/users-api:v3
docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/users-api:v3
```

Update the Deployment image to the ECR URI. ECR image scanning can replace Trivy's local scans.

## EKS Access Entries

Replaces the x509 client certs from s9. Instead of generating certificates with `CN=alice/O=devs`, you map IAM identities to Kubernetes users/groups:

```bash
aws eks create-access-entry \
  --cluster-name k8s-learn \
  --principal-arn arn:aws:iam::123456789:user/alice \
  --kubernetes-groups devs

aws eks associate-access-policy \
  --cluster-name k8s-learn \
  --principal-arn arn:aws:iam::123456789:user/alice \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy \
  --access-scope type=namespace,namespaces=default
```

The RBAC `RoleBinding` from s9 (`devs` group → `view` ClusterRole) works unchanged. Only the authentication mechanism changes from x509 to IAM.

## Commands

```bash
# 1. Create the EKS cluster
eksctl create cluster -f infra/eksctl-cluster.yaml

# 2. Install the AWS Load Balancer Controller
helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=k8s-learn \
  --set serviceAccount.create=true \
  --set serviceAccount.annotations."eks\.amazonaws\.com/role-arn"=arn:aws:iam::123456789:role/alb-controller

# 3. Install Karpenter
helm repo add karpenter https://charts.karpenter.sh
helm install karpenter karpenter/karpenter -n kube-system \
  --set settings.clusterName=k8s-learn \
  --set settings.clusterEndpoint=$(aws eks describe-cluster --name k8s-learn --query 'cluster.endpoint' --output text) \
  --set serviceAccount.annotations."eks\.amazonaws\.com/role-arn"=arn:aws:iam::123456789:role/karpenter

# 4. Apply Karpenter NodePool and EC2NodeClass
kubectl apply -f k8s/aws/karpenter-ec2nodeclass.yaml
kubectl apply -f k8s/aws/karpenter-nodepool.yaml

# 5. Update ESO SecretStore to use AWS Secrets Manager
kubectl apply -f k8s/aws/secret-store.yaml

# 6. Push images to ECR
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 123456789.dkr.ecr.us-east-1.amazonaws.com
docker tag users-api:local-v3 123456789.dkr.ecr.us-east-1.amazonaws.com/users-api:v3
docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/users-api:v3

# 7. Deploy the app (image name changes)
helm upgrade users-api helm/users-api \
  --set image.repository=123456789.dkr.ecr.us-east-1.amazonaws.com/users-api \
  --set image.tag=v3

# 8. Apply the ALB Ingress
kubectl apply -f k8s/aws/ingress.yaml
```

### Verify

```bash
# Check ALB is provisioned
kubectl get ingress
# ADDRESS: k8s-learn-xxxxx.us-east-1.elb.amazonaws.com

# Check Karpenter nodes
kubectl get nodes
# Karpenter-provisioned nodes appear as they're needed

kubectl get nodeclaim
# Shows Karpenter's node lifecycle

# Check IRSA is working
kubectl exec -it deploy/users-api -- env | grep AWS
# AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE should be set (if the SA has IRSA)

# Check EBS volumes
kubectl get pvc
kubectl get pv
# VOLUME shows ebs://vol-xxxxx
```

## Try to break it

### 1. IRSA annotation wrong — Pod can't reach Secrets Manager

```bash
kubectl describe externalsecret users-api
# Status: SecretSyncedError
# Message: AccessDeniedException: User: ... is not authorized
```

The ESO Pod can't assume the IAM role because the ServiceAccount annotation points at the wrong role ARN, or the IAM role's trust policy doesn't trust the EKS OIDC provider.

Fix: verify the role ARN in the ServiceAccount annotation and the trust policy's `Condition` block (must match the EKS OIDC issuer URL and the namespace/SA name).

### 2. EBS volume in wrong AZ

Without `WaitForFirstConsumer`, the EBS volume is created in `us-east-1a` but the Pod is scheduled in `us-east-1b`:

```bash
kubectl describe pod postgres-1
# Warning: 1 node(s) had volume node affinity conflict
```

Fix: use `volumeBindingMode: WaitForFirstConsumer` on the StorageClass.

### 3. Karpenter can't provision — instance limits

AWS accounts have EC2 instance limits. If Karpenter tries to launch a `c5.2xlarge` but you've hit your vCPU limit:

```bash
kubectl get nodeclaim -o wide
# STATUS: Error  MESSAGE: InsufficientInstanceCapacity
```

Fix: request a service quota increase, or broaden the NodePool's allowed instance types so Karpenter can fall back to other families.

## What's next

This is the final stage. The application and all its infrastructure now run on production-grade AWS services. From here, real-world extensions include:

- **Multi-cluster**: ArgoCD (s18) managing multiple EKS clusters across regions.
- **Service mesh at scale**: Istio ambient mode (s22) — per-node ztunnel scales better than sidecars across large fleets; AWS App Mesh as a managed alternative.
- **Cost optimization**: Spot instances via Karpenter, right-sizing via VPA (s13), scale-to-zero via KEDA (s17).
- **Compliance**: Kyverno (s19) policies for SOC2/HIPAA, AWS Config rules, CloudTrail audit.
