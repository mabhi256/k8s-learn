# s19e - Hardening Admission Control for Production

> **Tag:** `s19e`
> Goal: close the gaps that don't matter in a lab but do matter once Kyverno sits in front of real traffic: what happens when the webhook itself is unreachable, how to avoid locking yourself out of your own cluster, how to roll out a new policy without an outage, and how to audit resources that existed before the policy did.

s19b installed Kyverno and wrote three ClusterPolicies. That's enough to reject a bad Pod in a demo. It is not enough to run in production: Kyverno's admission webhook sits directly in the write path of the API server, so its availability, its blast radius, and its rollout process now matter as much as the rules themselves.

---

## How an admission request actually flows

```text
 kubectl / CI               API Server                  Kyverno
     │                          │                            │
     │ 1. create/update Pod     │                            │
     ├─────────────────────────▶│                            │
     │                          │ 2. AdmissionReview request │
     │                          ├───────────────────────────▶│
     │                          │                            │ 3. evaluate
     │                          │                            │    matching
     │                          │                            │    ClusterPolicies
     │                          │ 4. Allow / Deny / Patch    │
     │                          │◀───────────────────────────┤
     │ 5. object created, rejected, or mutated               │
     │◀─────────────────────────┤                            │
```

Every step between 2 and 4 happens synchronously, inside the timeout the API server allows for the request. If Kyverno is slow, unreachable, or crash-looping, that timeout — not the policy logic — decides what happens next.

## `failurePolicy`: what happens when Kyverno itself is down

Every Kyverno webhook has a `failurePolicy`, set globally in the Kyverno Helm values (or per-`ClusterPolicy` in older API versions):

| Setting | Behavior when Kyverno is unreachable | Risk |
| --- | --- | --- |
| `Fail` (default) | The API server rejects the write | A Kyverno outage becomes a cluster-wide outage: nobody can create or update anything |
| `Ignore` | The API server lets the write through unchecked | During the outage, privileged Pods, missing labels, missing limits — anything the policies exist to block — sails through silently |

Neither setting alone is safe. `Fail` without redundancy turns "K[=yverno pod OOMKilled" into "nobody can deploy." `Ignore` turns "Kyverno pod OOMKilled" into "policies silently stop applying and nothing tells you." The fix is `Fail` **plus** making Kyverno itself hard to take down (see the HA checklist below) — so `Fail` is rarely triggered, and when it is, it's a loud, visible incident rather than a silent bypass.

```yaml
# helm/values/kyverno.values.yaml
admissionController:
  replicas: 3
  # global default; Fail is correct once Kyverno is HA
webhooks:
  failurePolicy: Fail
```

## Don't lock yourself out

Kyverno ships with a default `resourceFilters` list that excludes `kube-system`, `kube-node-lease`, `kube-public`, and Kyverno's own namespace from every policy. That protects Kyverno from blocking its own upgrades. It does **not** protect anything else you run.

This project's `require-labels` policy is already scoped to `namespaces: [default]` — that scope landed when the policy was first committed, and it's worth reiterating *why* it's there. The naive version matches `Deployment`/`StatefulSet` with no namespace scope, meaning it applies cluster-wide. That's fine for `default`, where `users-api` and `notify-api` live and already carry `app`/`team` labels. It's a problem for every other namespace ArgoCD manages: `kyverno`, `external-secrets`, `falco`, `lgtm`. None of those Helm charts label their Deployments the way this policy expects. Enforce it cluster-wide and the next `helm upgrade` to any infra chart — synced by ArgoCD, s18b — gets rejected. ArgoCD reports `OutOfSync` with no clear reason unless you go read Kyverno's logs.

The general rule: any policy you write yourself needs an explicit `namespaces` (or `namespaceSelector`) scope. Kyverno's built-in exclusions only cover Kyverno's own survival, not the rest of your platform.

## Staged rollout: Audit before Enforce, at the fleet level

s19b already uses `validationFailureAction: Audit` for `require-resource-limits` — the policy runs but doesn't reject anything yet. The missing piece is *seeing* what it would have rejected, across every namespace, before flipping the switch.

Kyverno writes every evaluation to a `PolicyReport` (namespaced resources) or `ClusterPolicyReport` (cluster-scoped resources), whether or not the action is `Enforce`.

The raw `kubectl get policyreport -A` is nearly unreadable: this Kyverno version creates **one report per resource** and names each after the resource's UID, so you get a wall of rows keyed on random strings. The report name is useless — the resource identity lives in `.scope`, and the per-rule results live in `.results[]`. Project those out instead.

```bash
# Legible table: real resource kind/name from .scope, plus pass/fail counts.
# .summary.fail is the CURRENT count (background scanner keeps it live),
# not a history of past events.
kubectl get policyreport -A -o custom-columns=\
'NS:.metadata.namespace,KIND:.scope.kind,NAME:.scope.name,PASS:.summary.pass,FAIL:.summary.fail,WARN:.summary.warn'

# Only the reports that actually have failures, with the real workload name.
# .results[].resources is empty in per-resource reports, so lift .scope
# down into each result via variables.
kubectl get policyreport -A -o json | jq -r '
  .items[]
  | .metadata.namespace as $ns
  | .scope as $s
  | .results[]? | select(.result=="fail")
  | "\($ns)\t\($s.kind)/\($s.name)\t\(.policy)/\(.rule)"'

# Which policy is generating the noise: one count per policy, highest first.
kubectl get policyreport -A -o json | jq -r '
  [.items[].results[]? | select(.result=="fail") | .policy]
  | group_by(.)[] | "\(length)\t\(.[0])"' | sort -rn

kubectl get clusterpolicyreport
```

The `autogen-*` rule names in the output aren't extra policies you wrote: a rule matching `Pod` is auto-expanded by Kyverno into sibling rules for Deployment/StatefulSet/DaemonSet/Job/CronJob (`autogen-check-memory-limits`, `autogen-cronjob-check-memory-limits`, …). One rule fans out across every controller kind, which is why the failure list looks larger than the number of policies.

This also solves a gap admission control can never close on its own: admission webhooks only see *new* writes. A Pod that existed before the policy was created is never re-evaluated at admission time. Kyverno's background scanner (on by default, `background: true`) periodically re-checks existing resources and reports violations here — this is how you find out what's already non-compliant before you turn `Enforce` on and start rejecting the next legitimate change to those same resources.

Rollout sequence for any new policy. Because this is GitOps, every step that changes cluster state is gated on a **commit + push** — ArgoCD pulls from the GitHub remote, so an uncommitted (or unpushed) file is invisible to the cluster. Editing a manifest does nothing until it lands in Git.

1. **Ship it with `validationFailureAction: Audit`** (commit + push). ArgoCD syncs it; the policy runs but rejects nothing.
2. **Read the reports** across all namespaces with the queries above. The reports are already populated from step 1's commit — the scanner evaluates existing resources on its own.
3. **Fix what shows up as failing.** The failures split into two populations that get *different* fixes:
   - **Your own workloads** (here, `default`): a *mutate* policy like [`kyverno-mutate-defaults.yaml`](../k8s/security/kyverno-mutate-defaults.yaml) auto-injects the missing field (`limits.memory: 256Mi`) so you don't edit every Deployment. Fix-by-mutation.
   - **Infra namespaces** (kube-system, lgtm, argocd, falco, cert-manager…): you won't fork upstream Helm charts to add your labels/limits. The fix here is *scoping*, not mutating — keep the validate policy scoped to `default` (as `require-labels` already is) or leave it Audit-only for infra. Enforcing cluster-wide would block the next `helm upgrade` ArgoCD runs (see "Try to break it" below).

   Each fix is itself a commit + push.
4. **Re-run the queries** and confirm the `default` reports go clean.
5. **Flip the `default`-scoped policies to `Enforce`** (commit + push) once clean; leave infra as Audit.

## HA / production readiness checklist

| Item | Why it matters |
| --- | --- |
| `admissionController.replicas: 3` | A single Kyverno pod is a single point of failure for every write to the cluster |
| `PodDisruptionBudget` on Kyverno | Prevents a node drain from taking all replicas down at once |
| `resources.requests/limits` on Kyverno itself | An OOMKilled Kyverno pod under load *is* an outage with `failurePolicy: Fail` |
| Webhook `timeoutSeconds` tuned (default 10s) | A slow policy (many rules, large `match` sets) can push requests past the timeout — same effect as Kyverno being down |
| Scrape Kyverno's `/metrics` in Prometheus | `kyverno_admission_review_duration_seconds` and webhook error rate catch degradation before `failurePolicy: Fail` starts rejecting requests. Wire into the LGTM stack from s11/s12. |

## Commands

```bash
# Dry-run a policy against a manifest before committing it (local check,
# no cluster access needed)
kyverno apply k8s/security/kyverno-policies.yaml --resource k8s/users-api/deployment.yaml

# Check what's already non-compliant, cluster-wide, before enforcing anything
kubectl get policyreport -A
kubectl get clusterpolicyreport

# The manual equivalent of shipping the HA values, if you weren't
# GitOps-managing this:
# helm upgrade kyverno kyverno/kyverno -n kyverno -f helm/values/kyverno.values.yaml

# Ship the HA values + the mutate policy, and re-point kyverno.yaml at the
# new values file (see diff above). require-labels is already scoped to
# default from an earlier commit, so it isn't in this change set.
git add helm/values/kyverno.values.yaml k8s/argocd/infra/kyverno.yaml \
        k8s/security/kyverno-mutate-defaults.yaml
git commit -m "feat(security): harden Kyverno for HA, add mutate default"
git push
# ArgoCD rolls the kyverno Application to 3 replicas with a PDB, and
# syncs the updated/new ClusterPolicy CRs on security-resources' next pass.
```

### Verify

```bash
# Simulate a Kyverno outage
kubectl -n kyverno scale deployment kyverno-admission-controller --replicas=0

# With failurePolicy: Fail, every write now fails closed
kubectl run test --image=nginx
# Error: failed calling webhook ... context deadline exceeded

# Restore
kubectl -n kyverno scale deployment kyverno-admission-controller --replicas=3
```

The `kyverno` Application has `selfHeal: true`, so this manual scale-down is itself drift: ArgoCD reverts it back to the Git-defined replica count on its own within a few minutes, same as the `argocd app get` drift-detection example in s18b. Scale back manually only if you want the window closed immediately.

## Try to break it

### A cluster-wide policy blocks ArgoCD's own syncs

Apply `require-labels` without the `namespaces: [default]` scope, then let ArgoCD reconcile the `kyverno` or `lgtm` Application:

```bash
kubectl get application -n argocd kyverno
# STATUS: OutOfSync
# The Deployment inside the Helm chart has no 'app'/'team' label —
# Kyverno rejects the exact objects ArgoCD is trying to apply.
```

ArgoCD retries on its normal sync interval and keeps failing the same way. Nothing in the ArgoCD UI says "Kyverno did this" — you have to check `kubectl get events` in the target namespace or the Kyverno controller logs. Fix: scope the policy to the namespaces it's actually meant for.
